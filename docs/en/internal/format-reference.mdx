### 6b — Reusable text fragments

Standard blocks that must read identically on every page (support scope, recurring boilerplate) are maintained centrally in `config/fragments.ts` — one version per locale — and inserted with a token on its own line, surrounded by blank lines:

`[[fragment:<key>]]`

Available keys: `support-scope` (the support-scope disclaimer, rendered above).

- **Never paraphrase or paste the text into a guide.** Insert the token — `[[fragment:<key>]]` — so all pages stay in sync; the wording is edited once, centrally.
- Tokens resolve per locale at build time, before compilation, so a fragment may itself contain `/links/` targets.
- An unknown or misspelled key **fails the build** (`remarkNoUnresolvedFragments`).

### 10b — Zone-aware API links

Generic links to the OVHcloud API follow the reader's commercial zone (EU / CA), like Control Panel links do. Both components are globally registered — **no import needed**. Do not use `/links/api`, `/links/console` or hardcoded `https://eu.api.ovh.com/…` URLs.

A generic reference to the API or the API console (targets the zone's gateway page):

You can also do this with <ApiLink>the OVHcloud API</ApiLink>.

A **section deep link** — opens the console with the section selected (zone-aware, unlike a hardcoded `?section=` URL):

All API routes used in this guide are available under the <ApiLink section="/dedicated/nasha">*/dedicated/nasha* section of the API console</ApiLink>.

An **operation deep link** — same target as an `<Api>` pill, but rendered as a normal inline link with custom text (for tables and prose where a pill doesn't fit):

| Data | Access |
|---|---|
| API call logs | <ApiLink section="/me" method="GET" route={"/me/api/logs/self"} regions={["eu"]}>List of API calls done with your account</ApiLink> |
| Audit logs | <ApiLink section="/me" method="GET" route={"/me/logs/audit"}>Get your audit logs</ApiLink> |

The first row's operation exists **only in the EU API** (the EU and CA schemas differ per route) — `regions={["eu"]}` restricts it, which renders a plain direct link to the EU console for every reader. The second row exists in both schemas, so it stays zone-aware. When migrating hardcoded links, verify each route against **both** region schemas and restrict `regions` where they differ.

An EU-only product — offered zones derived from the route (SMS is EU-only):

Check your jobs with <ApiLink section="/sms" method="GET" route={"/sms/\{serviceName\}/jobs"}>this API call</ApiLink>.

A token-creation link with pre-filled rights:

<CreateToken rights="GET=/*&POST=/*&PUT=/*&DELETE=/*">Generate OVHcloud API tokens</CreateToken>

<summary>Troubleshooting — mount errors at boot</summary>

If `/hana/data` fails to mount on boot, check that the UUID in `/etc/fstab` matches the actual device:

```console
$ blkid /dev/vg_hana/lv_hanadata
/dev/vg_hana/lv_hanadata: UUID="a1b2c3d4-e5f6-7890-abcd-ef1234567890" TYPE="xfs"

$ grep hana /etc/fstab
UUID=a1b2c3d4-e5f6-7890-abcd-ef1234567890  /hana/data  xfs  noatime,nodiratime,logbsize=256k  0 0
```

:::danger
Do **not** use `/dev/sdX` paths in `/etc/fstab`. Device names are not stable across reboots. Always use UUIDs or LVM paths.
:::

### 14 — Russian-doll: formats inside a Details

<details>
<summary>Expand — API call, image, callout, code block, table and nested list inside a collapsible</summary>

Use this API call to list your active credentials:

<Api version="v1" section="/me" method="GET" route="/me/api/credential" />

The Control Panel shows the same data under **Account** > **API** > **My credentials**:

![OVHcloud IAM policies screen](/images/guides/account-and-service-management/account-information/iam-policy-ui/iam_policies.png)

:::info
Credentials created via the API and credentials created via the Control Panel are interchangeable — they share the same underlying token store.
:::

:::warning
If you rotate a credential that is embedded in an automation script, update the script **before** revoking the old credential, or your automation will fail.
:::

Revoke a credential by its ID with:

```bash
# Replace <credentialId> with the numeric ID returned by the GET call above
curl -X DELETE "https://eu.api.ovh.com/v1/me/api/credential/<credentialId>" \
  -H "X-Ovh-Application: <appKey>" \
  -H "X-Ovh-Consumer: <consumerKey>" \
  -H "X-Ovh-Timestamp: $(date +%s)" \
  -H "X-Ovh-Signature: <signature>"
```

Recommended rotation schedule by credential scope:

| Scope          | Rotation interval | Automation-safe? |
|----------------|-------------------|-----------------|
| `full-access`  | 30 days           | No — manual only |
| `read-only`    | 90 days           | Yes              |
| `scoped`       | 60 days           | Yes              |

Steps to rotate safely:

1. Create the new credential via the API or Control Panel.
2. Update all scripts and CI/CD pipelines that use the old credential:
   - Check your `.env` files and secret stores
   - Check scheduled jobs and cron tasks
     - Look for hardcoded tokens in shell scripts
     - Look for tokens injected as environment variables
3. Validate that the new credential works end-to-end.
4. Revoke the old credential.
