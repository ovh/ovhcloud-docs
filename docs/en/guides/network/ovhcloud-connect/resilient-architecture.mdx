## Objective

This tutorial guides you through connecting your infrastructure to OVHcloud using **two independent OVHcloud Connect links** for high availability. If one link fails, traffic automatically switches to the other.

## Instructions

Below are prerequisites and instructions for four use cases; choose the one matching your desired architecture.

<Tab label="On-Premises">

<a id="on-premises"></a>

This is the OVHcloud-grounded reference scenario: two OVHcloud Connect services in Layer 3 (BGP) mode, both attached to the same vRack, with your resources spread across two Availability Zones (AZs).

### When to use this architecture

| ✅ Recommended for | Details |
|---|---|
| Business-critical production | Workloads that cannot tolerate downtime |
| Regulated environments | Compliance frameworks requiring high availability |
| High availability SLA requirements | A multi-path architecture is needed to reach the config-based SLA tiers (see [SLAs](/guides/network/ovhcloud-connect/slas)) |
| Disaster recovery | Automatic failover without manual intervention |

### Prerequisites

Before you start, make sure you have:

- **Two OVHcloud Connect services** (Direct, Provider, or a mix), each terminating at a **different PoP** for physical diversity.
- **A BGP-capable router** (or two routers) on your side, able to run one BGP session per link and to apply routing policies for failover.
- **A vRack** to which both services will be attached.
- **OVHcloud resources spread across two AZs**, so that a failure affecting one zone does not take down your whole deployment.
- **An IP addressing plan with no overlaps** between your on-premises networks, the peering subnets, and your OVHcloud (vRack/AZ) subnets.

### Required configuration

Follow these steps to build the resilient dual-link Layer 3 setup.

#### 1. Order two OVHcloud Connect services at two different PoPs

Order two separate OVHcloud Connect services, each at a **different PoP**, to guarantee physical path diversity:

- **Service 1 (Primary):** ordered at PoP A — see [Order Direct](/guides/network/ovhcloud-connect/order-direct) or [Order Provider](/guides/network/ovhcloud-connect/order-provider).
- **Service 2 (Backup):** ordered at PoP B — same process, different PoP.

Then install the physical connections for each service: for **Direct**, order the cross-connects at each PoP (see [Cross Connect LOA](/guides/network/ovhcloud-connect/cross-connect-loa)); for **Provider**, share each service key with your provider(s).

> **Diversity tip:** use different data centres, or at minimum different physical paths, to avoid a shared failure point.

#### 2. Create the PoP configuration (L3) on each service

On **each** of the two services, create the **PoP configuration** in Layer 3 (BGP) mode. For each service you define:

- Your **User ASN** (your own BGP autonomous system number).
- The **OVHcloud ASN** — any ASN **except** the reserved values **65501** (Europe), **65502** (Canada) and **65519** (Asia).
- A **/30 peering subnet** for the point-to-point BGP peering between your router and the OVHcloud device at that PoP.

See [Configure OCC L3 with BGP](/guides/network/ovhcloud-connect/l3-bgp) for the detailed procedure.

#### 3. Create the AZ configuration and BGP extra configuration

Still on each service, configure the vRack side of the routing:

- Create an **AZ configuration** using a **/28 subnet** for that Availability Zone.
- Add a **BGP extra configuration** so that a BGP session is established with **both** OVHcloud devices **A and B** in the AZ, rather than a single device. This is what makes the routing inside OVHcloud redundant.

See [Set up the vRack network](/guides/network/ovhcloud-connect/vrack-network-setup).

#### 4. Associate both services with the same vRack

Associate **both** OVHcloud Connect services with the **same vRack** so that both links reach the same private network. See [Associate with vRack](/guides/network/ovhcloud-connect/associate-vrack).

#### 5. Choose active/standby or active/active

Decide how traffic should be distributed across the two links, then apply the matching routing policy.

**Active/standby** — prefer the primary link and make the backup less preferred:

| Attribute | Where it applies | Effect |
|---|---|---|
| **Local Preference** | Your own devices only | Selects the preferred **outbound** path leaving your network (higher = preferred). It does not influence how OVHcloud chooses its path toward you. |
| **AS-path prepending** | **Customer-side only** | Makes a path look longer, so it is less preferred. Prepend on the backup path to steer inbound traffic to the primary. It cannot be applied on the OVHcloud side. |
| **MED** | **Not supported** | MED cannot be used on OVHcloud Connect. Use AS-path prepending to steer inbound traffic instead. |

**Active/active** — load-balance across both links:

- **ECMP (Equal-Cost Multi-Path) is automatic** as soon as you have **2 or more PoPs**, across **up to 4 paths**. No extra configuration is required to enable it; simply keep the paths equally preferred.
- Traffic is balanced across both links, and if one link fails all traffic immediately flows through the surviving link.

> Active/active provides higher aggregate bandwidth but requires careful capacity planning — each link must be able to handle the full traffic load alone during a failure.

### Constraints

Keep these OVHcloud Connect Layer 3 (BGP) constraints in mind when designing your resilient architecture:

- **One BGP session per PoP** — eBGP multihop is not supported.
- Up to **4 BGP peers** per datacentre/AZ.
- Up to **100 prefixes** advertised per BGP session.
- **BFD is enabled by default** on OVHcloud Connect BGP sessions, which speeds up failure detection and convergence.
- **Enabling BGP disables VRRP** on that configuration.
- You **cannot mix BGP and static routing** in the same datacentre.
- Bandwidth per link: OVHcloud Connect **Direct** offers **1, 10 or 100 Gbps**; **Provider** offers **50 Mbps up to 50 Gbps**.

### Test failover

**This is critical.** Do not skip failover testing.

1. **Verify normal operation:**
   - Both BGP sessions are Established.
   - Traffic flows through the primary link.

2. **Simulate primary failure:**
   - Shut down the primary BGP session or physically disconnect the primary link.
   - Verify traffic switches to the backup link once BGP reconverges. BFD is enabled by default on OVHcloud Connect BGP sessions and speeds up convergence.
   - Confirm connectivity is restored over the backup path.

3. **Restore primary:**
   - Bring the primary link back up.
   - Verify traffic returns to the primary path.

4. **Test the reverse:**
   - Simulate failure of the backup link while the primary is up. This confirms both links work independently.

### Set up monitoring

Monitor **both links** independently. Set alerts for:

- BGP session drops on either link
- Traffic imbalance (all traffic on one link may indicate a failure on the other)
- Bandwidth approaching capacity on either link

See [Monitor](/guides/network/ovhcloud-connect/monitor).

### Prerequisites

- An **AWS account** with a VPC configured
- An **OVHcloud account** with a vRack
- Two AWS Direct Connect connections at **different locations**
- Two OVHcloud Connect Provider services at **different PoPs**
- A shared connectivity provider present at both locations (see [Providers](/guides/network/ovhcloud-connect/providers))
- Non-overlapping IP ranges between AWS VPC and OVHcloud subnets

### Architecture

<img className="thumbnail" alt="AWS resilient architecture diagram" src="/images/network/ovhcloud-connect/resilient-architecture/fig-3.svg" loading="lazy" />

### Resilience strategy

For maximum availability between AWS and OVHcloud:

1. **Two AWS Direct Connect connections** in different AWS Direct Connect locations.
2. **Two provider virtual circuits / connections** (or separate providers) bridging to two OVHcloud PoPs.
3. **Two OVHcloud Connect services** at different PoPs, both associated with your vRack.
4. **BGP failover** configured across both paths.

### Step-by-step

#### 1. Order redundant AWS Direct Connect connections

In the **AWS Console**, create two Direct Connect connections at **different locations**:

- Connection 1: AWS Direct Connect location A
- Connection 2: AWS Direct Connect location B

Create a **Private VIF** on each connection pointing to your VPC (via Virtual Private Gateway or Transit Gateway).

> AWS recommends using **Transit Gateway** with multiple Direct Connect Gateways for resilient multi-region architectures.

#### 2. Order two OVHcloud Connect Provider services

Order at **two different OVHcloud PoPs**. Get two separate service keys. See [Order Provider](/guides/network/ovhcloud-connect/order-provider).

#### 3. Create redundant provider bridges

On your provider platform:

- **Bridge 1:** AWS Direct Connect 1 ↔ OVHcloud PoP A
- **Bridge 2:** AWS Direct Connect 2 ↔ OVHcloud PoP B

A provider cloud router is **required** for each path: create separate cloud router instances or peering sessions so the two paths stay independent.

#### 4. Configure BGP failover

Ensure BGP routing preferences are set so traffic prefers the primary path and falls back to the backup:

- Use **Local Preference** on your own devices to prefer the primary path outbound.
- Use **AS-path prepending** on your own (customer-side) devices for the backup path. MED is **not supported** on OVHcloud Connect.
- On AWS, use **Direct Connect Gateway** with appropriate route priorities.

See [Configure OCC L3 with BGP](/guides/network/ovhcloud-connect/l3-bgp) for detailed instructions.

**Make routing inside OVHcloud redundant.** On each OVHcloud Connect service, create an **AZ configuration** using a **/28 subnet** and add a **BGP extra configuration**, so that a BGP session is established with **both** OVHcloud devices **A and B** in the Availability Zone rather than a single one. Without it, the OVHcloud side of the path is not redundant. See [Set up the vRack network](/guides/network/ovhcloud-connect/vrack-network-setup).

#### 5. Associate both links with your vRack

Associate both OVHcloud Connect services with the same vRack. See [Associate with vRack](/guides/network/ovhcloud-connect/associate-vrack).

#### 6. Test failover

1. Verify both paths are active and passing traffic.
2. Disable the primary AWS Direct Connect VIF — confirm traffic flows via the backup.
3. Disable the primary OVHcloud Connect — confirm traffic flows via the backup.
4. Restore both and verify traffic returns to the preferred path.

### Cost considerations

Resilient AWS-to-OVHcloud requires:

- 2× AWS Direct Connect connections (AWS billing)
- 2× provider virtual circuits / connections or cloud router sessions (provider billing)
- 2× OVHcloud Connect services (OVHcloud billing)

Plan your budget accordingly. The cost of redundancy is typically justified by the risk reduction for production workloads.

> For more information, please consult [AWS Direct Connect documentation](https://docs.aws.amazon.com/directconnect/).

### Prerequisites

- An **Azure subscription** with permissions to create ExpressRoute circuits
- An **OVHcloud account** with a vRack
- Two Azure ExpressRoute circuits at **different peering locations**
- Two OVHcloud Connect Provider services at **different PoPs**
- A shared connectivity provider present at both locations (see [Providers](/guides/network/ovhcloud-connect/providers))
- A vRack with Multi-AZ enabled ([Multi-AZ guide](/guides/network/ovhcloud-connect/multi-az))
- Non-overlapping IP ranges between Azure VNet and OVHcloud vRack

### Architecture

<img className="thumbnail" alt="Azure resilient architecture diagram" src="/images/network/ovhcloud-connect/resilient-architecture/fig-4.svg" loading="lazy" />

### Resilience strategy

Microsoft recommends **two ExpressRoute circuits in different peering locations** for maximum availability. Combined with two OVHcloud Connect Provider services at different PoPs, this provides end-to-end redundancy:

| Component | Primary | Backup |
|---|---|---|
| Azure ExpressRoute | Circuit 1 (Location A) | Circuit 2 (Location B) |
| Provider circuit | Circuit set 1 | Circuit set 2 |
| OVHcloud Connect | Service 1 (PoP A) | Service 2 (PoP B) |
| OVHcloud AZ | AZ 1 | AZ 2 |

### Step-by-step

#### 1. Create two ExpressRoute circuits

In the **Azure Portal** → **Create ExpressRoute** (repeat for each circuit):

| Setting | Circuit 1 | Circuit 2 |
|---|---|---|
| Provider | Your OVHcloud Connect provider | Your OVHcloud Connect provider |
| Peering location | Location A (e.g., Paris) | Location B (e.g., Frankfurt) |
| Bandwidth | Match your OVHcloud Connect link | Match your OVHcloud Connect link |
| SKU | Standard or Premium | Standard or Premium |

Note each circuit's **Service Key**.

> **Tip:** Use **ExpressRoute Premium** if your VNets are in different Azure regions than the peering locations.

#### 2. Order two OVHcloud Connect Provider services

[Order two OVHcloud Connect Provider services](/guides/network/ovhcloud-connect/order-provider) at different PoPs that correspond to the ExpressRoute peering locations:

- OVHcloud Connect 1 → PoP A
- OVHcloud Connect 2 → PoP B

Retrieve both **service keys**.

#### 3. Create provider bridges for each path

On your provider platform, create a bridge for each path. A provider cloud router is **required** to route between the two circuits. Refer to your provider's documentation for the exact steps; see [Providers](/guides/network/ovhcloud-connect/providers) for the list.

**Path 1 (Primary):**

1. Create a provider cloud router or port at Location A.
2. Virtual circuit / connection: Azure ExpressRoute 1 (Service Key 1) → provider cloud router A.
3. Virtual circuit / connection: provider cloud router A → OVHcloud Connect 1 (OVHcloud service key 1).

**Path 2 (Backup):**

1. Create a provider cloud router or port at Location B.
2. Virtual circuit / connection: Azure ExpressRoute 2 (Service Key 2) → provider cloud router B.
3. Virtual circuit / connection: provider cloud router B → OVHcloud Connect 2 (OVHcloud service key 2).

#### 4. Configure Azure Private Peering on both circuits

For each ExpressRoute circuit, configure **Azure Private Peering**:

| Parameter | Circuit 1 | Circuit 2 |
|---|---|---|
| Peer ASN | Provider ASN | Provider ASN |
| Primary /30 | 169.254.100.0/30 | 169.254.101.0/30 |
| Secondary /30 | 169.254.100.4/30 | 169.254.101.4/30 |
| VLAN ID | Assigned by provider | Assigned by provider |

#### 5. Link both circuits to your VNet

In Azure:

1. Go to **Virtual Network Gateways** → **Connections**.
2. Add Connection 1 → ExpressRoute Circuit 1 (weight: **100**).
3. Add Connection 2 → ExpressRoute Circuit 2 (weight: **50** — lower = backup).

Azure uses **connection weight** to prefer one path over the other.

#### 6. Configure OVHcloud BGP with failover

Use [Configure OCC L3 with BGP](/guides/network/ovhcloud-connect/l3-bgp) to prefer the primary path. To build an active/passive topology, use AS-path prepending on your own devices — it is customer-side only, and MED is **not supported** on OVHcloud Connect:

| Path | AS-path prepend (your devices) |
|---|---|
| OVHcloud Connect 1 (primary) | None |
| OVHcloud Connect 2 (backup) | 1× prepend |

**Make routing inside OVHcloud redundant.** On each OVHcloud Connect service, create an **AZ configuration** using a **/28 subnet** and add a **BGP extra configuration**, so that a BGP session is established with **both** OVHcloud devices **A and B** in the Availability Zone rather than a single one. Without it, the OVHcloud side of the path is not redundant. See [Set up the vRack network](/guides/network/ovhcloud-connect/vrack-network-setup).

#### 7. Associate both services with your vRack

[Associate both OVHcloud Connect services](/guides/network/ovhcloud-connect/associate-vrack) with the same vRack. Both will inject routes; the vRack will use the higher Local Preference path.

#### 8. Test failover

| Test | Action | Expected result |
|---|---|---|
| Primary link failure | Disable ExpressRoute 1 VIF in Azure | Traffic shifts to ExpressRoute 2 within BGP convergence time |
| Primary OCC failure | Disable OVHcloud Connect 1 | Traffic shifts to OVHcloud Connect 2 |
| Provider failure | Take down the path A virtual circuits / connections | Traffic shifts to the path B route |
| Full recovery | Re-enable all links | Traffic returns to primary path |

> **Convergence:** Failover completes once BGP reconverges. BFD is enabled by default on OVHcloud Connect BGP sessions and speeds up detection and convergence.

### Azure-specific considerations

- **ExpressRoute Global Reach**: If both OVHcloud PoPs are in different Azure regions, consider enabling [Global Reach](https://learn.microsoft.com/en-us/azure/expressroute/expressroute-global-reach) for direct circuit-to-circuit communication.
- **FastPath**: For Ultra Performance or ErGw3AZ gateways, enable [FastPath](https://learn.microsoft.com/en-us/azure/expressroute/about-fastpath) for improved network performance.
- **Route limits**: Azure Private Peering has its own per-circuit route limit (refer to Microsoft's current documentation). On the OVHcloud side, each BGP session accepts up to **100 prefixes**, so aggregate your prefixes to stay within both limits.

> For more information, please consult [Azure ExpressRoute documentation](https://learn.microsoft.com/en-us/azure/expressroute/).

### Architecture

<img className="thumbnail" alt="GCP resilient architecture diagram" src="/images/network/ovhcloud-connect/resilient-architecture/fig-5.svg" loading="lazy" />

### Resilience strategy

Google Cloud recommends using VLAN attachments in **different edge availability domains** to achieve 99.9%–99.99% SLA. Combined with dual OVHcloud Connect links, you get full end-to-end resilience:

| Component | Primary | Backup |
|---|---|---|
| GCP VLAN attachment | Edge domain zone1 | Edge domain zone2 |
| Provider circuit | Circuit set 1 | Circuit set 2 |
| OVHcloud Connect | Service 1 (PoP A) | Service 2 (PoP B) |
| OVHcloud AZ | AZ 1 | AZ 2 |

##### GCP SLA tiers

| Configuration | GCP SLA |
|---|---|
| Single VLAN attachment | No SLA |
| Two attachments in different edge domains, same metro | 99.9% |
| Four attachments in two different metros | 99.99% |

### Step-by-step

#### 1. Create two Cloud Routers

Create a Cloud Router in each region or for each edge availability domain:

| Router | Region | ASN |
|---|---|---|
| `router-ovhcloud-1` | `europe-west1` | 16550 (default) |
| `router-ovhcloud-2` | `europe-west3` | 16550 (default) |

#### 2. Create two VLAN attachments

For each Cloud Router, create a **Partner Interconnect VLAN attachment**:

| Attachment | Cloud Router | Edge availability domain |
|---|---|---|
| `attachment-1` | `router-ovhcloud-1` | `zone1` |
| `attachment-2` | `router-ovhcloud-2` | `zone2` |

Note both **GCP pairing keys**.

#### 3. Order two OVHcloud Connect Provider services

[Order two OVHcloud Connect Provider services](/guides/network/ovhcloud-connect/order-provider) at different PoPs:

- OVHcloud Connect 1 → PoP A
- OVHcloud Connect 2 → PoP B

Retrieve both **OVHcloud service keys**.

#### 4. Create provider bridges for each path

On your provider platform, create a bridge for each path. Use a provider cloud router if Layer 3 routing at the provider is needed. Refer to your provider's documentation for the exact steps; see [Providers](/guides/network/ovhcloud-connect/providers) for the list.

**Path 1 (Primary):**

1. Provider cloud router or port at Location A.
2. Virtual circuit / connection: GCP Partner Interconnect (GCP pairing key 1) → provider cloud router A.
3. Virtual circuit / connection: provider cloud router A → OVHcloud Connect 1 (OVHcloud service key 1).

**Path 2 (Backup):**

1. Provider cloud router or port at Location B.
2. Virtual circuit / connection: GCP Partner Interconnect (GCP pairing key 2) → provider cloud router B.
3. Virtual circuit / connection: provider cloud router B → OVHcloud Connect 2 (OVHcloud service key 2).

#### 5. Activate both GCP VLAN attachments

In the GCP Console:

1. Go to **Hybrid Connectivity** → **VLAN attachments**.
2. For each attachment: click **Activate** once it shows "Pending customer".
3. Verify BGP sessions are established in both Cloud Routers.

#### 6. Configure BGP failover

**GCP side:**

Within GCP, Cloud Router uses **MED (Multi-Exit Discriminator)** as its own native mechanism to influence path selection between its VLAN attachments. Set different MED values:

| Attachment | Advertised MED |
|---|---|
| `attachment-1` (primary) | 100 (lower = preferred) |
| `attachment-2` (backup) | 200 |

You can configure MED via custom route advertisements in the Cloud Router BGP peer settings. This is a GCP-internal mechanism and does not influence how OVHcloud selects its path toward you.

**OVHcloud side:**

Use [Configure OCC L3 with BGP](/guides/network/ovhcloud-connect/l3-bgp). To build an active/passive topology, use AS-path prepending on your own devices — it is customer-side only, and MED is **not supported** on OVHcloud Connect:

| Path | AS-path prepend (your devices) |
|---|---|
| OVHcloud Connect 1 (primary) | None |
| OVHcloud Connect 2 (backup) | 1× prepend |

**Make routing inside OVHcloud redundant.** On each OVHcloud Connect service, create an **AZ configuration** using a **/28 subnet** and add a **BGP extra configuration**, so that a BGP session is established with **both** OVHcloud devices **A and B** in the Availability Zone rather than a single one. Without it, the OVHcloud side of the path is not redundant. See [Set up the vRack network](/guides/network/ovhcloud-connect/vrack-network-setup).

#### 7. Associate both services with your vRack

[Associate both OVHcloud Connect services](/guides/network/ovhcloud-connect/associate-vrack) with the same vRack.

#### 8. Test failover

| Test | Action | Expected result |
|---|---|---|
| GCP link failure | Disable VLAN attachment 1 | Traffic shifts to attachment 2 |
| OCC link failure | Disable OVHcloud Connect 1 | Traffic shifts to OVHcloud Connect 2 |
| Provider failure | Take down the path A provider cloud router | Traffic shifts to the path B route |
| Full recovery | Re-enable all | Traffic returns to primary |

### GCP-specific considerations

- **Custom route advertisements**: Use Cloud Router custom route advertisements to control which subnets are announced to OVHcloud. Avoid advertising the entire VPC if only specific subnets are needed.
- **Dataplane v2**: If using GKE with Dataplane v2, ensure Pod CIDR ranges are included in route advertisements if GKE pods need to communicate with OVHcloud.
- **Shared VPC**: If using Shared VPC, create the Interconnect in the host project and share with service projects.
- **MTU**: GCP Interconnect sets its own MTU for Partner Interconnect (refer to Google's current documentation). On the OVHcloud side, jumbo frames up to **9000 bytes** are supported; ensure the MTU is consistent end to end across GCP, the provider virtual circuits / connections, and OVHcloud Connect.

> For more information, please consult [GCP Interconnect documentation](https://docs.cloud.google.com/network-connectivity/docs/interconnect) and [GCP Cloud Router documentation](https://docs.cloud.google.com/network-connectivity/docs/router).
