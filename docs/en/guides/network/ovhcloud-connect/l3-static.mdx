## Objective

Static routing is the simplest way to connect your network to OVHcloud when you have a small, stable set of prefixes and do not need a routing protocol. Unlike BGP, it offers no automatic failover — you update routes yourself when your network changes — though VRRP still protects the gateway within an AZ. Configuring OVHcloud Connect in L3 mode with static routing involves two levels of configuration:

1. **PoP configuration** — The L3 session between your router and OVHcloud at the Point of Presence.
2. **AZ extra configuration (network)** — Static routes within the OVHcloud AZ for route distribution.

:::info
If you prefer dynamic routing with BGP, see [Configure OVHcloud Connect L3 with BGP](/guides/network/ovhcloud-connect/l3-bgp).
:::

### When to use static routing vs BGP

| Criteria | Static routing | BGP |
|---|---|---|
| **Number of prefixes** | Small (1–5 routes) | Large or growing |
| **Network topology** | Simple, single-path | Complex, multi-path, multi-AZ |
| **Failover** | Manual — you must update routes yourself | Automatic — BGP reconverges |
| **Maintenance** | Routes must be updated manually when subnets change | Routes update dynamically |
| **Complexity** | Low — no routing protocol to manage | Higher — requires BGP configuration |

Use static routing when you have a simple setup with a small number of stable prefixes and do not require automatic failover.

## Requirements

- An active OVHcloud Connect service (status `active`)
- OVHcloud Connect associated with a vRack — see [Associate OVHcloud Connect with your vRack](/guides/network/ovhcloud-connect/associate-vrack)
- An AZ configuration created — see [Set up vRack networking](/guides/network/ovhcloud-connect/vrack-network-setup)
- A /30 peering subnet (e.g. `192.0.2.0/30`)
- OVHcloud API credentials (Application Key, Application Secret, Consumer Key). Refer to the [First steps with the OVHcloud API](/guides/manage-and-operate/api/first-steps) guide.

## Configure the OVHcloud side

You can configure the OVHcloud side of the L3 static-routing setup either from the **OVHcloud Control Panel** or with the **OVHcloud API**. Both methods achieve the same result. Afterwards, configure the matching static routes on your own router.

### Using the OVHcloud Control Panel

Configure the service from the <code className="action">Bare Metal Cloud</code> > <code className="action">Network</code> > <code className="action">OVHcloud Connect</code> section. Open your solution, then:

1. **Associate a vRack** (if not already done): click <code className="action">Attach a vRack</code> and select an existing vRack.
2. **Add a PoP configuration**: in the `PoP configuration` table, click <code className="action">Configure port</code> to open the **Add a PoP configuration** form, set the **Type** to **L3**, and enter your **User ASN**, the **OVHcloud ASN**, and a **/30 subnetwork** for the PoP link.
3. **Add an availability zone (AZ) configuration**: under the `AZ configuration` section, click <code className="action">Add an AZ</code>, select an availability zone, and enter the **OVHcloud ASN** and a **/28 subnetwork** (or larger) from your vRack.
4. **Add a routing configuration**: on the availability zone, click <code className="action">Routing rules</code>, choose **Static**, and enter:

   | Information | Description |
   |---|---|
   | Network Focus | The destination prefix, using CIDR notation |
   | Next hop | An IP address acting as gateway within the subnetwork range |

   You can add several static routes in the same availability zone by repeating this step.

Then add matching static routes on your own router (see **Configure static routes on your router** below).

### Using the OVHcloud API

The following steps configure the same L3 static-routing setup programmatically.

#### Step 1 — Identify your interface ID

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/interface"} />


#### Step 2 — Create the PoP configuration (L3)

The PoP configuration establishes the L3 session at the Point of Presence. This step is the same whether you use BGP or static routing at the AZ level.

<Api version="v1" section="/ovhCloudConnect" method="POST" route={"/ovhCloudConnect/\{serviceName\}/config/pop"} />

**Request parameters:**

| Parameter | Type | Required | Description |
|---|---|---|---|
| `interfaceId` | long | Yes | ID of the OVHcloud Connect interface |
| `type` | string | Yes | `l3` for Layer 3 mode |
| `customerBgpArea` | long | No | Your AS number (still required for L3 — used for PoP-level peering). Use a public ASN or a private ASN in the range 64512–65534 (e.g. `64512`). |
| `subnet` | ipv4Block | No | /30 peering subnet. First IP is OVHcloud, second is yours. |

**Example request:**

```json
{
  "interfaceId": 101,
  "type": "l3",
  "customerBgpArea": 64512,
  "subnet": "192.0.2.0/30"
}
```

#### Step 3 — Verify the PoP configuration

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}"} />


**Example response:**

```json
{
  "id": 5678,
  "interfaceId": 101,
  "type": "l3",
  "customerBgpArea": 64512,
  "ovhBgpArea": 35540,
  "subnet": "192.0.2.0/30",
  "status": "active"
}
```

From this response:

| Parameter | Value | Meaning |
|---|---|---|
| **OVHcloud peer IP** | `192.0.2.1` | First IP of the /30 |
| **Your peer IP** | `192.0.2.2` | Second IP of the /30 |

#### Step 4 — Create AZ extra configuration (static)

After the PoP configuration and the AZ configuration, create a **network extra configuration** to define static routes within the AZ.

:::info
The AZ (datacenter) configuration must already exist before you can create the extra configuration. Create it first with `POST .../config/pop/{popId}/datacenter` (providing the /28 subnet from your vRack) — see [Set up vRack networking](/guides/network/ovhcloud-connect/vrack-network-setup). This is what provides the `{datacenterId}` used in the `/extra` call below.
:::

:::info
With static routing, **VRRP remains active** on the AZ endpoint. OVHcloud devices A and B share a VRRP virtual gateway, which is the **first usable IP** of the AZ /28 subnet (OVHcloud routers A and B take the next two addresses; the first 3 IPs of the /28 are reserved for OVHcloud). Point your services' default gateway to this VRRP virtual IP for automatic failover between devices.
:::

<Api version="v1" section="/ovhCloudConnect" method="POST" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/datacenter/\{datacenterId\}/extra"} />

**Request parameters:**

| Parameter | Type | Required | Description |
|---|---|---|---|
| `type` | string | Yes | `network` for static routing |
| `nextHop` | ipv4 | No | Next-hop IP address for the static route |
| `subnet` | ipv4Block | No | Destination subnet for the static route |

**Example request — route your on-premises subnet through the OVHcloud Connect link:**

```json
{
  "type": "network",
  "nextHop": "172.16.1.1",
  "subnet": "10.0.0.0/16"
}
```

**Add multiple static routes**

Create one extra configuration per destination subnet. Repeat the `POST .../extra` call with a different `subnet` each time:

```json
{
  "type": "network",
  "nextHop": "172.16.1.1",
  "subnet": "10.1.0.0/16"
}
```

**Verify the extra configuration**

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/datacenter/\{datacenterId\}/extra/\{extraId\}"} />

**Example response:**

```json
{
  "id": 4568,
  "type": "network",
  "bgpNeighborArea": null,
  "bgpNeighborIp": null,
  "nextHop": "172.16.1.1",
  "subnet": "10.0.0.0/16",
  "status": "active"
}
```

**List all extra configurations for an AZ**

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/datacenter/\{datacenterId\}/extra"} />


## Configure static routes on your router

Configure your physical router with static routes pointing OVHcloud AZ subnets towards the OVHcloud Connect peering IP.

Configure BGP (or static routes) on your edge router according to your vendor's documentation, using the ASN, peer IP address, and subnet shown above.

## Verify connectivity

#### From your router

Consult your vendor's documentation to check the static routes and test connectivity to the OVHcloud AZ subnets.

**Expected results:**

| Check | Expected output |
|---|---|
| **Static routes present** | Routes to 172.16.x.x via 192.0.2.1 in routing table |
| **Ping succeeds** | Reply from OVHcloud AZ subnet gateway |
| **Traceroute** | Traffic goes through 192.0.2.1 (OVHcloud PoP) |

#### From the OVHcloud API

Check interface status:

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/interface/\{id\}/status"} />

Check PoP configuration status:

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/status"} />

## Limitations of static routing

:::warning
Static routing has significant limitations compared to BGP:

- **Manual updates required.** When you add or change subnets, you must update both the OVHcloud extra configuration and your router configuration.
- **No load balancing.** Static routes do not support ECMP or traffic engineering. Traffic follows a single path.
- **Not recommended for multi-AZ.** For resilient multi-AZ setups, BGP is strongly recommended — see [Multi-AZ](/guides/network/ovhcloud-connect/multi-az).

:::
