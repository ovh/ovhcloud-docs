## Objective

This tutorial guides you through connecting a single on-premises site to OVHcloud using **one OVHcloud Connect link**. This is the simplest architecture, suitable when you need private connectivity but can accept a single path (no built-in redundancy).

## Instructions

Below are prerequisites and instructions for four use cases; choose the one matching your desired architecture.

<Tab label="On-Premises">

### Prerequisites

- An OVHcloud account with a vRack
- A router in a data centre with OVHcloud PoP presence (for Direct) or a provider account (for Provider)
- BGP-capable network equipment
- An IP addressing plan with no overlaps between your network and OVHcloud subnets

### Layer 2 or Layer 3?

For a simple extension of your on-premises network into a single OVHcloud region, you can connect at **Layer 3 (routing with BGP)** or **Layer 2 (a transparent Ethernet bridge)**. The rest of this tab describes the Layer 3 / BGP flow; use the table below to decide which model fits your case.

| Choose **Layer 3 (BGP)** when you need… | Choose **Layer 2** when you need… |
|---|---|
| IP routing between your network and OVHcloud | An extension of the same broadcast domain (L2 adjacency) |
| To reach subnets across multiple PoPs | A lift-and-shift migration keeping IPs and VLANs unchanged |
| Redundancy and resilience across PoPs | VLAN transparency, with no routing in between |

**Layer 2** is a transparent, VLAN-preserving Ethernet bridge with no routing. It is available on **OVHcloud Connect Direct only** and is strictly **point-to-point** (one PoP to one availability zone). You can have only one Layer 2 per vRack, and redundancy is limited to LACP on the same PoP. If you choose Layer 2, follow [Configure OVHcloud Connect L2](/guides/network/ovhcloud-connect/l2) instead of the BGP steps below; the remaining vRack association steps still apply.

#### 1. Order OVHcloud Connect

Choose **Direct** or **Provider** depending on your situation:

- **Direct** — You have equipment in the same data centre as an OVHcloud PoP. See [Order Direct](/guides/network/ovhcloud-connect/order-direct).
- **Provider** — You prefer a managed connection. See [Order Provider](/guides/network/ovhcloud-connect/order-provider).

#### 2. Install the physical connection

- **Direct:** Provide the LOA to the data centre operator to install a cross-connect. See [Cross Connect LOA](/guides/network/ovhcloud-connect/cross-connect-loa).
- **Provider:** Share the service key with your provider and wait for activation.

#### 3. Configure BGP

Set up a single BGP session between your on-premises router and OVHcloud:

- Advertise your on-premises prefixes (e.g. `10.0.0.0/16`) to OVHcloud.
- Accept OVHcloud prefixes (e.g. `172.16.0.0/16`) from OVHcloud.

See [Configure OCC L3 with BGP](/guides/network/ovhcloud-connect/l3-bgp) for detailed instructions and configuration examples.

#### 4. Associate with vRack

Link your OVHcloud Connect service to your vRack. See [Associate with vRack](/guides/network/ovhcloud-connect/associate-vrack).

#### 5. Configure AZ subnets

Define the private subnets in OVHcloud that your on-premises network should reach. See [Set up your vRack network](/guides/network/ovhcloud-connect/vrack-network-setup).

#### 6. Test connectivity

| Test | Command |
|---|---|
| Ping from on-premises to OVHcloud VM | `ping 172.16.1.10` |
| Ping from OVHcloud VM to on-premises | `ping 10.0.0.1` |
| Traceroute | `traceroute 172.16.1.10` (should not go via internet) |
| BGP verification | Confirm the BGP session is `Established` on your router |

#### 7. Set up monitoring

Monitor link status and the BGP session state using your own monitoring tools. See [Monitor](/guides/network/ovhcloud-connect/monitor).

### Limitations of a simple connection

- **Single point of failure** — If the link, PoP, or cross-connect fails, connectivity is lost.
- **No automatic failover** — You need to manually intervene or rely on internet-based backup.
- **No availability commitment** — A single connection on a single PoP carries no availability SLA. See [SLAs](/guides/network/ovhcloud-connect/slas) for the config-based tiers.

**Recommendation:** For production workloads, consider upgrading to a [resilient architecture](/guides/network/ovhcloud-connect/resilient-architecture).

### How it works

The connection between AWS and OVHcloud is typically routed through a **shared connectivity provider** present at both AWS Direct Connect locations and OVHcloud PoPs. See [Providers](/guides/network/ovhcloud-connect/providers) for the list.

1. **On the AWS side**, you create a Direct Connect connection (or hosted connection) and a Virtual Interface (VIF) that connects your AWS VPC.
2. **On the provider side**, you create a virtual circuit / connection that bridges the AWS VIF to the OVHcloud Connect service.
3. **On the OVHcloud side**, you configure BGP and associate the connection with your vRack.

### Step-by-step

#### 1. Set up AWS Direct Connect

1. In the **AWS Console**, go to **Direct Connect** → **Connections**.
2. Create a new connection (or use a hosted connection via your provider).
3. Select the **AWS Direct Connect location** closest to your OVHcloud PoP.
4. Create a **Private Virtual Interface (VIF)** associated with your VPC or Virtual Private Gateway.
5. Note the BGP ASN, peer IPs, and VLAN ID.

For more information, please consult [AWS Direct Connect documentation](https://docs.aws.amazon.com/directconnect/).

#### 2. Order OVHcloud Connect Provider

1. In the **OVHcloud Control Panel**, order OVHcloud Connect Provider.
2. Select the same provider you're using for AWS. See [Providers](/guides/network/ovhcloud-connect/providers).
3. Choose the PoP location.
4. Copy the **service key**.

See [Order OVHcloud Connect Provider](/guides/network/ovhcloud-connect/order-provider).

#### 3. Create the bridge on the provider

In your provider's portal, create connections that bridge AWS and OVHcloud:

**Provider example:**

1. Create a port on your OVHcloud Connect provider, or use an existing one.
2. Create a **virtual circuit / connection to AWS** using the AWS Direct Connect hosted connection details.
3. Create a **virtual circuit / connection to OVHcloud** using the OVHcloud service key.
4. Use a **provider cloud router** to route between the two circuits. A cloud router is **required**: the two virtual circuits cannot be stitched together without Layer 3 routing at the provider level.

Refer to your provider's documentation for the exact steps. See [Providers](/guides/network/ovhcloud-connect/providers) for the list.

#### 4. Configure BGP

You need BGP sessions on three segments:

| Segment | Your side | Remote side |
|---|---|---|
| **AWS VIF** | AWS VPC (via VGW/TGW) | Provider or your router |
| **Provider bridge** | Handled by the provider cloud router | — |
| **OVHcloud Connect** | OVHcloud router | The provider cloud router |

The provider cloud router handles both sessions:

- The provider cloud router peers with AWS via the VIF.
- The provider cloud router peers with OVHcloud via OVHcloud Connect.
- Routes are exchanged automatically between the two peers.

#### 5. Associate OVHcloud Connect with vRack

See [Associate with vRack](/guides/network/ovhcloud-connect/associate-vrack).

#### 6. Test connectivity

| Test | Details |
|---|---|
| **From AWS EC2 to OVHcloud** | `ping 172.16.1.10` from an EC2 instance |
| **From OVHcloud to AWS** | `ping 10.1.0.10` from an OVHcloud VM |
| **Traceroute** | Verify traffic stays on private paths (no internet hops) |
| **BGP routes** | Check that AWS VPC routes and OVHcloud routes appear in each other's routing tables |

### Important considerations

- **Routing domains:** Ensure there are no overlapping IP ranges between AWS VPCs and OVHcloud subnets.
- **Costs:** You will be billed by AWS (Direct Connect), your OVHcloud Connect provider (the virtual circuits / connection and any cloud router), and OVHcloud (Connect). Review all three pricing models.
- **Latency:** The total latency depends on the distance between the AWS region and OVHcloud region, plus any intermediate provider hops.

- Non-overlapping IP ranges between Azure VNet and OVHcloud vRack

### Step-by-step

#### 1. Create an Azure ExpressRoute circuit

1. In the **Azure Portal** → **Create a resource** → **ExpressRoute**.
2. Select:
   - **Provider**: your OVHcloud Connect provider (see [Providers](/guides/network/ovhcloud-connect/providers))
   - **Peering location**: Choose a location shared with your OVHcloud PoP
   - **Bandwidth**: Match your OVHcloud Connect bandwidth (OVHcloud Connect Direct offers 1, 10 or 100 Gbps; Provider offers 50 Mbps up to 50 Gbps)
3. Complete the creation. Note the **Service Key** (a GUID).

#### 2. Order your OVHcloud Connect Provider

If not already done, [order an OVHcloud Connect Provider](/guides/network/ovhcloud-connect/order-provider) at a PoP served by the same provider.

Retrieve your **service key** from the OVHcloud Control Panel or API.

#### 3. Create the provider bridge

On the provider platform, create **two virtual circuits / connections**:

| Circuit | Source | Destination |
|---|---|---|
| Circuit 1 | Azure ExpressRoute (Service Key) | Provider cloud router / port |
| Circuit 2 | Provider cloud router / port | OVHcloud Connect (Service Key) |

A provider cloud router acts as the transit point between Azure and OVHcloud. It is **required** — the ExpressRoute circuit and the OVHcloud Connect circuit cannot be joined without it.

**Provider example:**

1. Create a provider cloud router (or use an existing port) in the same metro.
2. Create a virtual circuit / connection to Azure ExpressRoute using the Azure Service Key.
3. Create a virtual circuit / connection to OVHcloud Connect using the OVHcloud service key.
4. A provider cloud router is **required** to route between the two circuits.

Refer to your provider's documentation for the exact steps. See [Providers](/guides/network/ovhcloud-connect/providers) for the list.

#### 4. Configure Azure Private Peering

On the Azure ExpressRoute circuit:

1. Go to **Peerings** → **Azure private**.
2. Configure:
   - **Peer ASN**: Your provider cloud router or provider ASN
   - **Primary subnet**: A /30 for BGP (e.g., `169.254.100.0/30`)
   - **Secondary subnet**: A /30 for BGP (e.g., `169.254.100.4/30`)
   - **VLAN ID**: Provided by the provider

#### 5. Configure OVHcloud BGP peering

[Configure OCC L3 with BGP](/guides/network/ovhcloud-connect/l3-bgp) for the OVHcloud Connect service.

Ensure the provider cloud router advertises Azure prefixes (`10.2.0.0/16`) toward OVHcloud, and OVHcloud prefixes (`172.16.0.0/16`) toward Azure.

#### 6. Associate your vRack

[Associate the OVHcloud Connect service with your vRack](/guides/network/ovhcloud-connect/associate-vrack).

#### 7. Verify connectivity

| Check | Command / Action |
|---|---|
| Azure circuit status | Azure Portal → ExpressRoute → Overview → **Provider status: Provisioned** |
| Azure BGP peering | Azure Portal → ExpressRoute → Peerings → **State: Enabled** |
| OVHcloud BGP status | OVHcloud API: `GET /ovhCloudConnect/{serviceName}` → `status: active` |
| Provider circuit status | Provider portal → virtual circuit / connection → **Active / Up** |
| End-to-end ping | From Azure VM → OVHcloud server private IP |

### BGP route flow

There are **three BGP segments** in this architecture:

| Segment | Endpoints | ASNs |
|---|---|---|
| Azure ↔ Provider | Azure (ASN `12076`) ↔ provider cloud router / provider ASN | `12076` ↔ Provider |
| Provider ↔ OVHcloud | Provider cloud router / provider ASN ↔ the ASN you assign to the OVHcloud routing instance | Provider ↔ your OVHcloud-side ASN |
| OVHcloud ↔ vRack | Internal routing within OVHcloud | N/A |

:::info
Azure uses ASN **12076** for ExpressRoute Private Peering. On the OVHcloud side, you assign the ASN to the OVHcloud routing instance: you can use any ASN except the values reserved by OVHcloud per region (**65501** Europe, **65502** Canada, **65519** Asia), and it must differ from the ASN on the other side of the session. A common valid choice is a private ASN in the **64512–65534** range (for example `64512`).
:::

### Troubleshooting

| Symptom | Likely cause | Action |
|---|---|---|
| ExpressRoute circuit stuck in "Enabling" | Provider has not completed provisioning | Check provider portal; contact provider support |
| Azure private peering not established | Subnet or ASN mismatch | Verify /30 subnets and peer ASN match provider settings |
| OVHcloud BGP session down | Service key not activated or VLAN mismatch | Check OVHcloud API and the provider circuit configuration |
| No route to Azure VNet | Missing route advertisement | Verify the provider cloud router forwards Azure prefixes toward OVHcloud |
| Asymmetric routing | Different paths for outbound/inbound | Ensure both sides prefer the same path; check BGP attributes |

### GCP Interconnect types

GCP offers two main interconnect options:

| Type | Description | Use when |
|---|---|---|
| **Dedicated Interconnect** | Direct physical connection to Google's network | You have a presence in a GCP colocation facility |
| **Partner Interconnect** | Connection through a supported service provider | You use a shared connectivity provider that is also a GCP partner |

**For this tutorial**, we use **Partner Interconnect** since a shared connectivity provider (see [Providers](/guides/network/ovhcloud-connect/providers)) acts as a bridge between GCP and OVHcloud.

### Step-by-step

#### 1. Create a GCP Cloud Router

In the **GCP Console** → **Hybrid Connectivity** → **Cloud Routers** → **Create**:

- **Name**: `router-ovhcloud`
- **Network**: Your VPC
- **Region**: Region closest to the provider PoP (e.g., `europe-west1` for Paris)
- **ASN**: Use a private ASN in the `64512`–`65534` range (e.g., `64512`) or Google's default (`16550`)

#### 2. Create a Partner Interconnect VLAN attachment

Go to **Hybrid Connectivity** → **Interconnect** → **VLAN attachments** → **Create**:

1. Select **Partner Interconnect connection**.
2. Choose your Cloud Router.
3. Select the appropriate region and edge availability domain.
4. Set the **MTU** according to Google's current options for the attachment. On the OVHcloud side, jumbo frames up to **9000 bytes** are supported; make sure the MTU is consistent end to end across GCP, the provider, and OVHcloud Connect.
5. Note the **pairing key** generated by GCP.

**GCP pairing key format**: A string like `<random>/<region>/<edge-availability-domain>`

#### 3. Create the provider bridge

On the provider platform, create connections to bridge GCP and OVHcloud:

**Provider example:**

1. Create a provider cloud router (or use an existing port) in a metro with both GCP and OVHcloud presence.
2. **Circuit 1**: provider cloud router → Google Cloud Partner Interconnect (use GCP pairing key).
3. **Circuit 2**: provider cloud router → OVHcloud Connect (use OVHcloud service key).
4. Use a provider cloud router if Layer 3 routing at the provider is needed.

Refer to your provider's documentation for the exact steps. See [Providers](/guides/network/ovhcloud-connect/providers) for the list.

#### 4. Activate the GCP VLAN attachment

After the provider provisions the connection:

1. Return to **GCP Console** → **VLAN attachments**.
2. The attachment should show **"Waiting for provider"** → then **"Pending customer"**.
3. Click **Activate** to enable the attachment.
4. GCP will automatically configure BGP between the Cloud Router and the provider.

#### 5. Configure OVHcloud BGP peering

[Configure OCC L3 with BGP](/guides/network/ovhcloud-connect/l3-bgp).

Ensure the provider cloud router:

- Advertises GCP VPC prefixes (`10.3.0.0/16`) toward OVHcloud (peering with the ASN you assign to the OVHcloud routing instance).
- Advertises OVHcloud prefixes (`172.16.0.0/16`) toward GCP Cloud Router.

#### 6. Associate your vRack

[Associate the OVHcloud Connect service with your vRack](/guides/network/ovhcloud-connect/associate-vrack).

#### 7. Verify connectivity

| Check | How to verify |
|---|---|
| GCP VLAN attachment | GCP Console → VLAN attachments → **Status: Active** |
| GCP Cloud Router BGP | GCP Console → Cloud Routers → BGP peers → **Status: Established** |
| Provider circuit | Provider portal → virtual circuit / connection → **Active / Up** |
| OVHcloud BGP | OVHcloud API → service status = **active** |
| End-to-end | Ping from GCP VM → OVHcloud server private IP |

### BGP route flow

| Segment | Endpoints | ASNs |
|---|---|---|
| GCP ↔ Provider | Cloud Router (ASN `16550`) ↔ provider cloud router (Provider ASN) | `16550` ↔ Provider |
| Provider ↔ OVHcloud | Provider cloud router (Provider ASN) ↔ the ASN you assign to the OVHcloud routing instance | Provider ↔ your OVHcloud-side ASN |
| OVHcloud ↔ vRack | Internal OVHcloud routing | N/A |

:::info
GCP Cloud Router uses ASN **16550** by default. You can configure a custom ASN during Cloud Router creation. On the OVHcloud side, you assign the ASN to the OVHcloud routing instance: you can use any ASN except the values reserved by OVHcloud per region (**65501** Europe, **65502** Canada, **65519** Asia), and it must differ from the ASN on the other side of the session. A common valid choice is a private ASN in the **64512–65534** range (for example `64512`).
:::
