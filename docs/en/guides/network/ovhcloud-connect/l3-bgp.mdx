## Objective

BGP gives you dynamic route exchange and automatic failover between your network and OVHcloud: routes are learned and withdrawn automatically instead of being maintained by hand, and with two or more PoPs ECMP is enabled automatically to spread traffic across paths. Configuring OVHcloud Connect in L3 mode with BGP involves two levels of configuration:

1. **PoP configuration** — The eBGP session between your router and OVHcloud at the Point of Presence.
2. **AZ extra configuration (BGP)** — BGP peering within the OVHcloud AZ for route distribution.

:::info
If you prefer static routing instead of BGP, see [Configure OVHcloud Connect L3 with static routing](/guides/network/ovhcloud-connect/l3-static).
:::

For how an L3 service is structured at PoP and AZ level, and when to prefer BGP over static routing, see [Introduction to OVHcloud Connect](/guides/network/ovhcloud-connect/introduction#layer-3-l3-service).

## Requirements

- An active OVHcloud Connect service (status `active`)
- OVHcloud Connect associated with a vRack — see [Associate OVHcloud Connect with your vRack](/guides/network/ovhcloud-connect/associate-vrack)
- An AZ configuration created — see [Set up vRack networking](/guides/network/ovhcloud-connect/vrack-network-setup)
- Your ASN (a public ASN or a private ASN in the range 64512–65534)
- A /30 peering subnet (e.g. `192.0.2.0/30`)
- OVHcloud API credentials (Application Key, Application Secret, Consumer Key). Refer to the [First steps with the OVHcloud API](/guides/manage-and-operate/api/first-steps) guide.

Log in to your <ManagerLink to="/">OVHcloud Control Panel</ManagerLink> and open the <code className="action">Bare Metal Cloud</code> section, then go to <code className="action">Network</code> > <code className="action">OVHcloud Connect</code>.

## Overview

<img className="thumbnail" alt="OVHcloud Connect L3 implementation: an L3 domain (subnet and BGP ASN) is configured on each PoP and availability zone" src="/images/network/ovhcloud-connect/l3-bgp/occ-l3-implementation.png" loading="lazy" />

- **PoP level**: An eBGP session between your router (your ASN) and OVHcloud (the OVHcloud-side ASN) over a /30 peering subnet.
- **AZ level**: A BGP neighbour configured inside the AZ to distribute routes to your OVHcloud services.

## Configure the OVHcloud side

You can configure the OVHcloud side of the L3 BGP setup either from the **OVHcloud Control Panel** or with the **OVHcloud API**. Both methods achieve the same result. Afterwards, configure the matching BGP session on your own router.

### Using the OVHcloud Control Panel

Configure the service from the <code className="action">Bare Metal Cloud</code> > <code className="action">Network</code> > <code className="action">OVHcloud Connect</code> section. Open your solution, then:

1. **Associate a vRack** (if not already done): click <code className="action">Attach a vRack</code> and select an existing vRack.
2. **Add a PoP configuration**: in the `PoP configuration` table, click <code className="action">Configure port</code> to open the **Add a PoP configuration** form, set the **Type** to **L3**, and enter:

   | Information | Description |
   |---|---|
   | User ASN | Your BGP AS number, configured on your router in the PoP |
   | OVHcloud ASN | The AS number configured on the OVHcloud Connect routers in the PoP |
   | Subnetwork in /30 | A /30 IPv4 block for the link between your router and the OVHcloud router in the PoP |

3. **Add an availability zone (AZ) configuration**: under the `AZ configuration` section, click <code className="action">Add an AZ</code>, select an availability zone, and enter the **OVHcloud ASN** and a **/28 subnetwork** (or larger) from your vRack.
4. **Add a routing configuration**: on the availability zone, click <code className="action">Routing rules</code>, choose **BGP**, and enter your **User ASN** and the **IP Neighbour** (your router's BGP neighbour IP within the AZ subnetwork).

Then configure the matching eBGP session on your own router (see **Configure BGP on your router** below).

### Using the OVHcloud API

The following steps configure the same L3 BGP setup programmatically.

#### Step 1 — Identify your interface ID

Retrieve the interface ID for your OVHcloud Connect service:

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/interface"} />

#### Step 2 — Create the PoP configuration (L3)

The PoP configuration establishes the L3 BGP session at the Point of Presence.

<Api version="v1" section="/ovhCloudConnect" method="POST" route={"/ovhCloudConnect/\{serviceName\}/config/pop"} />

**Request parameters:**

| Parameter | Type | Required | Description |
|---|---|---|---|
| `interfaceId` | long | Yes | ID of the OVHcloud Connect interface |
| `type` | string | Yes | `l3` for Layer 3 mode |
| `customerBgpArea` | long | No | Your AS number (a public ASN or a private ASN in the range 64512–65534, e.g. `64512`) |
| `ovhBgpArea` | long | No | The ASN for the OVHcloud-side routing instance. You can use any ASN except the values reserved by OVHcloud per region (`65501` Europe, `65502` Canada, `65519` Asia); it must differ from your customer ASN (e.g. `35540`). |
| `subnet` | ipv4Block | No | /30 peering subnet (e.g. `192.0.2.0/30`). First IP is OVHcloud, second is yours. |

**Example request:**

```json
{
  "interfaceId": 101,
  "type": "l3",
  "customerBgpArea": 64512,
  "subnet": "192.0.2.0/30"
}
```

The `resourceId` in the response is your new `popId`. You can also retrieve it at any time by listing your PoP configurations with `GET .../config/pop`.

#### Step 3 — Verify the PoP configuration

Once the task completes:

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}"} />

**Example response:**

```json
{
  "id": 5678,
  "interfaceId": 101,
  "type": "l3",
  "customerBgpArea": 64512,
  "ovhBgpArea": 35540,
  "subnet": "192.0.2.0/30",
  "status": "active"
}
```

From this response, note:

| Parameter | Value | Meaning |
|---|---|---|
| **OVHcloud peer IP** | `192.0.2.1` | First IP of the /30 — OVHcloud side |
| **Your peer IP** | `192.0.2.2` | Second IP of the /30 — your router |
| **OVHcloud ASN** | `35540` | The `ovhBgpArea` value (any ASN except the reserved region values) |
| **Your ASN** | `64512` | The `customerBgpArea` value |

Check the BGP session state:

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/status"} />

#### Step 4 — Create AZ extra configuration (BGP)

After the PoP configuration and the [AZ configuration](/guides/network/ovhcloud-connect/vrack-network-setup), create a **BGP extra configuration** to enable BGP route distribution within the AZ.

<img className="thumbnail" alt="BGP session announcing the vRack IP network to the OVHcloud router" src="/images/network/ovhcloud-connect/l3-bgp/occ-l3-bgpvrack.png" loading="lazy" />

<img className="thumbnail" alt="OVHcloud Connect L3 BGP global topology" src="/images/network/ovhcloud-connect/l3-bgp/occ-l3-bgpglobal.png" loading="lazy" />

:::info
The AZ (datacenter) configuration must already exist before you can create the extra configuration. Create it first with `POST .../config/pop/{popId}/datacenter` (providing the /28 subnet from your vRack) — see [Set up vRack networking](/guides/network/ovhcloud-connect/vrack-network-setup). This is what provides the `{datacenterId}` used in the `/extra` call below.
:::

:::warning
Enabling BGP at the AZ level **disables VRRP** on that AZ configuration. BGP handles failover instead. You must establish a BGP session with **both** OVHcloud device A and device B (up to 4 BGP peers per AZ). By default, BFD (Bidirectional Forwarding Detection) is activated on all AZ BGP sessions — enabling BFD on your side as well is strongly recommended for faster convergence.
:::

<Api version="v1" section="/ovhCloudConnect" method="POST" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/datacenter/\{datacenterId\}/extra"} />

**Request parameters:**

| Parameter | Type | Required | Description |
|---|---|---|---|
| `type` | string | Yes | `bgp` for BGP routing |
| `bgpNeighborArea` | long | No | Your AS number for the AZ BGP neighbour (use the same customer ASN as at the PoP, e.g. `64512`) |
| `bgpNeighborIp` | ipv4 | No | Router IP for the BGP session within the AZ |

**Example request:**

```json
{
  "type": "bgp",
  "bgpNeighborArea": 64512,
  "bgpNeighborIp": "172.16.1.1"
}
```

Verify the extra configuration:

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/datacenter/\{datacenterId\}/extra/\{extraId\}"} />

**Example response:**

```json
{
  "id": 4567,
  "type": "bgp",
  "bgpNeighborArea": 64512,
  "bgpNeighborIp": "172.16.1.1",
  "nextHop": null,
  "subnet": null,
  "status": "active"
}
```

## Configure BGP on your router

Configure your physical router to establish the eBGP session with OVHcloud at the PoP. **Replace the example values** with your actual PoP configuration parameters (the OVHcloud peer IP, your peer IP, and both ASNs).

Configure BGP (or static routes) on your edge router according to your vendor's documentation, using the ASN, peer IP address, and subnet shown above.

## Verify the BGP session

#### From your router

Consult your vendor's documentation to check the BGP session state and the routes exchanged with OVHcloud.

**Expected results:**

| Check | Expected output |
|---|---|
| **BGP state** | `Established` |
| **Prefixes received** | At least 1 route from OVHcloud (your AZ subnets) |
| **Prefixes sent** | Your advertised prefixes visible |

#### From the OVHcloud API

Check PoP statistics (accepted prefixes):

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/statistics"} />

#### Run a diagnostic

If the session does not come up, run a peering diagnostic:

<Api version="v1" section="/ovhCloudConnect" method="POST" route={"/ovhCloudConnect/\{serviceName\}/diagnostic"} />

Select the diagnostic you need — for example a BGP peering test or a routes diagnostic. See [Monitor your OVHcloud Connect](/guides/network/ovhcloud-connect/monitor) for the available diagnostics, and the [API console](https://api.ovh.com/console/#/ovhCloudConnect) for the exact request body.

## Best practices

- **Only advertise prefixes you own.** Do not leak third-party routes through OVHcloud Connect.
- **Apply prefix filters.** Use prefix-lists on both import and export to prevent accidental route leaks.
- **Set maximum-prefix limits.** Protect your router from receiving an unexpected number of routes.
- **Monitor the session.** Set up alerts for BGP flaps and session drops — see [Monitor your connection](/guides/network/ovhcloud-connect/monitor).
- **For redundant setups.** With two or more PoPs, ECMP is enabled automatically; to build an active/passive topology instead, tune BGP path selection with AS-path prepending on your own devices — see [Multi-AZ](/guides/network/ovhcloud-connect/multi-az). AS-path prepending is customer-side only, and MED is **not supported** on OVHcloud Connect.

## Troubleshooting

| Issue | Possible cause | Solution |
|---|---|---|
| BGP stuck in `Active` | Incorrect peer IP or ASN | Verify IP addresses and ASN on both sides. Use `GET .../config/pop/{popId}` to check OVHcloud-side values. |
| BGP stuck in `Idle` | Interface down or firewall blocking TCP 179 | Check physical link and firewall rules. Use `GET .../interface/{id}/status` to check link status. |
| No routes received | Missing `network` statement or prefix filter too restrictive | Verify export policy and `network` commands. Run a routes diagnostic (see [Monitor](/guides/network/ovhcloud-connect/monitor)). |
| Session drops frequently (flapping) | Unstable physical link or MTU mismatch | Check interface errors and MTU settings. Use `GET .../interface/{id}/statistics` to check error counters. |
| PoP config stuck in `init` status | Task still in progress or failed | Check `GET .../task` for pending tasks. |
