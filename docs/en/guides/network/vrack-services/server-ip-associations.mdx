## Objective

A Server-IP association binds the private interface of a dedicated server to an IP address of a [vRack Services](/guides/network/vrack-services/global) subnet. The DHCP and netboot service of vRack Services then gives the server the same address at every boot, and lets it boot from the private network. Associations are what [private boot](/guides/bare-metal-cloud/dedicated-servers/private-boot) relies on: creating an association enables private boot on the server, and deleting it disables private boot.

**This guide explains how to create, modify and delete Server-IP associations, from the OVHcloud Console or with the OVHcloud API.**

:::warning
Modifying or deleting the association of a server that boots from the private network changes the address it boots with, or makes it boot from the public network at its next reboot.

:::

## Requirements

- A [vRack Services](/guides/network/vrack-services/global) attached to a <Tooltip term="vrack">vRack</Tooltip>, with an IPv4 subnet without a VLAN and a service range.
- A [dedicated server](/links/bare-metal/bare-metal) that supports [private boot](/guides/bare-metal-cloud/dedicated-servers/private-boot), in the same region as the vRack Services, attached to its vRack, with OVHcloud Link Aggregation (OLA) enabled in **Full private** mode.
- Access to the <ManagerLink to="/beta/#/network/vrack-services">OVHcloud Console</ManagerLink>, or OVHcloud API credentials (see [First steps with the OVHcloud API](/guides/manage-and-operate/api/first-steps)).

:::tip
To enable private boot on a single server, you can also start from its <code className="action">Connectivity</code> tab: the private boot form creates the association, and the vRack, vRack Services or subnet it needs. See [Enable private boot on an OVHcloud dedicated server](/guides/bare-metal-cloud/dedicated-servers/private-boot).

:::

## Instructions

This section lists the rules an association address must follow, then explains how to manage associations from the Console or the API.

### IP address rules

The IP address of an association must:

- be an IPv4 address of the subnet;
- be outside the service range, which is reserved for the services that OVHcloud manages;
- be outside the BGP range of the subnet, if it has one;
- not be the first or last address of the subnet, which are reserved;
- not be already used by another association.

Each server can have only one association. OVHcloud only checks the addresses it manages: make sure no other machine in your vRack already uses the address, for example a machine with a static IP address.

### Manage associations

<Tabs>
<Tab label="Control Panel">

During the Beta, open the <ManagerLink to="/beta/#/network/vrack-services">OVHcloud Console</ManagerLink> with the <code className="action">Discover the console &gt;BETA_</code> button in the top-right corner, then select your vRack Services.

Open the <code className="action">Subnets</code> tab and click the subnet. Its page shows the **DHCP & Netboot (Server-IP Association)** card, which lists each association with its **Server name** and **IP address**.

You cannot add an association while the subnet has no service range, is tagged with a VLAN, or belongs to a vRack Services that is not attached to a vRack: the card says which condition is missing. Actions are also unavailable while the vRack Services is being updated.

**Create an association**

1. Click <code className="action">Add a Server-IP Association</code>. The **Create a Server-IP Association** panel opens, with the **Subnet** shown.
2. In the **Associated server** field, select the server. The list only shows the servers in the same region as the vRack Services, attached to its vRack, in OLA **Full private** mode, and with no association yet.
3. In the **Associated IP address** field, enter the server's IP address.
4. Click <code className="action">Add a Server-IP Association</code>.

The server boots from the private network, with this address, at its next reboot.

**Modify an association**

1. In the list, open the actions menu of the association, then click <code className="action">Modify</code>.
2. In the **Modify Server-IP Association** panel, enter the new IP address. The server cannot be changed.
3. Click <code className="action">Modify</code>.

The server uses the new address at its next reboot.

**Delete an association**

1. In the list, open the actions menu of the association, then click <code className="action">Delete</code>.
2. In the **Delete Server-IP Association** window, click <code className="action">Delete</code>.

The IP address is released, and private boot is disabled on the server: it boots from the public network at its next reboot.

</Tab>
<Tab label="OVHcloud API">

Associations are part of the vRack Services configuration: each one is an entry of `dedicatedServerInterfaceAssociations`, in the DHCP configuration of the subnet's service range.

1. List the server interfaces that can be associated with the vRack Services. Note the `uuid` of the server's interface:

<Api version="v2" section="/vrackServices" method="GET" route={"/vrackServices/resource/\{vrackServicesId\}/eligibleDedicatedServerInterfaces"} />

2. Retrieve the `checksum` and the `targetSpec` of the vRack Services:

<Api version="v2" section="/vrackServices" method="GET" route={"/vrackServices/resource/\{vrackServicesId\}"} />

3. Send the `targetSpec` back with your change to `services.serviceRange[].dhcp.dedicatedServerInterfaceAssociations`, and the `checksum` you retrieved:

<Api version="v2" section="/vrackServices" method="PUT" route={"/vrackServices/resource/\{vrackServicesId\}"} />

| To… | Change in `dedicatedServerInterfaceAssociations` |
|---|---|
| Create an association | Add an entry `{"uuid": "<interface uuid>", "ip": "<IP address>"}`. |
| Modify an association | Change the `ip` of the entry. |
| Delete an association | Remove the entry. |

Keep every other value of the `targetSpec` as returned by the `GET`. A complete request body is shown in [Enable private boot with the OVHcloud API](/guides/bare-metal-cloud/dedicated-servers/private-boot#api), and the `checksum` and `targetSpec` mechanism in [vRack Services - Exposing a Managed Service on your vRack](/guides/network/vrack-services/global).

4. Follow the update until the vRack Services is `READY`:

<Api version="v2" section="/vrackServices" method="GET" route={"/vrackServices/resource/\{vrackServicesId\}/task"} />

In the `currentState` of the vRack Services, each association shows whether netboot is active (`netboot`). The `dhcpConfigurationStatus` of the service range is `READY`, or `DRAFT` with the reason `MISSING_DEDICATED_SERVER_INTERFACE_ASSOCIATIONS` when its DHCP configuration has no association.

</Tab>
