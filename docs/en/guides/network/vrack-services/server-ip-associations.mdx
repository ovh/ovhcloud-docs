## Objective

A Server/IP Association binds the MAC address of a dedicated server to a private IP address of a [vRack Services](/guides/network/vrack-services/global) subnet. The DHCP service of vRack Services then gives the server the same address at every boot, with no static IP configuration in its operating system. Associations are what [private boot](/guides/bare-metal-cloud/dedicated-servers/private-boot) relies on.

**This guide explains how to create, modify and delete Server/IP Associations, and how to check their lease status, from the OVHcloud Console or with the OVHcloud API.**

:::warning
If private boot is enabled on a server, deleting or modifying its association changes the address it boots with. A server with no association can no longer boot from the private network.

:::

## Requirements

- A [vRack Services](/guides/network/vrack-services/global) attached to a <Tooltip term="vrack">vRack</Tooltip>, with a subnet created with **No VLAN** and a **Service range**.
- A compatible [dedicated server](/links/bare-metal/bare-metal) attached to the same vRack: High Grade Gen 2 or later, Scale Gen 2 or later, or Advance Gen 3 or later. {/* [UNVERIFIED: api] Product Note PBM11 */}
- Access to the <ManagerLink to="/beta/#/network/vrack-services">OVHcloud Console</ManagerLink>, or OVHcloud API credentials (see [First steps with the OVHcloud API](/guides/manage-and-operate/api/first-steps)).

:::tip
If you enable private boot from the server's <code className="action">Connectivity</code> tab, the association is created for you. Use this guide to review it, change its address, or manage associations for several servers.

:::

## Instructions

This section lists the rules an association address must follow, then explains how to manage associations from the Console or the API.

### IP address rules

The IP address of an association must:

- be inside the subnet;
- be outside the service range, which is reserved for the services that OVHcloud manages;
- be outside the BGP range of the subnet, if it has one;
- not be the network or broadcast address of the subnet;
- not be already assigned to another server.

{/* DRAFT: To verify — network/broadcast exclusion is open question Q1 of the specification. */}

OVHcloud only checks the addresses it manages. Make sure no other machine in your vRack already uses the address, for example a machine with a static IP address.

**Create an association**

1. Click <code className="action">Add an association</code>.
2. Select the server. Its MAC address is filled in automatically.
3. Select the subnet.
4. Enter the IP address, or keep the suggested one: the first free address after the service range.
5. Click <code className="action">Confirm</code>.

The server receives the address at its next DHCP request, for example at its next reboot.

**Modify an association**

1. Click the <code className="action">...</code> button of the association, then <code className="action">Modify</code>.
2. Enter the new IP address, then click <code className="action">Confirm</code>.

If the server uses private boot, reboot it so that it boots with the new address.

**Delete an association**

1. Click the <code className="action">...</code> button of the association, then <code className="action">Delete</code>.
2. Confirm the deletion.

**Check the lease status**

The lease status shows whether the server currently holds its address. A server that has not sent a DHCP request since the association was created, for example because it has not rebooted, has no active lease. [TODO: lease status values]

1. Retrieve the identifier of your vRack Services:

<Api version="v2" section="/vrackServices" method="GET" route={"/vrackServices/resource"} />

2. Retrieve the MAC address of the server's network interfaces:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/networkInterfaceController"} />

3. Retrieve the `checksum` and `targetSpec` of the vRack Services:

<Api version="v2" section="/vrackServices" method="GET" route={"/vrackServices/resource/\{vrackServicesId\}"} />

4. Send the `targetSpec` back with the association added to the subnet, and the `checksum` you retrieved:

<Api version="v2" section="/vrackServices" method="PUT" route={"/vrackServices/resource/\{vrackServicesId\}"} />

| Parameter | Required | Description | Example |
|---|---|---|---|
| `vrackServicesId` | Yes | Identifier of your vRack Services. | `vrs-abc-xyz-123` |
| `checksum` (body) | Yes | Checksum returned by the previous `GET`. The request is refused if the resource changed in the meantime. | `5d8f…` |
| `targetSpec.subnets[].[TODO: association field]` (body) | Yes | The server's MAC address and its IP address. Leave the IP address out to get the first free address of the subnet. [TODO: exact structure] | — |

5. Follow the update until it is applied:

<Api version="v2" section="/vrackServices" method="GET" route={"/vrackServices/resource/\{vrackServicesId\}/task"} />

To modify or delete an association, send the same `PUT` with the association changed or removed from `targetSpec`. For the `checksum` and `targetSpec` mechanism, see [vRack Services - Exposing a Managed Service on your vRack](/guides/network/vrack-services/global#api).
