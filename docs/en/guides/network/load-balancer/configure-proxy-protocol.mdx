## Objective

The OVHcloud Load Balancer acts as a proxy between your clients and your backend servers. As a result, your backend servers see the Load Balancer outbound IP address as the source of every connection, not the real client address. ProxyProtocol restores this information by prepending a small header to each TCP connection, letting the backend recover the original client IP address, port, and protocol.

**This guide explains how to enable ProxyProtocol on a backend server of your OVHcloud Load Balancer and how to configure the server to trust and parse the ProxyProtocol header.**

> [!TIP]
> If your frontend uses the HTTP protocol, use HTTP headers (such as `X-Forwarded-For`) instead of ProxyProtocol. Refer to the Configure HTTP headers{/* TODO(iplb-revamp): restore this link before the final merge, once the revamp guide lands → [Configure HTTP headers](/guides/network/load-balancer/configure-http-headers) */} guide. ProxyProtocol is intended for TCP frontends, where HTTP headers are not available.

## Introduction

ProxyProtocol was developed by the [HAProxy](https://www.haproxy.org/) team as the TCP counterpart to HTTP headers such as `X-Forwarded-For`. When enabled for a backend server, the Load Balancer prepends a header that carries at minimum:

- The Layer 4 protocol used (`TCP4` for IPv4 or `TCP6` for IPv6).
- The source IPv4 or IPv6 address.
- The source port.

Because the header modifies the start of the TCP stream, the backend server must be configured to expect and parse it. The protocol has two versions:

| Version | Format | Notes |
|---|---|---|
| Version 1 | Text | Most widely supported. Sufficient for most use cases. |
| Version 2 | Binary | Faster to parse. Can also carry SSL/TLS information and the certificate Common Name. |

Your OVHcloud Load Balancer supports four ProxyProtocol modes:

| Mode | Description |
|---|---|
| `v1` | Version 1 in text format. The most widely supported mode. |
| `v2` | Version 2 in binary format, without options. |
| `v2-ssl` | Version 2 with a field describing the SSL connection, when applicable. |
| `v2-ssl-cn` | Version 2 with the SSL field and the certificate `Common Name`, when applicable. |

ProxyProtocol is enabled per server, not per farm. This lets you test it on a single backend before applying it across an active farm. When ProxyProtocol is enabled for a server, health probes also insert the header, unless a dedicated probe port is configured — in that case the probe connects without the header.

For the full specification, refer to the [ProxyProtocol specification](https://www.haproxy.org/download/1.8/doc/proxy-protocol.txt).

## Instructions

Enabling ProxyProtocol has two parts. First, enable the ProxyProtocol mode on the backend server in your OVHcloud Load Balancer. Then configure that backend server to trust and parse the header.

### Find your Load Balancer outbound IP addresses

To configure trust on your backend servers, you need the list of outbound IP addresses of your OVHcloud Load Balancer. Retrieve them before you start.

### Enable ProxyProtocol on a backend server

Enable a ProxyProtocol mode on the target server. The corresponding server property in the API is `proxyProtocolVersion`.

{/* CP-STEPS-START:enable-proxyprotocol */}
<Tabs>
<Tab label="Control Panel">

1. Log in to the <ManagerLink to="/">OVHcloud Control Panel</ManagerLink> and open your Load Balancer service.
2. Select the `Server Farms` tab.
3. Open the farm that contains the target server, then edit that server.
4. Set the `ProxyProtocol version` to `v1`, `v2`, `v2-ssl`, or `v2-ssl-cn`.
5. Save the server, then click `Apply changes` to deploy the configuration.

</Tab>
<Tab label="OVHcloud API">

Modify the backend server to set the ProxyProtocol mode. Use the TCP farm endpoint for a TCP frontend:

<Api version="v1" section="/ipLoadbalancing" method="PUT" route={"/ipLoadbalancing/\{serviceName\}/tcp/farm/\{farmId\}/server/\{serverId\}"} />

| Parameter | Required | Description | Example |
|---|---|---|---|
| `serviceName` | Yes | The name of your OVHcloud Load Balancer service. | `loadbalancer-a1b2c3d4` |
| `farmId` | Yes | The ID of the farm containing the server. | `12345` |
| `serverId` | Yes | The ID of the server to modify. | `67890` |
| `proxyProtocolVersion` (body) | No | ProxyProtocol mode: `v1`, `v2`, `v2-ssl`, or `v2-ssl-cn`. | `v1` |

Then apply the configuration to make the change effective:

<Api version="v1" section="/ipLoadbalancing" method="POST" route={"/ipLoadbalancing/\{serviceName\}/refresh"} />

| Parameter | Required | Description | Example |
|---|---|---|---|
| `serviceName` | Yes | The name of your OVHcloud Load Balancer service. | `loadbalancer-a1b2c3d4` |

</Tab>


### Configure your backend server to trust ProxyProtocol

After ProxyProtocol is enabled on the Load Balancer side, configure the backend server to expect, parse, and trust the header. Always restrict trust to the outbound IP addresses retrieved earlier. The examples below use the placeholder range `10.108.0.0/14` — replace it with your own outbound addresses.

#### Nginx

Nginx supports ProxyProtocol version 1 and exposes the client address through the `proxy_protocol_addr` variable. With the `ngx_http_realip` module, Nginx uses this variable as the real source address in logs.

```nginx
server {
    # Enable ProxyProtocol on port 80
    listen 80 proxy_protocol;

    # Trust ProxyProtocol only from your Load Balancer outbound addresses
    set_real_ip_from 10.108.0.0/14;
    real_ip_header proxy_protocol;

    # (optional) Forward the real client IP in headers
    proxy_set_header X-Real-IP        $proxy_protocol_addr;
    proxy_set_header X-Forwarded-For  $proxy_protocol_addr;

    # Your regular configuration here
    # ...
}
```

Reload the configuration:

```bash
service nginx reload
```

For more information, refer to the [Nginx ProxyProtocol documentation](https://docs.nginx.com/nginx/admin-guide/load-balancer/using-proxy-protocol/).

#### Apache

Apache supports ProxyProtocol through the `mod_remoteip` module, which also manages `X-Forwarded-For` headers and lets you control which addresses ProxyProtocol applies to.

Before enabling ProxyProtocol, restrict connections to the outbound addresses of your OVHcloud Load Balancer with `iptables`:

```bash
# Trust connections from your Load Balancer outbound addresses only
iptables -A INPUT -s 10.108.0.0/14 -p tcp --dport 80 -j ACCEPT
iptables -A INPUT                  -p tcp --dport 80 -j DROP
```

Configure the virtual host to enable ProxyProtocol:

```apache
<VirtualHost *:80>
    RemoteIPProxyProtocol On
    # ...
</VirtualHost>
```

Replace `%h` with `%a` in the `LogFormat` directives so the logs record the real client address. Then enable the module and restart Apache:

```bash
# Enable the remoteip module
a2enmod remoteip

# Restart Apache to load the module
service apache2 restart
```

For more information, refer to the [mod_remoteip documentation](https://httpd.apache.org/docs/trunk/mod/mod_remoteip.html#remoteipproxyprotocol).

#### HAProxy

ProxyProtocol was designed by the HAProxy team, so HAProxy handles it well. A common pattern is to place a local HAProxy instance in front of software that does not support ProxyProtocol (such as MySQL or PostgreSQL) to recover and log the client IP address.

The following example listens on TCP port 3306 for MySQL. It is a starting point, not a complete configuration.

Install HAProxy:

```bash
sudo apt install haproxy
```

Configure the local proxy:

```text
listen mysql
    # Listen on all interfaces, port 3306, TCP mode
    mode tcp
    option tcplog
    bind *:3306

    # Expect the ProxyProtocol header only from a trusted network
    tcp-request connection expect-proxy layer4 if { src 10.108.0.0/14 }

    # Forward to the local MySQL server on a non-standard port
    server mysql 127.0.0.1:3316 check
```

Reload the configuration:

```bash
service haproxy reload
```

### Legal obligations

Applicable laws and regulations may require you to retain logs and certain traffic data. Preserving the real client IP address through ProxyProtocol can be part of meeting these obligations. It is your responsibility to comply with the laws that apply to you. For example, the [Investigatory Powers Act 2016 (Section 87)](https://www.legislation.gov.uk/ukpga/2016/25/section/87) can require telecommunications operators to retain certain communications data, including data identifying the source and destination of a communication.

OVHcloud provides you with services for which you are responsible for the configuration and management.
