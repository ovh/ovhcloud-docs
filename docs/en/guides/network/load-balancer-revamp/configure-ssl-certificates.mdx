## Objective

The OVHcloud Load Balancer can terminate SSL/TLS connections on the frontend, decrypting incoming traffic before forwarding it to your backend servers. This is known as SSL termination. Handling termination on the Load Balancer reduces the load on your backend servers and centralises certificate management, which simplifies maintenance and security updates.

**In this guide, you will learn how to:**

- Add a custom SSL/TLS certificate that you already own.
- Order a free certificate managed by OVHcloud.
- Choose a cipher profile (Modern or Intermediate).
- Attach a certificate to an HTTPS frontend.

## Requirements

- An [OVHcloud Load Balancer](/links/network/load-balancer) in your OVHcloud account.
- Access to the <ManagerLink to="/">OVHcloud Console</ManagerLink>, or [OVHcloud API credentials](/guides/manage-and-operate/api/first-steps) for the API method.
- For SSL termination: an HTTPS frontend. Refer to [Configure frontends](/guides/network/load-balancer-revamp/configure-frontends).
- For a free certificate: a domain name that already resolves to your Load Balancer service.

## Introduction

A certificate proves the identity of your service to clients and enables encrypted communication. The Load Balancer supports two types of certificate source: a **custom certificate** that you supply (certificate, private key, and optional certificate chain), and a **free certificate** that OVHcloud orders and renews automatically for a domain pointing at your service. You also select a **cipher profile**, a single setting for the whole service, that controls the TLS versions and cipher suites your frontends negotiate.

### Overview <a name="overview"></a>

SSL termination fits into the request path as follows. The client opens a TLS connection to the frontend, the Load Balancer decrypts the traffic, and the request is routed in clear text (or re-encrypted, depending on your configuration) to the server farm.

<img className="thumbnail" alt="Overview diagram" src="/images/network/load-balancer-revamp/configure-ssl-certificates/fig-1.svg" loading="lazy" />

{/* CP-STEPS-START:overview-cipher-profiles */}

Two cipher profiles are available. The profile is a single setting for the whole service: you select it from the **Cipher Profile** drop-down list in the <code className="action">SSL</code> tab, not per certificate or per frontend.

| Profile | TLS versions | When to use |
|---|---|---|
| `Modern (TLS 1.3)` | TLS 1.3 only | Modern clients only. Highest security, but older clients may fail to connect. |
| `Intermediate (TLS 1.2+)` | TLS 1.2 and above | General-purpose default. Broad client compatibility while excluding legacy protocols. |

{/* CP-STEPS-END:overview-cipher-profiles */}

After any change to a certificate or a frontend, you must apply the configuration to deploy it to the relevant zone.

### Add a custom certificate <a name="custom-certificate"></a>

Use this method when you already hold a certificate issued by a certificate authority. You need the certificate, its private key, and, where applicable, the intermediate certificate chain.

{/* CP-STEPS-START:add-custom-certificate */}

<Tabs>
<Tab label="Console">

1. Select the Load Balancer you want to configure.
2. Open the <code className="action">SSL</code> tab.
3. In the **TLS Certificates** section, click <code className="action">Add Certificate</code>.
4. On the **Add Certificate** page, select **Custom (upload PEM)** from the **Certificate type** drop-down list.
5. Paste the certificate into **Certificate (PEM)**, the private key into **Private Key (PEM)** and, if needed, the intermediate chain into **Certificate Chain (PEM)**. You can also give the certificate a **Display name**.
6. Click <code className="action">Add Certificate</code> to confirm.

Once the certificate is added, apply the configuration to deploy the change: in the <code className="action">Overview</code> tab, under **General information** > **Deployment**, click <code className="action">Apply N changes</code>, where N is the number of pending changes. The deployment starts immediately, and you can follow it in the <code className="action">Operations</code> tab.

</Tab>
<Tab label="OVHcloud API">

Add the certificate by sending its content to the SSL endpoint.

<Api version="v1" section="/ipLoadbalancing" method="POST" route={"/ipLoadbalancing/\{serviceName\}/ssl"} />

| Parameter | Required | Description | Example |
|---|---|---|---|
| `serviceName` | Yes | Your Load Balancer service identifier. | `loadbalancer-a1b2c3...` |
| `certificate` (body) | Yes | The PEM-encoded certificate. | `-----BEGIN CERTIFICATE----- ...` |
| `key` (body) | Yes | The PEM-encoded private key. | `-----BEGIN PRIVATE KEY----- ...` |
| `chain` (body) | No | The PEM-encoded intermediate chain. | `-----BEGIN CERTIFICATE----- ...` |

Apply the configuration to deploy the certificate:

<Api version="v1" section="/ipLoadbalancing" method="POST" route={"/ipLoadbalancing/\{serviceName\}/refresh"} />

</Tab>
<Tab label="Terraform">

Manage custom (imported) certificates with the `ovh_iploadbalancing_ssl` resource, which uploads the `certificate`, `key`, and optional `chain` you already hold. The provider also covers related Load Balancer objects such as `ovh_iploadbalancing_http_farm` and `ovh_iploadbalancing_http_farm_server`. After your Terraform changes, deploy the staged configuration with the `ovh_iploadbalancing_refresh` resource (arguments `service_name` and `keepers`).

</Tab>
</Tabs>

{/* CP-STEPS-END:add-custom-certificate */}

### Order a free certificate <a name="free-certificate"></a>

Use this method to let OVHcloud order and manage a certificate for a domain that points at your Load Balancer. For the order to complete, the chosen domain name must already resolve to your Load Balancer service.

{/* CP-STEPS-START:order-free-certificate */}

<Tabs>
<Tab label="Console">

1. Select your Load Balancer and open the <code className="action">SSL</code> tab.
2. In the **TLS Certificates** section, click <code className="action">Add Certificate</code>.
3. On the **Add Certificate** page, select **Free (Let's Encrypt)** from the **Certificate type** drop-down list.
4. In the **Domain(s)** field, enter a fully qualified domain name (FQDN) to secure, then click <code className="action">Add</code>. Domain names are added one at a time: repeat for each domain the certificate must cover.
5. Click <code className="action">Add Certificate</code> to start the order.

The order runs as a background task. You can follow its progress in the <code className="action">Operations</code> tab. Once complete, the certificate is installed on your Load Balancer automatically. The free certificate is then renewed automatically every 90 days.

</Tab>
<Tab label="OVHcloud API">

Order the free certificate for a domain that already points at your service.

<Api version="v1" section="/ipLoadbalancing" method="POST" route={"/ipLoadbalancing/\{serviceName\}/freeCertificate"} />

| Parameter | Required | Description | Example |
|---|---|---|---|
| `serviceName` | Yes | Your Load Balancer service identifier. | `loadbalancer-a1b2c3...` |
| `fqdn` (body) | Yes | The fully qualified domain name to secure. | `www.example.com` |

Follow up on the order by listing tasks. You can filter on the `orderFreeCertificate` action type:

<Api version="v1" section="/ipLoadbalancing" method="GET" route={"/ipLoadbalancing/\{serviceName\}/task"} />

Retrieve the status of a specific task:

<Api version="v1" section="/ipLoadbalancing" method="GET" route={"/ipLoadbalancing/\{serviceName\}/task/\{id\}"} />

Once the task completes, the certificate is installed automatically. No `refresh` call is required for the free certificate order itself.

</Tab>
<Tab label="Terraform">

Custom (imported) certificates are managed with the `ovh_iploadbalancing_ssl` resource. However, that resource only imports a certificate, key, and chain you already hold — the OVHcloud Terraform provider has no resource for *ordering* a free certificate. Order and renew free certificates through the OVHcloud Console or the OVHcloud API.

</Tab>
</Tabs>

{/* CP-STEPS-END:order-free-certificate */}

### Attach a certificate to a frontend <a name="attach-frontend"></a>

A certificate only takes effect once it is bound to an HTTPS frontend that performs SSL termination. The steps below enable termination on a frontend and select the certificate.

{/* CP-STEPS-START:attach-frontend */}

<Tabs>
<Tab label="Console">

1. Open the <code className="action">Frontends</code> tab of your Load Balancer.
2. Click <code className="action">Create frontend</code> to add a new frontend. To edit an existing HTTPS frontend instead, click the <code className="action">⋮</code> button in the **Actions** column of its row, then <code className="action">Edit</code>.
3. From the **Protocol** drop-down list, select **HTTPS** so that SSL termination is enabled.
4. From the **TLS Certificate** drop-down list, select the certificate to use.
5. Under **Default route**, select **Route to farm**, then choose the server farm that must receive the decrypted traffic (or select **Redirect to URL** to redirect requests instead).
6. Click <code className="action">Create Frontend</code> to save the new frontend, or <code className="action">Save changes</code> when editing an existing one.

Once the frontend is saved, apply the configuration: in the <code className="action">Overview</code> tab, under **General information** > **Deployment**, click <code className="action">Apply N changes</code>, where N is the number of pending changes. A single click deploys the changes to every zone of the service at once; you can follow the deployment in the <code className="action">Operations</code> tab.

</Tab>
<Tab label="OVHcloud API">

Create or modify an HTTPS frontend with SSL termination enabled. SSL termination is controlled by the `ssl` boolean: set it to `true`, then set `defaultFarmId` or `redirectLocation` to the corresponding values.

<Api version="v1" section="/ipLoadbalancing" method="POST" route={"/ipLoadbalancing/\{serviceName\}/http/frontend"} />

| Parameter | Required | Description | Example |
|---|---|---|---|
| `serviceName` | Yes | Your Load Balancer service identifier. | `loadbalancer-a1b2c3...` |
| `ssl` (body) | Yes | Enables SSL termination on the frontend. | `true` |
| `defaultFarmId` (body) | No | The server farm that receives decrypted traffic. | `12345` |
| `port` (body) | No | The listening port for the frontend. | `443` |

To modify an existing frontend instead, use the corresponding `PUT` endpoint:

<Api version="v1" section="/ipLoadbalancing" method="PUT" route={"/ipLoadbalancing/\{serviceName\}/http/frontend/\{frontendId\}"} />

Apply the configuration to deploy the change:

<Api version="v1" section="/ipLoadbalancing" method="POST" route={"/ipLoadbalancing/\{serviceName\}/refresh"} />

</Tab>
<Tab label="Terraform">

Frontends are managed with the `ovh_iploadbalancing_http_frontend` resource. Enable SSL termination by setting its `ssl` argument and attach the certificate with `default_ssl_id` (the resource also supports `hsts`). Once a frontend exists, you can manage its server farms with `ovh_iploadbalancing_http_farm` and `ovh_iploadbalancing_http_farm_server`. Deploy the staged configuration with the `ovh_iploadbalancing_refresh` resource.

</Tab>
</Tabs>

{/* CP-STEPS-END:attach-frontend */}

### Choose a cipher profile <a name="cipher-profile"></a>

The cipher profile controls which TLS versions and cipher suites the frontends of your service negotiate with clients. It is a single setting for the whole service, not a choice made per certificate or per frontend. Choose the profile that matches your client compatibility requirements.

{/* CP-STEPS-START:cipher-profile */}

| Profile | Setting | Effect |
|---|---|---|
| `Modern (TLS 1.3)` | Restricts negotiation to TLS 1.3. | Strongest security. Clients that do not support TLS 1.3 cannot connect. |
| `Intermediate (TLS 1.2+)` | Allows TLS 1.2 and above. | Recommended default. Broad client support while excluding legacy protocols. |

In the <ManagerLink to="/">OVHcloud Console</ManagerLink>, the cipher profile is a single setting for the whole service: it is not chosen when adding a certificate or per frontend. Open the <code className="action">SSL</code> tab and, in the **SSL/TLS Configuration** section, select the profile from the **Cipher Profile** drop-down list. The change is saved as soon as you select a profile. If the **Deployment** field of the <code className="action">Overview</code> tab then shows pending changes, click <code className="action">Apply N changes</code> to deploy them.

> [!TIP]
> Use `Intermediate (TLS 1.2+)` unless you control every client connecting to your service. Switching to `Modern (TLS 1.3)` can break connectivity for older browsers, libraries, and embedded clients.

{/* CP-STEPS-END:cipher-profile */}

### Limitations <a name="limitations"></a>

The following constraints apply when configuring certificates.

| Limitation | Details |
|---|---|
| SSL termination scope | SSL termination is configured on HTTP/HTTPS frontends. TCP frontends pass traffic through without termination. |
| Free certificate prerequisite | A free certificate can only be ordered once the chosen domain resolves to your Load Balancer service. |

### Troubleshooting <a name="troubleshooting"></a>

The table below covers the most common problems encountered when configuring certificates.

{/* CP-STEPS-START:troubleshooting */}

| Issue | Possible cause | Solution |
|---|---|---|
| Free certificate order fails or stays pending | The domain does not resolve to the Load Balancer. | Verify the DNS records point to your Load Balancer, then re-order. Check the <code className="action">Operations</code> tab or the task API for the error. |
| Certificate not used by clients | The certificate is not attached to the frontend, or the configuration was not applied. | Select the certificate in the **TLS Certificate** field of the HTTPS frontend, then apply the configuration. |
| Custom certificate rejected | Mismatched certificate and private key, or a missing intermediate chain. | Confirm the key matches the certificate and include the full chain. |
| Older clients cannot connect | The cipher profile is set to `Modern (TLS 1.3)`. | In the <code className="action">SSL</code> tab, switch the **Cipher Profile** to `Intermediate (TLS 1.2+)` and apply any pending changes. |

{/* CP-STEPS-END:troubleshooting */}
