## Objective

The [Bring Your Own IP (BYOIP)](/links/network/byoip) feature allows you to use IPv4 and IPv6 address ranges that you already own, as Additional IPs directly on the OVHcloud network and products.

- **IPv4 ranges** are imported in the form of /24 IP blocks, and behave like a regular OVHcloud [Additional IP](/links/bare-metal/ip) block product.
- **IPv6 ranges** are imported as a single range. You then create /56 IP blocks inside it, which behave like Additional IPv6 blocks.

### Your IP range must be in a supported RIR <a name="supportedrir"></a>

A [Regional Internet registry](https://en.wikipedia.org/wiki/Regional_Internet_registry) (RIR) is an organization that manages IP addresses in a given region.

You need to own (see below) a public IPv4 or IPv6 block with one of the following RIRs:

- [ARIN](https://www.arin.net/)
- [RIPE](https://www.ripe.net/)
- [APNIC](https://www.apnic.net/) (support for National Internet Registries - NIRs - is experimental at the moment)

The WHOIS record for the provided public IP block **must precisely match the desired range**. Selecting a parent or child IP block will leave you unable to use that range.

You can use ARIN, RIPE or APNIC IP blocks in any OVHcloud region.

To be considered as a valid owned block, an imported **IPv4** block must be one of the following types:

| ARIN (object *Network type*) | RIPE (object *status*) | APNIC (object *status*) |
| :--- | :--- | :--- |
| &bull; Direct Allocation <br/>&bull; Direct Assignment <br/>&bull; Reallocated <br/>&bull; Reassigned  |  &bull; ALLOCATED PA <br/>&bull; LIR-PARTITIONED PA  <br/>&bull; SUB-ALLOCATED PA  <br/>&bull; ASSIGNED PA  <br/>&bull; ASSIGNED PI  <br/>&bull; LEGACY   |  &bull; Allocated-Portable <br/>&bull; Allocated-Non-Portable <br/>&bull; Assigned-Portable <br/>&bull; Assigned-Non-Portable  |
| **For more information:** <br/>&bull; [Using WhoIs - Network](https://www.arin.net/resources/registry/whois/#network) <br/>&bull; [Reporting Reassignments](https://www.arin.net/resources/registry/reassignments/) | **For more information:** <br/>[Description of the INETNUM Object](https://docs.db.ripe.net/RPSL-Object-Types/Descriptions-of-Primary-Objects/#description-of-the-inetnum-object) |  **For more information:** <br/>&bull; [INETNUM Quick Guide](https://www.apnic.net/manage-ip/using-whois/guide/inetnum/) <br/>&bull; [Recording network assignments](https://www.apnic.net/manage-ip/using-whois/updating-whois/network-assignments/) |

An imported **IPv6** block must be one of the following types. The ARIN and APNIC types are the same as for IPv4. The RIPE types are the statuses of the *inet6num* object, which differ from those of the *inetnum* object.

| ARIN (object *Network type*) | RIPE (object *status*) | APNIC (object *status*) |
| :--- | :--- | :--- |
| &bull; Direct Allocation <br/>&bull; Direct Assignment <br/>&bull; Reallocated <br/>&bull; Reassigned  |  &bull; ALLOCATED-BY-RIR <br/>&bull; ALLOCATED-BY-LIR  <br/>&bull; AGGREGATED-BY-LIR  <br/>&bull; ASSIGNED  <br/>&bull; ASSIGNED PI  |  &bull; Allocated-Portable <br/>&bull; Allocated-Non-Portable <br/>&bull; Assigned-Portable <br/>&bull; Assigned-Non-Portable  |
| **For more information:** <br/>&bull; [Using WhoIs - Network](https://www.arin.net/resources/registry/whois/#network) <br/>&bull; [Reporting Reassignments](https://www.arin.net/resources/registry/reassignments/) | **For more information:** <br/>[Description of the INET6NUM Object](https://docs.db.ripe.net/RPSL-Object-Types/Descriptions-of-Primary-Objects/#description-of-the-inet6num-object) |  **For more information:** <br/>&bull; [INETNUM Quick Guide](https://www.apnic.net/manage-ip/using-whois/guide/inetnum/) <br/>&bull; [Recording network assignments](https://www.apnic.net/manage-ip/using-whois/updating-whois/network-assignments/) |

RIPE IPv6 blocks with the *ASSIGNED ANYCAST* status are not accepted, as BYOIP does not support anycast.

### Your IP range must have a supported size <a name="supportedsize"></a>

**IPv4**

We accept IPv4 blocks from size /24 up to size /19. Below, is the number of /24 blocks you will receive from the imported range:

|CIDR|Number of /24 blocks|
|---|---|
| /24 | 1 |
| /23 | 2 |
| /22 | 4 |
| /21 | 8 |
| /20 | 16 |
| /19 | 32 |

**IPv6**

We accept IPv6 blocks from size /48 up to size /32. The prefix length must be a multiple of 4 (/32, /36, /40, /44 or /48).

No IP block is created when an IPv6 range is delivered. You create /56 blocks inside the imported range yourself, one by one (see [How to manage the IP blocks of an IPv6 range](#ipv6-blocks)). Below, is the number of /56 blocks that each range size can hold:

|CIDR|Number of /56 blocks in the range|
|---|---|
| /48 | 256 |
| /44 | 4,096 |
| /40 | 65,536 |
| /36 | 1,048,576 |
| /32 | 16,777,216 |

### You must not exceed the import quotas <a name="quotas"></a>

The following quotas apply to every OVHcloud account:

- **Imported ranges:** you can import up to 5 IPv6 ranges per region.
- **IPv6 blocks:** you can create up to 80 /56 blocks in each imported IPv6 range.

### Your IP range is not in use on the Internet <a name="notinuseontheinternet"></a>

The range should not be announced or in use on the Internet (no announcement in terms of Border Gateway Protocol (BGP) on at least one public network). If the range is announced elsewhere, OVHcloud cannot guarantee that the service works or provide support for it.

### Your IP/AS have a clean reputation <a name="cleanipreputation"></a>

We may refuse IP ranges or AS numbers with a bad reputation, and we reserve the right to stop announcing them if their reputation has a negative impact on OVHcloud's reputation.

### You need to choose a region <a name="choosearegion"></a>

A region can be viewed as a list of datacenters where an IP can be used.

You will need to choose one region where your IP will be used. Once the delivery is done, you will be able to move any block obtained from the imported range to any OVHcloud service in the same region as the one chosen at order time.

The list of available regions is displayed on the [Bring Your Own IP product page](/links/network/byoip).

### You must prove ownership of the IP range <a name="proveownershipip"></a>

To prove that you own the range, add the token displayed in the order form to the public whois object of your range, from your RIR's web portal.

- For RIPE, edit the **descr** field of the **inetnum** object (IPv4) or of the **inet6num** object (IPv6).
- For ARIN, edit the **Public Comments** field of the **Network** object.
- For APNIC, edit the **remarks** field of the **inetnum** object (IPv4) or of the **inet6num** object (IPv6).

The token needs to appear in the description field (see above) of the whois object, in a dedicated line. Other lines may be present, as long as the token is present in its own dedicated line in the description. The token must be added before placing the order, and must not be removed until the end of the delivery process.

### You must prove ownership of the AS number (required only if you provide an AS number) <a name="proveownershipas"></a>

To prove that you are the owner of the AS number, you will be required to reuse the same token previously used to prove ownership of the IP range, and insert it into the public whois object corresponding to the AS number. This will be done via the web portal of the RIR managing your AS number. This token is displayed in the order form (it may also be found directly in the OVHcloud Control Panel, in the IP section).

- For RIPE, edit the **descr** field of the **aut-num** object of the AS number.
- For ARIN, edit the **Public Comments** field of the **ASN** object.
- For APNIC, edit the **remarks** field of **aut-num** object.

Follow the same rules as for the IP range: the token must be on its own line, and must stay in place until delivery is complete.

### You have to allow OVHcloud to announce the IP range <a name="announceip"></a>

On the RIR where the IP range is registered, you will need to create a **route object** (IPv4) or a **route6 object** (IPv6) for it (matching exactly the IP range), with the OVHcloud **AS number** ("AS16276") or your own AS number in the **origin** field of the object.

For more information on route objects, refer to your RIR's documentation:

- RIPE - [Managing Route Objects](https://docs.db.ripe.net/Authorisation/Protection-of-Route-Object-Space/)
- ARIN - [Submitting Routing Information](https://www.arin.net/resources/manage/irr/#submitting-routing-information)
- APNIC - [Creating Route Objects](https://www.apnic.net/manage-ip/using-whois/guide/creating-route-objects/)

> [!TIP]
> We also recommend creating an RPKI ROA (Route Origin Authorisation) for your range, with the same origin AS. OVHcloud does not check ROAs at the moment.

:::warning
If your imported IP block is already advertised on the Internet from sites other than OVHcloud (multihoming case), you risk packet loss or other routing issues. We will therefore not be able to guarantee connectivity to OVHcloud services with your imported IP block.

:::

### How to use the product

**IPv4 ranges**

The imported IPs will behave like the current Additional IP product. An imported IPv4 range will be split into /24 blocks that will be movable to any service in the same region.

To activate the announcement of your imported IP range on the Internet, assign one of your blocks to an eligible product via the Control Panel or the OVHcloud API.

During the delivery, we will create ARPA zones on our DNS servers and any reverse DNS modification via the OVHcloud Control Panel/API will be applied on them. However, these modifications will be visible to the public when our DNS servers receive delegations of the ARPA zones by the RIR. (This is optional, if you want to continue managing your reverse DNS on your own, you can).

**IPv6 ranges**

The /56 blocks that you create in an imported IPv6 range behave like Additional IPv6 blocks. Like Additional IPv6, they can only be used with a [vRack](/links/network/vrack) at the moment: more services will become eligible as they support Additional IPv6. To route a /56 block to your vRack, follow our guide on [configuring an Additional IPv6 block in a vRack](/guides/bare-metal-cloud/dedicated-servers/configure-ipv6-in-vrack).

Reverse DNS is not available for IPv6 ranges: OVHcloud does not host any ip6.arpa zone for imported IPv6 ranges. Keep managing the reverse DNS of your IPv6 range with your current DNS provider.

:::warning
Some operations available on the Additional IP product will not be available on the BYOIP product.

For example, you will not be able to customize your blocks' WHOIS via the OVHcloud Control Panel/API, because OVHcloud does not own them.

You can only edit the reverse DNS of an IPv4 range in the OVHcloud Control Panel or API once your RIR has delegated its ARPA zone to our DNS servers.

:::

### How to manage the IP blocks of an IPv6 range <a name="ipv6-blocks"></a>

An imported IPv6 range does not contain any IP block when it is delivered. Create /56 blocks inside it, within the limit of 80 blocks per imported range. A new block is created in the parking area: route it to your vRack to use it.

To create a /56 block, follow these steps:

<Tabs>
  <Tab label="Via the OVHcloud Control Panel">
    1. Open the <code className="action">BYOIP Ranges</code> tab of the IP addresses page.
    2. Click the <code className="action">⋮</code> button to the right of your IPv6 range, then select <code className="action">View IP blocks</code>.
    3. Click <code className="action">Create IP Block</code>.
    4. Enter the first address of the /56 block you want to create. The /56 prefix length is added automatically. The block must fall within your imported range and must not overlap an existing block.
    5. Click <code className="action">Create IP block</code>.
  </Tab>
  <Tab label="Via the OVHcloud API">
    <Api version="v1" section="/ip" method="POST" route={"/ip/service/\{serviceName\}/bringYourOwnIp/subRange"} />

    Use the following parameters:

    - serviceName: the internal name of your BYOIP service.
    - ip: the /56 block to create, in CIDR notation.

    To list the blocks of an imported range, use the following API call:

### Range slicing (IPv4 only) <a name="range-slicing"></a>

Any imported IPv4 block can be further split into smaller blocks and/or individual addresses. IPv6 ranges cannot be sliced or aggregated: create /56 blocks instead (see [How to manage the IP blocks of an IPv6 range](#ipv6-blocks)).

:::warning
To be able to slice/merge an existing IP block, it must be unused (i.e. in the parking area) and there must not be any pending task associated with it (e.g. no pending move operation).

:::

The slice and aggregate actions apply to the IP blocks of an imported IPv4 range, not to the imported range itself.

To slice your BYOIP block, follow these steps:

<Tabs>
  <Tab label="Via the OVHcloud Control Panel">
    1. Open the <code className="action">BYOIP Ranges</code> tab of the IP addresses page.
    2. Click the <code className="action">⋮</code> button to the right of your IPv4 range, then select <code className="action">View IP blocks</code>.
    3. Click the <code className="action">⋮</code> button to the right of the block you want to slice, then select <code className="action">Slice into blocks</code>.
    4. In the **Split size** list, select the size of the child blocks.
    5. Review the resulting blocks, then click <code className="action">Slice IP block</code>.
  </Tab>
  <Tab label="Via the OVHcloud API">
    <Api version="v1" section="/ip" method="POST" route={"/ip/\{ip\}/bringYourOwnIp/slice"} />

    Use the following parameters:

    - ip: the IP block you want to slice, in CIDR notation.
    - slicingSize: the resulting size of the sliced blocks, expressed as a network prefix size, in bits. For example if you want to slice a /24 block into 2 smaller blocks of size /25, you should enter the value "25".

    :::info
    This API call is asynchronous, the newly created blocks are made available shortly after the call. They will be usable as any other Additional IP block or individual address.
    :::

    You can preview the resulting blocks that would be created for each block size, by using the following API call:

    <Api version="v1" section="/ip" method="GET" route={"/ip/\{ip\}/bringYourOwnIp/slice"} />

    Use the following parameters:

    - ip: the IP block you want to slice, in CIDR notation.
  </Tab>
</Tabs>

To aggregate several child blocks into a parent block, follow these steps:

**Limitations**:

- Configuration elements associated to individual IP addresses (/32) such as firewall rules or reverse DNS entries will be kept after slicing/merging operations.
- Slice/Aggregate API tasks cannot be followed up by the asynchronous task number returned by API, as associated IP objects will be destroyed in the slice/aggregate process.
- The listing of IP addresses and blocks returned by API is ordered by network prefix size. We are working to provide a solution to list IPs by numerical order.
- Once sliced, smaller blocks are not movable outside the region chosen during the order of the product.
- Moving a /24 block across French regions is not supported if it has been reaggregated from a previous slicing.

## FAQ

### Is it possible to import an IPv6 range?

Yes. You can import IPv6 ranges from /48 to /32, with a prefix length that is a multiple of 4. See [Your IP range must have a supported size](#supportedsize).

### Is it possible to import an IP range lower than a /24 (IPv4) or a /48 (IPv6)?

No, the minimum accepted size is a /24 for IPv4 and a /48 for IPv6.

### Is it possible to import an IP range bigger than a /19 (IPv4) or a /32 (IPv6)?

Not at the moment, but feel free to contact us to discuss this.

### Is splitting the imported /24 into smaller block size (/25, /26, /27, /28, /29, /30) or into /32 supported?

Yes, see the [Range slicing](#range-slicing) section for more details.

### Can I create IPv6 blocks of another size than /56?

Not at the moment. /56 is the only size supported by vRack and by the Additional IPv6 product.

### Can I import an IP and an AS number that are not in the same RIR?

Yes.

### Can I import an IP range or AS number managed by AFRINIC/LACNIC?

Not for the moment.

### Is it possible to use an IP range on more than one region?

No, an IP range must be used in only one region.

### Is changing the region of an imported IP range possible?

It is not possible to change the region of an imported IP range. To achieve this you would have to release the product and purchase it again.

However, if you have chosen the Gravelines, Roubaix or Strasbourg region at the time of the order and if you ordered the service after January 1st, 2023, you will be able to move your **/24** IPv4 blocks across those 3 regions (and only those 3 regions). This exception does not apply to IPv6 ranges.

As mentioned in the range slicing limitations, this is only available if the block you want to move was **not reaggregated** following a previous slicing.

### How will I know which OVHcloud DNS servers will handle the ARPA zone for my imported IP?

Their names will be communicated in the delivery email. This only applies to IPv4 ranges: OVHcloud does not host ARPA zones for IPv6 ranges.

### Can I order the service while I still have my IP range announced from another site?

Yes, but once the BYOIP service has been delivered, you must immediately cancel the announcement from the other site, as you risk connectivity issues with any services hosted at OVHcloud. In this case, OVHcloud cannot be held responsible.
