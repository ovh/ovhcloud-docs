## Overview

This guide provides instructions for configuring access rights on OVHcloud IAM to manage permissions for various components of Logs Data Platform. It will give you the best practices to handle the rights given to your users and will ensure that you can replicate the functionality of roles and permissions with the more advanced system of policies. This guide will use features explained in the [IAM documentation](/guides/account-and-service-management/account-information/iam-policy-ui). It is therefore recommended to read it before reading this guide.

## Requirements

- An [OVHcloud account](/guides/account-and-service-management/account-information/ovhcloud-account-creation)
- A Logs Data Platform Account With [IAM enabled](/guides/manage-and-operate/observability/logs-data-platform/iam-presentation-faq)

[[cpnav:iam-identities-console|en]]

## Policies and identities

This guide leverages [local users](/guides/account-and-service-management/account-information/ovhcloud-users-management) to explain how you can share resources with another user. The policies created can be applied to any OVHcloud identities through the OVHcloud API. You can use these policies to share data with a local user, another OVHcloud user account or an OAuth client. You can refer to the specific [IAM Policies with API guide](/guides/account-and-service-management/account-information/iam-policies-api) to re-create all these policies with the API.

The identity will see a new service listed in their Logs Data Platform. This service contains the shared Logs Data Platform items. To ensure the recipient can see the shared items, we must share a view of the service with them.

## Access Rights Management

This section details how to configure local user/identity groups and policies to replicate the behavior of the legacy role system.

### Create a group for local users

{/* CP-STEPS-START:create-group-local-users */}

By default, the least privileged group available for local users is read-only over all the products of your account. If you would like to have an even more restricted account able to read only shared data from your Logs Data Platform, we advise you to create a group with the role **None** and attach your local users to it. Navigate to <code className="action">Identity and Access Management</code> > <code className="action">Identities</code> > <code className="action">User groups</code> in the <ManagerLink to="/beta/#/iam/identities/groups">OVHcloud Console</ManagerLink> and click <code className="action">Create a group</code> to create such a group.

<img className="thumbnail" alt="Create a group panel with the Name, Role and Description fields, the None role selected" src="/images/manage-and-operate/observability/logs-data-platform/iam-access-management/console/create_group.png" loading="lazy" />

You can then create a policy with the basic rights to access the OVHcloud Console and attach it to the group. All your local users will be able to connect to the OVHcloud Console. Navigate to <code className="action">Identity and Access Management</code> > <code className="action">Policies</code> > <code className="action">My policies</code> and click <code className="action">Create a policy</code> to create this policy. To attach it to the user group, select the group on the <code className="action">Groups</code> tab of the **Identities** section.

<img className="thumbnail" alt="Create a policy form with the Policy information section and the Identities Groups tab" src="/images/manage-and-operate/observability/logs-data-platform/iam-access-management/console/basic_policy_1.png" loading="lazy" />

After attaching the group, follow the instructions from our guide: [Creating an IAM policy to allow users access to the OVHcloud Control Panel](/guides/account-and-service-management/account-information/iam-control-panel-access).

Once the group is configured, you can then create the local users.

{/* CP-STEPS-END:create-group-local-users */}

### Create a local user

{/* CP-STEPS-START:create-local-user */}

Creating a local user is fully documented in the [dedicated documentation](/guides/account-and-service-management/account-information/ovhcloud-users-management). Remember to attach the user to the group by selecting it in the **Main group** field of the **Create a local user** panel.

<img className="thumbnail" alt="Create a local user panel with the Main group and Additional groups fields" src="/images/manage-and-operate/observability/logs-data-platform/iam-access-management/console/create_user.png" loading="lazy" />

{/* CP-STEPS-END:create-local-user */}

### Create a policy for the service

{/* CP-STEPS-START:create-policy-service */}

You now need to create a policy in order to allow the local user to see the Logs Data Platform service inside the OVHcloud Console. The goal here is to have access to the service only but without any sub-resources visible (i.e. no streams, dashboards, indices, aliases or OpenSearch Dashboards instances). Navigate to <code className="action">Identity and Access Management</code> > <code className="action">Policies</code> > <code className="action">My policies</code> in the <ManagerLink to="/beta/#/iam/policies/my-policies">OVHcloud Console</ManagerLink> and click <code className="action">Create a policy</code> to create this policy.

Add the local user to your policy on the <code className="action">Users</code> tab of the **Identities** section. Then select the **Logs Data Platform: Service** product type to list your services in the **Resources** drop-down list and display the actions of this product type in the **Actions** section, in a list headed **ldp**.

<img className="thumbnail" alt="Create a policy form with a local user selected on the Identities Users tab" src="/images/manage-and-operate/observability/logs-data-platform/iam-access-management/console/create_policy_service_1.png" loading="lazy" />

The policy can then allow read-only access to the chosen service. Users need at least these basic read actions to see the Logs Data Platform service in the OVHcloud Console. The minimal set of actions, all in the **READ** category of the **ldp** list, is listed below:

```yaml
- ldp:apiovh:cluster/get
- ldp:apiovh:cluster/retention/get
- ldp:apiovh:encryptionKey/get
- ldp:apiovh:get
- ldp:apiovh:input/get
- ldp:apiovh:metrics/get
- ldp:apiovh:role/get
- ldp:apiovh:serviceInfos/get
- ldp:apiovh:services/form/get
- ldp:apiovh:services/get
- ldp:apiovh:token/get
- ldp:apiovh:url/get
```

<img className="thumbnail" alt="Actions section with the READ category of the ldp list selected" src="/images/manage-and-operate/observability/logs-data-platform/iam-access-management/console/create_policy_service_2.png" loading="lazy" />

Once the policy is attached to the identity, the users will see the new service in their OVHcloud Console, but with no items available.

{/* CP-STEPS-END:create-policy-service */}

### Create a sub resources group

All the items created by a Logs Data Platform (i.e. streams, dashboards, etc.) are materialized as sub-resources of the LDP service.
One of the new features available thanks to IAM is the ability to group sub-resources in a **Resource group**. A Resource group can be used to share related resources and is a convenient way to groups items that are supposed to be used together. For example: a stream and its related dashboard, an alias and a OpenSearch Dashboard to explore it, an alias with all the streams attached to it. This feature is a good way to completely isolate sub-resources and make sure you don't have to handle them one by one over all your policies.

{/* CP-STEPS-START:create-sub-resources-group */}

To create a resource group, navigate to <code className="action">Identity and Access Management</code> > <code className="action">Policies</code> > <code className="action">Resource groups</code> in the <ManagerLink to="/beta/#/iam/policies/resource-groups">OVHcloud Console</ManagerLink> and click <code className="action">Create a resource group</code>.

<img className="thumbnail" alt="Create a resource group panel with the Name, Product types and Resources fields" src="/images/manage-and-operate/observability/logs-data-platform/iam-access-management/console/create_rg.png" loading="lazy" />

You need to select the product type (**Logs Data Platform: Dashboards**, **Logs Data Platform: Data stream**, **Logs Data Platform: Alias**, **Logs Data Platform: Index**, **Logs Data Platform: OpenSearch Dashboards**) in the **Product types** field and then select the specific resource you want to share in the **Resources** field.

{/* CP-STEPS-END:create-sub-resources-group */}

### Create a policy for the sub resources

{/* CP-STEPS-START:create-policy-sub-resources */}

This policy is the one you need to effectively replicate the legacy roles' permissions. You will attach OVHcloud API rights and backend (Graylog, OpenSearch) rights to allow identities to see the items in their shared service and interact with them in the corresponding Web UIs and APIs. Again, navigate to <code className="action">Identity and Access Management</code> > <code className="action">Policies</code> > <code className="action">My policies</code> in the <ManagerLink to="/beta/#/iam/policies/my-policies">OVHcloud Console</ManagerLink> to create a policy.

Similar to the previous policy, you need to add your local user, and you need to select the product type of your resource or sub-resource if you want to enable the actions selection panel for these specific sub-resources. In the **Actions** section, each selected product type has its own list of actions, headed by its technical name (**ldp/dashboard**, **ldp/stream**, **ldp/index** or **ldp/osd**).

<img className="thumbnail" alt="Four Logs Data Platform product types selected and a data stream in Resources" src="/images/manage-and-operate/observability/logs-data-platform/iam-access-management/console/policy_sub_product_types.png" loading="lazy" />

:::warning

Do not add a Logs Data Platform service to this policy. If you do so it will transitively give access to all sub-resources of this service (ie all LDP items) to the local users/identities or groups attached to the policy. The previous service policy has been created to prevent this behaviour.

:::


You can mix resource groups and specific resources in the same policy. All actions attached to the policy will then be attached to all related sub-resources.
You have several actions for each sub-resource type. For brevity, this guide will not detail all the actions available for all the items.

Here are some use cases of several rights which can all be together in one policy showcasing the complexity enabled by IAM policies. Actions starting with **ldp:apiovh** are actions related to OVHcloud APIs (thus the OVHcloud Console). The other actions are related to their specific backend: Graylog or OpenSearch.

### Go further with local users

Local users are useful for generating Personal Access Tokens (PATs). These tokens have a configurable expiration date and can be used to interact with both the OVHcloud APIs and the Logs Data Platform backends.

<Api version="v1" section="/me" method="POST" route={"/me/identity/user/\\{user\\}/token"} />

Thanks to OVHcloud IAM, you can then delegate the creation rights of sub-resources (indices, aliases) to your local user and interact with the backend APIs directly with these Personal Access Tokens.

The actions related to creating items are part of the service actions. You will need to add them to a policy to allow a user to create items with their PAT.

:::info

You don't need to allow any OVHcloud APIs action to allow a local user to interact with the Logs Data Platform backends (OpenSearch, Graylog, OpenSearch Dashboards) APIs.
Local users allow you to generate tokens that can only interact with the backend similarly to legacy Logs Data Platform tokens.

:::
