## Objective

By default, the Seald SDK stores its identity database only in volatile memory. When the user closes and reopens the browser, the identity is lost and must be retrieved again from SSKS. Enabling a persistent local database caches the identity in the browser's storage, encrypted by a key provided by your backend. This improves the user experience by removing the need for repeated identity retrieval.

## Requirements

- The `@seald-io/sdk` package installed. See the [Install the Seald SDK](/guides/public-cloud/seald/seald-install-sdk) guide.
- A backend capable of generating and storing a `databaseKey` per user session.
- An identity protection method (SSKS Password or SSKS 2MR) for the initial identity retrieval.

## Instructions

This section explains how to enable the persistent database and how to use a raw key for better performance.

### Step 1 — Generate a `databaseKey` on your backend

Your backend must generate a cryptographically random `databaseKey` and associate it with the user's session. Return it to the frontend on authentication.

```javascript
// Node.js backend example
const crypto = require('node:crypto')
const util = require('util')
const randomBytes = util.promisify(crypto.randomBytes)

const keyBuffer = await randomBytes(32) // or more
const databaseKey = keyBuffer.toString('hex') // any string is valid for databaseKey
```

Use a different `databaseKey` for each user session (not per device) so that each session has its own encrypted database. Changing the key on a new session means a new `databasePath` must also be used.

### Step 2 — Initialise the SDK with `databasePath` and `databaseKey`

Pass both `databaseKey` and a unique `databasePath` when constructing the SDK instance. Include the session ID in the path to ensure uniqueness per session:

```javascript
import SealdSDK from '@seald-io/sdk'

const seald = SealdSDK({
  appId,
  apiURL,
  databaseKey,                                    // provided by your backend
  databasePath: `seald-session-${sessionID}`      // unique per session
})
await seald.initialize()
```

The SDK automatically reads the encrypted database from the browser's local storage on startup and writes back any changes. No extra code is needed.

:::warning
If `databasePath` is set but `databaseKey` is omitted, the SDK uses a fixed encryption key derived from `appId`. This is insecure and must be avoided in production.
:::

### Step 3 — Use `databaseRawKey` for faster initialisation (optional)

The `databaseKey` is derived through scrypt on startup, which adds a few hundred milliseconds. If your backend stores 64 cryptographically random bytes (Base64-encoded), you can pass them as `databaseRawKey` to bypass derivation:

```javascript
// Backend: generate a raw key
const rawKeyBuffer = await randomBytes(64)
const databaseRawKey = rawKeyBuffer.toString('base64')
// Store databaseRawKey in the user's session

// Frontend
const seald = SealdSDK({
  appId,
  apiURL,
  databaseRawKey,                              // exactly 64 bytes, Base64-encoded
  databasePath: `seald-session-${sessionID}`
})
await seald.initialize()
```

> [!INFO]
> `databaseRawKey` must be exactly 64 bytes encoded in Base64, from a cryptographically secure random source. If in doubt, use `databaseKey` — it accepts any string and handles derivation automatically.
