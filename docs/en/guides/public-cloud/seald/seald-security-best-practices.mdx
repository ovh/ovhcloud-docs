## Objective

This guide summarises security best practices for applications that integrate the Seald SDK. It covers credential management, identity protection strategy, key handling, backend integration patterns, and staging versus production considerations.

## JWT and credential management

**Store JWTSecrets server-side only.** JWTs are signed on your backend and delivered to the frontend as short-lived tokens. Never expose `JWTSecret` values in client-side code, mobile binaries, or version control.

**Use short-lived JWTs with `jti`.** Set `jti` (a unique nonce, for example a UUID v4) on every JWT that should be single-use, particularly signup JWTs and anonymous encryption session JWTs. This prevents replay attacks. Omit `jti` only for the `getKeys` JWT used in anonymous encryption, because that request may be paginated across multiple API calls.

**Limit JWT scopes.** Create separate JWT secrets for each permission type rather than using `PERMISSION_ALL`. A leaked secret then has minimal blast radius.

**Rotate JWT secrets regularly.** Generate new secrets from the dashboard or API, update your backend configuration, and invalidate old secrets.

## Identity protection strategy

**Choose the right protection mode for your threat model:**

| Mode | Recovery | Trade-off |
|---|---|---|
| **SSKS Password** | User knows password | No "forgotten password" recovery without data loss |
| **SSKS 2MR** | Backend + SSKS challenge | Not strictly end-to-end: both parties compromised simultaneously reveals the identity |
| **Manual export** | Developer-controlled | Full responsibility for export security |

**Prefer SSKS 2MR for consumer applications** where account recovery is expected. The two-man rule limits the blast radius of a single-party compromise.

**Never send the raw SSKS password to your server.** If the user's SSKS password is also their application password, apply a client-side pre-derivation (for example, PBKDF2 or scrypt) before any server call. Your server should only ever receive a derived value, never the plaintext password.

**Normalise auth factor values.** Email addresses and phone numbers sent to the SSKS API must be normalised before use. An unnormalised value may result in challenge delivery failures or silent identity conflicts.

## Key material storage

**Generate `databaseKey` and `twoManRuleKey` with a cryptographically secure random source.** Use `crypto.randomBytes` (Node.js) or `crypto.getRandomValues` (browser). Never derive these values from user-visible data.

**Use `databaseRawKey` and `rawTwoManRuleKey` when performance matters.** These bypass scrypt derivation and require exactly 64 cryptographically random bytes encoded in Base64. If in doubt, use the non-raw variants.

**Rotate `databaseKey` per session.** Using the same `databaseKey` across all sessions increases the impact of a key leak. Issue a new key on each login and tie the `databasePath` to the session ID.

**Protect the reversibility private key offline.** If you use Seald's reversibility feature, store the private key on physically secure offline media (encrypted USB drive, hardware security module). Consider escrow with a trusted third party.

## Backend integration

**Authenticate all SSKS-related endpoints.** The endpoints that generate `sessionId` and `twoManRuleKey` must be behind your application's authentication layer. An unauthenticated call would allow an attacker to generate a SSKS session for an arbitrary user.

**Use independent authentication methods for SSKS and your backend.** The two-man rule security guarantee relies on SSKS and your backend having independent authentication paths. If both use the same SSO provider, a compromised SSO breaks the two-party isolation.

**Never let the backend see the challenge.** The SSKS challenge is sent directly to the user's email or phone. Your backend must never receive or log it. The user enters it in the frontend and passes it directly to the SDK.

**Validate the auth factor in the frontend before calling `saveIdentity`.** Display the email address or phone number that will be registered with SSKS so the user can confirm it matches their expectation. This prevents a server-side MITM attack where your backend registers the user under a different auth factor.

## Staging versus production

**Never use `fake_otp: true` in production.** This flag bypasses 2MR challenge delivery and would allow your backend to impersonate users. It is blocked in production environments and returns a `406 Not Acceptable` error if sent.

**Do not migrate staging data to production.** Staging data cannot be moved to production. Start fresh with a production account before handling real user data.

**Test the reversibility procedure on staging before going live.** The reversibility tool requires careful preparation of backend exports. Validate the full procedure on staging to identify gaps in your key material exports before you depend on it in production.

## Connector privacy

**Avoid using personal data as connector values.** Connectors are stored in clear text in the Seald database. Use an internal UUID or opaque identifier instead of email addresses or names.
