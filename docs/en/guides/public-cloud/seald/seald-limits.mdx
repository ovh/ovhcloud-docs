## Objective

This guide lists the technical limits, key format requirements, operational constraints, and known behaviours of the Seald SDK that are relevant to integration design.

## Key format requirements

The following parameters have strict format requirements. Passing values in the wrong format causes a runtime error.

| Parameter | Type | Format |
|---|---|---|
| `databaseRawKey` | SDK init | Base64-encoded string representing exactly **64 cryptographically random bytes** |
| `rawTwoManRuleKey` | SSKS 2MR | Base64-encoded string representing exactly **64 cryptographically random bytes** |
| `rawOverEncryptionKey` (GroupTMRTemporaryKey) | Group TMR | Base64-encoded string representing exactly **64 cryptographically random bytes** |
| `rawEncryptionKey` (SSKS Password) | SSKS Password | Base64-encoded string representing exactly **64 bytes** |
| `rawStorageKey` (SSKS Password) | SSKS Password | String, max **256 characters**, characters: `/A-Za-z0-9+\/=\-_@./` |
| `rawSymKey` (SymEncKey) | SymEncKey | Base64-encoded string representing exactly **64 cryptographically random bytes** |

Use `crypto.randomBytes(64).toString('base64')` in Node.js, or `seald.utils.generateB64EncodedSymKey()` where the method is available.

## Sub-identity limits

There is no hard limit on the number of sub-identities per user, but **having several dozen sub-identities noticeably degrades performance** for operations involving that user:

- Creating a new sub-identity takes longer.
- Encrypting for a user with many sub-identities takes longer.

**Recommendation:** Do not create a new sub-identity on every login. Cache the identity client-side using a persistent local database (`databasePath` + `databaseKey`), or reuse an identity retrieved from SSKS.

## JWT constraints

| Constraint | Value |
|---|---|
| Default JWT validity | **10 minutes** after `iat` (overridable with `exp`) |
| `jti` reuse | Not permitted — each `jti` value can only be used once |
| `iat` format | Unix timestamp in **seconds** (not milliseconds) |
| Maximum scopes | Must be a subset of the signing secret's permissions |

## SSKS constraints

| Constraint | Value / Behaviour |
|---|---|
| 2MR challenge validity | **6 hours** from delivery |
| Rate limiting | Applies after multiple failed `retrieveIdentity` attempts; error: `Request throttled, retry after {N}s` |
| Concurrent retrieval | Not supported — do not call `retrieveIdentity` for the same user on two devices simultaneously |
| `fake_otp` in production | **Blocked** — returns `406 Not Acceptable` |
| `full_forget` in production | **Blocked** |
| Email template validation | Up to **2 business days** in production; instant in staging |
| Default challenge sender | `no-reply@seald.io` (customisable, requires DNS changes) |

## Staging environment constraints

| Aspect | Staging | Production |
|---|---|---|
| Data persistence | Not guaranteed — may be reset without notice | Backed up regularly |
| High availability | No | Yes (replicated) |
| SLA | None | Per contract |
| `fake_otp` | Available | Blocked |
| `full_forget` | Available | Blocked |
| Data migration to production | **Not possible** | N/A |

## SymEncKey constraints

- SymEncKey is currently only available in the **JavaScript SDK** (browser and Node.js). It is not yet implemented in the Android, iOS, or Flutter SDKs.
- The `rawSecret` and `rawSymKey` values must remain secret from your server. Only the `symEncKeyId` (non-secret) and `sessionId` (non-secret) can be transmitted via your backend.

## Connector constraints

- Connector format: `${IDENTIFIER}@${APP_ID}`, type must always be `'AP'`.
- Connectors are stored in **clear text** in the Seald database. Do not use personal data (email addresses, names) as connector values.
- An identity can have multiple connectors.

## Encryption session cache

- The default cache is **in-memory only** and is scoped to a single SDK instance.
- The `localStorage` cache (`createLocalStorageEncryptionSessionCache`) requires a persistent local database (`databasePath` + `databaseKey`).
- Cache TTL of `0` (default) disables caching entirely. Set to `-1` for no expiry.
- Cleanup interval default is equal to `encryptionSessionCacheTTL`, with a minimum of 10 seconds. An entry may remain in storage for up to **twice** the TTL in the worst case.

## Proxy sessions

- Proxy sessions cannot be nested: a session cannot be used as a proxy to another proxy session.
- Group keys can be renewed; proxy session keys cannot.
