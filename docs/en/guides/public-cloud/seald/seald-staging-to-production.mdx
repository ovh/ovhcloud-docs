## Objective

This guide explains the key differences between the Seald staging and production environments, and describes the steps required to migrate your integration to production before going live with real user data.

:::danger
Data from the staging environment **cannot** be migrated to production. Create a production account and complete your integration there **before** handling any real confidential data.
:::

## Requirements

- A completed staging integration of the Seald SDK.
- A Seald production account. Contact [Seald](mailto:contact@seald.io) to request one.

## Instructions

This section describes the differences between environments, changes to apply in your code and backend, and validation steps.

### Step 1 — Understand the differences between staging and production

Review the following differences before switching environments.

| Aspect | Staging | Production |
|---|---|---|
| **Server deployment** | Single server, no high availability | Replicated, high availability, automatic failover |
| **Data persistence** | Not guaranteed — can be reset without notice | Backed up regularly to remote sites |
| **`fake_otp`** | Allowed — challenges are set to `'aaaaaaaa'` | Blocked — returns `406 Not Acceptable` |
| **`full_forget`** | Allowed in SSKS API | Blocked in SSKS API |
| **Email/SMS template validation** | Instant | Up to 2 business days |
| **SLA** | None | Covered by your contract |

:::warning
`fake_otp: true` allows your backend to bypass 2MR challenges, which breaks the end-to-end encryption guarantee. It is deliberately blocked in production. Ensure all test code that sets `fake_otp: true` is removed before going live.
:::

### Step 2 — Obtain production credentials

After your production account is created, retrieve from the Seald administration dashboard:

- `appId` — your application identifier.
- `apiURL` — the production API endpoint.
- `keyStorageURL` — the production SSKS endpoint.
- `ssksAppKey` — your backend's SSKS authentication key (if using 2MR). Generate it from the SSKS management page.
- New JWT secrets with the appropriate permissions (see [Generate and manage JWT secrets](/guides/public-cloud/seald/seald-jwt)).

### Step 3 — Update your application configuration

Replace staging credentials with production credentials in your environment configuration. Never hardcode credentials directly in source code:

```bash
# .env.production
SEALD_APP_ID=your-production-app-id
SEALD_API_URL=https://api.seald.io
SEALD_KEY_STORAGE_URL=https://ssks.seald.io
SEALD_SSKS_APP_KEY=your-production-ssks-app-key
SEALD_JWT_SECRET_ID=your-production-jwt-secret-id
SEALD_JWT_SECRET=your-production-jwt-secret
```

### Step 4 — Remove staging-only code

Search your codebase for the following patterns and remove or guard them with environment checks:

- `fake_otp: true` in any `challenge_send` request body.
- `full_forget: true` in any SSKS API call.
- Hardcoded challenge values (`'aaaaaaaa'`).

```javascript
// Before (staging only)
const result = await fetch(`${ssksUrl}/tmr/back/challenge_send`, {
  method: 'POST',
  body: JSON.stringify({ ..., fake_otp: true })
})

// After (production-safe)
const result = await fetch(`${ssksUrl}/tmr/back/challenge_send`, {
  method: 'POST',
  body: JSON.stringify({ ... })  // fake_otp omitted
})
```

### Step 5 — Validate email and SMS templates

If you use custom challenge email or SMS templates, submit them in the production dashboard and allow up to 2 business days for validation. Templates approved in staging are not automatically transferred to production — they must be recreated and revalidated.

### Step 6 — Verify your integration end-to-end

Before going live, perform a full end-to-end test in the production environment:

1. Create a test user identity with a production signup JWT.
2. Save the identity with SSKS Password or SSKS 2MR using real email/SMS delivery.
3. Retrieve the identity from a second session using the received challenge.
4. Encrypt and decrypt a file between two test identities.
5. Confirm all operations complete without errors.

> [!INFO]
> Run the reversibility procedure (`/sot-update` or your data-export flow) on staging first and verify it succeeds. Production data exports require Seald support involvement and may take time to arrange. It is strongly recommended to test the full reversibility procedure before going live.
