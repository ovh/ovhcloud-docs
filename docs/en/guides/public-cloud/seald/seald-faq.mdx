## Objective

This FAQ answers common questions about integrating the Seald SDK, covering identity management, key storage options, encryption behaviour, and environment differences.

## Identity and key storage

### What is SSKS?

SSKS (Seald SDK Key Storage) is a Seald-hosted service that stores encrypted Seald identities on behalf of your users. It does not store encryption keys in the clear — identities are encrypted before being sent to SSKS, using either the user's password (SSKS Password) or a two-man rule protocol (SSKS 2MR) that splits the decryption key between SSKS and your backend.

### Do users need one Seald identity per device?

Not necessarily. An identity (private key) can be retrieved from SSKS on any device. To avoid SSKS round-trips on every session, you can create a sub-identity for each device and cache it using a persistent local database. Creating many sub-identities (several dozen) for the same user degrades performance, so avoid creating a new one on every login.

### What is the difference between SSKS Password and SSKS 2MR?

| | SSKS Password | SSKS 2MR |
|---|---|---|
| **How it works** | Identity encrypted with a key derived from the user's password | Identity split between your backend (`twoManRuleKey`) and SSKS (`encryptedIdentity`) |
| **Recovery** | Only the user (with their password) can recover | Backend + SSKS challenge — user can recover even without their device |
| **Strictly E2E** | Yes | No — both parties compromised simultaneously exposes the identity |
| **Forgotten password** | Not recoverable without data loss | Recoverable via the email/SMS challenge |

### Can I change a user's email address or phone number used for SSKS 2MR?

Yes. Save the identity to the new auth factor first (which may require an authentication challenge), then delete the identity stored under the old auth factor via the SSKS server API. Always save the new one before deleting the old one to avoid identity loss.

### Can I use both SSKS Password and SSKS 2MR for the same user?

Yes. You can save the same identity (or different sub-identities) with both protection methods for the same user, giving them multiple recovery options.

## Encryption

### Can I encrypt data without a Seald identity?

Yes, using the Anonymous SDK (`AnonymousSDKBuilder`). This allows your backend or an unauthenticated frontend to encrypt data for users who have Seald identities. The encryption is authorised by backend-issued JWTs. Decryption still requires a full Seald identity on the recipient's side.

### What happens when I revoke a session recipient?

Revoking a recipient removes their ability to decrypt messages from the session going forward. They cannot decrypt existing messages they have already received and stored locally, but they cannot retrieve the session key again. Only the session creator (or another user with the `revoke` right) can revoke recipients.

### What is the difference between a group and an encryption session?

| | Group | Encryption session |
|---|---|---|
| **Membership** | Managed independently; members added/removed; key renewable | Set at creation; recipients added/revoked per-session |
| **Key renewal** | Supported (`renewGroupKey`) | Not supported (revoke and re-encrypt instead) |
| **Use case** | Long-lived access control (team, project) | Per-item access control (document, chat thread) |

### What is a proxy session?

A proxy session is an encryption session that is itself a recipient of other sessions. Instead of adding individual users as recipients to each session, you add the proxy session. All users who have access to the proxy session can then access all sessions it proxies. Proxy sessions cannot be nested (a proxy session cannot proxy another proxy session), and their keys cannot be renewed.

### What is a SymEncKey?

A SymEncKey allows a user to retrieve an encryption session without being a direct recipient — by proving knowledge of a shared secret (`rawSecret`/`rawSymKey` or `password`). It is useful for password-protected sharing links or QR code-based access. SymEncKey is currently only available in the JavaScript SDK (browser and Node.js).

## Staging and production

### What is the staging environment?

Staging is a development environment provided by Seald when you first create an account. It is functionally equivalent to production but runs on a single server with no high availability or data persistence guarantees. Seald may reset staging data at any time without notice.

### Can I migrate staging data to production?

No. Data created in the staging environment cannot be moved to production. Create a production account before handling any real user data.

### Why does my backend receive a `406` error from SSKS?

A `406 Not Acceptable` response from the SSKS API almost always means that `fake_otp: true` was sent to a production endpoint. `fake_otp` is only available in the staging environment. Remove `fake_otp` from all production code paths.

## Reversibility

### What is the reversibility tool?

The `@seald-io/reversibility-tools` package allows bulk decryption of all data encrypted with the Seald SDK, using exports from the Seald API and SSKS servers combined with key material from your own backend. It is designed for exceptional scenarios — migrating away from the SDK or recovering data in bulk — not for routine use.

### Which identity protection modes support reversibility?

SSKS 2MR supports reversibility: you can provide the `twoManRuleKey` values from your backend to decrypt user identities from the SSKS export. SSKS Password supports reversibility only if you store the passwords or derived raw keys server-side, which is not recommended. Manual identity export supports reversibility if you export and securely store identities.
