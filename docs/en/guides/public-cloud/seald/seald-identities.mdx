## Objective

This guide explains how to create and manage cryptographic identities with the Seald SDK. Each user is represented by one or more identities — private keys generated locally on the user's device. Sub-identities allow the same user to operate across multiple devices while sharing access to all their encrypted data.

## Requirements

- An active Seald account with an `appId`, `apiURL`, and `keyStorageURL`. Contact [Seald support](mailto:support@seald.io) to obtain these.
- The `@seald-io/sdk` package installed and initialised. See the [Install the Seald SDK](/guides/public-cloud/seald/seald-install-sdk) guide.
- A valid signup JWT issued by your backend. See the [Generate and manage JWT secrets](/guides/public-cloud/seald/seald-jwt) guide.

## Instructions

This section walks you through creating a first identity, adding sub-identities for additional devices, pre-generating keys to speed up identity creation, and exporting or importing identity data manually.

### Step 1 — Create a first identity

To create an identity for a new user, call `sdk.initiateIdentity` with a signup JWT generated by your backend:

```javascript
import SealdSDK from '@seald-io/sdk'

const seald = SealdSDK({ appId, apiURL })
await seald.initialize()

// Create the user's first Seald identity
await seald.initiateIdentity({ signupJWT: 'your-signup-jwt' })
```

The signup JWT must have the `PERMISSION_JOIN_TEAM` scope (value `3`). Each JWT should include a `jti` (unique nonce) so that it can only be used once.

> [!INFO]
> To associate a custom identifier (connector) with the identity — for example, an internal user ID — include the `connector_add` claim in the JWT. The connector format must be `${IDENTIFIER}@${APP_ID}` with type `AP`. You can also add a connector later by calling `sdk.pushJwt()`.

### Step 2 — Create a sub-identity for a new device

Once a user has a first identity, you can create sub-identities for additional devices. A sub-identity shares the same access rights as the main identity: anything encrypted for this user can be decrypted by any of their sub-identities.

```javascript
// An already-initialised SDK instance with an existing identity
const { subIdentity } = await seald.createSubIdentity()
// subIdentity is a Buffer — store it or protect it with SSKS
```

The returned `Buffer` is in the same format as `sdk.exportIdentity()`. You can import it into another SDK instance, or save it to SSKS using `ssksPassword.saveIdentity()` or `ssks2MR.saveIdentity()`.

:::warning
Having a very large number of sub-identities for the same user (several dozen) can slow down operations. For users who reconnect frequently or use many devices, prefer reusing an identity stored on SSKS rather than creating a new sub-identity at each login.
:::

### Step 3 — Pre-generate identity keys (optional)

Generating cryptographic keys can take several hundred milliseconds. You can pre-generate them in the background to speed up the next `createSubIdentity` call:

```javascript
// Pre-generate one key in the background
seald.preGenerateIdentityKeys(1)

// … perform other work …

// The next createSubIdentity call will be faster
const { subIdentity } = await seald.createSubIdentity()
```

### Step 4 — Export and import an identity manually

If you need to manage identity storage outside of SSKS, use `exportIdentity` and `importIdentity`:

```javascript
// Export the current identity as a Buffer
const identityBuffer = await seald.exportIdentity()

// Import a Buffer into a fresh SDK instance
const seald2 = SealdSDK({ appId, apiURL })
await seald2.initialize()
await seald2.importIdentity(identityBuffer)
```

:::danger
You are responsible for securing exported identity buffers. If an exported identity is compromised, all data encrypted for that user is at risk. Store exported identities encrypted and in access-controlled storage.
:::
