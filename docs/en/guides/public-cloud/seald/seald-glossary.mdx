## Objective

This glossary is a reference for all technical terms used across the Seald documentation. Consult it whenever you encounter an unfamiliar concept while integrating the Seald SDK.

For a high-level introduction to Seald, see the [Seald overview](/guides/public-cloud/seald/seald-overview). For installation instructions, see [Install the Seald SDK](/guides/public-cloud/seald/seald-install-sdk).

## Glossary

### SDK configuration

| Term | Definition |
|------|------------|
| **appId** | A UUID that uniquely identifies your Seald application. It is public and can safely be included in frontend code. You retrieve it from the Seald administration dashboard. |
| **apiURL** | The URL of the Seald API server. Required when targeting a staging environment; you can omit it in production because the SDK defaults to the production URL. |
| **keyStorageURL** | The URL of the SSKS server (see [SSKS](#identity-storage)). Required for staging environments; can be omitted in production. |
| **JWTSecretId** | The identifier of a JWT secret, used as the `iss` (issuer) field in signed tokens. It is public and can be included in frontend code. You retrieve it from the Seald administration dashboard. |
| **JWTSecret** | The secret value used to sign JWTs (HS256 algorithm). This value must be kept server-side only and must never be exposed in frontend code or client-side bundles. |

### Identity model

| Term | Definition |
|------|------------|
| **Seald identity** | A cryptographic private key generated locally on a user's device. It represents the user's ability to encrypt and decrypt data. All identities belonging to the same user are linked together in a cryptographic signature chain. |
| **sealdId** | The unique identifier of a Seald identity. You use it to designate recipients when creating or managing encryption sessions. |
| **Sub-identity** | An additional identity for the same user, typically one per device. It is created from an existing identity, can decrypt everything the parent identity can decrypt, and is linked to the parent via a cryptographic signature chain. |
| **Connector** | A custom application-level identifier attached to a Seald identity, using the format `${IDENTIFIER}@${APP_ID}`. Connectors allow your application to look up Seald identities using your own user IDs rather than `sealdId` values. |
| **signupJWT** | A short-lived JWT with scope `JOIN_TEAM` (permission `3`), generated by your backend and passed to `sdk.initiateIdentity()`. It authorises the creation of a new Seald identity for a user. |

### Identity storage

| Term | Definition |
|------|------------|
| **SSKS (Seald SDK Key Storage)** | Seald's managed server for securely storing encrypted user identities. It acts as a key escrow that cannot reconstruct identities on its own — the decryption material remains with the user or the application backend. |
| **Password protection** (`@seald-io/sdk-plugin-ssks-password`) | An identity storage mode in which the identity is encrypted with a derivative of the user's password and stored on SSKS. Password resets are not possible without permanent data loss. |
| **Two-man rule (2MR)** (`@seald-io/sdk-plugin-ssks-2mr`) | An identity storage mode in which the identity is split: one part (`twoManRuleKey`) is held by the application backend, and the other (`encryptedIdentity`) is held by SSKS. Neither party alone can reconstruct the identity. This mode enables password-less recovery flows. |
| **twoManRuleKey** | The secret key held by the application backend in 2MR mode. It must be at least 64 bytes of cryptographically random data. Use `rawTwoManRuleKey` to skip scrypt derivation. This value must never be exposed to SSKS. |
| **rawTwoManRuleKey** | A variant of `twoManRuleKey` that skips scrypt derivation (faster). It must be the Base64 encoding of exactly 64 cryptographically random bytes. |
| **authFactor** | A user identifier used to authenticate against SSKS in 2MR mode. Typically an email address (`type: 'EM'`) or a phone number (`type: 'SMS'`). The value must be normalised before use. |
| **challenge** | A one-time code sent to the user's `authFactor` (by email or SMS) during 2MR authentication. It is valid for 6 hours and must never be forwarded to the application backend. |
| **databaseKey** | A symmetric key generated and held by the application backend, used to encrypt the SDK's local persistent database in the browser or on the device. |
| **databaseRawKey** | A variant of `databaseKey` that skips scrypt derivation. It must be the Base64 encoding of exactly 64 cryptographically random bytes. |
| **Manual export/import** | A direct export of an identity as a Buffer via `sdk.exportIdentity()`, and the corresponding import via `sdk.importIdentity()`. The application is responsible for securing the exported buffer. |

### Encryption

| Term | Definition |
|------|------------|
| **Encryption session** | A shared symmetric key created by `sdk.createEncryptionSession()`. All messages and files encrypted with the same session share the same key and recipient list. Each session is identified by a `sessionId`. |
| **sessionId** | The unique identifier of an encryption session. It is not secret and can be stored in your application database to retrieve the session later. |
| **Recipient** | A user or group whose Seald identity is listed when creating or updating an encryption session. Only recipients can decrypt data encrypted with that session. |
| **encryptForSelf** | An option on `createEncryptionSession()` that defaults to `true`. When set to `false`, the current user's identity is not directly added as a recipient — useful when the user is already a member of a group that is itself a recipient. |
| **Rights** | Per-recipient permissions on an encryption session: `read` (can decrypt), `forward` (can add recipients), and `revoke` (can revoke recipients and close the session). By default, only the session creator holds `revoke` rights. |

### Groups

| Term | Definition |
|------|------------|
| **Group** | A named collection of Seald identities. You encrypt for the group once, and all current members can decrypt. Members can be added or removed, and the group key can be renewed after a sensitive member is removed. |
| **Group admin** | A group member with permission to add or remove members, change admin status, and renew the group key. |
| **renewGroupKey** | An operation that rotates the group's symmetric key. You should call it after removing a sensitive member to ensure they can no longer decrypt future data encrypted for the group. |

### JWT authorisation

| Term | Definition |
|------|------------|
| **JWT (JSON Web Token)** | An HS256-signed token generated by your backend and passed to SDK functions that require authorisation — such as identity creation, connector addition, and anonymous encryption. Scopes control which operations each token authorises. |
| **Scope** | A permission encoded in a JWT. Key scopes are: `3` = `JOIN_TEAM` (identity creation), `4` = `ADD_CONNECTOR` (add a connector to an identity), `0` = `ANONYMOUS_CREATE_SESSION`, `1` = `ANONYMOUS_FIND_KEYS`, and `5` = `ANONYMOUS_FIND_SYMENCKEY`. |
| **jti (JWT ID)** | A unique nonce included in each JWT, used to prevent replay attacks. It must be globally unique per token. |

### Advanced features

| Term | Definition |
|------|------------|
| **Anonymous SDK** (`@seald-io/sdk-anonymous`) | A package that allows a backend service to encrypt data without a Seald identity. It uses JWTs with anonymous scopes for authorisation. |
| **Proxy session** | An encryption session that is itself listed as a recipient of other sessions. Users who are members of the proxy session gain access to all proxied sessions. It is lighter than a group but its key cannot be renewed. |
| **TmrAccess (Two-Man Rule Access)** | A mechanism to grant a user access to an encryption session via a 2MR challenge (email or SMS), without requiring the user to have a Seald identity yet. |
| **SymEncKey (Symmetric Encryption Key)** | A mechanism to access an encryption session using a shared secret — a password or a raw key pair — without being a direct identity-based recipient. |
| **GroupTMRTemporaryKey** | A mechanism for a group admin to invite a user to join a group via a 2MR challenge, before the user has created a Seald identity. |
| **Reversibility tool** (`@seald-io/reversibility-tools`) | An npm package that allows bulk-decryption of all data stored in a Seald application, using exports provided by Seald support. |

### Environments

| Term | Definition |
|------|------------|
| **Staging** | A single-server test environment hosted at `dashboard.staging-0.seald.io`. It carries no SLA and no data persistence guarantee. It supports `fake_otp: true` for testing without sending real email or SMS challenges. |
| **Production** | A high-availability, replicated environment with regular backups. The `fake_otp` option is blocked in production. Contact Seald to create a production account. |
| **fake_otp** | A test feature available only in staging. When set to `true` in the SSKS backend API call, no challenge message is sent; the expected challenge value is fixed to `'aaaaaaaa'`. |
