## Objective

This guide explains how to protect a Seald SDK cryptographic identity with a password using the `@seald-io/sdk-plugin-ssks-password` plugin. The identity is encrypted with a key derived from the user's password and stored on the SSKS (Seald SDK Key Storage) server. Only a user who knows the password can retrieve their identity.

:::warning
A "forgotten password" reset is not possible with this method without data loss. If your application requires account recovery, use [SSKS 2MR identity protection](/guides/public-cloud/seald/seald-ssks-2mr) instead.
:::

## Requirements

- An active Seald account with an `appId`, `apiURL`, and `keyStorageURL`.
- The `@seald-io/sdk` and `@seald-io/sdk-plugin-ssks-password` packages installed. See the [Install the Seald SDK](/guides/public-cloud/seald/seald-install-sdk) guide.
- An initialised Seald SDK instance with an existing identity.

## Instructions

This section walks you through saving an identity with SSKS Password, retrieving it on a new session, and changing the password.

### Step 1 — Instantiate the SDK with the SSKS Password plugin

Pass the `SealdSDKPluginSSKSPassword` plugin at SDK construction time:

```javascript
import SealdSDK from '@seald-io/sdk'
import SealdSDKPluginSSKSPassword from '@seald-io/sdk-plugin-ssks-password'

const seald = SealdSDK({
  appId,
  apiURL,
  plugins: [SealdSDKPluginSSKSPassword(keyStorageURL)]
})
await seald.initialize()
```

### Step 2 — Create an identity and save it with a password

After calling `initiateIdentity`, save the identity to SSKS encrypted with the user's password:

```javascript
await seald.initiateIdentity({ signupJWT: 'your-signup-jwt' })

await seald.ssksPassword.saveIdentity({
  userId: 'unique-user-id',     // a stable, unique string for this user
  password: 'user-secret-password'
})
```

> [!INFO]
> If you want to save a sub-identity rather than the current instance's identity, pass the `identity` argument:
> ```javascript
> const { identity: subIdentity } = await seald.createSubIdentity()
> await seald.ssksPassword.saveIdentity({
>   userId: 'unique-user-id',
>   password: 'user-secret-password',
>   identity: subIdentity
> })
> ```

### Step 3 — Retrieve an identity on a new session

On subsequent logins, retrieve the identity from SSKS using the same `userId` and `password`:

```javascript
const seald = SealdSDK({
  appId,
  apiURL,
  plugins: [SealdSDKPluginSSKSPassword(keyStorageURL)]
})
await seald.initialize()

await seald.ssksPassword.retrieveIdentity({
  userId: 'unique-user-id',
  password: 'user-secret-password'
})
// The SDK is now ready to encrypt and decrypt
```

> [!INFO]
> If the password is entered incorrectly several times in a row, the SSKS server applies rate limiting. In that case you receive the error message: `Request throttled, retry after {N}s`.

:::warning
Avoid calling `ssksPassword.retrieveIdentity` for the same user on multiple devices at exactly the same instant (for example in automated tests). Wait for one retrieval to complete before starting another.
:::

### Step 4 — Change the password

When a user changes their password, call `changeIdentityPassword` to re-encrypt the identity under the new password and remove the old one:

```javascript
await seald.ssksPassword.retrieveIdentity({
  userId: 'unique-user-id',
  password: 'old-password'
})

await seald.ssksPassword.changeIdentityPassword({
  userId: 'unique-user-id',
  currentPassword: 'old-password',
  newPassword: 'new-password'
})
```

> [!INFO]
> **Advanced — custom key derivation:** If your application derives its own encryption keys (for example with PBKDF2), you can bypass the default scrypt derivation by passing `rawEncryptionKey` (a Base64-encoded 64-byte random buffer) and `rawStorageKey` (a unique string, up to 256 characters, using `/A-Za-z0-9+\/=\-_@./`) instead of `password`:
> ```javascript
> await seald.ssksPassword.saveIdentity({
>   userId,
>   rawEncryptionKey: derivedKey,   // 64 bytes, Base64-encoded — must stay client-side only
>   rawStorageKey: serverStoredKey  // non-secret, unique identifier
> })
> ```

:::warning
If you use the same password for both SSKS protection and application authentication, **never send the raw password to your server**. Derive it client-side (with scrypt or PBKDF2) before any server call, so your server only sees a derived value and can never reconstruct the SSKS encryption key.
:::
