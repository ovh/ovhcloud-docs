## Objectives

OpenSearch is an open-source search and analytics suite used for a variety of use cases related to log and data analysis, real-time monitoring, and application searching. Forked from Elasticsearch and Kibana, OpenSearch offers users a highly-scalable system with easy access to large amounts of data and integrated metrics. 

This guide explains how to successfully configure a Public Cloud Databases for an OpenSearch service in the OVHcloud Control Panel. 

## Requirements

- a [Public Cloud project](/links/public-cloud/public-cloud) in your OVHcloud account

## Instructions

### Subscribe to the service

Click on the <code className="action">Create a service</code> button.

The creation form is displayed on a single page, organised in the following sections:

- <code className="action">Service</code>: select OpenSearch and the version to install. A name is generated automatically for your service; you can change it later.
- <code className="action">Datacentre</code>: choose the geographical region of the datacentre in which your service will be hosted.
- <code className="action">Service plan</code>: choose an appropriate service plan. If needed, you will be able to upgrade the plan after creation.
- <code className="action">Instance</code>: choose the node template. The number of nodes depends on the service plan.
- <code className="action">Storage</code>: check the storage of your service (storage is included in the price).
- <code className="action">Options</code>: decide to attach a public or private network and, optionally, add the authorised IPs.

Please visit the [OpenSearch capabilities page](/guides/public-cloud/databases/opensearch-capabilities) for the available versions and for detailed information on each plan's properties and hardware resources.

Take note of the pricing information in the order summary. The <code className="action">API and Terraform equivalent</code> button displays the equivalent of creating this service with the [OVHcloud API](/guides/manage-and-operate/api/first-steps) or Terraform. Click on <code className="action">Order</code> to create your service.

In a matter of minutes, your new database service will be deployed. Messages in the OVHcloud Control Panel will inform you when the database is ready to use.

### Configure the OpenSearch service

Once the Public Cloud Databases for OpenSearch service is up and running, you will have to define at least one user and one authorised IP in order to fully connect to the service.

The <code className="action">Dashboard</code> tab gives an overview of your service, including the <code className="action">Connection information</code> you need to connect to it.

#### Step 1 (mandatory): set up a user

Switch to the <code className="action">Users</code> tab. A default user, `avnadmin`, is pre-configured during the service installation with the ACL pattern `*` and the `admin` permission. You can add more users by clicking on the button <code className="action">Add user</code>.

Enter a username (3 to 32 characters) and, if needed, its ACLs (see below), then click <code className="action">Create User</code>.

Once the user is created, the password is generated. Please keep it securely as it will not be shown again.

Passwords can be reset afterwards for all users, including `avnadmin`, via the <code className="action">...</code> button in the <code className="action">Users</code> tab, then <code className="action">Reset password</code>.

#### Step 2 (mandatory): configure authorised IPs

:::warning
For security reasons the default network configuration doesn't allow any incoming connections. It is thus critical you authorize the suitable IP addresses in order to successfully access your database.

:::


If you did not add any IP when creating the service, switch to the <code className="action">Configuration</code> tab. At least one IP address must be authorised in the <code className="action">IPs</code> section before you can connect to your database.
It can be your laptop IP for example.

Enter a single IP address or an IP block in the <code className="action">IP address or IP/mask</code> field and add it to the list. You can also remove IP addresses from the list. Click on <code className="action">Save changes</code> to apply your changes.

If you don't know how to get your IP, please visit a website such as [www.WhatismyIP.com](https://www.whatismyip.com/).
Copy the IP address shown on this website and save them for later.

Your OpenSearch service is now fully accessible!

Optionally, you can configure access control lists (ACL) for granular permissions.

#### Optional: configure ACLs

OpenSearch database supports index-level access control lists (ACLs) to control permissions. This approach allows you to limit the operations that are available to specific connections and to restrict access to certain data sets, which improves the security of your data.

ACLs are managed in the <code className="action">Users</code> tab. Make sure the <code className="action">Enable ACLs</code> option is switched on, then define the ACLs of each user when you add or edit it.

You can grant the following permissions:

- **deny**: no access
- **admin**: full access to APIs and documents
- **readwrite**: full access to documents
- **read**: allows only searching and retrieving documents
- **write**: allows updating, adding, and deleting documents

*Note*: Write permission allows the service user to create new indexes that match the pattern, but it does not allow deletion of those indexes.

Rules are defined separately for each user as **pattern / permission** combinations. The **pattern** defines the indexes that the permission applies to. Patterns are glob-style, where **\*** matches any number of characters and **?** matches any character.

When multiple rules match, they are applied in the order listed above. If ACLs are enabled and no rules match, access is denied.

##### **Control access to top-level APIs**

OpenSearch has several “top-level” API endpoints (*_mget*, *_msearch*, and so on), where you have to grant access separately. To do this, use patterns similar to the index patterns, for example:

- pattern `_*` with the `admin` permission would grant unlimited access to all top-level APIs
- pattern `_msearch` with the `admin` permission grants unlimited access to the _msearch API only

##### **Access control and OpenSearch Dashboards**

Enabling ACLs does not restrict access to OpenSearch Dashboards itself, but all requests done by OpenSearch Dashboards are checked against the current user’s ACLs.

In practice, for OpenSearch Dashboards to work properly, you must grant the user admin-level access to the *_msearch* interface (permission: `admin`, pattern: `_msearch`).

### Advanced configuration

#### Indexes and index patterns

An index contains a database schema. Each data is based on a basic unit which is a JSON document, indexed with a unique ID. Indexing is the method used to store data and by the search engine for fast retrieval.

You can learn more browsing the [OpenSearch official documentation - Managing indexes](https://docs.opensearch.org/latest/im-plugin/)

Indexes cannot be created from the OVHcloud Control Panel: create them through the OpenSearch API (see the cURL example below), or let OpenSearch create them automatically when you write the first document.

The <code className="action">Index patterns</code> tab lets you limit the number of indexes kept for a given pattern, which is useful, for example, when an index is created every day to store logs. Click on <code className="action">Add a pattern</code>, enter a pattern (`*` matches any number of characters and `?` matches any character) and a <code className="action">Maximum number of indexes</code>, then confirm. When more indexes than this maximum match the pattern, the oldest ones are deleted. A value of `0` means that the pattern is not evaluated (no limit).

The same tab lists the indexes of your service. You can delete an index from this list.

#### Automatic backups

OVHcloud performs daily backups for your Public Cloud Databases for the OpenSearch service.
To find them, switch to the <code className="action">Backups</code> tab. Backups will be created automatically, and retention time depends on the service plan. Please visit the [Public Cloud Databases for OpenSearch capabilities page](/guides/public-cloud/databases/opensearch-capabilities) for detailed information on each plan's properties.

Via the <code className="action">...</code> button, you can <code className="action">Restore</code> a backup or <code className="action">Duplicate (Fork)</code> it to a new service. Backups cannot be deleted. For more information, read our guides on [backups](/guides/public-cloud/data-analytics/analytics/backups) and on [restoring a backup](/guides/public-cloud/data-analytics/analytics/restore-backup).

### Query the OpenSearch service

#### DB queries with cURL

Once the service is up and configured, you can try to connect from a remote session to it. You need to have at least:

- the user login and password, with accurate ACLs if enabled;
- the host and port of the OpenSearch service. They can be found in the <code className="action">Connection information</code> section of the <code className="action">Dashboard</code> tab. The port is specific to each service.

:::warning
Verify that the IP address of your system running the cURL command is part of the authorised IPs defined for this OpenSearch Database service.

:::


The URI displayed in the Control Panel starts with `opensearch://`. To use it with cURL, replace this scheme with `https://`. Once ready, try this in a command line, with your personal user and password:

```bash
export OPENSEARCH_URL=https://<service-host>:<port>
export OPENSEARCH_AUTH=<username>:<password>
```

Then try to connect:

```bash
curl -u $OPENSEARCH_AUTH $OPENSEARCH_URL
```

The database response should be similar to:

```json
{
  "name" : "opensearch-<service-id>-1",
  "cluster_name" : "<cluster-name>",
  "cluster_uuid" : "<cluster-uuid>",
  "version" : {
    "distribution" : "opensearch",
    "number" : "3.3.2",
    "build_type" : "unknown",
    "build_hash" : "unknown",
    "build_date" : "2026-08-19T00:00Z",
    "build_snapshot" : false,
    "lucene_version" : "10.3.1",
    "minimum_wire_compatibility_version" : "2.19.0",
    "minimum_index_compatibility_version" : "2.0.0"
  },
  "tagline" : "The OpenSearch Project: https://opensearch.org/"
}
```

Now create an index:

```bash
curl -u $OPENSEARCH_AUTH -X PUT $OPENSEARCH_URL/my-index
```

In case of a wrongly defined ACL for the user, the response will be similar to:

```bash
{"error":{"root_cause":[{"type":"security_exception","reason":"no permissions for [indices:admin/create] and User [name=<username>, backend_roles=[], requestedTenant=null]"}],"type":"security_exception","reason":"no permissions for [indices:admin/create] and User [name=<username>, backend_roles=[], requestedTenant=null]"},"status":403}
```

Try to add a document:

```bash
curl -u $OPENSEARCH_AUTH -X PUT $OPENSEARCH_URL/my-index/_doc/1 -H 'Content-Type: application/json' -d '{"Description": "To be or not to be, that is the question."}'
```

Retrieve the data:

```bash
curl -u $OPENSEARCH_AUTH -X GET $OPENSEARCH_URL/my-index/_doc/1
```

Delete the data:

```bash
curl -u $OPENSEARCH_AUTH -X DELETE $OPENSEARCH_URL/my-index/_doc/1
```

Delete the index:

```bash
curl -u $OPENSEARCH_AUTH -X DELETE $OPENSEARCH_URL/my-index/
```

:::info
With the `readwrite` permission, a user can create an index matching its pattern and add, read or delete documents, but cannot delete the index itself: deleting an index requires the `admin` permission on a matching pattern. You can also delete an index from the <code className="action">Index patterns</code> tab.
:::
