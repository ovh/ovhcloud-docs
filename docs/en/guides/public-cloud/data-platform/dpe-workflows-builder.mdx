## Objective

The workflow builder lays out a [workflow](/guides/public-cloud/data-platform/dpe-workflows) as a graph of actions. Instead of putting actions in successive stages, you say what each action waits for: an action starts once the actions it depends on have succeeded, or failed. This guide explains how to:

- add actions and set what each one waits for;
- group actions;
- run independent actions in parallel;
- set retries and a timeout on an action;
- decide what happens when an action fails;
- follow a run;
- create the same workflow with the API.

## Requirements

- Access to the Data Processing Engine of a [Data Platform](/links/public-cloud/data-platform) project.
- The [actions](/guides/public-cloud/data-platform/landing-page-dpe-actions) you want to chain, already created in the Data Processing Engine.

## Creating a workflow

In the Data Processing Engine, go to **Workflows** and click **New workflow**. The workflow opens in the builder.

<img className="thumbnail" alt="Empty workflow builder with Add your first action" src="/images/public-cloud/data-platform/product/dpe/workflows/picts/builder-empty.png" loading="lazy" />

1. Click **Add your first action**, then pick the action in the **Action** tab of the panel.
2. Grow the graph from the **+** menu of an action:
    - **Add action after**: a new action that runs when this one succeeds;
    - **Add parallel action**: a new action with the same dependencies and group as the selected one;
    - **Run on failure**: a new action that runs only if this one fails.
3. Select an action to configure it in the panel, which has 3 tabs: **Action**, **Dependencies** and **Options**. See the sections below.
4. Name the workflow in its **Preferences** tab, then click **Create**.

<img className="thumbnail" alt="Action tab of the panel, choosing the action to add to the graph" src="/images/public-cloud/data-platform/product/dpe/workflows/picts/builder-choose-action.png" loading="lazy" />

The graph lays itself out from the dependencies: you do not place the actions yourself. Above the graph, **Add a first-level action** adds an action that starts with the run, **New group** creates a group, **Undo** reverts the last change and **Find an action** searches by name, ID, group or repository. The minimap shows the whole graph.

:::info
Workflows created with stages keep opening in the stage editor, described in [Orchestrate ETL pipelines with Data Platform workflows](/guides/public-cloud/data-platform/dpe-workflows).

:::

## Setting what an action waits for

In the **Dependencies** tab of an action, **Runs after** lists what the action waits for. Each row is an action or a group of the workflow, with one of two conditions:

- **succeeds**: the action waits for that action, or that group, to succeed;
- **fails**: the action waits for that action to fail. This is a failure route; see "[When an action fails](#when-an-action-fails)".

The action starts when **all** its rows are true. An action with no row starts when the run starts.

Click **Add an action** to add a row: **From this workflow** waits for an action or a group already on the graph, **New action** adds a new action placed before this one. **Runs before** lists, read-only, the actions and groups that wait for this one.

For example, with B and C both waiting for A to succeed, and D waiting for B and C, D starts only once B and C have both succeeded.

<img className="thumbnail" alt="Dependencies tab: the action runs after all actions of the Load sources group succeed" src="/images/public-cloud/data-platform/product/dpe/workflows/picts/builder-dependencies.png" loading="lazy" />

## Grouping actions

A group gathers actions that share the same dependencies, and lets other actions wait for all of them at once.

1. Click **New group**, give it a name and tick the actions to put in it, then click **Create group**. The **Runs after** rows that the ticked actions all share move to the group.
2. To set what the whole group waits for, use the **Runs after** rows in the panel of the group: they apply to every action in the group.
3. To make an action wait for the whole group, add a **Runs after** row on the group, for example *All of Load sources* **succeeds**. The action starts once every action of the group has succeeded.

A group name starts with a letter and holds at most 40 characters: letters, digits, spaces, `-` and `_`. **Ungroup** keeps the actions and copies the group's **Runs after** rows onto each of them.

## Running actions in parallel

Actions that do not wait for each other can run at the same time, but only when the workflow has several instances. A workflow runs on **one instance by default**: its actions then run one after another, in an order that respects the dependencies, even if they do not depend on each other.

To run independent actions in parallel, raise the number of instances of the workflow in its **Preferences** tab; see the "[Scale your jobs horizontally](/guides/public-cloud/data-platform/dpe-jobs-resources#scale-your-jobs-horizontally)" section of the "Scale Data Processing Engine resources" guide. In the **Resources** section, the total is **Instances** × **Instance Size** in DPU. The same fields appear when you click **Run**. Each instance takes its DPU from the quota of the project: if the quota is reached, the run does not start.

<img className="thumbnail" alt="Resources section of the workflow preferences: Instances, Instance Size and Total DPU" src="/images/public-cloud/data-platform/product/dpe/workflows/picts/builder-resources.png" loading="lazy" />

## Retries and timeout

In the **Options** tab of an action, under **Retries and timeout**:

| Field | Values | Effect |
|---|---|---|
| **Retries** | 0 to 10, default 0 | Number of new attempts after a failure. The run shows each attempt. |
| **Delay between retries** | 1 second to 60 minutes | Wait before each new attempt. Available once **Retries** is above 0. |
| **Timeout** | Up to 24 hours. 0, the default, means **No timeout**. | The action is stopped and fails when it runs longer, with a message such as "Action timed out after 60s". |

An action that still fails after its last attempt, or that times out, is handled as described in "[When an action fails](#when-an-action-fails)".

## When an action fails

Under **If it fails**, in the **Options** tab, you decide what happens to the rest of the run when the action fails:

| Option | Actions waiting for it to succeed | Its failure routes | The workflow |
|---|---|---|---|
| **Fail the workflow** (default) | Not run | Run | Ends as failed |
| **Continue** | Run, as if it had succeeded | Run | Ends as failed |


<img className="thumbnail" alt="Options tab: Retries and timeout, and If it fails set to Fail the workflow" src="/images/public-cloud/data-platform/product/dpe/workflows/picts/builder-options.png" loading="lazy" />

A failure route is an action that waits for this action to fail (a **fails** row, or **Run on failure** in the **+** menu). Use it to clean up, or to notify, when something goes wrong.

With either option, a workflow in which an action failed ends as failed. **Continue** only lets the rest of the graph run.

## Version of an action

In the **Action** tab, **Version** picks which version of its repository the workflow runs:

- **Deployed version**: the deployed version of the repository;
- **Latest version**: the latest version, which changes with each new version of the repository.

The panel shows which version this choice runs, for example "Runs v1, the deployed version of the repository". **Show version** displays the choice on each action of the graph.

<img className="thumbnail" alt="Action tab with the Version choice: Deployed version or Latest version" src="/images/public-cloud/data-platform/product/dpe/workflows/picts/builder-version.png" loading="lazy" />

When an environment or the workflow's execution options force a version, the field shows it and cannot be changed here.

## Checking the workflow

**Validate** checks the workflow before you save it, and lists each problem with the name of the action concerned. A workflow can be saved only when:

- it has at least 1 action;
- every action has been chosen;
- no action is in a group that does not exist;
- every group that something waits for has at least 1 action;
- no actions wait for each other in a loop.

## Following a run

Start the workflow like any other workflow: on demand, with a trigger, or through the API. While it runs, the graph shows the state of each action:

| State | Meaning |
|---|---|
| **Pending** | Waits for its dependencies |
| **Running** | Runs; shows **Running · attempt 2** when it is retried after a first failure |
| **Completed** | Succeeded |
| **Failed** | Failed after its last attempt, or timed out |
| **Not run** | Skipped: an action it waited for did not succeed |

After the run, the graph keeps the state of each action of the last run, and **Last run** shows its duration and result. A group shows how many of its actions are in each state. You cannot edit the graph while the workflow runs.

<img className="thumbnail" alt="Graph after a run showing Completed, Failed and Not run actions" src="/images/public-cloud/data-platform/product/dpe/workflows/picts/builder-run-result.png" loading="lazy" />

As with any workflow, the logs are in the [Logs Explorer](/guides/public-cloud/data-platform/control-center-logs-explorer) of the Control Center, and you can [configure an alert](/guides/public-cloud/data-platform/control-center-alerting-job-execution) on its failures.

## Creating a workflow with the API

A builder workflow is a workflow with `nodes` and `groups` instead of `stages`. Send it to the Data Processing Engine API with `POST /dpe/v3/workflows`, and start it with `POST /dpe/v3/workflows/{workflowId}/start`.

Each node has an `_id` that you choose, 24 hexadecimal characters, so that other nodes can refer to it. Example: the load action runs first, the check action runs when the load succeeds, and the cleanup action runs if the load fails:

```json
{
  "display_name": "Load and check orders",
  "nodes": [
    {
      "_id": "6a1f00000000000000000001",
      "group": null,
      "requires": [],
      "action": {"action_id": "<load action id>", "repository": "<repository id>", "repository_version_override": "deployed"},
      "params": {},
      "retries": {"count": 1, "delay": "30s"},
      "timeout": "900s",
      "stop_on_failure": true
    },
    {
      "_id": "6a1f00000000000000000002",
      "group": null,
      "requires": [{"node": "6a1f00000000000000000001", "group": null, "on": "success"}],
      "action": {"action_id": "<check action id>", "repository": "<repository id>", "repository_version_override": "deployed"},
      "params": {},
      "retries": {"count": 0, "delay": "0s"},
      "timeout": null,
      "stop_on_failure": true
    },
    {
      "_id": "6a1f00000000000000000003",
      "group": null,
      "requires": [{"node": "6a1f00000000000000000001", "group": null, "on": "failure"}],
      "action": {"action_id": "<cleanup action id>", "repository": "<repository id>", "repository_version_override": "deployed"},
      "params": {},
      "retries": {"count": 0, "delay": "0s"},
      "timeout": null,
      "stop_on_failure": true
    }
  ],
  "groups": []
}
```

| Field | Content |
|---|---|
| `requires` | What the node waits for: one entry per **Runs after** row, with `node` or `group`, and `on` set to `success` or `failure` |
| `action.action_id` | The runnable ID of the action (its `action_id` field, not its `_id`) |
| `action.repository_version_override` | `deployed` or `latest` |
| `retries` | `count` (0 to 10) and `delay` in seconds, for example `30s` |
| `timeout` | In seconds, for example `900s`, or `null` for no timeout |
| `stop_on_failure` | `true` for **Fail the workflow**, `false` for **Continue** |
| `group` | The `_id` of the node's group, or `null` |

A group is `{"_id": "<24 hexadecimal characters>", "name": "<group name>", "requires": [...]}`. A node waits for a whole group with `{"node": null, "group": "<group id>", "on": "success"}`.

To run independent nodes in parallel, set `environment.fpu.instances` to more than 1. `environment` is a field of the workflow itself, at the same level as `nodes` and `groups`.

:::warning
The API ignores, without an error, the fields it does not know. Read the workflow back after creating it to check that it holds what you sent.

:::

The state of each node during and after a run is in the `execution.nodes` field of the response to `GET /dpe/v3/jobs/{executionId}`, with its status, number of attempts and error message.
