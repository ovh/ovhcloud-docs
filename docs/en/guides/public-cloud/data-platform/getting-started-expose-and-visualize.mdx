## Objective

An **API** exposes the data of your Project to the outside world, and an **application** turns it into a dashboard your users can open. In this last step of the Getting Started guide, you deploy both, one after the other:

1. **Deploy an API**, the interface between the outside world and the rest of your Project, so that applications can run your queries over HTTP.
2. **Build the application that reads it**, the site your users open, with a dashboard and a chart drawn from your own data.

You do not write any code for either of them. Data Platform provides a template for each:

- **Query API** creates a *Front API*, a service that exposes the data of your Project over HTTP. Your applications send it their queries, including the ones saved in your [Analytics Manager](/guides/public-cloud/data-platform/landing-page-analytics-manager), and it can keep the results in a cache.
- **Mosaic** creates a *Front App*, the web application your users open, with a menu, a page layout and a chart library. Its pages are described in configuration files rather than written in code: you build them in the *Visual Editor*, an editor that the application itself serves inside the console.

All that is left is to name things and describe what you want to see. For an overview of APIs and applications beyond this guide, see [Application APIs](/guides/public-cloud/data-platform/landing-page-app-services-apis) and [Data Platform applications](/guides/public-cloud/data-platform/landing-page-app-services-apps).

## Requirements

Complete the previous steps of the Getting Started guide first: your [sources are connected](/guides/public-cloud/data-platform/getting-started-connect-sources), your [Lakehouse Manager schema is built](/guides/public-cloud/data-platform/getting-started-organize-data), your [workflow has run](/guides/public-cloud/data-platform/getting-started-prepare-data) and your [queries return data](/guides/public-cloud/data-platform/getting-started-create-queries).

Expect some waiting along the way: this page runs 3 builds and 3 deployments, each taking a couple of minutes.

## Part 1: Exposing your data through an API

### Creating the API

From your Project, open **Applications & APIs**. The list shows every application and API deployed in the Project, with its type, its URL and its status.

Click **+ ADD**.

<img className="thumbnail" alt="The empty Applications list of the Project, with the Add button at the top right" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/01-applications-list.png" loading="lazy" />

The *Choose application type* dialog offers three kinds of application:

- **Front App**: a front-end application that uses the data your APIs expose.
- **Front API**: an API that exposes the data of the services of your Project.
- **Apache Superset**: a ready-made Apache Superset instance.

Select **Front API**, then click **NEXT**.

<img className="thumbnail" alt="The Choose application type dialog with Front API selected" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/02-front-api-package.png" loading="lazy" />

### Configuring its first version

In **Application name**, enter `rides`. Data Platform derives the technical name and the URL from it, so your API is served at `/rides-api/`.

Leave **Source** on *From Template* and **Version Name** on its default value, `v1`. A version is a deployable snapshot of your API: you can add a `v2` later without ever taking `v1` down.

Under **Select a template**, choose **Query API (Node + Express)**. This template lets your applications run queries on your data over HTTP, including the queries saved in your Analytics Manager.

Then tick the 3 options:

- **Auto Build**: start a build as soon as the version is created.
- **Auto Deploy**: deploy the version as soon as the build succeeds.
- **Enable cache**: deploy an in-memory cache (Valkey) alongside the API, so that repeated calls do not query your data warehouse again. The default values, *Valkey 8.1.8-alpine* and 20% of a DPU, are enough for this guide.

With the first two options, a single click downloads, builds and deploys your API. Click **CREATE**.

<img className="thumbnail" alt="The Create APIs form with rides, v1, the Query API template and three options ticked" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/03-api-version-form.png" loading="lazy" />

### Letting it build

Data Platform opens your new API. The *Application details* section already shows the essentials: the technical name `rides-api`, the URL your applications call, and the IAM application that protects it.

On the right, *Versions* lists `v1`; below *Application details*, *Recent builds* shows the build that Auto Build has just started. The build takes a couple of minutes.

<img className="thumbnail" alt="The overview of the rides API while its first version builds" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/04-api-building.png" loading="lazy" />

:::info
Data Platform uses a **[blue-green](https://en.wikipedia.org/wiki/Blue-green_deployment) deployment methodology**, so you can deploy new versions of your API without downtime.

:::

When the build succeeds, Auto Deploy takes over. Back in **Applications & APIs**, your API is listed as *Running*.

<img className="thumbnail" alt="The Applications list showing the rides API with the Running status" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/05-api-running.png" loading="lazy" />

### Checking that your API responds

Open the URL shown in the *Link* field of *Application details*, or in the *URL* column of the list. Your API answers with a welcome page.

<img className="thumbnail" alt="The welcome page returned by the deployed API" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/06-api-answering.png" loading="lazy" />

Your API is deployed and reachable.

[Learn more about your Project APIs](https://docs.dataplatform.ovh.net/sdk/api)

The application you create next connects to that URL: its form offers it in the **API URL** field.

## Part 2: Visualising your data in an application

### Creating the application

Back in **Applications & APIs**, click **+ ADD**, select **Front App** and click **NEXT**.

<img className="thumbnail" alt="The Choose application type dialog with Front App selected" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/07-front-app-package.png" loading="lazy" />

Fill in the form:

- **Application name**: `analytics`. Data Platform derives the URL from it, so your application is served at `/analytics-app/`.
- **API URL**: select the URL of the `rides` API you have just deployed. This field is what connects your application to your API.
- **Select a template**: **Mosaic**.
- **Version Name**: `v1.0.0`. A full version number leaves room for `v2.0.0`, which you create at the end of this page.
- Tick **Auto Build** and **Auto Deploy**, so that the version builds and goes live on its own.

Click **CREATE**.

<img className="thumbnail" alt="The Create Applications form with analytics, the rides API URL, the Mosaic template and v1.0.0" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/08-app-version-form.png" loading="lazy" />

Data Platform opens the new application while its first version builds. The build takes a couple of minutes.

<img className="thumbnail" alt="The overview of the analytics application while version v1.0.0 builds" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/09-app-building.png" loading="lazy" />

When the build succeeds, Auto Deploy takes over and your application is listed as *Running*.

<img className="thumbnail" alt="The Applications list showing the analytics application and the rides API, both Running" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/10-app-running.png" loading="lazy" />

### Opening the Visual Editor

Open your application, then its version `v1.0.0`, and go to the *Visual Editor* tab.

Data Platform opens your application inside the console and signs you in as an administrator. The toolbar across the top only appears in the Visual Editor: your users never see it. From now on, you build everything (pages, charts, filters, menus, number formats) inside the application itself.

<img className="thumbnail" alt="The analytics application in the Visual Editor tab, with the editing toolbar at the top" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/11-visual-editor.png" loading="lazy" />

:::info
The *Visual Editor* tab only appears on a running version. The editor is served by the application itself, so a stopped version has nothing to open.

:::

### Creating a page

In an application, dashboards are pages. The Mosaic template includes one, served at `/home`: it is the page currently displayed.

Click **Dashboards** in the toolbar, then the *+ New* tab, and fill in:

- **Name**: `Rides analytics`
- **Route**: `/rides-analytics`

Leave the description empty, and leave **Add a link to it in the "sidebar" menu** ticked: your users need to reach this page, and the option adds the link to the sidebar for you.

<img className="thumbnail" alt="The Dashboards dialog with the new Rides analytics page filled in" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/12-dashboards-panel.png" loading="lazy" />

Click **Create**, then **Close**.

This creates three things at once: the page itself, its entry in the configuration of the application, and the link in the sidebar. Creating the page from this dialog keeps the three consistent.

Click **Rides analytics** in the sidebar to open your new page, which is still empty.

<img className="thumbnail" alt="The empty Rides analytics page, reached from its new link in the sidebar" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/13-dashboard-created.png" loading="lazy" />

### Building your first chart

#### Creating a panel

Click **+ Add** in the toolbar and select **Containers** > **Panel**. A panel is a container for the other components. Resize it by dragging its bottom-right corner.

<img className="thumbnail" alt="An empty panel added to the page, with its options open on the right" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/14-panel-added.png" loading="lazy" />

#### Adding the chart

Inside the panel, click its **+** button and select **Charts** > **Semi donut**.

In the *General* tab, name the chart `Rides per temperature`.

Then open the *Data* tab, where you describe the data to display rather than the drawing. Leave **Data source** on *Query builder*, which builds the query right here (the same list also offers the queries saved in the Analytics Manager), then:

- under *Measures*, click **+ Add** and select `rides` with the `sum` aggregation.
- under *Group by*, click **+ Add** and select `cat_temperature`.

<img className="thumbnail" alt="The Data tab of the chart dialog, with rides summed and grouped by cat_temperature" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/15-chart-options.png" loading="lazy" />

Click **Apply**. The chart queries your data through the API you deployed in Part 1 and displays one slice per temperature category.

<img className="thumbnail" alt="The Rides per temperature semi donut chart, with its options on the right" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/16-chart-added.png" loading="lazy" />

#### Adding a filter

A filter lets your users narrow the chart down. Click the **+** button of the panel again and select **Filters** > **Select**.

The filter is added immediately and its options open on the right. Set **Field** to `station_name`, the column the filter constrains.

The chart options list *All filters on the page* under *Filters*, so the chart responds to this filter without any further setting.

<img className="thumbnail" alt="The filter options panel with the Field set to station_name" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/17-filter-options.png" loading="lazy" />

Click **Save** in the toolbar. The counter next to it goes back to *no changes*: your dashboard is saved in the sources of the version.

<img className="thumbnail" alt="The saved dashboard, with the toolbar counter showing no changes" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/18-dashboard-saved.png" loading="lazy" />

:::info
Saving writes your dashboard into the sources of the version. It does not make it available to your users yet: the build and deployment at the end of this page do that.

:::

### Trying it out

Click the **▶** button at the right end of the toolbar to leave edit mode. The toolbar collapses into a single **Edit** button, and you see your application as your users do.

Select a station in the filter: the chart redraws for that station only.

<img className="thumbnail" alt="The dashboard in preview, filtered on one station" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/19-preview-filtered.png" loading="lazy" />

Your dashboard is ready.

### Deploying a new version

Go back to the overview of your application. A banner indicates that *the configuration has been modified since the last build*: your users are still served the version deployed earlier, which does not include the dashboard you have just built.

You could stop the running version and rebuild it, but that would take your application offline. Copy it instead: on the `v1.0.0` row, open the **…** menu and select **Copy**.

Name the copy `v2.0.0`, tick **Auto Build** and **Auto Deploy**, and click **CREATE**.

<img className="thumbnail" alt="The Versions list with v2.0.0 building while v1.0.0 is still deployed and marked Rebuild needed" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/20-version-copied.png" loading="lazy" />

:::info
The same **[blue-green](https://en.wikipedia.org/wiki/Blue-green_deployment) deployment** as for your API applies: `v1.0.0` keeps serving your users while `v2.0.0` builds and deploys. The switch happens once the new version is ready, with no interruption.

:::

The build takes a couple of minutes. To follow it, or to investigate a failed build, open the *Builds* tab of the version and click the logs icon. The *Build Logs* dialog shows the state of the build, its time in the queue and each step as it runs, with a link to the Control Center for advanced filtering.

<img className="thumbnail" alt="The Build Logs dialog of version v2.0.0, streaming the build steps" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/21-build-logs.png" loading="lazy" />

### Opening your live application

Once `v2.0.0` is built, Data Platform switches to it and stops `v1.0.0`. The switch can take a moment: until it completes, your users are still served the previous version, so nobody experiences an interruption.

Open your application from the URL shown in the *Link* field of its *Application details*. Unlike the Visual Editor, which the console opens on your behalf, your application is a standalone, protected site, so it asks you to sign in. Sign in with **Data Platform**.

:::info
You configure who can open your application, and how they sign in, in the [Identity Access Manager](/guides/public-cloud/data-platform/landing-page-iam).

:::

Your application opens. **Rides analytics**, the menu entry you added, is in the sidebar, and it leads to your chart, live and filterable.

<img className="thumbnail" alt="The deployed analytics application showing the Rides per temperature chart and the station filter" src="/images/public-cloud/data-platform/getting-started/expose-and-visualize/picts/22-deployed-application.png" loading="lazy" />

Your dashboard is online and reads its data through your own API. Nothing refreshes on a timer: each chart queries the API when a page opens and when a filter changes.

:::info
Because you ticked **Enable cache**, the API answers from Valkey any query it has already run, and by default it keeps those results until the cache is cleared. When new data reaches your tables, a chart can therefore still show the previous results. A *cached* badge on the chart says so: clicking it runs the query again without the cache, for that chart and that reader only. To make cached results expire, set the `DATAQUERY_CACHE_TTL` environment variable of your API to a lifetime in seconds.

:::
