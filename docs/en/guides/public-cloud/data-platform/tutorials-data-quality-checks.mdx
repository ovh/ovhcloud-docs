## Objective

In this tutorial, we add quality rules to the `chicago_calendar_full` table, run the [Data quality](/guides/public-cloud/data-platform/dpe-actions-data-quality) action on it and read its results in the Lakehouse Manager. Then, in [Go further](#go-further-a-quality-gate-between-two-tables), we use the same action as a gate in a workflow: data is published to a final table only when its quality checks pass.

Everything is done in the Data Platform interface.

## Requirements

- The `chicago_calendar_full` table, created and loaded in the [Getting Started](/guides/public-cloud/data-platform/landing-page-getting-started) tutorial ([Connect sources](/guides/public-cloud/data-platform/getting-started-connect-sources) and [Organize data](/guides/public-cloud/data-platform/getting-started-organize-data)). Each row of this table is one day, with its `date`, `month`, `temperature`, `week_day`, `week_day_label` and `weekend`.

## Step 1: add quality rules to the table

In the Lakehouse Manager, open the `chicago_calendar_full` table and go to its **Quality** tab.

Click **+ Add rule** and create the following four rules. Two of them have a warning level, two only a critical one:

| Name | Type | Column | Parameters | Warning | Critical | Job impact |
|---|---|---|---|---|---|---|
| Temperature is filled | Not null | `temperature` | None | Warning when below 99 % | Critical when below 95 % | Fail the job |
| Temperature is plausible | Range | `temperature` | Minimum -40, maximum 120 | Warning when below 99 % | Critical when below 90 % | Report only |
| One row per day | Uniqueness | `date` | None | None | Critical when above 0 % (duplicates) | Fail the job |
| At least a year of data | Volume | None | None | None | Critical when fewer than 365 | Report only |

What these rules mean:

- **Temperature is filled** is in warning when fewer than 99 % of the days have a temperature, and critical below 95 %.
- **Temperature is plausible** checks that temperatures, in Fahrenheit, stay between -40 and 120. It is in warning when fewer than 99 % of the values are in that range, and critical below 90 %.
- **One row per day** has no warning level: 100 % means no duplicate, so a single duplicated date makes it critical.
- **At least a year of data** is evaluated by the Lakehouse Manager from the table's metadata, without any action. It is critical when the table holds fewer than 365 rows.

The two rules set to **Fail the job** are the ones that fail the Data quality job when they end critical. The two **Report only** rules are reported without stopping the job. See [Job impact](/guides/public-cloud/data-platform/lakehouse-manager-data-quality#job-impact).

## Step 2: create the Data quality action

In the **Quality** tab, click **Create a DPE action**, or in the Data Processing Engine, go to **Actions** and create a **Data quality** action.

In **Table to check**, pick `chicago_calendar_full`, then keep the other default parameters:

- In **When the job fails**, **Critical Results Allowed** and **Warning Results Allowed** are empty: only rules set to **Fail the job** can fail it, and warnings never fail it.
- The action runs on Python 3.11, on 2 DPU.

Save the action.

<img className="thumbnail" alt="The Data quality action for chicago_calendar_full, with Table to check, When the job fails left empty and the advanced settings" src="/images/public-cloud/data-platform/getting-further/data-quality-checks/picts/data-quality-action.png" loading="lazy" />

Once the action is saved, its **Open the Quality tab in Lakehouse** button takes you back to the rules of the table.

## Step 3: run the action

Click **Run** and wait for the job to end. The job evaluates the three column rules on the current snapshot of the table, sends the report to the Lakehouse Manager, then succeeds or fails depending on the rules set to **Fail the job**.

## Step 4: read the results

Click **Open the Quality tab in Lakehouse** on the action, or open the `chicago_calendar_full` table in the Lakehouse Manager and go to its **Quality** tab.

<img className="thumbnail" alt="The Quality tab after the run: three rules OK and Temperature is plausible in warning at 94.1 %, with the summary of outcomes" src="/images/public-cloud/data-platform/getting-further/data-quality-checks/picts/quality-tab-results.png" loading="lazy" />

Each rule shows its outcome (`ok`, `warning` or `critical`) and its result: a pass rate for the Not null and Range rules, the share of duplicates for the Uniqueness rule, a row count for the Volume rule. The icons under the bar show its warning and critical levels. The status of the table is the worst outcome of its rules.

Hover a result to see its outcome, its thresholds and when it was checked.

<img className="thumbnail" alt="Hovering the result of Temperature is filled shows 100 % OK, its thresholds and the time of the check" src="/images/public-cloud/data-platform/getting-further/data-quality-checks/picts/rule-result-detail.png" loading="lazy" />

To see a rule fail, edit **Temperature is plausible** and set its maximum to 80, then run the action again: the rule ends in warning or critical, and its history shows both runs with the rule as it was at each run.

## Go further: a quality gate between two tables

A common pattern is to load new data into a staging table, check it, and publish it to the final table only when the checks pass. This is often called *Write, Audit, Publish*: the consumers of the final table never see data that failed its checks.

We build it with two tables:

- `silver`, the staging table, loaded from the source;
- `gold`, the final table, with the same columns, filled from `silver`.

### Create the silver table and its load

1. In the Lakehouse Manager, create the `silver` table from the `chicago_calendar_full` source, with a Load action, as in [Organize data](/guides/public-cloud/data-platform/getting-started-organize-data).
2. Build the table.

### Add quality rules to the silver table

Open the **Quality** tab of `silver` and create the same four rules as in [Step 1](#step-1-add-quality-rules-to-the-table). The rules set to **Fail the job** decide whether the data is published.

Then create a Data quality action with `silver` as **Table to check** and the default parameters, as in [Step 2](#step-2-create-the-data-quality-action).

### Create the gold table and its load

1. Create an empty `gold` table with the same columns as `silver`, and build it.
2. In the Data Processing Engine, create an [Aggregate](/guides/public-cloud/data-platform/dpe-actions-aggregate) action that reads `silver` and writes `gold`, mapping each column to the column of the same name.

### Chain them in a workflow

In the Data Processing Engine, create a [workflow](/guides/public-cloud/data-platform/dpe-workflows) with three actions, each one depending on the previous one:

1. the Load action of `silver`;
2. the Data quality action of `silver`;
3. the Aggregate action from `silver` to `gold`.

Each action starts once the previous one has succeeded. When a rule of `silver` set to **Fail the job** ends critical, the Data quality action fails, the Aggregate action does not run, and `gold` keeps its previous data. The report of the failed run is in the **Quality** tab of `silver`, so you can see which rule failed and why.

<img className="thumbnail" alt="A run of the workflow stopped at the Data quality action: Load silver completed, Data quality failed, Aggregate silver to gold not run" src="/images/public-cloud/data-platform/getting-further/data-quality-checks/picts/workflow-quality-gate.png" loading="lazy" />

To be notified when the gate stops the workflow, [configure an alert](/guides/public-cloud/data-platform/control-center-alerting-job-execution) on the Data quality action with *status = failure*.
