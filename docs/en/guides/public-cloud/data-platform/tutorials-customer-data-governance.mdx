## Objective

This guide walks you through protecting a customer table that holds personal data with policy tags, IAM groups, a governed view and Time Travel. You classify its columns with [policy tags](/guides/public-cloud/data-platform/lakehouse-manager-policy-tags), restrict each team with [IAM groups](/guides/public-cloud/data-platform/iam-groups) and CEL conditions, publish a [view](/guides/public-cloud/data-platform/lakehouse-manager-views) that gives analysts a coarser version of the data, and undo a destructive mistake with [Time Travel](/guides/public-cloud/data-platform/lakehouse-manager-time-travel).

By the end you will have a customer table classified column by column, three teams with access matched to their needs, a governed view for analysts, and a tested way to restore the table after a deletion made by mistake.

## Requirements

To follow this guide you need:

- A Data Platform project. This guide uses a project named `customer-governance`.
- An administrator account on this project.
- A second account for a test user, who is not an administrator: another person's account, or a second address of your own, for example `firstname.lastname+governance-test@example.com`.
- The customer file:

| **Type** | **Name** |
| --- | --- |
| Customers, 5,000 fictitious records | <a className="rp-link" href="/images/public-cloud/data-platform/getting-further/customer-data-governance/resources/customers.parquet" download>customers.parquet</a> |

:::info
**About the data:** `customers.parquet` is derived from [Nemotron-Personas-USA](https://huggingface.co/datasets/nvidia/Nemotron-Personas-USA), by NVIDIA, licensed under [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). It keeps a sample of 5,000 adult records; names are extracted from the persona field, and emails, phone numbers and SSNs are synthetic (domain `example.com`, numbers 555-0100 to 555-0199, SSN area 000).
:::

We recommend reading the [policy tags](/guides/public-cloud/data-platform/lakehouse-manager-policy-tags) and [CEL conditions](/guides/public-cloud/data-platform/lakehouse-manager-policy-tags-cel-conditions) guides first. This guide assumes you are comfortable with the main components of Data Platform.

## What you will build

| Stage | Component | Result |
|---|---|---|
| 1. Load the customers | [Connectors](/guides/public-cloud/data-platform/connectors-sources-upload-files), [Lakehouse Manager](/guides/public-cloud/data-platform/lakehouse-manager-tables) | Table `crm.customers`, 5,000 rows |
| 2. Classify the columns | [Policy Tags](/guides/public-cloud/data-platform/lakehouse-manager-policy-tags) | Every column has a sensitivity level |
| 3. Define the access rules | [Identity Access Manager](/guides/public-cloud/data-platform/iam-roles-conditions) | Three roles, three groups, three CEL conditions |
| 4. Check the rules | [Explorer](/guides/public-cloud/data-platform/lakehouse-manager-explorer), test user | Each group reads only what it should |
| 5. Publish a view for analysts | [Views](/guides/public-cloud/data-platform/lakehouse-manager-views), CEL conditions | Age bands and 3-digit ZIP codes instead of exact values |
| 6. Undo a mistake | [SQL action](/guides/public-cloud/data-platform/dpe-actions-sql), [Time Travel](/guides/public-cloud/data-platform/lakehouse-manager-time-travel) | 591 deleted customers restored |

Three groups read the table `crm.customers`: *Analysts* read the `low` columns only, *Customer Support* the `low` and `medium` columns, *Data Stewards* every column. Analysts also read the governed view `customer_profiles`, built on the same table.

### Step 1: Load the customers

#### Create the source

1. Go to **Connectors** > **Sources** > **New Source** and click **File Upload** at the bottom of the window.

<img className="thumbnail" alt="The New source window listing the source types, with the File Upload button at the bottom" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/01-new-source-picker.png" loading="lazy" />

2. Rename the source `customers`.
3. Drop `customers.parquet` in the *Files* area, then click **Create**.

<img className="thumbnail" alt="The File Upload source customers being created, with customers.parquet listed in the Files area" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/02-file-upload-source.png" loading="lazy" />

#### Check the types

Go to **Connectors** > **Analyzer** and open `customers.parquet` in the source `customers`. The [metadata extraction](/guides/public-cloud/data-platform/connectors-analyzer-extract-metadata) starts on its own. Check two columns:

- `zipcode` must be **String**: ZIP codes such as `02760` would lose their leading zero as numbers.
- `age` is **Double**, which works for the age bands of step 5.

<img className="thumbnail" alt="The Analyzer on customers.parquet, listing the detected attributes with age as Double and the other columns as String" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/04-analyzer-types.png" loading="lazy" />

1. Go to **Lakehouse Manager** > **Datasets** > **New Dataset**, name it `crm` and click **Create**.

<img className="thumbnail" alt="The New dataset window with the name crm and the Lakehouse Manager storage engine" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/05-new-dataset.png" loading="lazy" />

2. Go to **Tables**, click the arrow of **New table** and select **Create from a Connectors source**.
3. Select `customers.parquet` from the source `customers` and click **Next**.

<img className="thumbnail" alt="The Create table window with customers.parquet selected from the source customers" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/06-new-table-source.png" loading="lazy" />

4. Name the table `customers`, select the dataset `crm`, keep the three automatic options turned on and click **Create**.

<img className="thumbnail" alt="The second step of the Create table window, with the table customers in the dataset crm and the three automatic options turned on" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/07-new-table-options.png" loading="lazy" />

When the load ends, the table `customers` shows **16** attributes and **5k** rows.

<img className="thumbnail" alt="The Tables list showing customers in the dataset crm with 16 attributes and 5k rows, and the load logs below" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/08-table-loaded.png" loading="lazy" />

### Step 2: Classify the columns

The access rules of step 3 read a [policy tag](/guides/public-cloud/data-platform/lakehouse-manager-policy-tags) on each column to decide who can read it.

#### Review the sensitivity tag

Go to **Lakehouse Manager** > **Policy Tags** and click `sensitivity`. The project provides this key with three values, which this guide uses as follows:

| Value | Meaning |
|---|---|
| `low` | Business data, readable by everyone |
| `medium` | Identifies or reaches a person, alone or combined |
| `high` | Special category data, government identifier, free text that leaks identity |

<img className="thumbnail" alt="The values high, medium and low of the tag key sensitivity" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/10-sensitivity-values.png" loading="lazy" />

#### Tag the dataset

Tag the dataset `low`: every column without a tag of its own inherits it.

Go to **Datasets**, open `crm`, then the *Policy Tags* tab, click **+ Add policy tag**, select the key `sensitivity`, then the value `low`. Changes are saved automatically.

<img className="thumbnail" alt="The Policy Tags tab of the dataset crm with the tag sensitivity: low" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/11-dataset-policy-tag.png" loading="lazy" />

#### Tag the columns

Go to **Tables**, open `customers`, then the *Policy Tags* tab. In *Column-level policy tags*, click **+ Add policy tag** on each column below, then select `sensitivity` and its value:

| Sensitivity | Columns | What to do |
|---|---|---|
| `medium` | `age`, `sex`, `marital_status`, `city`, `zipcode`, `first_name`, `last_name`, `email`, `phone` | Add `sensitivity: medium` |
| `high` | `ssn`, `cultural_background`, `persona` | Add `sensitivity: high` |
| `low` | `uuid`, `state`, `occupation`, `education_level` | Nothing: inherited from the dataset |

<img className="thumbnail" alt="The Policy Tags tab of the table customers, with the dataset tag inherited and column tags such as medium on age and city and high on cultural_background" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/12-table-policy-tags.png" loading="lazy" />

Tags apply immediately, without rebuilding the table.

### Step 3: Define the access rules

Access combines two kinds of [roles](/guides/public-cloud/data-platform/iam-roles-conditions), both created in the **project** IAM:

- a **base role** opens the interface and runs queries, without access to data;
- a **data role** gives access to data through *Advanced Data Access Control*, limited by a CEL condition set on each group.

#### Create the roles

Go to **Identity Access Manager** > **Roles** > **New role** and create the three roles below with **Add permission**, then **Create**.

| Role | Service | Resource | Action |
|---|---|---|---|
| `Lakehouse Explorer` | Data Manager | `*` | Read |
| | Data Manager | explorer | Run, History |
| | Query Builder Legacy | `*` | Read |
| | Analytics Manager | `*` | Read |
| | Analytics Manager | Query | Run, History, Write |
| `Customer Data Reader` | Advanced Data Access Control | `*` | Read |
| `Customer Data Steward` | Advanced Data Access Control | `*` | Read, Write, Delete |

<img className="thumbnail" alt="The role Lakehouse Explorer with its eight Data Manager, Query Builder Legacy and Analytics Manager permissions" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/13-lakehouse-explorer-role.png" loading="lazy" />

`Lakehouse Explorer` has no Advanced Data Access Control permission: on its own, it reads no data.

<img className="thumbnail" alt="The role Customer Data Reader with the single permission Advanced Data Access Control, resource *, action Read" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/15-customer-data-reader-role.png" loading="lazy" />

#### Create the groups

Each group binds a data role to a CEL condition:

| Group | Data role | Columns readable |
|---|---|---|
| Analysts | Customer Data Reader | `low` |
| Customer Support | Customer Data Reader | `low` and `medium` |
| Data Stewards | Customer Data Steward | `low`, `medium` and `high` |

For each group:

1. Go to **Groups** > **New group** and name the group.
2. In *Roles & conditions*, click **+ Add** and select its data role.
3. Click the condition link next to the role, paste the condition of the group and click **Confirm**.

<img className="thumbnail" alt="The condition editor for the role Customer Data Reader in the group Analysts, with the CEL condition pasted" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/18-analysts-condition.png" loading="lazy" />

4. Click **Create**.

**Analysts**:

```text
Service == "adac" && (
  (PolicyTags.sensitivity == "low" && Resource == "dataset")
  || (PolicyTags.sensitivity == "low" && Resource == "table")
  || (PolicyTags.sensitivity == "low" && Resource == "attribute")
  || (!has(PolicyTags.sensitivity) && Resource != "dataset")
)
```

**Customer Support**:

```text
Service == "adac" && (
  (PolicyTags.sensitivity == "low" && Resource == "dataset")
  || (PolicyTags.sensitivity == "low" && Resource == "table")
  || (PolicyTags.sensitivity in ["low", "medium"] && Resource == "attribute")
  || (!has(PolicyTags.sensitivity) && Resource != "dataset")
)
```

**Data Stewards**:

```text
Service == "adac" && (
  (PolicyTags.sensitivity == "low" && Resource == "dataset")
  || (PolicyTags.sensitivity == "low" && Resource == "table")
  || (PolicyTags.sensitivity in ["low", "medium", "high"] && Resource == "attribute")
  || (!has(PolicyTags.sensitivity) && Resource != "dataset")
)
```

The access check walks down dataset, table, then attribute, and each level must pass. The first two lines let every group through `crm` and `customers`. The third decides which column levels the group reads. The fourth lets the groups read the view of [step 5](#step-5-publish-a-view-for-analysts). CEL compares strings exactly: `"low"` does not match `"Low"`.

<img className="thumbnail" alt="The Groups list with Analysts, Customer Support and Data Stewards" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/22-groups.png" loading="lazy" />

### Step 4: Check the rules with a test user

Administrators are not restricted by policy tags, so run the checks with the test user. The administrator account changes the test user's groups; the test user runs the queries in **Lakehouse Manager** > **Explorer**, in SQL mode.

#### Create the test user

1. In the organization IAM, invite the test user's address and add them to the group **Viewers**.
2. In the project IAM, go to **Users** > **+ New User** and add the same address as a *Team Member*.
3. On the user's page, add the role `Lakehouse Explorer` only and the group **Analysts**, then click **Save**.

<img className="thumbnail" alt="The test user in the project IAM, member of the group Analysts with the role Lakehouse Explorer only" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/23-test-user.png" loading="lazy" />

4. Accept the invitation and log in with the test user in a private browser window.

:::warning
**Do not give the test user the default role DM & AM Editor.** It includes Advanced Data Access Control / Read without condition and reads every column whatever its tags.
:::

:::info
**Note:** A change of group or role takes effect within about 30 seconds, without logging out: reload the test user's page before running the query again.
:::

#### Check the Analysts group

With the test user, run:

| Query | Result |
|---|---|
| `SELECT uuid, state, occupation FROM crm.customers` | Success |
| `SELECT zipcode FROM crm.customers` | Error |
| `SELECT * FROM crm.customers` | Error |

<img className="thumbnail" alt="The Explorer returning uuid, state and occupation to the Analyst" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/24-analyst-success.png" loading="lazy" />

<img className="thumbnail" alt="The Explorer returning Access Denied: Cannot select from columns [zipcode] to the Analyst" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/25-analyst-zipcode-error.png" loading="lazy" />

A policy tag denies access, it does not mask values: one denied column makes the whole query fail.

#### Check the Customer Support group

With the administrator account, go to **Identity Access Manager** > **Users**, open the test user and, in *Groups*, click the bin icon on the **Analysts** row, then click **+ Add**, select **Customer Support** and click **Save**.

:::info
**Note:** Always remove the previous group. Rights add up: a user in **Data Stewards** and **Analysts** reads every column.
:::

With the test user, run:

| Query | Result |
|---|---|
| `SELECT first_name, last_name, email, phone, zipcode FROM crm.customers` | Success |
| `SELECT ssn FROM crm.customers` | Error |
| `SELECT persona FROM crm.customers` | Error |

#### Check the Data Stewards group

With the administrator account, replace **Customer Support** with **Data Stewards** in the same way. With the test user, run:

| Query | Result |
|---|---|
| `SELECT * FROM crm.customers` | Success |
| `SELECT first_name, last_name, persona FROM crm.customers LIMIT 5` | Success |

<img className="thumbnail" alt="The Explorer returning first_name, last_name and persona to the Data Steward, the persona text opening with the customer's full name" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/28-steward-persona.png" loading="lazy" />

The `persona` text opens with the customer's full name and often quotes their age: that is why it is tagged `high`.

### Step 5: Publish a view for analysts

Analysts cannot read the age or the ZIP code. The [view](/guides/public-cloud/data-platform/lakehouse-manager-views) `customer_profiles` gives them an age band and the first three digits of the ZIP code instead.

#### Create the view

1. With the administrator account, go to **Lakehouse Manager** > **Views** > **New view**.
2. Name the view `customer_profiles`, select the target dataset `crm` and paste this SQL definition:

```sql
SELECT
    uuid,
    state,
    substr(zipcode, 1, 3) AS zip3,
    CASE
        WHEN age < 25 THEN '18-24'
        WHEN age < 35 THEN '25-34'
        WHEN age < 45 THEN '35-44'
        WHEN age < 55 THEN '45-54'
        WHEN age < 65 THEN '55-64'
        ELSE '65+'
    END AS age_band,
    occupation,
    education_level
FROM customers
```

<img className="thumbnail" alt="The Create a new view window with the name customer_profiles, the target dataset crm and the SQL definition" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/29-new-view.png" loading="lazy" />

3. Click **Create**. The view shows the status **Valid**.

#### Check the view

The test user is in **Data Stewards**. Run these queries, then move them back to **Customer Support**, then **Analysts**, and run them again each time:

| Query | Analysts | Customer Support | Data Stewards |
|---|---|---|---|
| `SELECT * FROM crm.customer_profiles` | Success | Success | Success |
| `SELECT zipcode FROM crm.customers` | Error | Success | Success |

<img className="thumbnail" alt="The Explorer returning the view customer_profiles to the Analyst, with the columns zip3 and age_band" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/31-analyst-view.png" loading="lazy" />

:::warning
A view can expose any column of its source table: anyone who can create a view in `crm` decides what analysts read. Keep view creation for data stewards. `Lakehouse Explorer` cannot create views.
:::

### Step 6: Undo a mistake with Time Travel

Every change to a Lakehouse Manager table creates a snapshot, and [Time Travel](/guides/public-cloud/data-platform/lakehouse-manager-time-travel) rolls the table back to any snapshot still kept.

#### Make the mistake

1. With the administrator account, run this count in the Explorer: 5,000 customers, 591 in California.

```sql
SELECT count(*) AS customers, count_if(state = 'CA') AS california FROM crm.customers
```

2. Go to **Data Processing Engine** > **Actions** > **New action** and create a *SQL Action*.
3. In the *Tables* panel, click `customers` in `crm` to copy its full name, in the form `catalog.schema.table`, for example `db_mv0m4qnl_crm.crm.customers`. A [SQL action](/guides/public-cloud/data-platform/dpe-actions-sql) needs this full name.
4. Type this query with the copied name, then click **Validate**:

```sql
DELETE FROM <catalog>.crm.customers WHERE state = 'CA'
```

The dry run announces **591 rows would be deleted**.

<img className="thumbnail" alt="The SQL action Delete California customers after validation, stating that 591 rows would be deleted in a dry run" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/32-delete-validation.png" loading="lazy" />

5. Click **Create**, then **Run** the action. The count now gives 4,409 customers, none in California.

#### Restore the table

1. Go to **Lakehouse Manager** > **Tables**, open `customers`, then the *Time Travel* tab. The latest snapshot is **Data deleted**, on top of two **Data inserted** snapshots.

<img className="thumbnail" alt="The Time Travel tab of the table customers, listing a Data deleted snapshot on top of two Data inserted snapshots" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/33-time-travel-history.png" loading="lazy" />

2. Check a snapshot before restoring it, with its ID from the *Snapshot ID* column:

```sql
SELECT count(*) AS customers, count_if(state = 'CA') AS california
FROM customers FOR VERSION AS OF <snapshot ID>
```

The most recent **Data inserted** holds 5,000 customers. The oldest one is empty: it records the table creation, before the load.

3. Click the rollback icon (↻) on the most recent **Data inserted** snapshot, then **Rollback to snapshot**.

<img className="thumbnail" alt="The Rollback to snapshot window with the snapshot ID, its creation date and the caution message" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/34-rollback-confirmation.png" loading="lazy" />

A **Data rollbacked** line appears on top of the history, which keeps the deletion. The count gives 5,000 customers again, 591 in California.

<img className="thumbnail" alt="The Time Travel tab after the rollback, with Data rollbacked on top of the full history" src="/images/public-cloud/data-platform/getting-further/customer-data-governance/picts/35-time-travel-rolled-back.png" loading="lazy" />

## Good to know

- **Policy tags deny, they do not mask.** A query that includes a denied column fails as a whole. To give coarser data to a team, publish a view.
- **The default role DM & AM Editor bypasses policy tags.** It includes Advanced Data Access Control / Read without condition. Give data consumers a custom base role without any Advanced Data Access Control permission.
- **You cannot add yourself to a group.** The IAM prevents users from granting themselves rights.
- **Rights add up.** A user in several groups, or with several roles, gets access as soon as one of them allows it.
- **Check a snapshot before rolling back to it.** The oldest snapshot of a table can be empty: it records the table creation, before any data was loaded.
- **Validation shows the impact of a change.** In an SQL action, **Validate** runs the query as a dry run and gives the number of rows affected, before anything changes.
- **Time Travel has a time limit.** Snapshots are kept 14 days by default, between 7 and 28 days depending on the dataset or table setting. After that, a mistake can no longer be undone this way.

## What you have built

You have a customer table classified column by column, three teams with access matched to their needs, a governed view that gives analysts coarser data, and a way to undo a destructive mistake. The same pattern applies to any table that holds personal data: classify, define roles, test with a non-administrator, and keep Time Travel within reach.
