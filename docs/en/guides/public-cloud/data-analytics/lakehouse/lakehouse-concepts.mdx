## Objective

**This guide describes the building blocks of a Lakehouse and how they fit together.**

## Instructions

### The Lakehouse and its data

A **Lakehouse** lives in one region of your Public Cloud project. It holds your data as **Apache Iceberg** tables, an open table format, in an OVHcloud Object Storage bucket managed for you. Several engines can read and write the same tables at the same time: a table written with Python is immediately visible in SQL, and the other way round.

Data is organised in three levels:

| Level | Description | Example |
|---|---|---|
| **Catalog** | Top-level container. Engines connect to a catalog by its name. A Lakehouse can hold several catalogs, for example one per team or per environment. | `sales` |
| **Schema** | Groups tables inside a catalog (a *namespace* in Iceberg). | `raw` |
| **Table** | An Iceberg table, created with SQL or with an Iceberg client. Each change is kept as a snapshot of the table. | `orders` |

You create catalogs and schemas in the OVHcloud Control Panel or the API. Tables are created by your engines (SQL, Python, DuckDB…).

### Access points

The **Connection details** section of the **Overview** tab lists how to reach the data:

- **Iceberg REST catalog**: for any tool that speaks the Iceberg REST protocol (pyiceberg, DuckDB, Spark, Trino…). Requests carry the realm of the Lakehouse in the `Polaris-Realm` header.
- **SQL endpoint**: a Trino-compatible endpoint (JDBC or HTTPS) provided with the Lakehouse. Each catalog is exposed under its own SQL catalog name, shown in the connection details.
- **S3**: the bucket that stores the files of the tables, for tools that read or write them directly.
- **Data console**: a web interface to browse catalogs, run SQL queries, load files and review the query history.

### Users, roles and credentials

Data access is managed inside the Lakehouse:

- A **user** is a person (type **User**) or an application (type **Service account**). Users can be gathered in **groups**.
- A **role** grants privileges on the data: read (`BROWSE`, `SELECT`), write (`INSERT`, `UPDATE`, `DELETE`) and structure (`CREATE_TABLE`, `ALTER`, `DROP`). Six roles are provided (**Lakehouse Admin**, **Data Owner**, **Data Editor**, **Data Viewer**, **Metadata Viewer**, **User Admin**) and you can create custom roles.
- A role is **assigned** to a user, a service account or a group. A predefined role can be narrowed to one catalog when you assign it.
- A **credential** is a client ID and a client secret that act with the rights of the user's roles. It can also include an S3 access key. A credential expires after 10 minutes to 90 days and can be revoked at any time.

:::info
The roles of the Lakehouse only control access to the data. Managing the Lakehouse itself (creating catalogs, users or roles, assigning roles) is controlled by OVHcloud IAM, like any other resource of your project.
:::

### Compute

SQL queries run on a **Compute Pool**:

- By default, they run on the **shared Compute Pool** of the region.
- You can add a **dedicated Compute Pool**, sized for your needs and reserved for your Lakehouse. It suspends itself after a period without queries and resumes on the next query.

The SQL address of the Lakehouse stays the same in both cases. See [Lakehouse - Using a dedicated Compute Pool](/guides/public-cloud/data-analytics/lakehouse/lakehouse-compute-pools).

Tools connected to the Iceberg REST catalog (Python, DuckDB…) use their own compute and do not use a Compute Pool.

### Network access

By default, every address can reach the Lakehouse, provided it holds a valid credential. You can restrict access to a list of IP addresses. See [Lakehouse - Restricting network access](/guides/public-cloud/data-analytics/lakehouse/lakehouse-network-access).
