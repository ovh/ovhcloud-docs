## Objective

Kafka MirrorMaker continuously copies the messages of Kafka topics from a source Kafka service to a target Kafka service. You can use it to migrate to a new Kafka service or version, or to keep a copy of your topics in another service.

This guide explains how to replicate a topic between two Kafka services of the same Public Cloud project with the OVHcloud API.

## Requirements

- A [Public Cloud project](/links/public-cloud/public-cloud) in your OVHcloud account
- Two [Kafka services](/guides/public-cloud/data-analytics/analytics/kafka-create-cluster) in this project: a source and a target. They can run different Kafka versions; this guide was tested with a Kafka 3.9 source and a Kafka 4.3 target.
- A topic to replicate on the source service, here `inventory`
- A Kafka MirrorMaker service in the same project
- Access to the [OVHcloud API](/guides/manage-and-operate/api/first-steps)

## Instructions

### Step 1 - Linking both Kafka services to MirrorMaker

On your MirrorMaker service, create one integration for the source service and one for the target service:

<Api version="v1" section="/cloud" method="POST" route={"/cloud/project/\{serviceName\}/database/kafkaMirrorMaker/\{clusterId\}/integration"} />

```json
{
  "type": "kafkaMirrorMaker",
  "sourceServiceId": "<source Kafka service ID>",
  "destinationServiceId": "<MirrorMaker service ID>"
}
```

```json
{
  "type": "kafkaMirrorMaker",
  "sourceServiceId": "<target Kafka service ID>",
  "destinationServiceId": "<MirrorMaker service ID>"
}
```

In both cases, `sourceServiceId` is the Kafka service and `destinationServiceId` is the MirrorMaker service. Keep the `id` returned for each integration.

### Step 2 - Creating the replication flow

Create a replication flow from the source integration to the target integration:

<Api version="v1" section="/cloud" method="POST" route={"/cloud/project/\{serviceName\}/database/kafkaMirrorMaker/\{clusterId\}/replication"} />

```json
{
  "sourceIntegration": "<source integration ID>",
  "targetIntegration": "<target integration ID>",
  "topics": ["inventory"],
  "syncGroupOffsets": true,
  "syncInterval": 60,
  "emitHeartbeats": true,
  "enabled": true
}
```

The API returns the replication flow with its default replication policy:

```json
{
  "id": "<replication ID>",
  "sourceIntegration": "<source integration ID>",
  "targetIntegration": "<target integration ID>",
  "replicationPolicyClass": "org.apache.kafka.connect.mirror.DefaultReplicationPolicy",
  "topics": ["inventory"],
  "topicExcludeList": [],
  "syncGroupOffsets": true,
  "syncInterval": 60,
  "emitHeartbeats": true,
  "enabled": true
}
```

In this replication flow:

- `topics` lists the topics to replicate, and `topicExcludeList` the topics to leave out;
- `syncGroupOffsets` copies the offsets of the consumer groups to the target service, every `syncInterval` seconds;
- `emitHeartbeats` makes MirrorMaker write heartbeat messages to the target service.

### Step 3 - Checking the replicated topic

With the default replication policy, the replicated topic is created on the target service with the alias of the source service as a prefix. For the `inventory` topic, the target service contains a topic of the form `xxxxxxxxx.kafka-xxxxxxxx.inventory`, with the same messages as the source topic.

MirrorMaker also creates its own topics on the target service: `heartbeats`, `xxxxxxxxx.kafka-xxxxxxxx.checkpoints.internal`, and topics starting with `mm2-`.

To read the replicated messages, grant your users a `read` ACL on the replicated topic of the target service. See the [ACL guide](/guides/public-cloud/data-analytics/analytics/kafka-configure-acl).

### Step 4 - Managing the replication flow

Read or delete a replication flow:

<Api version="v1" section="/cloud" method="GET" route={"/cloud/project/\{serviceName\}/database/kafkaMirrorMaker/\{clusterId\}/replication/\{replicationId\}"} />

<Api version="v1" section="/cloud" method="DELETE" route={"/cloud/project/\{serviceName\}/database/kafkaMirrorMaker/\{clusterId\}/replication/\{replicationId\}"} />
