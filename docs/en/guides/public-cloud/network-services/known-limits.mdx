## Private Network

### One vRack per Public Cloud project

For a given Public Cloud project, you can attach only one vRack. If you wish to build private connectivity between 2 (or more) Public Cloud projects, you should attach the same vRack to those Public Cloud projects.

### IPs used by services

When a service is spawned in a subnet, it uses some IPs from the subnet CIDR. The following table provides the number of IPs used by each service. If the subnet has a "small" number of available IPs, this can have impact. If all L3 services are in use, the total number of IPs used will be 7. We advise to use at least a `/28` mask.

| Service | In DHCP allocation pool | Outside of allocation pool (gateway_ip) |
| :---: | :---: | :---: |
| DHCP | 2 | |
| Public Cloud Gateway | 1 | 1 |
| Public Cloud Load Balancer (Octavia) | 3 | |

### Subnet allocation pool update

When updating an allocation pool, e.g. from `[10.0.0.2:10.0.0.255]` to `[10.0.0.128:10.0.0.255]`, **all IPs already used prior to the allocation pool update are kept even if they are not in the new allocation pool.**

For instance, if the subnet DHCP is activated, the IPs `10.0.0.2` and `10.0.0.3` will be used by DHCP servers and will still be used after the pool update.

In order to release these IPs, you need to delete the two DHCP ports. They will be recreated automatically in the updated allocation pool. This can be done in Horizon or using the OpenStack CLI.

For instance, you can delete all the dhcp ports from the private network with ID `<PRIVATE_NETWORK_ID>` with:

```bash
openstack port list --network <PRIVATE_NETWORK_ID> --device-owner network:dhcp -f value -c ID | xargs -I {} openstack port delete {}
```

Then check the newly created port that should be inside the updated IP allocation pool with:

```bash
openstack port list --network <PRIVATE_NETWORK_ID> --device-owner network:dhcp
+--------------------------------------+------+-------------------+---------------------------------------------------------------------------+--------+
| ID                                   | Name | MAC Address       | Fixed IP Addresses                                                        | Status |
+--------------------------------------+------+-------------------+---------------------------------------------------------------------------+--------+
| 4d991711-4322-4934-a06e-2e2b9cff2a56 |      | fa:16:3e:cc:48:27 | ip_address='10.0.0.129', subnet_id='578deb7c-211f-4f0f-8e45-c8ed07b3e16b' | ACTIVE |
| 738e3c59-439d-4eed-bded-c7c301717a8c |      | fa:16:3e:62:32:5e | ip_address='10.0.0.128', subnet_id='578deb7c-211f-4f0f-8e45-c8ed07b3e16b' | ACTIVE |

```

### No cross-region IP or MAC collision check

When Private Networks in several regions share the same VLAN ID, they form one private network segment, but each region manages its own addresses: IP and MAC address uniqueness is not enforced across regions. Two regions can use the same CIDR with overlapping allocation pools, and two ports in two regions can get the same fixed IP or the same MAC address. No error is returned at creation; the conflict only shows up later, as a duplicate address.

**Mitigation:** Keep the addressing plan disjoint — one CIDR per region, or one shared CIDR with split allocation pools — and choose fixed IPs inside the region's own range.

### No IP address conflict detection with other vRack products

Nothing prevents a Public Cloud instance from getting a private IP address already used, on the same vRack, by another OVHcloud product (Bare Metal server, Hosted Private Cloud…). The conflict is not detected, and only shows up later as a duplicate address.

**Mitigation:** Keep the other products' addresses out of the Subnet's allocation pools.

### No vRack in a Local Zone

A [Local Zone](/guides/public-cloud/compute/local-zones-capabilities-limitations) is not connected to the vRack. A Private Network created there stays confined to the Local Zone: it cannot be routed to Private Networks of other regions, nor connected to other OVHcloud products (Bare Metal servers, Hosted Private Cloud). For the same reason, it has no VLAN ID.

**Mitigation:** None within the Local Zone — a workload that needs vRack connectivity or a multi-region L2 domain must run in a standard region.

## Public IPs

### OpenStack router and Floating IP routing conflict

The `172.31.0.0/17` range is reserved for Floating IP routing on the Ext-Net network. If one of your private subnets overlaps with this range, routing conflicts may occur, preventing Floating IP traffic from working correctly.

:::warning
Avoid using any CIDR within the `172.31.0.0/17` range for your private subnets when Floating IPs are in use. Use a different private address range (e.g. `10.0.0.0/8` or `192.168.0.0/16`) to prevent routing conflicts.

:::

### No Floating IP in a Local Zone

[Floating IPs](/guides/public-cloud/network-services/attach-floating-ip-to-instance) are not available in a Local Zone. Public connectivity relies entirely on each instance's Basic IP, which is bound to the instance: no public address can be moved from one instance to another.

**Mitigation:** None for a movable address — the Basic IP still routes ingress and egress without a Gateway.

### No IPv6 on Basic IP in EU-WEST-PAR and EU-SOUTH-MIL

In the EU-WEST-PAR and EU-SOUTH-MIL regions, an instance created with a Basic IP as its public connectivity only gets IPv4, while in the other regions its public interface carries both an IPv4 and an IPv6 address. These two regions use a separate public network for IPv6, `ext-net-v6`, to which the instance is not attached.

**Mitigation:** Attach the instance to the `ext-net-v6` network through OpenStack.

### No Internet egress through a Floating IP alone

A Floating IP only carries inbound traffic. An instance with a Floating IP and no Gateway on its Subnet is reachable from the internet, but cannot open outbound connections.

**Mitigation:** Attach a [Gateway](/guides/public-cloud/network-services/getting-started-gateway) to the Subnet — on the OVHcloud API it is a prerequisite of the Floating IP attachment itself.

## Gateway

### No Gateway in a Local Zone

You cannot create a Gateway in a Local Zone, so no Subnet there can get outbound internet access through a Gateway.

**Mitigation:** A Basic IP on each instance routes both directions without a Gateway — per instance, not shared.

### One Gateway cannot serve Subnets with overlapping CIDRs

A Gateway can be attached to Subnets of several Private Networks, but not to two Subnets whose address ranges overlap, such as two `10.0.0.0/24` Subnets in two different Private Networks: the second attachment fails. Private Networks that reuse the same addressing plan need one Gateway each.

**Mitigation:** Use one Gateway per Private Network whose Subnets overlap, each with its own public IP, or keep a disjoint addressing plan across the Private Networks that must share a Gateway.

### A Gateway does not route traffic between Private Networks

A Gateway attached to Subnets of several Private Networks gives them outbound internet access and a shared public IP, but it does not connect those Private Networks to each other: it cannot be used to make instances of two Private Networks communicate.

### Exactly one public IP per Gateway

A Gateway always has exactly one public IP, assigned automatically. You cannot create a Gateway without a public IP, add a second one, or choose the address.

## Load Balancer

### Default quotas

| Resource | Default quota |
| --- | --- |
| Maximum number of load balancers | 10 |
| Maximum number of listeners | 100 |
| Maximum number of pools | 100 |
| Maximum number of members | 500 |
| Maximum number of health monitors | 100 |
| Maximum number of L7 policies | 50 |
| Maximum number of L7 rules | 250 |

### ICMP traffic towards Load Balancer IP

Traffic towards the Load Balancer IP (private IP or Floating IP) is filtered, which means that these IPs do not answer `ping` requests.

### One-call Load Balancer creation fails with an HTTPS listener

Creating a Load Balancer and a `TERMINATED_HTTPS` listener in the same request fails.

**Mitigation:** Create the Load Balancer with an HTTP listener (or none) first, then create the `TERMINATED_HTTPS` listener separately with an `OPAQUE` PKCS#12 secret.

### Floating IP created with the Load Balancer outlives it

Deleting a Load Balancer removes its listeners, pools, members, health monitors and L7 policies, but not a Floating IP created at the same time as the Load Balancer. The Floating IP stays in your project, and is still billed.

**Mitigation:** Delete the Floating IP explicitly after deleting the Load Balancer.

### Certificate for an IP address refused

A `TERMINATED_HTTPS` listener refuses a certificate issued for an IP address only, such as a Let's Encrypt IP certificate: the certificate must name a domain. A Load Balancer reached only by its public IP cannot serve a publicly trusted certificate.

**Mitigation:** Point a domain name at the Load Balancer's Floating IP and certify that name.

### TLS certificate accepted only as a PKCS#12 secret

A `TERMINATED_HTTPS` listener only accepts a certificate stored as a single secret containing a PKCS#12 bundle (certificate, private key and optional chain). Other formats are refused.

**Mitigation:** Bundle the certificate, key and chain into a PKCS#12 file and store it as one `OPAQUE` secret. See how to [configure a third-party certificate on a Load Balancer](/guides/public-cloud/network-services/load-balancer-third-party-certificat).

### No built-in Let's Encrypt certificate

The Load Balancer does not obtain or renew Let's Encrypt certificates by itself. You obtain the certificate with your own ACME client, store it, and replace it on the listener at every renewal, before it expires.

**Mitigation:** Automate renewal with an ACME client whose deploy hook stores the new certificate as a PKCS#12 secret and swaps it on the listener; keep port 80 open to Let's Encrypt.

## Private Endpoint

### A Private Endpoint is effectively immutable

Only the name and the description of a Private Endpoint can be changed. The service, the Subnet, the private IP and the public DNS setting are chosen at creation: changing them means deleting and recreating the endpoint, which gets a new private IP unless you set it explicitly.

**Mitigation:** Pin the private IP address at creation, so a recreated endpoint keeps the same address.

### One Private Endpoint per service and Subnet

A Subnet cannot hold two Private Endpoints for the same service.

**Mitigation:** Place the second endpoint in another Subnet.

## Security Group

### The default Security Group is permissive

The region's default Security Group, applied when an instance is created without an explicit Security Group, allows all inbound traffic.

**Mitigation:** Always create instances with an explicit, restrictive [Security Group](/guides/public-cloud/compute/setup-security-group). Do not modify or delete the `default` group itself: automated tasks on the infrastructure can reset it.

### One Security Group set per instance, instances only

This limitation applies to Security Groups managed through the OVHcloud API. Security Groups apply to the instance as a whole: its public and private interfaces always get the same filtering, and there is no per-interface Security Group. A Security Group cannot be applied to a Load Balancer, a Gateway or a Private Endpoint.

**Mitigation:** Use the OpenStack API directly if you need per-port Security Group assignment.

## General

### Instance bandwidth

To achieve the maximum bandwidth provided with each instance you may need to use **multi-flow**.

For example, when using iperf to test your instance bandwidth, you can enable multi-flow by adding the `-P n` or `--parallel n` option. If n = 1 (which is the default if this option is omitted), you are testing bandwidth with a single flow. To achieve maximum bandwidth, you should increase the value of n.
