## Objective

**This page lists the known limitations of the Private Network and its Subnets: performance limitations, functional limitations with their workarounds, and quotas.**

## Performance limitations

A Private Network and its Subnets have no model or size: their throughput is bounded by the bandwidth of the instances attached to them. See [Instance bandwidth](/guides/public-cloud/network-services/known-limits#instance-bandwidth).

## Functional limitations

### One vRack per Public Cloud project

A Public Cloud project is attached to exactly one vRack. To build private connectivity between two or more Public Cloud projects, attach the same vRack to those projects.

### No vRack in a Local Zone

A Local Zone is not connected to the vRack. A Private Network created there stays confined to the Local Zone: it cannot be routed to Private Networks of other regions, nor connected to other OVHcloud products (Bare Metal servers, Hosted Private Cloud). For the same reason, it has no VLAN ID.

**Workaround:** none within a Local Zone. A workload that needs vRack connectivity or a multi-region Private Network must run in a standard region.

### No cross-region IP or MAC collision check

When Private Networks in several regions share the same VLAN ID, they form one private network segment, but each region manages its own addresses and nothing checks them across regions. Two regions can use the same CIDR with overlapping allocation pools, and two ports in two regions can get the same fixed IP or the same MAC address. The conflict is accepted at creation and only shows up later, as a duplicate address.

**Workaround:** keep the addressing plan disjoint: one CIDR per region, or one shared CIDR with a separate allocation pool and a distinct gateway IP in each region, the gateway IP outside every region's allocation pools; choose fixed IPs inside the region's own range. If you do not need the same private network segment across regions, use a different VLAN ID in each region.

### No IP address conflict detection with other vRack products

Nothing prevents a Public Cloud instance from getting a private IP address already used, on the same vRack, by another OVHcloud product (Bare Metal server, Hosted Private Cloud…). The conflict is not detected, and only shows up later as a duplicate address.

**Workaround:** keep the addresses of the other products out of the Subnet's allocation pools.

### IPs used by services

A service spawned in a Subnet uses IPs from the Subnet's CIDR. With all services in use, 7 IPs are taken: use at least a `/28` mask.

| Service | IPs in the allocation pool | IPs outside the allocation pool (gateway IP) |
| :---: | :---: | :---: |
| DHCP | 2 | |
| Gateway | 1 | 1 |
| For each Load Balancer | 3 | |

The range of a Subnet cannot be changed after its creation: a Subnet sized too small must be recreated.

**Workaround:** size the Subnet with this headroom: at least a `/28` when a Gateway and a Load Balancer are planned on it.

### Allocation pool update keeps the IPs already used

When you update an allocation pool, for example from `[10.0.0.2:10.0.0.254]` to `[10.0.0.128:10.0.0.254]`, **all IPs already used before the update are kept, even if they are outside the new allocation pool.** The update succeeds with no error or warning.

For instance, if DHCP is enabled on the Subnet, the IPs `10.0.0.2` and `10.0.0.3` are used by the DHCP servers and stay in use after the update. Instances, Gateways and Load Balancers keep their addresses too.

**Workaround:** delete the two DHCP ports, in Horizon or with the OpenStack CLI. They are recreated automatically in the updated allocation pool. Move or recreate the other resources whose address must leave the old range.

For instance, to delete all the DHCP ports of the Private Network with ID `<PRIVATE_NETWORK_ID>`:

```bash
openstack port list --network <PRIVATE_NETWORK_ID> --device-owner network:dhcp -f value -c ID | xargs -I {} openstack port delete {}
```

Then check that the new ports are inside the updated allocation pool:

```bash
openstack port list --network <PRIVATE_NETWORK_ID> --device-owner network:dhcp
+--------------------------------------+------+-------------------+---------------------------------------------------------------------------+--------+
| ID                                   | Name | MAC Address       | Fixed IP Addresses                                                        | Status |
+--------------------------------------+------+-------------------+---------------------------------------------------------------------------+--------+
| 4d991711-4322-4934-a06e-2e2b9cff2a56 |      | fa:16:3e:cc:48:27 | ip_address='10.0.0.129', subnet_id='578deb7c-211f-4f0f-8e45-c8ed07b3e16b' | ACTIVE |
| 738e3c59-439d-4eed-bded-c7c301717a8c |      | fa:16:3e:62:32:5e | ip_address='10.0.0.128', subnet_id='578deb7c-211f-4f0f-8e45-c8ed07b3e16b' | ACTIVE |
+--------------------------------------+------+-------------------+---------------------------------------------------------------------------+--------+
```

### Subnets in `172.31.0.0/17` conflict with Floating IP routing

The `172.31.0.0/17` range is reserved for the routing of Floating IPs. A Subnet whose CIDR overlaps this range can prevent Floating IP traffic from working. Nothing prevents you from creating such a Subnet or attaching a Floating IP to it: the problem only shows up when traffic fails.

:::warning
Do not use a CIDR within `172.31.0.0/17` for your Subnets when you use Floating IPs. Use another private range, for example `10.0.0.0/8` or `192.168.0.0/16`.
:::

**Workaround:** recreate an affected Subnet in another range.

## Quotas

Private Networks and Subnets are limited by the quotas of your project, per project and per region. See [Quotas](/guides/public-cloud/network-services/known-limits#quotas).
