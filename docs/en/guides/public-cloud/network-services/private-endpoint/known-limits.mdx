## Objective

**This page lists the known limitations of the Private Endpoint: performance limitations, functional limitations with their workarounds, and quotas.**

## Performance limitations

A Private Endpoint is created at a tier (S, M or L), chosen at creation and not changeable afterwards. Each tier has its own bandwidth, published per service and per region:

| Service | S | M | L |
|---|---|---|---|
| S3 — bandwidth | 500 Mbit/s | 2 Gbit/s | 4 Gbit/s |

To get more bandwidth, create a new Private Endpoint at a higher tier.

## Functional limitations

### A Private Endpoint is effectively immutable

Only the name and the description of a Private Endpoint can be changed. The service, the Subnet, the private IP and the public DNS setting are chosen at creation: changing them means deleting and recreating the endpoint, which gets a new private IP unless you set it explicitly.

**Workaround:** set the private IP at creation, so that a recreated endpoint keeps the same address.

### One Private Endpoint per service and Subnet

A Subnet cannot hold two Private Endpoints for the same service.

**Workaround:** create the second endpoint in another Subnet.

## Quotas

Private Endpoints are limited by the quotas of your project, per project and per region. See [Quotas](/guides/public-cloud/network-services/known-limits#quotas).
