## Objective

This guide shows you how to manage scheduling on your OVHcloud Managed Kubernetes Service:

- Propagate *labels*, *annotations* and *taints* to Nodes through a `Node Pool` template (recommended with autoscaling, when Nodes are created and deleted automatically)
- Target all Nodes in a Node Pool with `kubectl` using the propagated `nodepool` label

This enables multiple scheduling scenarios, like optimizing the cost of a cluster by distributing `Pods` across two labelled `Node Pools`, or dedicating a Node Pool to specific workloads.

## Requirements

- a [Public Cloud project](/links/public-cloud/public-cloud) in your OVHcloud account
- [kubectl](https://kubernetes.io/docs/tasks/tools/) configured to access your cluster
- [Terraform](https://developer.hashicorp.com/terraform/install), if you create the Node Pool with Terraform

## Instructions

### Create a Kubernetes cluster

You can follow the Kubernetes cluster creation step by step guide if you want to create it through the [OVHcloud Console](/guides/public-cloud/containers-orchestration/managed-kubernetes/label-nodeaffinity-node-pools#cluster-creation) or through [Terraform](/guides/public-cloud/containers-orchestration/managed-kubernetes/create-cluster).

### Manage Node Pools via the API

You can create a Node Pool template through the API. You can use the [API Explorer](/guides/manage-and-operate/api/first-steps) for example to interact with our API.

To create a Node Pool with a template (labels, annotations, taints...), you have to make a call on:

<Api version="v1" section="/cloud" method="POST" route={"/cloud/project/\{serviceName\}/kube/\{kubeId\}/nodepool"} />


with the following request body:

```json
{
  "name": "my-system-node-pool",
  "flavorName": "b3-8",
  "desiredNodes": 1,
  "minNodes": 0,
  "maxNodes": 1,
  "template": {
    "metadata": {
      "annotations": {
        "my-annotation": "my-value"
      },
      "labels": {
        "app": "my-app"
      }
    },
    "spec": {
      "unschedulable": false,
      "taints": [
        {
          "effect": "NoSchedule",
          "key": "CriticalAddonsOnly",
          "value": "true"
        }
      ]
    }
  }
}
```

Replace `serviceName` and `kubeId` with your Public Cloud project ID and cluster ID in the endpoint path.

`effect` accepts `NoSchedule` (Pods without a matching toleration cannot be scheduled), `PreferNoSchedule` (Kubernetes avoids scheduling them), or `NoExecute` (they are evicted). `key` and `value` can be any values specific to your workloads; `CriticalAddonsOnly=true` is the pair tolerated by OVHcloud system components. Tolerations must match the key and value, and the effect when one is specified.

The `CriticalAddonsOnly` taint reserves the Node Pool for OVHcloud system workloads (CoreDNS, metrics-server, etc.), which tolerate it. Workloads that do not tolerate this taint cannot be scheduled on this Node Pool.

:::warning
A MKS cluster needs at least one Node on which its system components can be deployed. This can be:

- a Node with no taint at all;
- a Node whose only taint is `CriticalAddonsOnly`.

If all Nodes are tainted in a way that prevents this, the cluster will not be operational.

:::

To evict Pods that do not tolerate the taint instead of only preventing new scheduling, use the `NoExecute` effect. Pods that must remain on the Node need a toleration with the `NoExecute` effect.

#### Delete the Node Pool through the API

To delete a Node Pool with the API, use the following call:

<Api version="v1" section="/cloud" method="DELETE" route={"/cloud/project/\{serviceName\}/kube/\{kubeId\}/nodepool/\{nodePoolId\}"} />


with the following information:

- `serviceName`: your Public Cloud project ID
- `kubeId`: your cluster ID
- `nodePoolId`: the ID of the node pool to delete

### Create a Node Pool Template with Terraform

Check out the [OVH Terraform provider](https://registry.terraform.io/providers/ovh/ovh/latest/docs/resources/cloud_project_kube_nodepool) for the full documentation.

#### Getting your cluster/API tokens information

The "OVH provider" needs to be configured with a set of credentials:

* an `application_key`
* an `application_secret`
* a `consumer_key`

**Why?**

Because, behind the scenes, the "OVH Terraform provider" is doing requests to OVHcloud APIs. 

In order to retrieve this necessary information, please follow our [First steps with the OVHcloud APIs](/guides/manage-and-operate/api/first-steps) tutorial.

Specifically, you have to generate these credentials via the <CreateToken rights="GET=/*&POST=/*&PUT=/*&DELETE=/*">OVHcloud token generation page</CreateToken> with the following rights: **GET**, **POST**, **PUT** and **DELETE** on `/*`.

When you have successfully generated your OVHcloud tokens, please save them as you will have to use them very soon.

The last needed information is the `service_name`: it is the ID of your Public Cloud project.

**How to get it?**

To retrieve your Public Cloud project ID, click the project selector at the top of the left-hand menu of your Public Cloud project, then click the copy icon on the row of your project (it appears when you hover the row).

You will also use this information in Terraform resources definition files.

#### Terraform instructions

First, create a `provider.tf` file with the minimum version, the European endpoint (`ovh-eu`) and the keys previously retrieved in this guide.

```terraform
terraform {
  required_providers {
    ovh = {
      source = "ovh/ovh"
    }
  }
}

provider "ovh" {
  endpoint           = "ovh-eu"
  application_key    = "<your_access_key>"
  application_secret = "<your_application_secret>"
  consumer_key       = "<your_consumer_key>"
}
```

Alternatively the secret keys can be retrieved from your environment.

- `OVH_ENDPOINT`
- `OVH_APPLICATION_KEY`
- `OVH_APPLICATION_SECRET`
- `OVH_CONSUMER_KEY`

This latter method (or a similar alternative) is recommended to avoid storing secret data in a source repository.

Here, we defined the `ovh-eu` endpoint because we want to call the OVHcloud Europe API, but other endpoints exist, depending on your needs:

* `ovh-eu` for OVHcloud Europe API
* `ovh-us` for OVHcloud US API
* `ovh-ca` for OVHcloud North-America API

Then, define the resources you want to create in a new file called `ovh_kube_cluster_nodepool.tf`:

```terraform
resource "ovh_cloud_project_kube_nodepool" "pool" {
    service_name  = "<service_name>"
    kube_id       = "<cluster_id>"
    name          = "my-system-node-pool"
    flavor_name   = "b3-8"
    desired_nodes = 1
    min_nodes     = 0
    max_nodes     = 1
    template {
        metadata {
            annotations = {
                my-annotation = "my-value"
            }
            labels = {
                app = "my-app"
            }
        }
        spec {
            unschedulable = false
            taints = [
                {
                    effect = "NoSchedule" // NoSchedule, PreferNoSchedule or NoExecute
                    key    = "CriticalAddonsOnly" // Or a key specific to your workloads
                    value  = "true" // Or a value specific to your workloads
                }
            ]
        }
    }
}
```

:::info
Don't forget to replace `<service_name>` and `<cluster_id>` with your values.
:::


In this resource configuration, we ask Terraform to add a Node Pool with a template to your Kubernetes cluster.

:::info
Go to the **ovh terraform provider** documentation in order to see the [ovh_cloud_project_kube_nodepool resource definition](https://registry.terraform.io/providers/ovh/ovh/latest/docs/resources/cloud_project_kube_nodepool).
:::

### Check everything is correctly configured

To do some operations on your Nodes, through `kubectl` CLI, we invite you to follow our guide to [configuring default settings](/guides/public-cloud/containers-orchestration/managed-kubernetes/configure-kubectl).

### Operate existing Nodes with kubectl

A taint, cordon or drain applied with `kubectl` only affects the Nodes that exist at that moment. When autoscaling creates new Nodes, they do not inherit those `kubectl` changes — use the Node Pool template above for lasting configuration.

Thanks to the `nodepool` label propagated to every Node, you can target all Nodes of a given Node Pool by adding `-l "nodepool=my-system-node-pool"` to commands such as `kubectl cordon`, `kubectl drain` or `kubectl taint node`. For the operations themselves and their effects, see the Kubernetes documentation on [taints and tolerations](https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/) and [safely draining a Node](https://kubernetes.io/docs/tasks/administer-cluster/safely-drain-node/).

### Delete the Node Pool with Terraform

To delete the Node Pool, remove its `ovh_cloud_project_kube_nodepool` resource block from `ovh_kube_cluster_nodepool.tf`, then review and apply the resulting plan:

```bash
$ terraform plan

Plan: 0 to add, 0 to change, 1 to destroy.

$ terraform apply

Apply complete! Resources: 0 added, 0 changed, 1 destroyed.
```

This targets the resource you removed from the configuration.
