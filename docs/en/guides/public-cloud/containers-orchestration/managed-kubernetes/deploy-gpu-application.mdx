## Objective

In this tutorial we will show you how to deploy a GPU application on an OVHcloud Managed Kubernetes cluster.

GPUs provide compute power to drive AI/ML & Deep Learning tasks with intensive calculations such as image recognition, natural language processing (NLP), as well as other compute-intensive tasks such as video transcoding and image processing.

Using GPUs with Kubernetes allows you to extend the scalability of Kubernetes to AI/ML applications.

## Before you begin

This tutorial presupposes that you already have a working OVHcloud Managed Kubernetes cluster, and some basic knowledge of how to operate it. If you want to know more on those topics, please look at the [OVHcloud Managed Kubernetes Service Quickstart](/guides/public-cloud/containers-orchestration/managed-kubernetes/deploy-hello-world).

You also need to have [Helm](https://docs.helm.sh/) installed on your workstation and your cluster. Please refer to the [How to install Helm on OVHcloud Managed Kubernetes Service](/guides/public-cloud/containers-orchestration/managed-kubernetes/install-helm) tutorial.

## Prerequisites

To get the best and most cost-effective benefit from GPUs on OVHcloud Managed Kubernetes, and to take advantage of cluster autoscaling, we recommend that you create separate GPU node pools in your Kubernetes clusters.

GPU node pools group nodes of the same GPU flavor and can be configured with autoscaling to handle variable workloads efficiently.

The GPU operator that you will install should run on Kubernetes nodes that are equipped with GPUs.

Create a node pool that uses a GPU flavor. The [worker node flavors](/guides/public-cloud/containers-orchestration/managed-kubernetes/datacenters-nodes-storage-flavors#available-worker-nodes-flavors) list shows the GPU flavors and their regions, and the [Public Cloud prices](/links/public-cloud/prices) page shows the GPU model of each flavor. The driver installed later depends on the architecture:

- Current architectures: `A100-180`, `H100-*`, `L4-*`, `L40s-*` and `rtx5000-*` (Ampere, Hopper, Ada and Turing).
- Tesla V100 and V100S: `T1-*` and `T2-*` (Volta).

If you already have an OVHcloud Kubernetes cluster with a GPU node pool, you can skip the following `Autoscaling GPU Node Pool creation` step.

:::warning
GPU Virtual machines are extremely powerful and significantly more expensive than general purpose nodes. If you are usually using OVHcloud Public Cloud at small scale and/or are a new user, you may need to [raise your Public Cloud quota](/guides/public-cloud/cross-functional/increasing-public-cloud-quota) to enable access to those type of machines for your project. Also note that these machines are only available in some of our Public Cloud regions.

Also note that while worker nodes (be them added manually or through cluster autoscaler) are created within a few minutes, our GPU worker nodes ready status can take up to a bit more than one hour.
:::

## Instructions

### Autoscaling GPU Node Pool creation

Click on your cluster, then on the <code className="action">Node pools</code> tab.

We will create our special GPU Node Pool.
Click on <code className="action">Add a node pool</code>.

In the node pool creation form, enter a name for your GPU node pool (for example, `gpu-node-pool`).

On the flavor selection step, click the **GPU** tab. For a current GPU, choose a flavor such as `H100`, `L4`, `L40S`, `A100-180` or `rtx5000`. For a Tesla V100 or V100S, choose a `T1` or `T2` flavor, for example **T1-45**.

Set the node count and, if desired, enable **Autoscaling** and define the minimum and maximum pool size (for example, 3 minimum and 10 maximum).

Select **Hourly** as the billing mode for this GPU node pool.

The node pool creation is now in progress. It should be available within a few minutes in your OVHcloud Control Panel.

```bash
kubectl get node --show-labels | grep "node.k8s.ovh/type=gpu"
```

Once the node pool status shows `OK` in the OVHcloud Control Panel, you can confirm the GPU nodes are correctly labelled using the command above.

### NVIDIA GPU Operator

The [NVIDIA GPU Operator](https://github.com/NVIDIA/gpu-operator) uses the [Operator Framework](https://github.com/operator-framework/getting-started) within Kubernetes to automate the management of all NVIDIA software components needed to provision GPU. These components include the NVIDIA drivers (to enable CUDA), Kubernetes device plugin for GPUs, the NVIDIA Container Runtime, automatic node labelling, DCGM based monitoring and others.

![NVIDIA GPU Kubernetes Operator](/images/public-cloud/containers-orchestration/managed-kubernetes/deploying-gpu-application/nvidia-gpu-operator.jpeg)

If you are interested about the operator, feel free to read the [NVIDIA GPU operator official documentation](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/overview.html).

### Installing the NVIDIA GPU Operator Helm chart

For this tutorial we are using the [NVIDIA GPU Operator Helm chart](https://github.com/NVIDIA/gpu-operator/tree/master/deployments/gpu-operator) found on [NVIDIA repository](https://github.com/nvidia/). The chart is [fully configurable](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/getting-started.html). The commands below set only the driver options required for the GPU architecture of your node pool.

Add the NVIDIA Helm repository:

:::info
The Nvidia Helm chart has moved. If you already added a repo with the name `nvidia`, you can remove it: `helm repo remove nvidia`.

:::


```bash
helm repo add nvidia https://helm.ngc.nvidia.com/nvidia
helm repo update
```

This will add the NVIDIA repository and update all of your repositories: 

```console
$ helm repo add nvidia https://helm.ngc.nvidia.com/nvidia
helm repo update
"nvidia" has been added to your repositories
Hang tight while we grab the latest from your chart repositories...
...Successfully got an update from the "nvidia" chart repository
[...]
Update Complete. ⎈Happy Helming!⎈
```

Install the GPU Operator in the `gpu-operator` namespace. Pick the tab that matches the GPU flavor of the node pool. Each command compiles the driver modules for the node kernel.

<Tabs>
<Tab label="L4, L40S, H100, A100">

On the [NGC driver catalog](https://catalog.ngc.nvidia.com/orgs/nvidia/containers/driver/tags), select the latest Ubuntu 22.04 tag of the form `` `<version>-ubuntu22.04` ``. Pass that version to `driver.version` (e.g: 595.91.07).

```bash
helm install gpu-operator nvidia/gpu-operator \
  -n gpu-operator --create-namespace \
  --set driver.version=<version> \
  --set driver.usePrecompiled=false
```

</Tab>
<Tab label="RTX 5000">

On the [NGC driver catalog](https://catalog.ngc.nvidia.com/orgs/nvidia/containers/driver/tags), select the latest Ubuntu 22.04 tag of the form `` `<version>-ubuntu22.04` ``. Pass that version to `driver.version` (e.g: 595.91.07).

The Quadro RTX 5000 does not initialize with GPU firmware enabled. Create a ConfigMap that disables it:

```bash
kubectl create namespace gpu-operator
kubectl create configmap kernel-module-params -n gpu-operator \
  --from-literal=nvidia.conf=NVreg_EnableGpuFirmware=0
```

The open kernel modules always use GPU firmware, so install the proprietary modules with that ConfigMap:

```bash
helm install gpu-operator nvidia/gpu-operator \
  -n gpu-operator --create-namespace \
  --set driver.version=<version> \
  --set driver.kernelModuleType=proprietary \
  --set driver.kernelModuleConfig.name=kernel-module-params \
  --set driver.usePrecompiled=false
```

</Tab>
<Tab label="Tesla V100 and V100S (T1, T2)">

These cards use the Volta architecture, which the latest driver branch does not support. In the [NVIDIA driver and architecture matrix](https://docs.nvidia.com/datacenter/tesla/drivers/latest/cuda-toolkit-driver-and-architecture-matrix.html), read the last driver branch that still supports Volta. On the [NGC driver catalog](https://catalog.ngc.nvidia.com/orgs/nvidia/containers/driver/tags), select the latest Ubuntu 22.04 tag of that branch, of the form `` `<version>-ubuntu22.04` ``. Pass that version to `driver.version` (e.g: 580.178.04).

```bash
helm install gpu-operator nvidia/gpu-operator \
  -n gpu-operator --create-namespace \
  --set driver.version=<version> \
  --set driver.usePrecompiled=false
```

The open kernel modules do not support Volta, so the operator compiles the proprietary modules.

</Tab>
</Tabs>

:::info
If the cluster mixes Tesla V100 nodes with other GPU flavors, use the Tesla V100 command: that driver branch also supports the current architectures. If one of the flavors is RTX 5000, also create the ConfigMap and add the `driver.kernelModuleType` and `driver.kernelModuleConfig.name` options from the RTX 5000 tab.
:::

#### Using a precompiled driver (optional)

On L4, L40S, H100 and A100 nodes, a [precompiled driver](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/precompiled-drivers.html) image skips the compilation. NVIDIA publishes these images for some Ubuntu 22.04 kernels only. Read the node kernel:

```bash
kubectl get nodes -o jsonpath='{.items[0].status.nodeInfo.kernelVersion}'
```

On the [NGC driver catalog](https://catalog.ngc.nvidia.com/orgs/nvidia/containers/driver/tags), look for a generic Ubuntu 22.04 tag that contains this kernel, and pass it to `driver.image` (e.g: `driver:580-5.15.0-187-generic-ubuntu22.04`). If no tag contains the node kernel, keep the command from the L4, L40S, H100, A100 tab.

```bash
helm install gpu-operator nvidia/gpu-operator \
  -n gpu-operator --create-namespace \
  --set driver.image=driver:<tag>
```

### Verify GPU Operator Install

When the GPU operator is UP and running, it will add `nvidia.com/gpu` labels on GPU Nodes.

You can check new labels with the command:

```bash
kubectl get nodes --show-labels | grep "nvidia.com/gpu"
```

New labels should appear only on your GPU Nodes:

### Running Sample GPU Applications

You can now proceed to running a GPU application/workload on your cluster.

To configure Pods to consume GPUs, you need to use a resource limit in your YAML manifest file. You have to specify a resource limit in a Pod specification using the following key-value pair:

```bash
Key: nvidia.com/gpu
Value: Number of GPUs to consume
```

Create a `vector.yaml` YAML manifest file with the following content:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: cuda-vectoradd
spec:
  restartPolicy: OnFailure
  containers:
  - name: cuda-vectoradd
    image: "nvcr.io/nvidia/k8s/cuda-sample:vectoradd-cuda11.7.1"
    resources:
      limits:
         nvidia.com/gpu: 1
```

Apply it:

```bash
kubectl apply -f vector.yaml -n default
```

And watch the Pod startup:

```bash
kubectl get pod -n default -w
```

You should have results like this:

```console
$ kubectl apply -f vector.yaml -n default
pod/cuda-vectoradd created

$ kubectl get pod -n default -w
NAME             READY   STATUS              RESTARTS   AGE
cuda-vectoradd   0/1     ContainerCreating   0          4s
cuda-vectoradd   0/1     Completed   0          35s
```

When the `cuda-vectoradd` has started, run and completed its task, watch the logs with the following command:

```bash
kubectl logs cuda-vectoradd -n default
```

```console
$ kubectl logs cuda-vectoradd -n default
[Vector addition of 50000 elements]
Copy input data from the host memory to the CUDA device
CUDA kernel launch with 196 blocks of 256 threads
Copy output data from the CUDA device to the host memory
Test PASSED
Done
```

Our first GPU workload is just started up and has done its task in our OVHcloud Managed Kubernetes cluster.

### Troubleshooting

If the `nvidia-driver-daemonset` pod stays not ready after the build, run `nvidia-smi` in it:

```bash
kubectl exec -n gpu-operator ds/nvidia-driver-daemonset -c nvidia-driver-ctr -- nvidia-smi
```

If it reports `No devices were found`, read the kernel log:

```bash
kubectl exec -n gpu-operator ds/nvidia-driver-daemonset -c nvidia-driver-ctr -- sh -c 'dmesg | grep NVRM | tail -n 20'
```

Lines such as `Cannot initialize GSP firmware RM`, `kgspWaitForGfwBootOk` or `RmInitAdapter failed` mean that the GPU firmware did not start. This happens on RTX 5000 nodes. Uninstall the operator, then install it with the command from the RTX 5000 tab.
