## Objective

On an **OVHcloud On-Prem Cloud Platform (OPCP)**, the `opcp-cli` tool installed on your controllers manages the configuration of the control plane: the platform settings and the description of the hardware. It checks that your configuration files are valid, then applies them to the platform.

**This guide explains how to edit the configuration of your OPCP with `opcp-cli` and apply your changes.**

## Requirements

- An active [OPCP](/links/hosted-private-cloud/onprem-cloud-platform) service.
- SSH access to your OPCP controller with your `opcp-admin` account, the Linux administrator account provided with your OPCP. This account can run `opcp-cli` with `sudo` whether your OPCP is managed by OVHcloud or not (see [IAM rights management](/guides/hosted-private-cloud/opcp/iam-rights-management)).

## Instructions

`opcp-cli` must run as `root`: run each command with `sudo`. If you forget `sudo`, `opcp-cli` stops with the message `Please run opcp-cli as root user (no sudo)`: run the command again with `sudo`. All the commands and options are described in the built-in help:

```bash
opcp-cli --help
opcp-cli config --help
```

The configuration of your OPCP is stored on the controller, in two files:

| File | Content | Command to edit it |
|------|---------|--------------------|
| `/opt/opcp/config/opcp-deployment-config.yaml` | The platform settings: identity of the environment, OPCP version, backups, NTP servers, etc. | `opcp-cli config edit` |
| `/opt/opcp/config/opcp-hardware-config.yaml` | The hardware: controllers and their IP addresses, OOB virtual IP, racks and devices declared in NetBox | `opcp-cli config edit --hardware` |

Always edit these files with `opcp-cli` rather than directly. A change has no effect on the platform until you apply it (step 4).

### 1. Edit the deployment configuration

Log in to your controller over SSH, then run:

```bash
sudo opcp-cli config edit
```

The file opens in `vi`. To use another editor installed on the controller, set the `EDITOR` variable, for example `sudo EDITOR=nano opcp-cli config edit`. This is possible only if your OPCP is not managed by OVHcloud.

Make your changes, then save and close the file. `opcp-cli` checks that the file is valid YAML and that the mandatory fields are filled in, then reminds you how to apply it:

```text
please run opcp-cli deploy --system to apply the changes
✅ Command 'edit' completed in 1m12.081606602s
```

If a mandatory field is empty, `opcp-cli` displays the error, for example:

```text
❌ error when validating opcp config: field 'site' is required and cannot be empty
```

Your changes are saved even when the check fails, and the deployment does not check the file again. Run `sudo opcp-cli config edit` again to fix the file before you apply it.

:::warning
Check the YAML syntax (indentation, quotes, brackets) before you save the file. If the file can no longer be read, `opcp-cli` refuses to run any command, including `config edit`, and displays `error parsing deployment config file` or `error parsing hardware config file`, followed by the path of the file. If your OPCP is not managed by OVHcloud, fix the file directly as `root` (for example with `sudo vi` followed by the path of the file), or restore a previous copy from `/opt/opcp/backup/opcp-cli/config/` (see step 4). If your OPCP is managed by OVHcloud, contact OVHcloud support.
:::

:::warning
Some settings cannot be modified after your OPCP is installed, such as the environment variables (`env`, `region`, `stage`, `org`, `site`, `location`) or the DNS domain (`base_dns_name`). Before you change a value, check whether it can be modified in the *Summary* section of the guide [Technical prerequisites for deployment](/guides/hosted-private-cloud/opcp/opcp-prerequisites).
:::

To change the OPCP version, follow the guide [How to upgrade OPCP](/guides/hosted-private-cloud/opcp/how-to-upgrade-opcp).

### 2. Edit the hardware configuration

:::warning
Never modify the hardware configuration, except to extend your platform to several racks or to add network devices.
:::

To edit the hardware configuration, add the `--hardware` option:

```bash
sudo opcp-cli config edit --hardware
```

This file describes the controllers (`hosts`), the OOB virtual IP (`oob_vip`), and the racks and devices declared in NetBox (`netbox_racks`, `netbox_devices`). `opcp-cli` checks it in the same way as the deployment configuration.

### 3. Add a trusted certificate authority

If the platform must connect to a service whose certificate is signed by your own certificate authority (CA), for example an LDAP directory federated in Keycloak over LDAPS, add this CA to the trusted CAs of the platform.

Copy the certificate of your CA, in PEM format with the `.crt` extension, to the controller, then run:

```bash
sudo opcp-cli secrets certificates trust-ca --ca-crt-path <path-to-your-ca>.crt --name <ca-name>
```

The `--name` option identifies the CA on the platform. It accepts only lowercase letters, digits and hyphens, and defaults to the file name without its extension. If a CA with the same name already exists, `opcp-cli` asks you to confirm that you want to replace it.

The file must contain the certificate of the CA itself, not the certificate of the server.

`opcp-cli` adds the CA to the trusted certificates of the controller and publishes it to the platform. Within a few minutes, the platform components trust it: Keycloak restarts automatically to load it, and the other components use it the next time they restart. To also add the CA on the other controllers, apply the change (step 4).

### 4. Apply your changes

Before you apply your changes, check that the configured version of your OPCP matches the deployed version:

```bash
sudo opcp-cli version
```

If they differ, follow the guide [How to upgrade OPCP](/guides/hosted-private-cloud/opcp/how-to-upgrade-opcp) instead. Do not delete the installation files of the deployed version from `/opt/opcp/artifacts`: the deployment needs them.

Apply your changes to the control plane:

```bash
sudo opcp-cli deploy --system
```

`opcp-cli` generates the configuration of the control plane from your files and publishes it to the platform, copies the files to the other controllers, saves a dated copy of the `/opt/opcp/config` directory in `/opt/opcp/backup/opcp-cli/config/`, then applies the configuration of the controllers.

The deployment can take more than 10 minutes. The command displays the path of its detailed log file, `/var/log/opcp-cli/opcp-cli.log`. To display the detailed progress in your terminal, add the `--debug` option. The command ends with messages such as:

```text
✅ Deployment of control plane terminated
Please watch the reconcilation process to be sure the system is fully deployed
✅ Command 'deploy' completed in 10m19.19421549s
```

The platform then converges to the new configuration, which can take several more minutes. Then run a diagnosis to check that the platform is healthy:

```bash
sudo opcp-diag run
```

`opcp-cli deploy` provides other options. Run `opcp-cli deploy --help` for the full list.

## Useful configuration options

The settings below are the ones you most often change after installation. Add them to the deployment configuration with `sudo opcp-cli config edit` (step 1), then apply your changes with `sudo opcp-cli deploy --system` (step 4).

Unless stated otherwise, write only the keys you change: the other settings of the same block keep their default values. If a key already exists in your file, modify it rather than adding it a second time.

:::info
The guide [Technical prerequisites for deployment](/guides/hosted-private-cloud/opcp/opcp-prerequisites) lists the network flows to open for each of these options.
:::

### S3 backups

The `backups` block defines the S3-compatible storage where the platform stores its backups. To change it, follow the guide [How to update the backup S3 buckets](/guides/hosted-private-cloud/opcp/how-to-update-backup-s3-buckets).

### NTP servers

The `ntp` block defines the time sources of the platform. The controllers synchronize with them, then serve the time to the rest of the platform, such as the network devices and the nodes.

```yaml
ntp:
  servers:
    - "<your-ntp-server-1>"
    - "<your-ntp-server-2>"
```

Each entry is an IP address or a DNS name. A DNS name must be resolvable by the DNS resolvers of the platform (see below). For a DNS name that resolves to several NTP servers, use the `pools` key instead of `servers`, with the same format.

List all the servers to use. Without any server or pool, the platform uses the clock of the controller as its only time reference.

### DNS resolvers

The `public_forward_resolvers` key lists the DNS resolvers that the control plane uses to resolve external names, such as your S3 endpoint, your syslog server or your LDAP directory.

```yaml
public_forward_resolvers:
  - "<your-dns-resolver-1>"
  - "<your-dns-resolver-2>"
```

Give IP addresses. This list replaces the default resolver entirely: list all the resolvers you want to use.

### Log forwarding to a syslog server

The `monitoring.logs.forwarder` block sends the logs of the platform to your syslog servers, in addition to the local log storage.

```yaml
monitoring:
  logs:
    forwarder:
      enabled: true
      syslog:
        enabled: true
        endpoints:
          - host: "<your-syslog-server>"
            port: "514"
            mode: tcp
```

- Set both `enabled` keys to `true`.
- `host`: an IPv4 address or a DNS name.
- `port`: mandatory, written in quotes.
- `mode`: `tcp` (default) or `tls`. UDP is not supported.

Add one entry under `endpoints` per syslog server.

### Keycloak allowed endpoints

Keycloak can reach an external service, such as the LDAP directory or the identity provider you federate, only if this service is listed in `keycloakAllowedEndpoints`. To set up the federation itself, see the guide [IAM rights management](/guides/hosted-private-cloud/opcp/iam-rights-management).

:::warning
This list replaces the default list. Always keep the two default entries for Keystone and NetBox, as shown below. Without them, Keycloak can no longer reach these components.
:::

```yaml
keycloakAllowedEndpoints:
  # Default entries, to keep as they are
  - host: "keystone.%{lookup('base_dns_name')}"
    port: 443
  - host: "netbox.%{lookup('base_dns_name')}"
    port: 8004
  # Your entries
  - host: "<your-ldap-server>"
    port: 636
```

- `host`: a DNS name or a single IPv4 address. Network ranges are not supported.
- `port`: a single TCP port. To open several ports on the same server, add one entry per port.

If your directory uses a certificate signed by your own certificate authority, also add this authority to the trusted CAs of the platform (step 3).
