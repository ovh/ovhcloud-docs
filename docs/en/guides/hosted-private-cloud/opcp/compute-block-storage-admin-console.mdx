## Objective

**This guide shows IT Admins how to deploy the Compute and Block Storage service from the OPCP Admin Console, configure it, scale it and enable it for Organizations.**

**Compute and Block Storage** provides virtual machines (instances), persistent block storage volumes and private networks to the Organizations of your platform. It is built on OpenStack: Nova runs the instances on hypervisors, and Cinder stores the volumes in a Ceph cluster. Both run on bare-metal hosts of your OPCP.

This guide covers what is specific to Compute and Block Storage. The general steps (Service Catalog, Service Deployments, Organizations) are described in the guide [OPCP Admin Console](/guides/hosted-private-cloud/opcp/admin-console-getting-started). How Organization users work with the service is described in the guide [Using Compute and Block Storage](/guides/hosted-private-cloud/opcp/compute-block-storage-cloud-console).

## Requirements

- Access to the OPCP Admin Console, as described in the guide [OPCP Admin Console](/guides/hosted-private-cloud/opcp/admin-console-getting-started).
- Bare-metal hosts enrolled in OPCP Core, available in OpenStack and not used by another service:
    - at least **1 host for the `compute` Host Pool**, which becomes a hypervisor. Add more hosts for capacity, and to keep instances running when a hypervisor fails. Each needs a data disk of at least 1,000 GiB. AMD EPYC hosts must have their NUMA mode set to **NPS4**;
    - at least **3 hosts for the `storage` Host Pool**, which form the Ceph cluster. Ceph keeps 3 copies of each volume, each on a different host.
- An Organization to enable the service for. To create one, read [Creating an Organization](/guides/hosted-private-cloud/opcp/admin-console-getting-started#creating-an-organization).

## Instructions

### Architecture overview

| Component | Runs on | Role |
|-----------|---------|------|
| **Control plane** | The OPCP controller | Deployed once per Service Deployment. Runs the OpenStack services that manage instances and volumes, and a Horizon web interface. |
| **Hypervisors** | Hosts of the `compute` Host Pool | Run the instances. They are shared by all Organizations the service is enabled for. |
| **Ceph cluster** | Hosts of the `storage` Host Pool | Stores the block storage volumes. |
| **Data plane** | The OPCP controller | Created for each Organization when you enable the service for it. Gives the Organization its own OpenStack project, its access through the OPCP Cloud Console and its own web interface for the service. |

Each Organization only sees its own instances, volumes and networks.

### Deploying the service

1. Go to <code className="action">Management</code> > <code className="action">Service Catalog</code> and open **Compute and Block Storage**. Click <code className="action">New deployment</code>.
2. **Choose the version of your service**, then click <code className="action">Next</code>.
3. **Allocate the host pools**:
    - `compute`: select the hosts that become hypervisors;
    - `storage`: select the hosts that form the Ceph cluster.

    A host can belong to only one Host Pool.

    <img className="thumbnail" alt="Allocating the hosts of a Host Pool: OpenStack project and list of available hosts" src="/images/hosted-private-cloud/opcp/compute-block-storage-admin-console/deploy_host_pools.png" loading="lazy" />

4. **Configure your service**. The service has two settings, both with a default value that suits most deployments. See [Settings](#settings) below.
5. Click <code className="action">Deploy</code>.

:::warning
The selected hosts are wiped and reinstalled during the deployment.

:::

The deployment installs the hypervisors and the Ceph cluster. It takes from several tens of minutes to a few hours, depending on the number of hosts. The Service Deployment is `deploying`, then `deployed`.

Once it is `deployed`, the <code className="action">Host pools</code> tab of the Service Deployment lists the hosts of the `compute` and `storage` Host Pools.

<img className="thumbnail" alt="Host pools tab of a Compute and Block Storage Service Deployment, with its compute and storage hosts" src="/images/hosted-private-cloud/opcp/compute-block-storage-admin-console/deployment_host_pools.png" loading="lazy" />

:::warning
**Alpha: manual step required.** The deployment does not yet create the instance flavors (`cb-` flavors) and the host aggregate that places them on the hypervisors. Until this is done, Organizations cannot create instances. Once your Service Deployment is `deployed`, contact OVHcloud to have this step performed.

:::

#### Settings

| Setting | Default | Description |
|---------|---------|-------------|
| `horizon_enabled` | `true` | Deploys the Horizon web interface. Organization users reach it through a link in the OPCP Cloud Console, for the cases the service interface does not cover yet. |
| `allow_uninstall_with_bound_nodes` | `false` | Allows deleting the Service Deployment while hosts are still in use. The hosts are then released and wiped. Leave it at `false` unless OVHcloud support asks you to change it. |

### Outputs

Once the Service Deployment is `deployed`, its <code className="action">Outputs</code> tab shows, among others, the hosts of each Host Pool (`compute_nodes`, `storage_nodes`) and the address of Horizon (`horizon_url`).

Each Enabled Service has its own Outputs, used by the Organization's users. They are shown in the <code className="action">Overview</code> tab of the service in the OPCP Cloud Console:

| Output | Content |
|--------|---------|
| `Console` | The link to the web interface of the service for this Organization. |
| `Horizon` | The link that signs the Organization's users in to Horizon, if `horizon_enabled` is `true`. |
| `OpenRC` | An `openrc.sh` file for the OpenStack CLI. It holds no secret: users authenticate with an application credential of their own. |

### Enabling the service for an Organization

Enable the Service Deployment for each Organization that needs instances, as described in [Enabling a service for an Organization](/guides/hosted-private-cloud/opcp/admin-console-getting-started#enabling-a-service-for-an-organization).

- The hypervisors and the Ceph cluster are shared between Organizations: the Host Pool step is marked `not applicable`.
- There is no property to fill in: the service takes everything it needs from the Outputs of the Service Deployment.

The Enabled Service is `deploying`, then `deployed`. The Organization's users then find **Compute and Block Storage** in the OPCP Cloud Console. Send them the guide [Using Compute and Block Storage](/guides/hosted-private-cloud/opcp/compute-block-storage-cloud-console).

### Scaling the service

#### Adding hosts

To add capacity, open the <code className="action">⋮</code> menu of the Service Deployment and choose <code className="action">Expand capacity</code>, as described in [Scaling capacity](/guides/hosted-private-cloud/opcp/admin-console-getting-started#scaling-capacity). In the dialog, first choose the Host Pool to expand, `compute` or `storage`, then select the hosts to add.

<img className="thumbnail" alt="Expand capacity dialog: choice of the Host Pool and list of available hosts" src="/images/hosted-private-cloud/opcp/compute-block-storage-admin-console/expand_capacity.png" loading="lazy" />

- A host added to the `compute` Host Pool becomes a new hypervisor.
- A host added to the `storage` Host Pool joins the Ceph cluster, and its disks add to the storage capacity.

:::warning
**Alpha: manual step required.** A new hypervisor only runs instances once it has been added to the host aggregate of the `cb-` flavors. This is not done automatically yet: after adding hosts to the `compute` Host Pool, contact OVHcloud to have them added.

:::

#### Removing hosts

Removing hosts from a Service Deployment is not supported in the Alpha.

### Deleting the service

1. Ask the Organizations to delete all their instances and volumes.
2. Disable the service for each Organization.
3. Delete the Service Deployment, as described in [Disabling a service or deleting a Service Deployment](/guides/hosted-private-cloud/opcp/admin-console-getting-started#disabling-a-service-or-deleting-a-service-deployment).

:::warning
Delete all instances and volumes before deleting the Service Deployment. Instances left on a hypervisor block the deletion of the Service Deployment.

:::

### Known limitations

The Alpha has the following known limitations:

| What you notice | What to do |
|-----------------|------------|
| Organizations cannot create instances on a new Service Deployment, or on hosts added with <code className="action">Expand capacity</code>. | Contact OVHcloud to have the `cb-` flavors and their host aggregate set up (see [Deploying the service](#deploying-the-service)). |
| The deployment takes long, or the first attempts to set up a hypervisor fail. | Wait: the deployment retries automatically and usually succeeds on the second or third attempt. If it stays in error, contact OVHcloud. |
| Setting up a hypervisor fails on an AMD EPYC host. | Check that the NUMA mode of the host is set to **NPS4** in the BIOS, or use another host. |
| Deploying Compute and Block Storage a second time on the same platform fails. | Deploy the service only once per platform. |
| Deleting the Service Deployment never finishes. | Delete all instances and volumes first (see [Deleting the service](#deleting-the-service)). If the deletion is already stuck, contact OVHcloud. |
| A new deployment fails after a previous Service Deployment was deleted. | The deletion leaves resources behind, and the Ceph cluster is deliberately kept. Contact OVHcloud to have them cleaned up before you deploy again. |
| Disabling the service fails for an Organization whose name contains a space. | Use Organization names without spaces. |
| All `cb-` flavors use dedicated CPUs, so a hypervisor runs fewer instances than its number of cores suggests. | Plan enough hosts for the `compute` Host Pool. |
| A Service Deployment cannot be upgraded in place. | Delete it and deploy the new version. |
