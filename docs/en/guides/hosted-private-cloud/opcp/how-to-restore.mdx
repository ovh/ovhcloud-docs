## Introduction

There are different scenarios in which you might want to restore a backup. However, in OPCP, restoring only part of a backup is not supported. You can only restore the full backup, including all resources.

The backup contains the following kinds of resources:

- Databases
- tfstate resources
- PVs from Kubernetes
- KMS setup

:::danger
This guide only covers the control plane. All of your data and workloads must be restored separately.
:::

:::warning
This process can take a long time. Expect to spend most of the time waiting for operations to complete.
:::

:::info
It is really helpful to run the commands in a `screen` or `tmux` session to be able to watch logs or fix things in another window. If neither is installed on the controller, install one by running `apt install -y screen` or `apt install -y tmux`. Also make sure you know how to work with these tools.
:::

## Prerequisites

There are several prerequisites that must be fulfilled before you start to restore from a backup:

- SSH access to all OPCP controller(s), including `sudo` permissions.
- The backup IDs you want to restore from.
- The KMS unseal shares, which are not in the backup itself, as they are considered to be very sensitive data.
- Access to the S3[^1] buckets the database backups are stored in.

### Retrieve the backup IDs

You need a backup ID from the `tfstate`, `pvs` and `kms` resources. Get your latest backups by running:

```bash
BACKUP_FILE="backups_velero_$(date +%s).json"
BACKUP_NAMES=("tfstate-backup" "pvs-backup" "kms-autounsealer-shares-backup")
velero backup get -o json > "${BACKUP_FILE}"
for BACKUP_NAME in "${!BACKUP_NAMES[@]}"; do
  echo "${BACKUP_NAME}:"
  jq -r < "${BACKUP_FILE}" "[ .items[] | select(.metadata.labels.\"velero.io/schedule-name\" == \"${BACKUP_NAMES[$BACKUP_NAME]}\") | {name: .metadata.name, ts: .metadata.creationTimestamp|strptime(\"%Y-%m-%dT%H:%M:%SZ\")|mktime}]|sort_by(.ts)|reverse[0]|.name"
  echo "\n"
done
```

:::info
OPCP must still be running while you get the latest backup.
:::

### Prepare S3[^1] access

Make sure you have access to the S3[^1] buckets containing the backup data.

The first step is to get credentials with permissions for full read, write and delete access to the S3[^1] bucket containing the database backups.

[`s3cmd`](https://s3tools.org/s3cmd) must be installed on your workstation. It must be configured as well:

```bash
ACCESS_KEY_ID=your-access-key-id # replace with your access key ID
SECRET_ACCESS_KEY=your-access-key-secret # replace with your secret key
REGION=your-s3-region # replace with your region
cat <<EOF > $HOME/.s3cfg
[default]
access_key = ${ACCESS_KEY_ID}
secret_key = ${SECRET_ACCESS_KEY}
bucket_location = ${REGION}
host_base = s3.gra.io.cloud.ovh.net; replace with your base s3 host given by the provider
host_bucket = %(bucket)s.s3.gra.io.cloud.ovh.net; replace with your s3 URL given by the provider
EOF
```

:::info
Please also read your S3[^1] provider's documentation on accessing S3[^1]-compatible storage.
:::

Verify your access by running:

```bash
s3cmd ls
```

You will see a list of all the S3[^1] buckets you have access to. It will look something like this:

```
2026-08-17 02:00  s3://dev-opcp-test-config
2026-08-06 07:25  s3://dev-opcp-test-db
2026-08-17 02:00  s3://dev-opcp-test-etcd-snapshots
2026-09-25 11:22  s3://opcp-pg-dev-opcp-test
2026-09-25 11:09  s3://opcp-pv-dev-opcp-test

2026-09-22 07:02  s3://opcp-release-dev
2026-08-17 14:31  s3://opcp-volumes-dev-opcp-test
```

There are two buckets that are very important:

- The bucket storing your database backups
- The bucket storing your Velero backups (`tfstate`, `pvs`, `kms-autounsealer-shares`)

Run `opcp-cli config edit` to check for custom entries. If none are given, use the generated default ones:

- databases: `opcp-pg-{stage}-{env}`
- velero: `opcp-volumes-{stage}-{env}`

You can find the values for `stage` and `env` in the OPCP config (`opcp-cli config edit`) as well.

:::warning
Make sure you have the KMS unseal shares backed up somewhere. Otherwise, you will not be able to restore.
:::

## Instructions

The first step is to [reset OPCP](how-to-reset-opcp), except for the last step, the [reinstall of OPCP](how-to-reset-opcp#redeploy-controller). Skip this one for now; it is covered later in this guide as part of the restore process.

### Move database backups

The next step is to move the database backups within the S3[^1] bucket. To restore the backups, they must be present in the `/recovery` prefix:

```bash
OPCP_DB_BACKUP_BUCKET=your-bucket-name # change to your bucket name
s3cmd cp --recursive --exclude "recovery/*" --exclude "archived-backups/*" "s3://${OPCP_DB_BACKUP_BUCKET}/" "s3://${OPCP_DB_BACKUP_BUCKET}/recovery/"
```

Make sure all the files have been copied:

```bash
s3cmd ls "s3://${OPCP_DB_BACKUP_BUCKET}/recovery/"
```

Finally, all the database backups must be moved from the root to the `/archived-backups` prefix:

```bash
s3cmd mv --recursive --exclude "recovery/*" --exclude "archived-backups/*" "s3://${OPCP_DB_BACKUP_BUCKET}/" "s3://${OPCP_DB_BACKUP_BUCKET}/archived-backups/$(date '+%Y-%m-%d_%Hh-%Mm')/"
```

Verify that only the `/archived-backups` and `/recovery` prefixes remain in the root:

```bash
s3cmd ls "s3://${OPCP_DB_BACKUP_BUCKET}"
```

:::info
Be patient: copying and moving the data can take a while, as there may be a lot of it.
:::

### Redeploy OPCP

After all the database backups are moved and your config is prepared, you can start a redeploy:

```bash
opcp-cli deploy --force-reconcile
```

:::warning
The artifacts must be the same version as when the backup was made. Otherwise, there could be some complications.
:::

Once the deployment is done, verify that the databases not managed by OpenTofu are restored:

```bash
kubectl get Cluster -A
```

Wait until all database clusters not managed by OpenTofu are available.

```
NAMESPACE   NAME          AGE    INSTANCES   READY   STATUS                     PRIMARY
keycloak    keycloak-db   104s   1           1       Cluster in healthy state   keycloak-db-1
kms         kms-db        104s   1           1       Cluster in healthy state   kms-db-1
netbox      netbox-db     104s   1           1       Cluster in healthy state   netbox-db-1
```

You can assume that these instances are restored from backup.

:::info
This step may take some time.

However, recovery might get stuck at this point. You then have to reset the controller and clean the DB backups by running the following on your machine:

```bash
s3cmd rm --recursive --exclude "recovery/*" --exclude "archived-backups/*" "s3://${OPCP_DB_BACKUP_BUCKET}/" --force
```

When this is done, you can start with a [redeploy](#redeploy-opcp).
:::

#### Restore tfstate

To restore the `tfstate`s, run the following commands:

```bash
# 1. ensure_ks_ready: wait until all Kustomizations in flux-system are Ready
while [[ $(kubectl get Kustomization -n flux-system | awk '{print $3}' | grep -Ev "READY|True" | wc -l) > 0 ]]; do
    sleep 1
done

# 2. suspend_tf
if flux get hr -n flux-system | grep -q "tofu-controller"; then
    flux suspend hr -n flux-system tofu-controller
fi
for tf in $(kubectl get Terraform -n flux-system -o jsonpath='{.items[*].metadata.name}'); do
    tfctl suspend $tf
done
while [[ $(kubectl get pods -n flux-system -o name | grep tf-runner | wc -l) > 0 ]]; do
    sleep 1
done
if flux get hr -n flux-system | grep -q "tofu-controller"; then
    kubectl scale --replicas=0 -n flux-system $(kubectl get rs -n flux-system -o name | grep tofu-controller)
fi
sleep 2

# 3. Delete TF state/plan secrets and wait until they are gone
kubectl -n flux-system delete secret $(kubectl -n flux-system get secrets -o name | grep -E '^secret/tfstate-default|^secret/tfplan-default' | cut -d '/' -f 2)
while [[ $(kubectl -n flux-system get secrets -o name | grep -E '^secret/tfstate-default|^secret/tfplan-default' | wc -l) > 0 ]]; do
    sleep 1
done

# 4. Restore
velero restore create --from-backup "<TF_STATE_BACKUP>" --wait

# 5. Check the restore
velero describe restore <restore-id>
```

When the restore is successful, resume the `tofu-controller` and the Terraform resources:

```bash
if flux get hr -n flux-system | grep -q "tofu-controller"; then
    flux resume hr -n flux-system tofu-controller
fi
for tf in $(kubectl get Terraform -n flux-system -o jsonpath='{.items[*].metadata.name}'); do
    tfctl resume $tf
done
```

#### Restore PVs

After the `tfstate` is restored, you can continue by restoring the PVs:

```bash
# 1. ensure_ks_ready
while [[ $(kubectl get Kustomization -n flux-system | awk '{print $3}' | grep -Ev "READY|True" | wc -l) > 0 ]]; do
    sleep 1
done

# 2. suspend_tf (same as in tfstates)
if flux get hr -n flux-system | grep -q "tofu-controller"; then
    flux suspend hr -n flux-system tofu-controller
fi
for tf in $(kubectl get Terraform -n flux-system -o jsonpath='{.items[*].metadata.name}'); do
    tfctl suspend $tf
done
while [[ $(kubectl get pods -n flux-system -o name | grep tf-runner | wc -l) > 0 ]]; do
    sleep 1
done
if flux get hr -n flux-system | grep -q "tofu-controller"; then
    kubectl scale --replicas=0 -n flux-system $(kubectl get rs -n flux-system -o name | grep tofu-controller)
fi
sleep 2

# 3. Suspend needed HRs
flux suspend hr -n monitoring kube-prometheus-stack
flux suspend hr -n kms ovhcloud-ssm

# 4. Set the backup location to read-only
kubectl patch backupstoragelocation backup-location --namespace velero --type merge --patch '{"spec":{"accessMode":"ReadOnly"}}'

# 5. Delete workloads and PVCs
kubectl delete deploy -n monitoring kube-prometheus-stack-grafana
kubectl delete pvc -n monitoring kube-prometheus-stack-grafana
kubectl delete deploy -n glance glance-api
kubectl delete pvc -n glance glance-images
kubectl delete sts -n kms ovhcloud-ssm
kubectl delete deploy -n kms ovhcloud-ssm
kubectl delete pvc -n kms ovhcloud-ssm-sqlite-ovhcloud-ssm-0
kubectl delete deploy -n ironic ironic-conductor
kubectl delete pvc -n ironic ironic-shared

# 6. Wait loops
while [[ $(kubectl get deploy -A | grep -E "kube-prometheus-stack-grafana|glance-api|ironic-conductor" | wc -l) > 0 ]]; do sleep 1; done
while [[ $(kubectl get sts -A | grep -E "ovhcloud-ssm" | wc -l) > 0 ]]; do sleep 1; done
while [[ $(kubectl get pvc -A | grep -E "kube-prometheus-stack-grafana|glance-images|ovhcloud-ssm-sqlite-ovhcloud-ssm-0|ironic-shared" | wc -l) > 0 ]]; do sleep 1; done
while [[ $(kubectl get pv -A | grep -E "kube-prometheus-stack-grafana|glance-images|ovhcloud-ssm-sqlite-ovhcloud-ssm-0|ironic-shared" | wc -l) > 0 ]]; do sleep 1; done
# get_pods: wait until these pods are gone (removed manually by the operator)
while [[ $(kubectl get pods -A -o name | grep -E "^pod/ironic-conductor|^pod/glance-api|^pod/ovhcloud-ssm|^pod/kube-prometheus-stack-grafana" | grep -Ev "netbox-initializers|-db" | wc -l) -gt 0 ]]; do
    kubectl get pods -A -o name | grep -E "^pod/ironic-conductor|^pod/glance-api|^pod/ovhcloud-ssm|^pod/kube-prometheus-stack-grafana" | grep -Ev "netbox-initializers|-db"
    sleep 1
done

# 7. Restore
velero restore create --from-backup "<PV_BACKUP>" --wait
```

Check the restore state:

```bash
velero describe restore <restore-id>
```

When the restore is successful, resume the Terraform and HelmRelease resources:

```bash
if flux get hr -n flux-system | grep -q "tofu-controller"; then
    flux resume hr -n flux-system tofu-controller
fi
for tf in $(kubectl get Terraform -n flux-system -o jsonpath='{.items[*].metadata.name}'); do
    tfctl resume $tf
done
flux resume hr -n monitoring kube-prometheus-stack
flux resume hr -n kms ovhcloud-ssm
```

#### Restore KMS

Get the name of the pod starting with `ovhcloud-kms-setup-selfunseal` in the `kms` namespace and look into the logs:

```bash
kubectl logs -n kms ovhcloud-kms-setup-selfunseal-7vg52
```

You should see something like this:

```
Creating empty config file at /root/.ovh-kms/okms.yaml
KMS status: Sealed
KMS status: Sealed
KMS is sealed. Unsealing KMS...
Init unsealing KMS
Completed: false
Error: Seal key is incorrect or deprecated.
ID="5d0385bc-1ab8-4260-bfb4-3377e2b27ca1", Request-ID:"OVHKMS.5d0385bc-1ab8-4260-bfb4-3377e2b27ca1", Code=33624076, System=SSM, Component=General, Category=Internal
```

This is because the secrets you just restored do not match the SSM instance. You should have stored your secret shares in a safe place. If you did not, the KMS cannot be restored.

Get your secret shares from your secure location and adjust them by removing the keys `creationTimestamp`, `uid` and `resourceVersion`, as well as `status`, if present, from the YAML file.

After that, use `kubectl apply -f` to apply the secrets.

Once this succeeds, delete the `kms-auto-unsealer-ccm-admin-certificate` secret by using `kubectl -n kms delete secret kms-auto-unsealer-ccm-admin-certificate`.

Finally, you can run the restore:

```bash
# 1. Suspend and scale down the auto-unsealer
flux suspend hr -n kms kms-auto-unsealer
kubectl scale --replicas=0 -n kms sts/kms-auto-unsealer

# 2. Restore
velero restore create --from-backup "<KMS_SHARES_BACKUP>" --wait
```

Check the restore state:

```bash
velero describe restore <restore-id>
```

When the restore is successfully completed, resume the auto-unsealer and scale it to 1:

```bash
flux resume hr -n kms kms-auto-unsealer
kubectl scale --replicas=1 -n kms sts/kms-auto-unsealer
```

When this is finished, run `flux reconcile ks apps` to make sure everything in the `kms` namespace is updated and restarted, except for the `kms-db` pod.

After the shares are restored, you have to recreate the Barbican certificate. First, check which certificate you have to recreate:

```bash

```

```bash
kubectl -n nova rollout restart deploy/nova-api
```

Your OPCP restore is now complete. Verify that all services are working as expected.
