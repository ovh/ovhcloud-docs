## Objective

[#objective](#objective)

Your NetBox instance is partially managed by an automated process driven by an external Source of Truth (SoT). This guide explains how to identify what's automated, what's yours, and how to work with NetBox without conflicting with the objects that the automation is managing.

**This guide will help you interact with your NetBox instance safely while parts of its inventory are managed automatically.**

## Requirements

[#requirements](#requirements)

- Access to your NetBox web interface.
- A user account with at least read permission on the affected sections.
- For any change to automation-managed objects, a coordination channel with your operations team.


## Instructions

[#instructions](#instructions)

### How NetBox is organised

[#how-netbox-is-organised](#how-netbox-is-organised)

Your NetBox instance contains two kinds of objects:

- **Objects managed automatically.** These carry the **`automation-managed`** tag. They are created and kept in sync with the external SoT. You do not need to maintain them.

- **Objects managed by you.** These do not carry the `automation-managed` tag. They are yours: create, edit, delete, retag, comment — whatever your workflow requires.


The `automation-managed` tag is the single signal that tells you which side an object belongs to. When in doubt, check the tag.

:::warning
Do not remove the `automation-managed` tag from objects that carry it, and do not add it to objects you create yourself. Doing either of these will cause the automation to overwrite your changes on its next run.
:::

### Making changes

[#making-changes](#making-changes)

The method to modify an object depends on whether it is automation-managed.

**For objects without the `automation-managed` tag:**

Make changes directly in the NetBox UI as usual. The automation does not touch these objects.

**For objects with the `automation-managed` tag:**

These are driven by the external Source of Truth. To request a change, contact your operations team so the SoT can be updated. On the next automation run, NetBox will reflect the new state.

:::info
If you edit an `automation-managed` object directly in NetBox, the next automation run will revert your change. The SoT is authoritative for these objects.
:::

### Fields preserved on automation-managed objects

[#fields-preserved-on-automation-managed-objects](#fields-preserved-on-automation-managed-objects)

The automation only manages fields that are declared in the SoT. Other fields are left untouched. On an `automation-managed` object you can safely:

- Add or remove tags other than `automation-managed`.
- Add journal entries.
- Set custom field values that are not managed by the automation.
- Add comments.


These changes will persist across automation runs.

### The Automation State tenant

[#the-automation-state-tenant](#the-automation-state-tenant)

In the **Tenancy** section of NetBox, you will see a tenant named **`Automation State`** (slug: `automation-state`). This tenant holds internal bookkeeping used by the automation.

:::warning
Do not delete the `Automation State` tenant, and do not edit its custom fields (`automation_non_taggable_state` and `initializer_sot_hash`). Modifying or deleting them will cause the automation to misbehave on its next run.
:::

### Review branches (if applicable)

[#review-branches-if-applicable](#review-branches-if-applicable)

If your environment uses the **netbox-branching** plugin, the automation may stage its changes on a branch named **`initializer-automation`** before they take effect on the main NetBox state. You may see this branch listed under the Plugins menu.

You can:

- Inspect the branch to see what the automation is about to apply.
- Merge or reject the branch, if your workflow includes a human review step.


:::warning
Do not create a branch named `initializer-automation` yourself. The automation reserves this name; any branch you create with it will be deleted on the next automation run.
:::

### Quick reference

[#quick-reference](#quick-reference)

| Action | Allowed? |
|---|---|
| Edit an object without the `automation-managed` tag | Yes |
| Add journal entries, comments, or other tags on any object | Yes |
| Edit a field on an `automation-managed` object that the SoT manages | Will be reverted on the next run |
| Delete an object with the `automation-managed` tag | Will be recreated on the next run |
| Remove the `automation-managed` tag from an object | Will be added again on the next run |
| Add the `automation-managed` tag to an object you created | Causes the automation to overwrite or delete it |

### What to expect during normal operation

[#what-to-expect-during-normal-operation](#what-to-expect-during-normal-operation)

- **Changelog entries from the automation account** after each successful run. This is normal.
- **A short-lived branch** named `initializer-automation`. It is created, used, and merged (or removed) by the automation.
- **The `automation-managed` tag** present on many objects.
- **The `Automation State` tenant** present in your tenant list.


## Go further

[#go-further](#go-further)

If you observe behaviour that does not match what is described in this guide — duplicates, reverted fields, unexpected branches — start by checking whether the affected object carries the `automation-managed` tag. The answer determines who can fix it:

- **Tagged** → contact your operations team.
- **Not tagged** → you can edit, fix, or delete it directly.
