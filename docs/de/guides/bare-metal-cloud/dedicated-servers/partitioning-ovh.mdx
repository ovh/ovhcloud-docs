## Ziel

:::warning
Dieser Artikel richtet sich an erfahrene Benutzer mit grundlegenden Linux-Kenntnissen und vor allem mit vertieften technischen Kenntnissen im Bereich Speicher, insbesondere Hardware- und Software-RAID sowie Logical Volume Management (LVM).

:::

Mit [OVHcloud Dedicated Servern](/links/bare-metal/bare-metal) können Sie bei der [OS-Neuinstallation](/guides/bare-metal-cloud/dedicated-servers/getting-started-with-dedicated-server) über die <ApiLink>OVHcloud API</ApiLink> sowie über die <ManagerLink to="/">OVHcloud Console</ManagerLink> Festplatten, [Hardware-RAID](/guides/bare-metal-cloud/dedicated-servers/raid-hard), Partitionen, [Software-RAID](/guides/bare-metal-cloud/dedicated-servers/raid-soft), LVM, ZFS usw. konfigurieren. In diesem Artikel konzentrieren wir uns auf die <ApiLink>OVHcloud API</ApiLink>. Dadurch erhalten Sie mehr Details zu der im Hintergrund laufenden Engine, die anhand der an die OVHcloud API übergebenen Eingabedaten die angepasste Speicherkonfiguration auf dem Dedicated Server erstellt.

Detaillierte Informationen zur Speicherkonfiguration können Kunden helfen zu verstehen, warum:

- ihre angepasste Speicherkonfiguration nicht auf ihren Dedicated Server angewendet werden konnte.
- die tatsächliche Speicherkonfiguration auf dem Dedicated Server leicht von der angeforderten Konfiguration abweicht.

## Voraussetzungen

* Sie verfügen über einen [Dedicated Server](/links/bare-metal/bare-metal) in Ihrem OVHcloud Account, der **bereit für die Installation/Neuinstallation** ist.
* Sie haben Zugriff auf die <ApiLink>OVHcloud API</ApiLink>.

:::warning
Bei der Neuinstallation eines Dedicated Servers werden alle derzeit darauf gespeicherten Daten gelöscht.

:::

## In der praktischen Anwendung

Bei der Standardinstallation eines Betriebssystems fordert das (vom Softwarehersteller bereitgestellte) Installationsprogramm den Benutzer interaktiv auf, die Festplatten anzugeben, auf denen das Betriebssystem installiert werden soll, sowie das Partitionierungsschema usw. Nach der Installation des Betriebssystems kann das Partitionierungsschema zwar noch geändert werden, dies kann jedoch sehr schwierig und riskant sein, insbesondere bei Partitionen, die gerade vom System verwendet werden. Aus diesem Grund ist der Speicher ein sehr wichtiges Thema, das **vor** der Installation eines Betriebssystems berücksichtigt werden muss.

Neben der Einfachheit einer API besteht der Hauptvorteil darin, dass Sie die Festplatten und Partitionen, auf denen das Betriebssystem installiert wird, vollständig anpassen können.

Auf dieser Seite konzentrieren wir uns ausschließlich auf den Unter-Hash `storage` des API-Aufrufs, mit dem ein Betriebssystem auf einem Dedicated Server neu installiert wird. Weitere Informationen zu Anpassungen, die nicht den Speicher betreffen, finden Sie in der Anleitung [OVHcloud API und OS-Installation](/guides/bare-metal-cloud/dedicated-servers/api-os-installation).

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "diskGroupId": 1,
            "erase": true
        },
        {
            "diskGroupId": 2,
            "erase": true,
            "hardwareRaid": [
                {
                    "raidLevel": null,
                    "disks": 2
                }
            ],
            "partitioning": {
                "disks": 2,
                "layout": [
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/boot",
                        "size": 1000,
                        "raidLevel": 1
                    },
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/",
                        "size": 0
                    }
                ]
            }
        }
    ]
}
```

### Festplattengruppen <a name="disk-group"></a>

Einige [Dedicated Server](/links/bare-metal/bare-metal) verfügen über mehrere Festplattengruppen, zum Beispiel eine Gruppe mit SATA-Festplatten und eine weitere Gruppe mit SSDs. Diese Server werden manchmal auch als **Hybrid-Server** bezeichnet.

Um die Festplattengruppen und ihre Festplatten aufzulisten, können Sie den folgenden API-Aufruf verwenden. So ermitteln Sie die Festplattengruppe, auf der das Betriebssystem neu installiert werden soll:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/specifications/hardware"} />

Beispielantwort:

```json
{
    "bootMode": "uefi",
    "coresPerProcessor": 64,
    "defaultDiskGroupId": 1,
    "defaultHardwareRaidSize": null,
    "defaultHardwareRaidType": null,
    "description": "SCALE-7 - AMD Epyc 7763",
    "diskGroups": [
        {
            "defaultHardwareRaidSize": null,
            "defaultHardwareRaidType": null,
            "description": "2 X Disk SSD 480 GB, JBOD",
            "diskGroupId": 1,
            "diskSize": {
                "unit": "GB",
                "value": 480
            },
            "diskType": "SSD",
            "numberOfDisks": 2,
            "raidController": null
        },
        {
            "defaultHardwareRaidSize": null,
            "defaultHardwareRaidType": null,
            "description": "2 X Disk NVME 1920 GB, JBOD",
            "diskGroupId": 2,
            "diskSize": {
                "unit": "GB",
                "value": 1920
            },
            "diskType": "NVME",
            "numberOfDisks": 2,
            "raidController": null
        }
    ],
    "expansionCards": null,
    "formFactor": "1u",
    "memorySize": {
        "unit": "MB",
        "value": 524288
    },
    "motherboard": "S8036-M",
    "numberOfProcessors": 1,
    "processorArchitecture": "x86_64",
    "processorName": "Epyc7763",
    "threadsPerProcessor": 128,
    "usbKeys": null
}
```

In diesem Beispiel gibt es 2 Festplattengruppen:

- Die erste (diskGroupId=1) enthält 2 Festplatten mit je 480 GB. Dies ist die Standard-diskGroupId.
- Die zweite (diskGroupId=2) enthält 2 Festplatten mit je 1,9 TB.

Beispiel für die Installation von Debian 13 (Trixie) auf diskGroup 2:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "diskGroupId": 2
        }
    ]
}
```

:::info
Wenn keine diskGroupId angegeben ist oder sie auf 0 gesetzt ist, wird das Betriebssystem standardmäßig auf der Standard-diskGroupId 1 installiert.

:::

<br />

:::warning
Derzeit unterstützt die API die OS-Installation und die Anpassung des Speichers nur auf einer einzigen Festplattengruppe. Von einer bis zu allen Festplatten der ausgewählten Festplattengruppe können in die Speicheranpassung einbezogen werden. Die übrigen Festplatten dieser Festplattengruppe werden jedoch gelöscht. Festplatten, die zu anderen Festplattengruppen gehören, werden standardmäßig ebenfalls gelöscht, ihre Daten können jedoch erhalten bleiben: Siehe [Löschen der Daten](#data-erasure). In jedem Fall bleiben alle diese Festplatten im neu installierten Betriebssystem sichtbar und können anschließend für Daten verwendet/konfiguriert werden.

:::

### Hardware-RAID <a name="hard-raid"></a>

Dieser Abschnitt gilt nur für Server, die in mindestens einer ihrer [Festplattengruppen](#disk-group) über mindestens einen Hardware-RAID-Controller verfügen.

#### Kompatibilität von Server und Hardware-RAID

Diese Information erhalten Sie mit dem folgenden API-Aufruf:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/install/hardwareRaidProfile"} />

Wenn Ihr Server keinen Hardware-RAID-Controller hat, wird ein HTTP-Fehler 403 (Forbidden) mit folgender Meldung zurückgegeben:

```json
{
  "message": "Hardware RAID is not supported by this server"
}
```

Beispielantwort für einen Server mit Hardware-RAID-Controller:

```json
{
  "controllers": [
    {
      "type": "mega",
      "disks": [
        {
          "names": [
            "c0:d0",
            "c0:d1",
            "c0:d2"
          ],
          "type": "SSD",
          "capacity": {
            "unit": "GB",
            "value": 960
          },
          "speed": {
            "value": "6g",
            "unit": "GB/s"
          }
        }
      ],
      "model": "9361-8i-2G"
    }
  ]
}
```

:::info
Sie können diese Information auch über den Wert des Attributs `raidController` aus dem im Abschnitt [Festplattengruppen](#disk-group) beschriebenen API-Aufruf erhalten.

:::

#### API und Hardware-RAID

:::warning
Derzeit unterstützt die API die Anpassung des Hardware-RAID nur für einen einzigen Hardware-RAID-Controller. Wenn Ihr Server über mehrere Hardware-RAID-Controller verfügt, deren Konfiguration Sie anpassen möchten, können Sie die Controller, die nicht zu der für die OS-Neuinstallation ausgewählten Festplattengruppe gehören, **vor** der OS-Neuinstallation konfigurieren (Sie können dies auch nach Abschluss der OS-Neuinstallation tun, wir empfehlen jedoch, es **vorher** zu erledigen, um jedes Risiko eines versehentlichen Datenverlusts zu vermeiden).

:::

Beispiel für eine OS-Installation mit Hardware-RAID 1 zwischen den ersten 2 Festplatten der Festplattengruppe:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "hardwareRaid": [
                {
                    "raidLevel": 1,
                    "disks": 2
                }
            ]
        }
    ]
}
```

:::info
Wenn der Wert `disks` weggelassen wird, wird das Hardware-RAID über **alle** Festplatten der Festplattengruppe konfiguriert.

:::

Nehmen wir nun an, Sie haben einen Dedicated Server mit 1 an den RAID-Controller angeschlossenen Festplattengruppe und 12 Festplatten in dieser Festplattengruppe. Beispiel mit einem Hardware-RAID 10:

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "hardwareRaid": [
                {
                    "raidLevel": 10,
                    "arrays": 4
                }
            ]
        }
    ]
}
```

In diesem Beispiel werden alle 12 Festplatten in ein Hardware-RAID der Stufe 10 einbezogen. Es gibt 4 Gruppen mit je 3 Festplatten, d. h. 4 RAID 1 über jeweils 3 Festplatten, und die 4 Gruppen befinden sich in einem RAID 0.

:::info
Hardware-RAID befindet sich auf einer Ebene, die für das Betriebssystem nicht sichtbar ist. Alle Betriebssysteme sind mit Hardware-RAID "kompatibel".

:::

Alle Festplatten, die Teil einer Hardware-RAID-Konfiguration sind, werden vom Betriebssystem als eine einzige virtuelle Festplatte erkannt.

Wenn Sie also alle Festplatten der Ziel-Festplattengruppe in eine Hardware-RAID-Konfiguration einbezogen haben, ist es nicht möglich, darauf ein Software-RAID zu konfigurieren, da das Betriebssystem nur eine einzige virtuelle Festplatte sieht.

### Partitionierung <a name="partitioning"></a>

Das Partitionierungsschema legt fest, wie Ihre Daten organisiert sind und vom Betriebssystem gesehen werden, d. h. alles, was oberhalb Ihrer physischen Festplatten (bzw. der virtuellen Festplatte, wenn Sie ein Hardware-RAID konfiguriert haben) liegt, bis hin zum eingehängten Dateisystem, von der untersten bis zur obersten Ebene:

- Festplatte (physische/virtuelle Festplatte, PD),
- Partition (physische Partition, PP),
- ZFS: vdev (zgroup, ZG), zpool (ZP), ZFS-Dataset (ZD), ZFS-Volume (ZV),
- [Software-RAID](/guides/bare-metal-cloud/dedicated-servers/raid-soft) (SR),
- LVM: Physical Volume (PV), Volume Group (VG), Logical Volume (LV),
- Dateisystem mit Mountpoint (FS)

Die folgende Tabelle gibt einen Überblick über die verschiedenen Partitionierungskomponenten und darüber, wie diese Ebenen miteinander interagieren:

<img className="thumbnail" alt="Tabelle der Partitionierungsebenen" src="/images/bare-metal-cloud/dedicated-servers/partitioning-ovh/partitioning-layers-table.png" loading="lazy" />

:::info
In der obigen Tabelle steht `/dev/zd1` für ein ZFS-Volume (auch `zvol` genannt). Dabei handelt es sich um eine virtuelle Festplatte oberhalb eines ZFS-Datasets (ZD) und eines zpools (ZP), die vom Betriebssystem als normale physische Festplatte (PD) erkannt wird. Diese Funktion ist über die OVHcloud API nicht verfügbar, und ihre Implementierung ist nicht geplant.

:::

#### Kompatibilität von Betriebssystem und Partitionierung <a name="os-partitioning-compatibility"></a>

Da die Partitionierungskonfiguration für das Betriebssystem sichtbar ist, hat das für die Neuinstallation gewählte Betriebssystem Auswirkungen auf die Möglichkeiten zur Anpassung Ihrer Partitionierung.

Im Abschnitt <code className="action">/dedicated/installationTemplate</code> können Sie für ein bestimmtes Betriebssystem Speicherdetails wie LVM-Kompatibilität und verfügbare Dateisysteme anzeigen:

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}"} />

Beispiel:

```json
{
    "templateName": "debian13_64",
    "filesystems": [
        "btrfs",
        "ext4",
        "swap",
        "xfs",
        "zfs"
    ],
    ...
    "lvmReady": true,
    "noPartitioning": false,
    "softRaidOnlyMirroring": false
}
```

|Attribut|Beschreibung|
|---|---|
|filesystems|Mit diesem Betriebssystem kompatible Dateisystemtypen|
|lvmReady|Gibt an, ob dieses Betriebssystem mit LVM kompatibel ist|
|noPartitioning|Bei true unterstützt das Betriebssystem keine benutzerdefinierte Partitionierung|
|softRaidOnlyMirroring|Bei true unterstützt das Betriebssystem die benutzerdefinierte Partitionierung nur teilweise (nur die Software-RAID-Stufen 0 und 1 können konfiguriert und den ersten 2 Festplatten der Festplattengruppe zugewiesen werden)|

Mit dem folgenden API-Aufruf können Sie die Namen der Partitionierungsschemata der verschiedenen Betriebssysteme auflisten. Die meisten Betriebssysteme unterstützen eine benutzerdefinierte Partitionierung und haben daher nur ein einziges Schema mit dem Namen `default`. Nur einige wenige Betriebssysteme, die keine benutzerdefinierte Partitionierung unterstützen (`noPartitioning` auf `true` gesetzt), **können** mehrere Schemata haben.

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}/partitionScheme"} />

Mit den folgenden API-Aufrufen können Sie herausfinden, welche Partitionierung standardmäßig angewendet wird, wenn sie nicht angepasst wird oder vom Betriebssystem nicht angepasst werden kann.

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}/partitionScheme/\{schemeName\}/partition"} />

<br />

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}/partitionScheme/\{schemeName\}/partition/\{mountpoint\}"} />

#### Kompatibilität von LVM, RAID-Stufen und Dateisystemen <a name="lvm-raid-levels-filesystems-compatibility"></a>

Die folgende Tabelle gibt einen Überblick über die Kompatibilität der Dateisysteme mit den RAID-Stufen sowie mit LVM im Kontext von OVHcloud:

|Dateisystem|LVM|RAID 0|RAID 1|RAID 5|RAID 6|RAID 7|RAID 10|
|---|---|---|---|---|---|---|---|
|Btrfs, ext4, XFS|✅|✅|✅|✅|✅|❌|✅|
|ZFS¹|❌|✅|✅|✅|✅|✅|❌|
|swap|❌|⚠️²|❌|❌|❌|❌|❌|
|NTFS|❌|❌|✅³|❌|❌|❌|❌|
|UFS, VMFS5, VMFS6, VMFS-L⁴|❌|❌|❌|❌|❌|❌|❌|

¹ Weitere Informationen finden Sie in der Tabelle [ZFS-vdevs im Vergleich zu Standard-RAID](#raidz2RAID).<br />
² Die RAID-Stufe für swap kann in der <ApiLink>OVHcloud API</ApiLink> nur auf 1 gesetzt werden. Tatsächlich verwenden die swap-Partitionen kein RAID. Wenn auf einem Server mit `n` Festplatten eine swap-Partition der Größe `s` definiert wird, werden `n` Partitionen der Größe `s` auf jeder Festplatte erstellt, ohne dass ein Software-RAID-Gerät darunter liegt.<br />
³ Das native Windows-RAID (das vom OVHcloud Installationsprogramm konfigurierte) unterstützt RAID 1, allerdings nur zwischen zwei Festplatten, während andere Implementierungen mehr als zwei Festplatten zulassen.<br />
⁴ Das ESXi-Installationsprogramm unterstützt keine benutzerdefinierten Partitionierungsschemata. Die Partitionierung wird vom Softwarehersteller festgelegt. Die <ApiLink>OVHcloud API</ApiLink> kann Ihnen dennoch einen Eindruck davon vermitteln, wie die Partitionierung aussieht: Weitere Informationen finden Sie unter [Kompatibilität von Betriebssystem und Partitionierung](#os-partitioning-compatibility).<br />

:::warning
Diese Tabelle dient nur zu Informationszwecken. Bitte beachten Sie, dass die Kompatibilität mit LVM und insbesondere mit den Dateisystemen auch vom installierten Betriebssystem (OVHcloud Template) abhängt. Weitere Informationen finden Sie unter [Kompatibilität von Betriebssystem und Partitionierung](#os-partitioning-compatibility).

#### ZFS-vdevs im Vergleich zu Standard-RAID <a name="raidz2RAID"></a>

ZFS unterstützt keine Standard-RAID-Stufen. Stattdessen werden virtuelle Geräte (vdevs) verwendet, um die Fehlertoleranz innerhalb einer Gruppe von Geräten zu beschreiben. Weitere Informationen zu vdevs finden Sie in der [offiziellen OpenZFS-Dokumentation](https://openzfs.github.io/openzfs-docs/man/7/zpoolconcepts.7.html).

Um die OVHcloud API so einfach wie möglich zu halten, müssen Kunden für ZFS-Dateisysteme in der API ein Standard-RAID definieren. Die Standard-RAID-Stufe wird dann in eine entsprechende vdev-Definition übersetzt. Die folgende Tabelle veranschaulicht die Übersetzung der verschiedenen von der OVHcloud API angebotenen RAID-Stufen und erinnert an ihre jeweiligen Eigenschaften.

|Standard-RAID|Entsprechender vdev-Typ|Mindestanzahl an Datenfestplatten|Anzahl der Paritätsfestplatten|Erforderliche Gesamtmindestanzahl an Festplatten|
|---|---|---|---|---|
|RAID 0|striped vdev|1|0|1|
|RAID 1|mirror|2|0|2|
|RAID 5|raidz1|2|1|3|
|RAID 6|raidz2|3|2|5|
|RAID 7|raidz3|4|3|7|
|RAID 10|❌|4|0|4|

#### API und Partitionierung

:::warning
Ein benutzerdefiniertes Partitionierungsschema kann, obwohl es gültig ist und von der <ApiLink>OVHcloud API</ApiLink> akzeptiert wird, dennoch verhindern, dass der Server ordnungsgemäß startet (zum Beispiel bei einer ungewöhnlichen Kombination aus Dateisystem und Bootloader oder bei einem für Ihr Schema spezifischen Problem beim Zusammensetzen von RAID/LVM/ZFS). In diesem Fall wird auf dem Server nicht automatisch ein Support-Eingriff angelegt: Nach dem letzten Neustart wird eine eindeutige Meldung für den Kunden angezeigt. Weitere Informationen finden Sie unter [Häufige Kundenfehler](#errors).

:::

Beispiel für eine OS-Installation mit einem benutzerdefinierten Partitionierungsschema:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "partitioning": {
                "disks": 2,
                "layout": [
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/boot",
                        "size": 1000,
                        "raidLevel": 0
                    },
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/",
                        "size": 0
                    }
                ]
            }
        }
    ]
}
```

`size` 0 bedeutet, dass die Partition den gesamten verbleibenden Speicherplatz auf den betroffenen Festplatten belegt.

:::info
Höchstens 1 Partition kann so konfiguriert werden, dass sie den verbleibenden Speicherplatz belegt (Größe 0).

:::

<br />

:::info
Wenn nicht angegeben, wird `raidLevel` auf 1 gesetzt.

:::

In diesem Beispiel werden nur die ersten 2 Festplatten der Festplattengruppe in die Partitionierung (d. h. in das Software-RAID) einbezogen.

:::info
Der Parameter `disks` kann weggelassen werden, wenn Sie alle Festplatten der Festplattengruppe in das Software-RAID einbeziehen möchten.

:::

Wie Sie sehen, ist ein Partitionierungsschema eine Liste von Partitionen. Hier ein Beispiel für die Struktur einer Partition:

```json
{
    "mountPoint": "/var/lib/vz",
    "fileSystem": "ext4",
    "size": 0,
    "raidLevel": "1",
    "extras": {
        "lv": {
            "name": "data"
        }
    }
}
```

Der Unter-Hash `extras` ist optional. Mit ihm können Sie festlegen, dass die Partition ein Logical Volume sein soll (und welchen Namen es trägt). Er kann auch für ZFS verwendet werden:

```json
{
    "mountPoint": "/",
    "fileSystem": "zfs",
    "size": 0,
    "raidLevel": "5",
    "extras": {
        "zp": {
            "name": "poule"
        }
    }
}
```

In diesem Beispiel verweist der Mountpoint `/` auf ein ZFS-Dataset in einem zpool namens "poule" in einem raidz1. Die Zuordnung zwischen raidz und Standard-RAID-Stufen finden Sie unter [ZFS-vdevs im Vergleich zu Standard-RAID](#raidz2RAID).

:::info
Wenn kein zpool-Name angegeben ist, wird automatisch ein benutzerdefinierter zpool-Name generiert. Standardmäßig versucht der Algorithmus, verschiedene Datasets im selben zpool zusammenzufassen, mit Ausnahme der Datasets, die `/` oder `/boot` enthalten und in separaten zpools abgelegt werden. So können auf den anderen zpools erweiterte ZFS-Funktionen aktiviert werden, die mit dem Bootloader nicht kompatibel sind.

:::

<br />

:::info
Mit einem benutzerdefinierten zpool-Namen können Sie:

- Datasets mit denselben RAID-Stufen gruppieren: Verwenden Sie denselben zpool-Namen,
- erzwingen, dass Datasets mit denselben RAID-Stufen in getrennten zpools liegen: Verwenden Sie unterschiedliche zpool-Namen.

:::

### Löschen der Daten <a name="data-erasure"></a>

Standardmäßig werden die Festplatten aller Festplattengruppen des Servers während der OS-Installation gelöscht, unabhängig davon, ob ihre Festplattengruppe in der `storage`-Anfrage angegeben ist oder nicht. Die einzige Möglichkeit, die Daten einer Festplattengruppe zu behalten, besteht darin, `erase` für diese Festplattengruppe auf `false` zu setzen.

Andere Festplattengruppen als die, auf der das Betriebssystem installiert wird, können ebenfalls angegeben werden, jedoch nur, um festzulegen, ob ihre Daten gelöscht (`erase: true`) oder behalten (`erase: false`) werden.

Das Betriebssystem wird auf der Festplattengruppe installiert, die die Installationsattribute (`partitioning`, `hardwareRaid`) enthält. Die anderen angegebenen Festplattengruppen enthalten nur `erase`. Wenn keine von ihnen ein Installationsattribut enthält, wird das Betriebssystem auf der Standard-Festplattengruppe installiert, wie im Abschnitt [Festplattengruppen](#disk-group) beschrieben.

Beispiel mit einem Server mit 2 Festplattengruppen: eine einfache OS-Installation auf `diskGroupId` 1 (implizit gelöscht) und `diskGroupId` 2, die nur angegeben wird, um ihre vorhandenen Daten zu behalten:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "diskGroupId": 1,
            "partitioning": {
                "schemeName": "default"
            }
        },
        {
            "diskGroupId": 2,
            "erase": false
        }
    ]
}
```

:::warning
Für das Array `storage` gelten folgende Einschränkungen:

- Sie können `erase: false` nicht für die Festplattengruppe festlegen, auf der das Betriebssystem installiert wird.
- Sie können dieselbe `diskGroupId` nicht mehrmals angeben.
- Sie können nicht mehr als eine Festplattengruppe angeben, auf der das Betriebssystem installiert werden soll. Für jede weitere Festplattengruppe kann nur das Attribut `erase` festgelegt werden, ohne OS-Installation, Partitionierung oder Hardware-RAID-Konfiguration.

:::

:::warning
Wenn Sie `erase` auf `false` setzen, bleiben alle Daten auf dieser Festplattengruppe erhalten, OVHcloud kann jedoch nicht garantieren, dass die OS-Installation erfolgreich ist: Verbliebene Boot-Metadaten, `mdadm`-Superblöcke, LVM-Signaturen oder ZFS-Labels aus einer früheren Installation auf dieser Festplattengruppe (d. h. auf einer ihrer Festplatten) können mit der neuen Installation in Konflikt geraten.

Schlägt die Installation aus einem dieser Gründe fehl, wird nicht automatisch ein Support-Ticket erstellt. Stattdessen wird dem Kunden eine eindeutige Meldung angezeigt, entweder während der Partitionierung oder beim ersten Start des installierten Betriebssystems. Weitere Informationen finden Sie unter [Häufige Kundenfehler](#errors).

:::

### Fehlerbehandlung

Einfache Fehler in den Eingabedaten des Kunden werden direkt von der OVHcloud API behandelt. Dies ist der häufigste und einfachste Fall, da Kunden den Fehler synchron sehen und es sofort erneut versuchen können.

Eingabedaten des Kunden zur Partitionierung können zu spezifisch sein, um von der OVHcloud API geprüft zu werden, und erfordern daher eine Vorverarbeitungszeit. Der Nachteil ist, dass Kunden erst später im Verlauf der OS-Neuinstallation benachrichtigt werden.

In der <ManagerLink to="/#/dedicated-servers/server">OVHcloud Console</ManagerLink> ist dies am Fortschrittsbalken zu erkennen.
Über die <ApiLink>OVHcloud API</ApiLink> kann dieser Status mit folgendem API-Aufruf abgerufen werden:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/install/status"} />

Es gibt 2 Arten von Fehlern:

- **OVH-Fehler**: Der Kunde ist für den Fehler nicht verantwortlich. Er kann mit einem anderen Partitionierungsschema neu installieren, OVHcloud muss den Fehler jedoch beheben.
- **Kundenfehler**: Der Kunde hat ein Partitionierungsschema angefordert, das nicht umgesetzt werden kann oder das verhindern würde, dass der Server ordnungsgemäß startet.

Im nächsten Abschnitt konzentrieren wir uns ausschließlich auf die **Kundenfehler** im Zusammenhang mit der Partitionierung, da nur diese für den Kunden hilfreich sind.

#### Automatische Korrektur der Kundeneingaben

Um das Kundenerlebnis zu verbessern, die Arbeitslast des OVHcloud Supports zu verringern und Breaking Changes für Kunden zu vermeiden, werden einige Kundeneingaben vom Backend automatisch korrigiert oder geändert. Die folgende Tabelle gibt einen Überblick darüber, was derzeit automatisch korrigiert/geändert wird:

|Thema|Beschreibung|
|---|---|
|ZP-Gruppierung|Alle ZFS-Partitionen mit derselben RAID-Stufe werden nach Möglichkeit (abhängig von der Größe der Festplatten) im selben zpool (ZP) zusammengefasst, sofern derselbe zpool-Name oder kein zpool-Name angegeben ist|
|LV-Gruppierung|Alle Partitionen vom Typ `lv` mit derselben RAID-Stufe werden in derselben VG zusammengefasst (sofern dies abhängig von der Größe der Festplatten möglich ist)|
|VG-Erweiterung|Bei LV-Partitionen mit RAID-Stufe 0 erstreckt sich die VG über mehrere PPs (und damit PDs), und es wird kein SR-Gerät erstellt|
|VG-Festplattenfüllung|Der verbleibende Festplattenspeicher wird durch eine VG belegt (sofern ein LV vorhanden ist). Die Größe der an die VG angeschlossenen LVs bleibt davon unberührt.|
|Verringerung der RAID-Stufe|Wenn der Kunde eine Partition mit einer RAID-Stufe wählt, die mehr Festplatten erfordert, als der Server hat, wird die RAID-Stufe automatisch in folgender Reihenfolge verringert: 6, 10, 5, 1, 0 (bzw. raidz3, raidz2, raidz, mirror, striped vdev für ZFS)|
|Verringerung der PP-Größe|Wenn der Kunde eine PP gewählt hat, die mehr Speicherplatz erfordert, als der Server hat, wird die Größe dieser PP so verringert, dass sie auf die Festplatte passt. Beachten Sie, dass das Skript bei mehreren PPs, die mehr Speicherplatz benötigen, als das System hat, nur auf die erste Partition einwirkt und später im Skript einen Fehler für die zweite überdimensionierte Partition auslöst. Beachten Sie außerdem, dass ein Fehler ausgelöst wird, wenn der Kunde über die OVHcloud API eine andere Partition so festgelegt hat, dass sie die Festplatte füllt|
