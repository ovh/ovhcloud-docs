Die Profiling-Funktion befindet sich in der **Beta-Phase**. Funktionsumfang, Profilnamen und Limits können sich bis zur allgemeinen Verfügbarkeit noch geringfügig ändern.

:::

## Ziel

Der VAC DDoS-Schutz schützt standardmäßig jeden OVHcloud Dienst, ohne Konfiguration und ohne Zusatzkosten. VAC ist ein zentraler Bestandteil der [DDoS-Schutz-Infrastruktur](/links/security/antiddos) von OVHcloud: eine von OVHcloud kontinuierlich weiterentwickelte Kombination von Technologien, die den eingehenden Traffic so filtert, dass nur legitime Pakete Ihren Server erreichen. Die Erkennung basiert auf den Mustern Ihres Traffics: Paketraten, Fluktuation der Verbindungen, plötzliche Volumenänderungen oder bekannte Traffic-Signaturen.

Die generische Erkennung funktioniert für die meisten geschützten Anwendungen gut, kann aber einige spezifischere, dennoch legitime Workloads falsch einschätzen: Ein stark ausgelasteter WireGuard-Tunnel sieht aus wie ein UDP-Flood, und Zuschauerspitzen bei Live-Events sehen aus wie ein volumetrischer Angriff.

Mit der Profiling-Funktion können Sie solche Dienste genauer beschreiben, anstatt den Schutz zu umgehen. Wählen Sie ein Profil aus dem Katalog, legen Sie eine Empfindlichkeitsstufe fest und verknüpfen Sie Ihre Dienste. Eine einzige Änderung an einer Richtlinie passt alle damit verknüpften Adressen neu an. Wenn sich Ihr Workload ändert, wechseln Sie das Profil oder passen Sie die Empfindlichkeit an.

**In dieser Anleitung erfahren Sie:**

- wie Sie erkennen, wann Ihr Workload ein Profil benötigt.
- wie Sie das Profiling für Ihren Account aktivieren und eine Schutzrichtlinie erstellen.
- wie Sie eine Richtlinie auf Ihre IP-Adressen anwenden und ihren Status verstehen.
- wie Sie eine Richtlinie anpassen, deaktivieren oder löschen und ihre Wirkung beurteilen.

## Voraussetzungen

- Sie verfügen über mindestens einen OVHcloud Dienst mit einer öffentlichen IPv4-Adresse.

### Warum der Schutz eine Feinabstimmung benötigen kann <a name="why"></a>

In zwei Hauptsituationen kann es sinnvoll sein, die Standardeinstellungen anzupassen:

| | Was passiert | Was Sie beobachten |
|---|---|---|
| **Falsch positiv** | Legitimer Traffic wird als Angriff eingestuft und gefiltert. | Abgebrochene Sitzungen, unterbrochene Tunnel, getrennte Benutzer während einer Traffic-Spitze, obwohl tatsächlich kein Angriff stattfindet. |
| **Falsch negativ** | Der Angriffs-Traffic ist nicht aggressiv genug, um die generischen Schwellenwerte auszulösen. | Beeinträchtigter Dienst während eines Angriffs, der nie vollständig abgewehrt wurde. |

Falsch positive Erkennungen sind der häufigere Fall, und einige wenige Workloads sind für die meisten davon verantwortlich: VPN-Tunnel, deren UDP-Paketraten hoch sind; Blockchain-/Solana-Knoten, die große Portbereiche bei ständig wechselnden Peers nutzen; Livestreaming- und Sprachdienste, die plötzlichen, aber legitimen Zuschaueranstiegen ausgesetzt sind; sowie Webdienste während eines Produktstarts oder einer Verkaufsaktion.

Erstellen Sie eine Schutzrichtlinie, wenn eine der folgenden Situationen zutrifft:

- Legitimer Traffic wird gefiltert und Sie umgehen dies bisher, indem Sie bei einem VPN den TCP-Modus erzwingen, die MTU senken oder nach jedem Vorfall ein Support-Ticket eröffnen.
- Sie bereiten sich auf eine absehbare Traffic-Spitze vor, etwa ein Live-Event oder einen Produktstart.
- Sie betreiben eine Anwendung mit strukturell ungewöhnlichem Traffic und möchten diese lieber im Voraus deklarieren, anstatt auf die erste falsch positive Erkennung zu warten.
- Ein Angriff wurde abgewehrt, aber nicht gründlich genug, und Sie möchten, dass die Erkennung früher reagiert.

Wenn keine dieser Situationen zutrifft, ist keine Änderung erforderlich: Ihre Dienste bleiben standardmäßig geschützt.

### So funktioniert das Profiling <a name="concepts"></a>

Sie erstellen **Schutzrichtlinien**. Eine Schutzrichtlinie kombiniert ein Netzwerk-Traffic-Profil mit einer Empfindlichkeitsstufe und gilt für die öffentlichen IPv4-Adressen oder -Blöcke, die Sie ihr hinzufügen.

#### Netzwerk-Traffic-Profile

OVHcloud entwickelt und pflegt die spezifischen Netzwerk-Traffic-Profile: Wählen Sie beim Erstellen einer Richtlinie dasjenige aus, das am besten zu Ihrem Workload passt.

| Netzwerk-Traffic-Profil | Geeignet für |
|---|---|
| VPN - WireGuard | WireGuard-VPN-Server. |
| VPN - OpenVPN | OpenVPN-Server, die über UDP laufen, mit TCP als Fallback. |
| Game Server - Generic | Game-Server, die sowohl TCP als auch UDP verwenden. Dieses Profil ist toleranter als die reinen UDP- und TCP-Profile für Game-Server und hält während eines Angriffs alle Spielfunktionen aufrecht, etwa TCP-Downloads von einem Server, dessen Spiel-Traffic ansonsten über UDP läuft. |
| Game Server - Generic UDP | UDP-basierte Spieldienste. Das Profil eignet sich auch für TeamSpeak-Traffic. |
| Game Server - Generic TCP | TCP-basierte Spielprotokolle. |
| VoIP - TeamSpeak | TeamSpeak-Server. Das Profil schützt auch die meisten UDP-basierten Spieldienste. |
| WebServer - Generic | Webserver, die ausschließlich HTTP- und HTTPS-Traffic auf den TCP-Ports 80 und 443 empfangen. |
| Generic - Proxied TCP | Back-End-Server, deren Front-End außerhalb von OVHcloud gehostet wird, zum Beispiel bei einem externen CDN-Anbieter. Hosts, die legitimerweise viele Verbindungen zum Back-End öffnen, werden mit deutlich geringerer Wahrscheinlichkeit als Angreifer eingestuft. |
| Blockchain - Solana | Solana-Knoten, deren legitimer Traffic ein sehr hohes Volumen erreichen kann. |
| DNS - Server | DNS-Server. Das Profil nutzt die spezifischen Traffic-Muster von DNS, um möglichst viel Angriffs-Traffic zu blockieren, mit minimalen Auswirkungen auf legitime Anfragen. |
| Default | Ein generisches Profil mit mehreren Empfindlichkeitsstufen. Verwenden Sie es, wenn kein anderes Profil zu Ihrem Workload passt. |

:::warning
Auf Bare-Metal-Servern der Game-Reihe empfehlen wir, das Profiling, insbesondere die Profile Game Server (Generic, Generic UDP und Generic TCP), nicht mit IP-Adressen zu kombinieren, die durch eine Regel vom Typ **Minecraft Java** im [Game DDoS-Schutz](/guides/bare-metal-cloud/dedicated-servers/firewall-game-ddos) geschützt sind. Dies kann die Qualität des Gesamtschutzes beeinträchtigen.

:::

#### Optimale Ergebnisse mit einem Profil erzielen

So erzielen Sie mit einigen Profilen die besten Ergebnisse:

- **VPN - WireGuard:** Betreiben Sie WireGuard auf seinem Standardport UDP 51820. So vermeiden Sie den Verlust von legitimem Traffic während eines Angriffs.
- **VPN - OpenVPN:** Betreiben Sie OpenVPN auf seinen Standardports UDP 1194 und TCP 443. Wenn Sie den TCP-Fallback nicht benötigen, blockieren Sie diesen Traffic mit der [Edge Network Firewall](/guides/bare-metal-cloud/dedicated-servers/firewall-network).
- **WebServer - Generic:** Verwenden Sie dieses Profil nicht, wenn der Server auch UDP-Traffic empfängt. QUIC (HTTP/3) wird noch nicht unterstützt: QUIC-Traffic wird während eines Angriffs verworfen.
- **Generic - Proxied TCP:** Wählen Sie dieses Profil anstelle von WebServer - Generic, wenn einem bei OVHcloud betriebenen Webserver ein externes CDN oder ein außerhalb von OVHcloud gehosteter Reverse Proxy vorgeschaltet ist. Der Ursprungsserver empfängt dann viele Verbindungen von einer kleinen Anzahl von CDN-Edge-Adressen, und dieses Profil erwartet dieses Muster, anstatt diese Adressen als Angreifer einzustufen.
- **Blockchain - Solana:** Während eines Angriffs vermeidet die Mitigation, legitimen Solana-Traffic zu beeinträchtigen. Der Nachteil ist, dass bei sehr gezielten Angriffen mehr schädlicher Traffic bis zum Server gelangen kann.

#### Empfindlichkeit

Die Empfindlichkeit bestimmt, wo die Richtlinie im Spannungsfeld zwischen zu viel und zu wenig Mitigation angesiedelt ist. Die verfügbaren Stufen hängen vom Profil ab.

| Empfindlichkeit | Wirkung | Anwendungsfall |
|---|---|---|
| `Niedrig` | Weniger falsch positive Erkennungen: am tolerantesten gegenüber legitimen Traffic-Spitzen. | Die Verfügbarkeit während Spitzen ist wichtiger als die Filtertiefe. |
| `Mittel` | Ausgewogene Erkennung. Der empfohlene Ausgangspunkt. | Sie wenden zum ersten Mal ein Profil an. |
| `Hoch` | Weniger falsch negative Erkennungen: die aggressivste Filterung. | Angriffe sind durchgekommen. |

#### Eine Richtlinie pro IP-Adresse

Eine IP-Adresse wird nur von einer einzigen Richtlinie abgedeckt. Wenn ein Block mit einer Richtlinie und eine Adresse innerhalb dieses Blocks mit einer anderen verknüpft ist, hat der spezifischste Eintrag Vorrang. Wenn zum Beispiel `203.0.113.0/24` mit einer Richtlinie WebServer - Generic und `203.0.113.10` mit einer Richtlinie VPN - WireGuard verknüpft ist, verwendet `203.0.113.10` die Richtlinie VPN - WireGuard und der Rest des Blocks die Richtlinie WebServer - Generic.

Die Einstellungen einer Richtlinie bleiben für eine Additional IP erhalten, wenn diese zwischen Ihren Diensten verschoben wird. Sie werden nur zurückgesetzt, wenn die Adresse den Inhaber wechselt oder ihr Dienst gekündigt wird.

### Schritt 1 — Profiling aktivieren <a name="activate"></a>

Die Aktivierung ist nur einmal pro Account erforderlich.

1. Öffnen Sie den Tab <code className="action">Profilerstellung</code>.
2. Klicken Sie auf <code className="action">Profiling aktivieren</code>.

    Folgen Sie gegebenenfalls den angezeigten Anweisungen, um die Aktivierung abzuschließen. Es wird kein Betrag berechnet.

Nach Abschluss der Aktivierung listet der Tab <code className="action">Profilerstellung</code> Ihre definierten Schutzrichtlinien auf. Die Aktivierung des Profilings ändert die Schutzeinstellungen einer IP-Adresse erst, wenn Sie diese einer Richtlinie hinzufügen.

### Schritt 2 — Eine Schutzrichtlinie erstellen <a name="create"></a>

1. Klicken Sie im Tab <code className="action">Profilerstellung</code> auf <code className="action">Schutzrichtlinie erstellen</code>.
2. Geben Sie im Feld `Name` einen Namen ein, der den Workload identifiziert, zum Beispiel `vpn-concentrators`.
3. Wählen Sie in der Liste `Netzwerk-Traffic-Profil` das Profil aus, das zu Ihrem Workload passt. Seine Beschreibung wird unterhalb der Liste angezeigt.
4. Legen Sie die `Empfindlichkeit` fest. Beginnen Sie mit `Mittel`, es sei denn, Sie wissen bereits, in welche Richtung der Schutz angepasst werden muss.
5. Klicken Sie auf <code className="action">Richtlinie erstellen</code>.

Sie fügen IP-Adressen hinzu, sobald die Richtlinie existiert. Bis dahin hat die Richtlinie den Status **Nicht konfiguriert**: Sie gilt noch für keine Adresse.

### Schritt 3 — Ihre IP-Adressen hinzufügen <a name="targets"></a>

1. Klicken Sie in der Liste der Richtlinien auf den Namen der Richtlinie oder auf den Button <code className="action">...</code> am Ende ihrer Zeile und dann auf <code className="action">Ändern</code>.
2. Klicken Sie im Abschnitt `Ziele` des Panels `Schutzrichtlinie bearbeiten` auf das Feld `IP hinzufügen…`. Die Liste zeigt die IP-Blöcke und einzelnen IP-Adressen an, die in Ihrem Account verfügbar sind. Geben Sie den Anfang einer Adresse ein, um die Liste zu filtern.
3. Wählen Sie eine Adresse oder einen ganzen Block aus. Wenn sich Ihre Server in einem zusammenhängenden Block befinden, fügen Sie statt jeder einzelnen Adresse den Block hinzu.
4. Nachdem Sie einen IP-Block ausgewählt haben, können Sie die Auswahl im Eingabefeld ändern: Geben Sie statt des ganzen Blocks eines seiner Subnetze oder eine einzelne IP-Adresse aus diesem Block ein.
5. Wiederholen Sie diesen Vorgang für jede Adresse oder jeden Block und klicken Sie dann auf <code className="action">Änderungen speichern</code>. Eine Bestätigungsmeldung wird angezeigt.

Ab diesem Zeitpunkt folgt der VAC DDoS-Schutz für diese Adresse dem Profil und der Empfindlichkeit der Richtlinie statt der generischen Einstellungen. Die Änderung erfolgt im Hintergrund: Die Adresse ist mit **Pending** markiert, bis die Änderung angewendet ist, danach verschwindet das Badge.

Wenn eine von Ihnen hinzugefügte Adresse bereits ältere Anti-DDoS-Einstellungen aufweist, die nicht durch eine Richtlinie festgelegt wurden, etwa benutzerdefinierte Einstellungen der OVHcloud Support-Teams, öffnet sich beim Speichern das Fenster `Legacy-Anti-DDoS-Einstellungen erkannt`. Um die Richtlinie trotzdem anzuwenden, aktivieren Sie das Kontrollkästchen <code className="action">Ich verstehe</code> und klicken Sie dann auf <code className="action">Überschreiben und speichern</code>. Auf diese Weise erhalten Sie die Kontrolle über die Schutzeinstellungen der IP-Adresse und können diese mit den neuesten Profiling-Optionen ändern.

:::warning
Das Überschreiben älterer Einstellungen ist unumkehrbar: Diese lassen sich danach nicht wiederherstellen. Wenn Sie die Richtlinie später deaktivieren, kehrt die Adresse zum standardmäßigen VAC DDoS-Schutz zurück, nicht zu ihren vorherigen Einstellungen.

:::

### Statusanzeigen verstehen <a name="statuses"></a>

Die Liste der Richtlinien zeigt für jede Richtlinie ihr Netzwerk-Traffic-Profil, ihre Empfindlichkeit, die Anzahl ihrer IP-Adressen, den zuletzt erkannten Angriff und ihren Status an. Sie können die Liste nach Profil, Empfindlichkeit und Status filtern.

| Ort | Status | Bedeutung |
|---|---|---|
| Liste der Richtlinien | **Aktiv** | Aktiviert, mit mindestens einer IP-Adresse. Der Schutz ist angepasst. |
| Liste der Richtlinien | **Nicht konfiguriert** | Aktiviert, aber noch ohne IP-Adresse. Fügen Sie ein Ziel hinzu. |
| Liste der Richtlinien | **Deaktiviert** | Ausgeschaltet. Für ihre Adressen, die weiterhin verknüpft bleiben, gilt der standardmäßige VAC DDoS-Schutz. |
| Abschnitt `Ziele` | Kein Badge | Die Adresse ist durch die Richtlinie geschützt. |
| Abschnitt `Ziele` | **Pending** | Die Adresse wird mit dem Profiling-System synchronisiert. Dies kann einige Minuten dauern. |
| Abschnitt `Ziele` | **Deleting** | Die Adresse wird aus der Richtlinie entfernt. |

### Ihre Schutzrichtlinien verwalten <a name="manage"></a>

Jede Richtlinie verfügt in der Liste der Richtlinien am Ende ihrer Zeile über einen Aktionsbutton (<code className="action">...</code>) mit den folgenden Optionen:

| Aktion | Vorgehensweise | Wirkung |
|---|---|---|
| Profil oder Empfindlichkeit ändern | <code className="action">Ändern</code>, dann ändern Sie `Netzwerk-Traffic-Profil` oder `Empfindlichkeit` und klicken auf <code className="action">Änderungen speichern</code>. | Gilt für alle Adressen der Richtlinie gleichzeitig. Ändern Sie die Empfindlichkeit jeweils nur um eine Stufe und beobachten Sie das Ergebnis, bevor Sie sie erneut ändern. |
| Richtlinie deaktivieren | <code className="action">Deaktivieren</code>, dann bestätigen Sie den Vorgang. | Die Adressen kehren zum standardmäßigen VAC DDoS-Schutz zurück. Diese bleiben verknüpft, und die Richtlinie kann jederzeit wieder aktiviert werden. Nutzen Sie diese Option bei der Fehlerbehebung, um das Profil als Ursache zu bestätigen oder auszuschließen, anstatt die Richtlinie zu löschen. |
| Richtlinie aktivieren | <code className="action">Aktivieren</code> bei einer deaktivierten Richtlinie. | Das Profil wird erneut auf die verknüpften Adressen angewendet. |
| Adresse verschieben | <code className="action">Ändern</code>, dann entfernen Sie die Adresse aus dem Abschnitt `Ziele` der einen Richtlinie, speichern und fügen sie einer anderen Richtlinie hinzu. | Eine Adresse gehört nur zu einer einzigen Richtlinie. |
| Richtlinie löschen | <code className="action">Löschen</code>, dann bestätigen Sie den Vorgang. | Entfernt die Richtlinie und alle ihre Ziele. Die Adressen der Richtlinie kehren zum Standardschutz zurück. Dies kann nicht rückgängig gemacht werden. |

### Die Wirkung einer Richtlinie überwachen <a name="monitoring"></a>

Eine Richtlinie verändert, welcher Traffic der Mitigation unterliegt. Beurteilen Sie sie daher, indem Sie die Mitigationsaktivität vor und nach ihrer Anwendung vergleichen.

Gehen Sie in der OVHcloud Konsole zu <code className="action">Sicherheit</code> > <code className="action">Anti-DDoS</code>. Der Tab <code className="action">Dashboard</code> listet die auf Ihren Adressen erkannten Angriffe auf, und während Erkennungsereignissen zeigt der Tab <code className="action">Traffic</code> den legitimen Traffic der ausgewählten Adresse sowie den Traffic an, der während abgewehrter Angriffe gefiltert wurde. Eine wirksame Richtlinie filtert während legitimer Spitzen weniger Traffic und während echter Angriffe nicht weniger. Weitere Informationen zu den auf Ihren Diensten erkannten Angriffen finden Sie in unserer Anleitung [DDoS-Angriffe mit dem Anti-DDoS-Dashboard überwachen](/guides/bare-metal-cloud/dedicated-servers/network-security-dashboard).

Wenn sich ein Profil nicht wie erwartet verhält, teilen Sie uns dies über den Link <code className="action">Gefällt es Ihnen?</code> oben im Tab Profilerstellung mit. Während der Beta-Phase hilft uns dieses Feedback, den Katalog zu verbessern.

### Einschränkungen <a name="limitations"></a>

| Einschränkung | Details |
|---|---|
| Schutzrichtlinien | 20 pro Account. |
| Zieltypen | Nur IPv4-Adressen und IPv4-Blöcke. Die Unterstützung von IPv6 wird später hinzugefügt. |
| Public Cloud | Floating IPs, einschließlich der von Managed Kubernetes Service verwendeten, können einzeln hinzugefügt werden. Eine Richtlinie kann noch keine gesamte Ressource eines Public Cloud Projekts als Ziel haben. |

### Fehlerbehebung <a name="troubleshooting"></a>

| Problem | Mögliche Ursache | Lösung |
|---|---|---|
| Legitimer Traffic wird weiterhin verworfen | Die Empfindlichkeit ist zu hoch, oder das Profil passt nicht zum Workload. | Senken Sie die Empfindlichkeit um eine Stufe und beobachten Sie das Ergebnis. Wenn das Problem bei `Niedrig` weiterhin besteht, ist das Profil wahrscheinlich nicht das richtige: Probieren Sie ein anderes aus und melden Sie dies über den Feedback-Link. |
| Ein Angriff wurde nicht vollständig abgewehrt | Die Empfindlichkeit ist zu niedrig. | Erhöhen Sie die Empfindlichkeit um eine Stufe und vergleichen Sie den gefilterten Traffic vorher und nachher. |
| Eine Adresse bleibt im Status **Pending** oder **Deleting** | Die Änderung wurde noch nicht vollständig angewendet. | Warten Sie einige Minuten und aktualisieren Sie die Seite. Wenn sich der Status nicht ändert, [kontaktieren Sie den Support](/links/support) und geben Sie den Namen der Richtlinie und die Adresse an. |
| Traffic wird verworfen, obwohl sich die Adresse in einer geeigneten Richtlinie befindet | Möglicherweise filtert eine andere Schutzebene den Traffic, etwa die Edge Network Firewall oder eine Firewall auf Anwendungsebene. Eine Richtlinie setzt diese nicht außer Kraft. | Überprüfen Sie Ihre Regeln der [Edge Network Firewall](/guides/bare-metal-cloud/dedicated-servers/firewall-network) oder spezifische Filterungen auf Anwendungsebene. |

Wenn ein Profil angewendet ist und das Problem weiterhin besteht, hilft ein Traffic-Mitschnitt (pcap) der betroffenen Datenflüsse dem Support bei der Analyse.
