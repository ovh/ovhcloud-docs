## Objective

This guide explains how to move the data of an existing MongoDB replica set to a Public Cloud Databases for MongoDB service. It covers two methods:

- **mongodump and mongorestore**: a one-off copy. Writes to the source must be stopped during the copy, so it implies downtime.
- **mongosync**: a continuous synchronisation, followed by a switchover when the target has caught up. Downtime is limited to the switchover.

**This guide explains how to prepare the target service, run each method and check the result.**

## Requirements

- A [Public Cloud project](/links/public-cloud/public-cloud) in your OVHcloud account
- A [Public Cloud Databases for MongoDB service](/guides/public-cloud/databases/getting-started), running a MongoDB version equal to or higher than the source
- A source MongoDB deployment running as a replica set
- A machine that can reach both the source and the target, to run the migration tools

## Instructions

### Before you start

#### Users are not migrated

On Public Cloud Databases for MongoDB, users are managed only from the OVHcloud Control Panel or the OVHcloud API. A user created any other way, for example with `createUser` or restored by `mongorestore --restoreDbUsersAndRoles`, is accepted by MongoDB, then deleted automatically a few minutes later.

Before switching your applications over, create their users on the target service from the <code className="action">Users</code> tab, with the roles they need. Do not use the `--dumpDbUsersAndRoles` and `--restoreDbUsersAndRoles` options, and do not restore the `admin` database.

#### Authorise the migration machine

In the OVHcloud Control Panel, open your service, then the <code className="action">Configuration</code> tab. In the `IPs` section, add the public IP address of the machine that runs the migration tools, then click <code className="action">Save changes</code>.

#### Create a migration user

In the <code className="action">Users</code> tab, click <code className="action">Add user</code>, enter a username, add the roles listed below, then click <code className="action">Create User</code>. Note the password displayed: it cannot be retrieved later.

| Method | Roles of the migration user |
|---|---|
| mongodump and mongorestore | `readWriteAnyDatabase@admin`, `restore@admin` |
| mongosync | `backup@admin`, `clusterManager@admin`, `clusterMonitor@admin`, `readWriteAnyDatabase@admin`, `restore@admin` |

Delete this user once the migration is complete.

#### Build the target connection string

Copy the `mongodb+srv://` URI from the `Connection information` section of the <code className="action">Dashboard</code> tab. For the migration tools, replace the `/admin` path with an `authSource=admin` parameter:

```bash
mongodb+srv://<username>:<password>@<srv-hostname>/?authSource=admin&tls=true
```

:::warning
If you keep `/admin` in the path, `mongorestore` treats `admin` as the target database and skips your other databases.
:::

### Method 1: mongodump and mongorestore

Install the [MongoDB Database Tools](https://www.mongodb.com/docs/database-tools/installation/) on the migration machine.

1. Stop the writes of your applications to the source.

2. Export the source databases:

    ```bash
    mongodump --uri "<source-uri>" --out dump
    ```

    The `dump` folder contains one sub-folder per database, including `admin`.

3. Import them into the target, excluding the `admin` database:

    ```bash
    mongorestore --uri "mongodb+srv://<username>:<password>@<srv-hostname>/?authSource=admin&tls=true" \
      --nsExclude 'admin.*' \
      dump
    ```

    Collections and their indexes are recreated on the target. The last line of the output shows the number of documents restored and the number of documents that failed.

4. If you run the import again, documents that already exist on the target are not overwritten: they are counted as failed. Add the `--drop` option to drop each collection before restoring it:

    ```bash
    mongorestore --uri "mongodb+srv://<username>:<password>@<srv-hostname>/?authSource=admin&tls=true" \
      --nsExclude 'admin.*' \
      --drop \
      dump
    ```

5. [Check the result](#check-the-migrated-data), then point your applications to the target.

### Method 2: mongosync

[mongosync](https://www.mongodb.com/docs/cluster-to-cluster-sync/current/reference/mongosync/) copies the data, then applies the changes made on the source until you commit the migration. Check its [limitations](https://www.mongodb.com/docs/cluster-to-cluster-sync/current/reference/limitations/) and its [version compatibility](https://www.mongodb.com/docs/cluster-to-cluster-sync/current/reference/supported-server-version/) before you start.

On the source, mongosync needs a user with authentication enabled and the privileges listed in the [mongosync documentation](https://www.mongodb.com/docs/cluster-to-cluster-sync/current/connecting/onprem-to-onprem/). If the source has no authentication, the start request fails with `Missing privileges: Source: AnyDB: [changeStream]`.

1. Download [mongosync](https://www.mongodb.com/try/download/mongosync) on the migration machine, then start it:

    ```bash
    mongosync \
      --cluster0 "<source-uri>" \
      --cluster1 "mongodb+srv://<username>:<password>@<srv-hostname>/?authSource=admin&tls=true"
    ```

    mongosync listens on port `27182` of the local machine and waits for instructions.

2. In another terminal, start the synchronisation:

    ```bash
    curl -X POST localhost:27182/api/v1/start \
      --data '{"source":"cluster0","destination":"cluster1"}'
    ```

    The answer is `{"success":true}`.

3. Follow the progress:

    ```bash
    curl localhost:27182/api/v1/progress
    ```

    When the initial copy is complete, `state` is `RUNNING` and `canCommit` is `true`. From then on, the inserts, updates and new collections created on the source are applied to the target. The `lag` field shows how far behind the source the target is, in seconds.

4. When you are ready to switch over, stop the writes of your applications to the source, wait until `lagTimeSeconds` is `0`, then commit:

    ```bash
    curl -X POST localhost:27182/api/v1/commit --data '{}'
    ```

5. Call the progress endpoint again. When `state` is `COMMITTED` and `canWrite` is `true`, the target is ready: stop mongosync with `Ctrl+C`, then point your applications to the target.

6. mongosync leaves its metadata in a `__mdb_internal_mongosync` database on the target. Drop its collections with the migration user, for example with mongosh:

    ```javascript
    const meta = db.getSiblingDB("__mdb_internal_mongosync");
    meta.getCollectionNames().forEach((name) => meta.getCollection(name).drop());
    ```

### Check the migrated data

Connect to the target with [mongosh](/guides/public-cloud/databases/mongodb-connect-cli) and compare, for each collection, the number of documents and the indexes with the source:

```javascript
use <database>
db.<collection>.countDocuments({})
db.<collection>.getIndexes()
```

Then make sure the users of your applications exist on the target, with the right roles, and delete the migration user.
