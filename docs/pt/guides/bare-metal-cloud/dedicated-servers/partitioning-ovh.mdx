## Objetivo

:::warning
Este artigo destina-se a utilizadores experientes que tenham, no mínimo, conhecimentos básicos de Linux e, sobretudo, conhecimentos mais aprofundados sobre armazenamento, em particular sobre RAID por software, RAID por hardware e gestão lógica de volumes (LVM).

:::


Os [servidores dedicados](/links/bare-metal/bare-metal) OVHcloud permitem-lhe configurar os discos, o [RAID por hardware](/guides/bare-metal-cloud/dedicated-servers/raid-hard), o [RAID por software](/guides/bare-metal-cloud/dedicated-servers/raid-soft), LVM, ZFS, etc. durante [a reinstalação](/guides/bare-metal-cloud/dedicated-servers/getting-started-with-dedicated-server) do seu sistema operativo a partir da <ApiLink>API OVHcloud</ApiLink> ou da <ManagerLink to="/">consola OVHcloud</ManagerLink>. Neste artigo, vamos concentrar-nos na <ApiLink>API OVHcloud</ApiLink>.<br/>
Isto dar-lhe-á mais detalhes sobre o motor que é executado em segundo plano para criar a personalização do armazenamento no servidor dedicado a partir dos dados de entrada transmitidos à API OVHcloud.

Dispor de detalhes avançados sobre a configuração do armazenamento pode ajudá-lo a compreender por que razão:

- a sua personalização do armazenamento não pôde ser aplicada no seu servidor dedicado.
- a personalização real do armazenamento no seu servidor dedicado é ligeiramente diferente da que tinha pedido.

## Requisitos

* Dispor de um [servidor dedicado](/links/bare-metal/bare-metal) **pronto a ser instalado/reinstalado** na sua conta OVHcloud.
* Ter acesso à <ApiLink>API OVHcloud</ApiLink>.

:::warning
A reinstalação de um servidor dedicado elimina todos os dados que nele se encontram armazenados.

:::


## Instruções

Durante a instalação predefinida do sistema operativo, o instalador do sistema operativo (fornecido pelo editor do software) pede ao utilizador que especifique os discos nos quais o sistema operativo será instalado, a configuração do particionamento, etc. Depois de o SO estar instalado, é possível modificar a disposição do particionamento, mas isso pode revelar-se muito delicado e arriscado, nomeadamente no caso das partições que estão a ser utilizadas pelo sistema. Por esta razão, a configuração do armazenamento é um assunto muito importante que deve ser tido em conta **antes** de instalar um sistema operativo.

Além da simplicidade da API, a principal vantagem é a possibilidade de personalizar totalmente os discos e as partições nos quais o SO será instalado.

Nesta página, vamos concentrar-nos apenas no sub-hash `storage` da chamada API utilizada para reinstalar um SO num servidor dedicado. Para as personalizações da reinstalação do SO não relacionadas com o armazenamento, consulte a página [API OVHcloud e instalação de um SO](/guides/bare-metal-cloud/dedicated-servers/api-os-installation) para mais detalhes.

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "diskGroupId": 1,
            "erase": true
        },
        {
            "diskGroupId": 2,
            "erase": true,
            "hardwareRaid": [
                {
                    "raidLevel": null,
                    "disks": 2
                }
            ],
            "partitioning": {
                "disks": 2,
                "layout": [
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/boot",
                        "size": 1000,
                        "raidLevel": 1
                    },
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/",
                        "size": 0
                    }
                ]
            }
        }
    ]
}
```

### Grupos de discos <a name="disk-group"></a>

Alguns [servidores dedicados](/links/bare-metal/bare-metal) possuem vários grupos de discos. Por exemplo, um grupo com discos SATA e um grupo com discos SSD. Chamamos a este tipo de servidores **servidores híbridos**.

Para listar os grupos e os respetivos discos, pode utilizar a seguinte chamada para determinar o grupo de discos no qual pretende efetuar a reinstalação do SO:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/specifications/hardware"} />

Exemplo de resposta:

```json

            "diskSize": {
                "unit": "GB",

            "numberOfDisks": 2,
            "raidController": null
        },
        {
            "defaultHardwareRaidSize": null,
            "defaultHardwareRaidType": null,
            "description": "2 X Disk NVME 1920 GB, JBOD",
            "diskGroupId": 2,
            "diskSize": {
                "unit": "GB",
                "value": 1920
            },

```

Neste exemplo, existem 2 grupos de discos:

- o primeiro (diskGroupId=1) contém 2 discos de 480 GB cada. Trata-se do diskGroupId predefinido.
- o segundo (diskGroupId=2) contém 2 discos de 1,9 TB cada.

Exemplo de instalação do Debian 13 (Trixie) no diskGroupId 2:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "diskGroupId": 2
        }
    ]
}
```

:::info
Por predefinição, se nenhum diskGroupId for especificado ou se estiver definido como 0, o sistema operativo é instalado no diskGroupId 1 predefinido.

:::


<br />

:::warning
De momento, a API apenas suporta a instalação do SO e a personalização do armazenamento num único grupo de discos. Pode incluir desde 1 até todos os discos do grupo escolhido na personalização do armazenamento. No entanto, os restantes discos desse grupo serão apagados. Os discos pertencentes aos outros grupos também são apagados por predefinição, mas os respetivos dados podem ser conservados: consulte a secção [Eliminação dos dados](#data-erasure). Em qualquer caso, estes discos continuarão visíveis para o SO instalado e poderão ser utilizados/configurados posteriormente para armazenar dados.

:::


### RAID por hardware <a name="hard-raid"></a>

Esta secção aplica-se apenas aos servidores que tenham pelo menos um controlador RAID por hardware num dos seus [grupos de discos](#disk-group).

#### Servidor e compatibilidade do RAID por hardware

Pode utilizar a seguinte chamada API para saber se o seu servidor dedicado é compatível:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/install/hardwareRaidProfile"} />

Se o seu servidor dedicado não tiver controlador RAID por hardware, a chamada devolve um erro HTTP 403 (Forbidden) com a seguinte mensagem:

```json
{
  "message": "Hardware RAID is not supported by this server"
}
```

Exemplo de resposta para um servidor que possui RAID por hardware:

```json
{
  "controllers": [
    {
      "type": "mega",
      "disks": [
        {
          "names": [
            "c0:d0",
            "c0:d1",
            "c0:d2"
          ],
          "type": "SSD",
          "capacity": {
            "unit": "GB",
            "value": 960
          },
          "speed": {
            "value": "6g",
            "unit": "GB/s"
          }
        }
      ],
      "model": "9361-8i-2G"
    }
  ]
}
```

:::info
Também pode obter esta informação a partir do valor do atributo `raidController` da chamada API descrita na secção [Grupos de discos](#disk-group).

:::


#### API e RAID por hardware

:::warning
De momento, a API apenas suporta a personalização do RAID por hardware para um único controlador RAID por hardware. Se o seu servidor possuir vários controladores RAID por hardware cuja configuração pretende personalizar, pode configurar os controladores diferentes do controlador do grupo de discos escolhido para a reinstalação do SO **antes** da reinstalação do SO (também pode fazê-lo depois de concluída a reinstalação do SO, mas recomendamos que o faça **antes**, para evitar qualquer risco de erro de manipulação que possa provocar uma perda de dados).

:::


Exemplo de uma instalação do SO com um RAID 1 por hardware entre os 2 primeiros discos do grupo de discos:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "hardwareRaid": [
                {
                    "raidLevel": 1,
                    "disks": 2
                }
            ]
        }
    ]
}
```

:::info
Se `disks` não for especificado, **todos** os discos do grupo de discos serão incluídos no RAID por hardware.

:::


Suponhamos agora que tem um servidor dedicado com 1 grupo de discos ligado ao controlador RAID por hardware e 12 discos nesse grupo. Exemplo com um RAID 10 por hardware:

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "hardwareRaid": [
                {
                    "raidLevel": 10,
                    "arrays": 4
                }
            ]
        }
    ]
}
```

Neste exemplo, os 12 discos serão incluídos no RAID por hardware de nível 10. Haverá 4 grupos de 3 discos, o que significa 4 RAID 1 entre 3 discos, e os 4 grupos ficarão em RAID 0.

:::info
O RAID por hardware situa-se numa camada que não é visível para o SO. Assim, todos os SO são "compatíveis" com o RAID por hardware.

:::


Todos os discos incluídos na configuração do RAID por hardware serão vistos pelo SO como um único disco virtual.

Por conseguinte, se tiver incluído todos os discos do grupo de discos de destino numa configuração de RAID por hardware, não será possível configurar um RAID por software por cima, uma vez que o SO apenas vê um único disco virtual.

### Particionamento <a name="partitioning"></a>

Quando falamos de esquema de particionamento, referimo-nos à organização dos seus dados nos discos, ou seja, tudo o que se encontra acima do seu disco físico (ou disco virtual, se tiver configurado um RAID por hardware), até ao sistema de ficheiros montado e visível no SO, das camadas mais baixas às mais altas:

- Disco (disco físico/virtual, PD)
- Partição (partição física, PP)
- ZFS: vdev (zgroup, ZG), zpool (ZP), dataset ZFS (ZD), volume ZFS (ZV)
- [RAID por software](/guides/bare-metal-cloud/dedicated-servers/raid-soft) (SR)
- LVM: volume físico (VP), grupo de volumes (VG), volume lógico (LV)
- Sistema de ficheiros com ponto de montagem (FS)

A tabela seguinte apresenta uma visão geral dos diferentes componentes do particionamento e da forma como estas camadas interagem:

<img className="thumbnail" alt="Tabela que representa as diferentes camadas do particionamento" src="/images/bare-metal-cloud/dedicated-servers/partitioning-ovh/partitioning-layers-table.png" loading="lazy" />

:::info
Na tabela acima, `/dev/zd1` representa um volume ZFS (também chamado `zvol`). Trata-se de um disco virtual situado acima de um conjunto de dados ZFS (ZD) e de um zpool (ZP), que o sistema operativo considera um disco físico normal (PD). Esta funcionalidade não está disponível na API OVHcloud e não prevemos implementá-la.

:::


#### SO e compatibilidade do particionamento <a name="os-partitioning-compatibility"></a>

Uma vez que a configuração do particionamento será visível para o SO, o SO escolhido para a reinstalação tem impacto nas possibilidades de personalização do seu particionamento.

Na secção <code className="action">/dedicated/installationTemplate</code>, pode obter detalhes como a compatibilidade com LVM e a disponibilidade dos sistemas de ficheiros para um SO específico:

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}"} />

Por exemplo:

```json
{
    "templateName": "debian13_64",
    "filesystems": [
        "btrfs",
        "ext4",
        "swap",
        "xfs",
        "zfs"
    ],
    ...
    "lvmReady": true,
    "noPartitioning": false,
    "softRaidOnlyMirroring": false
}
```

|Atributo|Descrição|
|---|---|
|filesystems|Sistemas de ficheiros compatíveis com este sistema operativo|
|lvmReady|Indica se este sistema operativo suporta LVM ou não|
|noPartitioning|Se verdadeiro, este sistema operativo não suporta a personalização do particionamento|
|softRaidOnlyMirroring|Se verdadeiro, este sistema operativo suporta apenas parcialmente a personalização do particionamento (apenas os RAID por software de níveis 0 e 1 podem ser configurados e atribuídos aos 2 primeiros discos do grupo de discos)|

A seguinte chamada API pode ser utilizada para listar os diferentes esquemas de particionamento de um sistema operativo específico. A maioria dos sistemas operativos suporta a personalização do particionamento e tem, por conseguinte, um único esquema chamado "default". Apenas alguns deles não suportam a personalização do particionamento (`noPartitioning` tem o valor `true`) e **podem**, por conseguinte, ter vários esquemas de particionamento.

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}/partitionScheme"} />

As seguintes chamadas API podem ser utilizadas para saber que particionamento será aplicado por predefinição se não for especificada nenhuma personalização do particionamento ou se esta não for suportada pelo SO.

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}/partitionScheme/\{schemeName\}/partition"} />


<br />

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}/partitionScheme/\{schemeName\}/partition/\{mountpoint\}"} />


#### LVM, níveis de RAID e compatibilidade dos sistemas de ficheiros <a name="lvm-raid-levels-filesystems-compatibility"></a>

A tabela seguinte apresenta uma visão geral da compatibilidade dos sistemas de ficheiros com os níveis de RAID e LVM no contexto OVHcloud:

|Sistema de ficheiros|LVM|RAID 0|RAID 1|RAID 5|RAID 6|RAID 7|RAID 10|
|---|---|---|---|---|---|---|---|
|Btrfs, ext4, XFS|✅|✅|✅|✅|✅|❌|✅|
|ZFS¹|❌|✅|✅|✅|✅|✅|❌|
|swap|❌|⚠️²|❌|❌|❌|❌|❌|
|NTFS|❌|❌|✅³|❌|❌|❌|❌|
|UFS, VMFS5, VMFS6, VMFS-L⁴|❌|❌|❌|❌|❌|❌|❌|

¹ Para mais informações, consulte a tabela [Vdevs ZFS vs RAID padrão](#raidz2RAID).<br />
² O nível de RAID para swap só pode ser igual a 1 na <ApiLink>API OVHcloud</ApiLink>. Na realidade, as partições swap não utilizarão RAID. Quando uma partição swap de tamanho `s` é definida num servidor com um número `n` de discos, serão criadas `n` partições de tamanho `s` em cada disco, sem qualquer dispositivo RAID por software subjacente.<br />
³ O RAID nativo do Windows (o configurado pelo instalador OVHcloud) suporta RAID 1, mas apenas entre dois discos, ao passo que outras implementações permitem mais de dois.<br />
⁴ O instalador ESXi não suporta esquemas de particionamento personalizados. O particionamento é definido pelo editor do software. No entanto, a <ApiLink>API OVHcloud</ApiLink> pode dar-lhe uma ideia do aspeto do particionamento: para mais informações, consulte [SO e compatibilidade do particionamento](#os-partitioning-compatibility).<br />

:::warning
Esta tabela é fornecida apenas a título informativo. Tenha em conta que a compatibilidade com LVM e, sobretudo, com os sistemas de ficheiros depende também do SO (template OVHcloud) instalado. Consulte a secção [SO e compatibilidade do particionamento](#os-partitioning-compatibility) para mais detalhes.

:::


#### Vdevs ZFS vs RAID padrão <a name="raidz2RAID"></a>

O ZFS não suporta os níveis de RAID padrão. Utiliza dispositivos virtuais (vdevs) para descrever a tolerância a falhas dentro de um grupo de dispositivos. Consulte a [documentação oficial do OpenZFS](https://openzfs.github.io/openzfs-docs/man/7/zpoolconcepts.7.html) (em inglês) para mais detalhes sobre os vdevs.

Para tornar a API OVHcloud o mais simples possível, é necessário que defina um RAID padrão na API para os sistemas de ficheiros ZFS. O nível de RAID padrão será então traduzido numa definição de vdev equivalente. A tabela seguinte ilustra a tradução dos diferentes níveis de RAID propostos pela API OVHcloud, bem como um lembrete das respetivas características.

|RAID padrão|Tipo de vdev equivalente|Número mínimo de discos de dados|Número de discos de paridade|Número mínimo total de discos necessários|
|---|---|---|---|---|
|RAID 0|striped vdev|1|0|1|
|RAID 1|mirror|2|0|2|
|RAID 5|raidz1|2|1|3|
|RAID 6|raidz2|3|2|5|
|RAID 7|raidz3|4|3|7|
|RAID 10|❌|4|0|4|

#### API e particionamento

:::warning
Um particionamento personalizado, embora válido e aceite pela <ApiLink>API OVHcloud</ApiLink>, pode ainda assim impedir o servidor de arrancar corretamente (por exemplo, uma combinação invulgar de sistema de ficheiros e gestor de arranque, ou um problema de montagem RAID/LVM/ZFS próprio da sua configuração). Nesse caso, nenhuma intervenção do suporte será criada automaticamente no servidor: será apresentada ao cliente uma mensagem explícita após o último reinício. Consulte a secção [Erros frequentes dos clientes](#errors) para mais detalhes.

:::

Exemplo de instalação do SO com um particionamento personalizado:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "partitioning": {
                "disks": 2,
                "layout": [
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/boot",
                        "size": 1000,
                        "raidLevel": 0
                    },
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/",
                        "size": 0
                    }
                ]
            }
        }
    ]
}
```

`size` 0 significa que a partição ocupará todo o espaço restante nos discos em causa.

:::info
No máximo, 1 partição pode ser configurada para ocupar o espaço restante (tamanho 0).

:::


<br />

:::info
Se não for especificado, `raidLevel` terá o valor 1.

:::


Neste exemplo, apenas os 2 primeiros discos do grupo são incluídos no particionamento (ou seja, no RAID por software).

:::info
O parâmetro `disks` pode ser omitido se pretender incluir todos os discos do grupo de discos no RAID por software.

:::


Como pode ver, um esquema de particionamento é uma lista de partições. Eis um exemplo de estrutura de uma partição:

```json
{
    "mountPoint": "/var/lib/vz",
    "fileSystem": "ext4",
    "size": 0,
    "raidLevel": "1",
    "extras": {
        "lv": {
            "name": "data"
        }
    }
}
```

O sub-hash `extras` é opcional. De momento, pode ser utilizado para especificar que a partição será um volume lógico (LVM) e indicar o nome desse volume lógico. O sub-hash também pode ser utilizado para ZFS:

```json
{
    "mountPoint": "/",
    "fileSystem": "zfs",
    "size": 0,
    "raidLevel": "5",
    "extras": {
        "zp": {
            "name": "poule"
        }
    }
}
```

Neste exemplo, o ponto de montagem `/` corresponde a um dataset ZFS num zpool chamado "poule" do tipo raidz1. Consulte a tabela [Vdevs ZFS vs RAID padrão](#raidz2RAID) para obter a correspondência entre os raidz e os níveis de RAID padrão.

:::info
Se nenhum nome de zpool for especificado, este será gerado automaticamente. Por predefinição, o algoritmo tenta agrupar os diferentes datasets num mesmo zpool, com exceção dos datasets que contêm `/` ou `/boot`, que são colocados em zpools separados. Isto permite ativar nos outros zpools funcionalidades avançadas do ZFS incompatíveis com o gestor de arranque.

:::


<br />

:::info
Utilizar um nome de zpool personalizado pode ser útil nos seguintes casos:

- agrupar datasets com os mesmos níveis de RAID: utilize o mesmo nome de zpool,
- forçar datasets com os mesmos níveis de RAID a ficarem em zpools distintos: utilize nomes diferentes.

:::

### Eliminação dos dados <a name="data-erasure"></a>

Por predefinição, os discos de cada grupo de discos do servidor são apagados durante a instalação do SO, quer o respetivo grupo esteja ou não declarado no pedido `storage`. Definir `erase` como `false` num grupo de discos é a única forma de conservar os seus dados.

Os grupos de discos diferentes daquele em que o SO é instalado também podem ser declarados, mas apenas para controlar se os respetivos dados são apagados (`erase: true`) ou conservados (`erase: false`).

O SO é instalado no grupo de discos que contém os atributos de instalação (`partitioning`, `hardwareRaid`); os outros grupos declarados contêm apenas o atributo `erase`. Se nenhum deles contiver um atributo de instalação, o SO é instalado no grupo de discos predefinido, tal como descrito na secção [Grupos de discos](#disk-group).

Exemplo com um servidor que dispõe de 2 grupos de discos: uma instalação simples do SO no `diskGroupId` 1 (cujos discos são implicitamente apagados) e o `diskGroupId` 2 declarado apenas para conservar os dados existentes:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "diskGroupId": 1,
            "partitioning": {
                "schemeName": "default"
            }
        },
        {
            "diskGroupId": 2,
            "erase": false
        }
    ]
}
```

:::warning
Aplicam-se as seguintes restrições à lista `storage`:

- Não pode definir `erase: false` para o grupo de discos no qual o SO é instalado.
- Não pode declarar várias vezes o mesmo `diskGroupId`.
- Não pode declarar mais de um grupo de discos no qual instalar o SO. Para qualquer grupo de discos adicional, apenas pode ser definido o atributo `erase`, sem instalação do SO, particionamento ou configuração de RAID por hardware.

:::

:::warning
Definir `erase` como `false` conserva todos os dados desse grupo de discos, mas a OVHcloud não pode garantir que a instalação do SO seja bem-sucedida: metadados de arranque residuais, superblocos `mdadm`, assinaturas LVM ou etiquetas ZFS provenientes de uma instalação anterior nesse grupo de discos (em qualquer um dos seus discos) podem entrar em conflito com a nova instalação.

Se a instalação falhar por um destes motivos, nenhum ticket de suporte é criado automaticamente. Em vez disso, é apresentada ao cliente uma mensagem explícita, durante o particionamento ou no primeiro arranque do SO instalado. Consulte a secção [Erros frequentes dos clientes](#errors) para mais detalhes.

:::

### Gestão dos erros

Os erros básicos nos dados de entrada do cliente são tratados diretamente pela API OVHcloud. Trata-se da situação mais comum e mais simples, uma vez que os clientes podem ver o erro de forma síncrona e tentar novamente de imediato.

Os dados de entrada do cliente relacionados com o particionamento podem ser demasiado específicos para serem verificados pela API OVHcloud e exigir, por conseguinte, um tempo de processamento. A desvantagem é que os clientes são notificados mais tarde, durante o processo de reinstalação do sistema operativo.

Este estado é visível através da barra de progresso na <ManagerLink to="/#/dedicated-servers/server">consola OVHcloud</ManagerLink>.
A partir da <ApiLink>API OVHcloud</ApiLink>, este estado pode ser obtido com a seguinte chamada API:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/install/status"} />

Existem 2 tipos de erros:

- **erros ovh**: não é responsável pelo erro; pode reinstalar com outra disposição do particionamento, mas a OVHcloud terá de corrigir a anomalia.
- **erros do cliente**: pediu um esquema de particionamento que não pode ser realizado ou que impediria o servidor de arrancar corretamente.

Na secção seguinte, vamos concentrar-nos apenas nos tipos de **erros do cliente** na etapa do particionamento, uma vez que só são úteis para os clientes.

#### Erros frequentes dos clientes <a name="errors"></a>

A tabela seguinte apresenta uma visão geral dos erros do cliente mais conhecidos e da forma de os corrigir.

|Mensagem de erro|Detalhes|Solução(ões)|
|---|---|---|
|Partition of type `t` with mountpoint `m` cannot fill the disk.|Escolheu que a partição `swap` ocupasse o disco (ou partição de tamanho zero se definida através da <ApiLink>API OVHcloud</ApiLink>). Não o permitimos para evitar criar partições `swap` desnecessariamente grandes.|- Defina um tamanho fixo para a partição `swap`.|
|`message`. Please adjust partitions so that the `p` partition fits on `n` disk(s)|Escolheu uma partição com um RAID que requer um número de discos que o seu servidor pode fornecer, mas alguns discos já estão cheios devido a outras partições e/ou a esta partição.|- Se ainda não o fez noutra partição, defina o tamanho da partição para que ocupe o disco (ou partição de tamanho zero se definida através da <ApiLink>API OVHcloud</ApiLink>).<br />- Reduza o tamanho desta partição para que caiba nos discos.<br />- Reduza o tamanho das outras partições para que esta partição caiba nos discos.|
|Error with MBR partition table: Partition `p` is larger than 2TiB and this server does not support GPT|Definiu uma partição cujo tamanho excede 2TiB e está a aplicar este particionamento num servidor que não suporta GPT.|- Reduza o tamanho desta partição para 2TiB.<br />- Aplique este particionamento noutro servidor semelhante que suporte GPT.|
|Error with MBR partition table: partition `p` cannot end after 2 TiB (`interval stop`) and this server does not support GPT! Therefore all customer partitions must end before (2TiB - `cloud-init size`).|Adicionamos sistematicamente uma partição config-drive no fim de um disco do seu servidor dedicado. A última partição do seu particionamento vai terminar depois da posição 2TiB no disco. Assim, se adicionarmos uma partição config-drive depois da última partição, esta terá de começar depois da posição 2TiB no disco de um servidor que não suporta GPT.|- Reduza o tamanho desta partição de modo que a soma total de todas as partições do disco seja inferior a 2TiB.<br />- Nunca defina uma partição que ocupe um disco (ou partição de tamanho zero se definida através da <ApiLink>API OVHcloud</ApiLink>) num [template personalizado](#customertemplates) que pretenda utilizar em servidores com discos maiores do que 2TiB e que não suportem GPT.|

|`/boot` (or `/` if no `/boot` defined) partition type cannot be `XFS`|A partição que contém o GRUB não suporta o sistema de ficheiros `XFS` neste sistema operativo. É geralmente o caso dos sistemas operativos da família Debian (Debian, Proxmox, Ubuntu).|- Crie uma partição `/boot` separada com um sistema de ficheiros diferente de `XFS`.<br />- Não crie uma partição `/boot` separada, mas escolha um sistema de ficheiros diferente de `XFS` para a partição `/`.|

Como o módulo `ZFS` não está incluído na imagem oficial, não queremos torná-la mais pesada com este módulo para os clientes que não utilizam `ZFS`. Por esta razão, o módulo `ZFS` é compilado e instalado durante a reinstalação e apenas para os clientes que o pedem. Uma vez que a compilação requer memória RAM além da que já é utilizada para executar o SO do modo rescue em `RAM`, fixámos o limiar em 8 GiB para garantir um bom funcionamento e uma boa experiência do cliente.|- Elimine todas as partições `ZFS` ou mude para um sistema de ficheiros diferente de `ZFS`.<br />- Escolha um SO que suporte `ZFS` nativamente, como o Ubuntu ou o Proxmox.<br />- Utilize um servidor com pelo menos 8 GiB de memória RAM.|

|Partitioning failed. |The server does not seem to have booted properly into the newly installed operating system. This is likely related to the custom partitioning you requested; please check the KVM, if available.|O particionamento pedido é aceite pela <ApiLink>API OVHcloud</ApiLink>, mas produz uma combinação de gestor de arranque/sistema de ficheiros/RAID a partir da qual o servidor não consegue arrancar.|- Consulte o KVM para identificar o problema de arranque exato<br />- Ajuste o seu particionamento (por exemplo, a escolha do sistema de ficheiros, o nível de RAID, a configuração de `/boot`) e reinstale|

#### Autocorreção dos dados de entrada do cliente

Para melhorar a experiência do cliente, reduzir a carga de trabalho do suporte OVHcloud e evitar alterações bruscas que possam ter impacto no cliente, alguns dados introduzidos pelo cliente são automaticamente corrigidos ou modificados pelo backend. A tabela seguinte apresenta uma visão geral do que é atualmente corrigido/alterado automaticamente:

|Assunto|Descrição|
|---|---|
|Agrupamento ZP|Todas as partições ZFS do mesmo nível de RAID serão agrupadas num mesmo zpool (ZP), se possível em função do tamanho dos discos e se nenhum nome de zpool for especificado ou se o mesmo nome de zpool for especificado para todas essas partições.|
|Agrupamento LV|Todas as partições do tipo `lv` com o mesmo nível de RAID serão agrupadas num mesmo VG (se possível em função do tamanho dos discos).|
|Expansão VG|No caso de partições lv de nível RAID 0, o VG estender-se-á por vários PP (e, portanto, PD) e nenhum dispositivo SR será criado.|
|VG Preenchimento do disco|O espaço em disco restante será preenchido por um VG (se existir um LV). O tamanho dos LV contidos nesse VG não é afetado.|
|Redução do nível de RAID|Caso escolha uma partição com um nível de RAID que requeira mais discos do que os que o servidor tem, o nível de RAID será automaticamente reduzido pela seguinte ordem: 6, 10, 5, 1, 0 (ou raidz3, raidz2, raidz, mirror, striped vdev para ZFS).|
|Redução do tamanho da PP|Caso tenha escolhido uma PP que requeira mais espaço do que o servidor tem, o tamanho dessa PP será reduzido para que caiba no disco. Tenha em conta que, caso várias PP requeiram mais espaço do que aquele de que o sistema dispõe, o script só atuará sobre a primeira partição, devolvendo um erro mais adiante no script para a segunda partição sobredimensionada. Tenha também em conta que será gerado um erro se tiver configurado outra partição para ocupar o disco através da API OVHcloud.|
