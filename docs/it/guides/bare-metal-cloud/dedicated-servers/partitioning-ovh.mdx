## Obiettivo

:::warning
Questo articolo è destinato a utenti esperti che dispongono almeno di conoscenze di base di Linux e, soprattutto, di conoscenze più approfondite sullo storage, in particolare sul RAID software, sul RAID hardware e sulla gestione logica dei volumi (LVM).

:::


I [server dedicati](/links/bare-metal/bare-metal) OVHcloud ti permettono di configurare i dischi, il [RAID hardware](/guides/bare-metal-cloud/dedicated-servers/raid-hard), il [RAID software](/guides/bare-metal-cloud/dedicated-servers/raid-soft), LVM, ZFS, ecc. durante [la reinstallazione](/guides/bare-metal-cloud/dedicated-servers/getting-started-with-dedicated-server) del sistema operativo dall'<ApiLink>API OVHcloud</ApiLink> o dalla <ManagerLink to="/">console OVHcloud</ManagerLink>. In questo articolo ci concentreremo sull'<ApiLink>API OVHcloud</ApiLink>.<br/>
In questo modo otterrai maggiori dettagli sul motore che viene eseguito in background per creare la personalizzazione dello storage sul server dedicato a partire dai dati di input trasmessi all'API OVHcloud.

Disporre di dettagli avanzati sulla configurazione dello storage può aiutarti a capire perché:

- la tua personalizzazione dello storage non è stata applicata sul server dedicato.
- la personalizzazione effettiva dello storage sul server dedicato è leggermente diversa da quella che avevi richiesto.

## Prerequisiti

* Disporre di un [server dedicato](/links/bare-metal/bare-metal) **pronto per essere installato/reinstallato** nel tuo account OVHcloud.
* Avere accesso all'<ApiLink>API OVHcloud</ApiLink>.

:::warning
La reinstallazione di un server dedicato elimina tutti i dati attualmente memorizzati su di esso.

:::


## Procedura

Durante l'installazione predefinita del sistema operativo, l'installer del sistema operativo (fornito dall'editore del software) chiede all'utente di specificare i dischi su cui verrà installato il sistema operativo, la configurazione del partizionamento, ecc. Una volta installato l'OS, è possibile modificare lo schema di partizionamento, ma l'operazione può rivelarsi molto delicata e rischiosa, in particolare per le partizioni attualmente utilizzate dal sistema. Per questo motivo, la configurazione dello storage è un aspetto molto importante che deve essere preso in considerazione **prima** di installare un sistema operativo.

Oltre alla semplicità dell'API, il vantaggio principale è la possibilità di personalizzare completamente i dischi e le partizioni su cui verrà installato l'OS.

In questa pagina ci concentreremo solo sul sotto-hash `storage` della chiamata API utilizzata per reinstallare un OS su un server dedicato. Per le personalizzazioni della reinstallazione dell'OS non legate allo storage, consulta la pagina [API OVHcloud e installazione di un OS](/guides/bare-metal-cloud/dedicated-servers/api-os-installation) per maggiori dettagli.

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "diskGroupId": 1,
            "erase": true
        },
        {
            "diskGroupId": 2,
            "erase": true,
            "hardwareRaid": [
                {
                    "raidLevel": null,
                    "disks": 2
                }
            ],
            "partitioning": {
                "disks": 2,
                "layout": [
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/boot",
                        "size": 1000,
                        "raidLevel": 1
                    },
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/",
                        "size": 0
                    }
                ]
            }
        }
    ]
}
```

### Gruppi di dischi <a name="disk-group"></a>

Alcuni [server dedicati](/links/bare-metal/bare-metal) dispongono di più gruppi di dischi, ad esempio un gruppo con dischi SATA e un gruppo con dischi SSD. Questi tipi di server sono chiamati **server ibridi**.

Per elencare i gruppi e i relativi dischi, puoi utilizzare la seguente chiamata per individuare il gruppo di dischi su cui vuoi effettuare la reinstallazione dell'OS:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/specifications/hardware"} />

Esempio di risposta:

```json
{
    "bootMode": "uefi",
    "coresPerProcessor": 64,
    "defaultDiskGroupId": 1,
    "defaultHardwareRaidSize": null,
    "defaultHardwareRaidType": null,
    "description": "SCALE-7 - AMD Epyc 7763",
    "diskGroups": [
        {
            "defaultHardwareRaidSize": null,
            "defaultHardwareRaidType": null,
            "description": "2 X Disk SSD 480 GB, JBOD",
            "diskGroupId": 1,
            "diskSize": {
                "unit": "GB",
                "value": 480
            },
            "diskType": "SSD",
            "numberOfDisks": 2,
            "raidController": null
        },
        {
            "defaultHardwareRaidSize": null,
            "defaultHardwareRaidType": null,
            "description": "2 X Disk NVME 1920 GB, JBOD",
            "diskGroupId": 2,
            "diskSize": {
                "unit": "GB",
                "value": 1920
            },
            "diskType": "NVME",
            "numberOfDisks": 2,
            "raidController": null
        }
    ],
    "expansionCards": null,
    "formFactor": "1u",
    "memorySize": {
        "unit": "MB",
        "value": 524288
    },
    "motherboard": "S8036-M",
    "numberOfProcessors": 1,
    "processorArchitecture": "x86_64",
    "processorName": "Epyc7763",
    "threadsPerProcessor": 128,
    "usbKeys": null
}
```

In questo esempio sono presenti 2 gruppi di dischi:

- il primo (diskGroupId=1) contiene 2 dischi da 480 GB ciascuno. Si tratta del diskGroupId predefinito.
- il secondo (diskGroupId=2) contiene 2 dischi da 1,9 TB ciascuno.

Esempio di installazione di Debian 13 (Trixie) sul diskGroupId 2:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "diskGroupId": 2
        }
    ]
}
```

:::info
Per impostazione predefinita, se non viene specificato alcun diskGroupId o se è impostato su 0, il sistema operativo viene installato sul diskGroupId 1 predefinito.

:::


<br />

:::warning
Per il momento, l'API supporta l'installazione dell'OS e la personalizzazione dello storage su un solo gruppo di dischi. Puoi includere da 1 a tutti i dischi del gruppo scelto nella personalizzazione dello storage. Tuttavia, i dischi restanti di questo gruppo verranno cancellati. Anche i dischi appartenenti agli altri gruppi vengono cancellati per impostazione predefinita, ma i loro dati possono essere conservati: consulta la sezione [Cancellazione dei dati](#data-erasure). In ogni caso, questi dischi resteranno visibili dall'OS installato e potranno essere utilizzati/configurati in seguito per memorizzare dati.

:::


### RAID hardware <a name="hard-raid"></a>

Questa sezione si applica solo ai server che dispongono di almeno un controller RAID hardware in uno dei loro [gruppi di dischi](#disk-group).

#### Server e compatibilità del RAID hardware

Per sapere se il tuo server dedicato è compatibile, puoi utilizzare la seguente chiamata API:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/install/hardwareRaidProfile"} />

Se il server dedicato non dispone di un controller RAID hardware, la chiamata restituisce un errore HTTP 403 (Forbidden) con il seguente messaggio:

```json
{
  "message": "Hardware RAID is not supported by this server"
}
```

Esempio di risposta per un server dotato di RAID hardware:

```json
{
  "controllers": [
    {
      "type": "mega",
      "disks": [
        {
          "names": [
            "c0:d0",
            "c0:d1",
            "c0:d2"
          ],
          "type": "SSD",
          "capacity": {
            "unit": "GB",
            "value": 960
          },
          "speed": {
            "value": "6g",
            "unit": "GB/s"
          }
        }
      ],
      "model": "9361-8i-2G"
    }
  ]
}
```

:::info
Puoi ottenere questa informazione anche dal valore dell'attributo `raidController` della chiamata API descritta nella sezione [Gruppi di dischi](#disk-group).

:::


#### API e RAID hardware

:::warning
Per il momento, l'API supporta la personalizzazione del RAID hardware per un solo controller RAID hardware. Se il server dispone di più controller RAID hardware di cui vuoi personalizzare la configurazione, puoi configurare i controller diversi da quello del gruppo di dischi scelto per la reinstallazione dell'OS **prima** della reinstallazione dell'OS (puoi farlo anche dopo il termine della reinstallazione, ma ti consigliamo di farlo **prima** per evitare qualsiasi rischio di errore di manipolazione che potrebbe causare una perdita di dati).

:::


Esempio di un'installazione dell'OS con un RAID 1 hardware tra i primi 2 dischi del gruppo di dischi:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "hardwareRaid": [
                {
                    "raidLevel": 1,
                    "disks": 2
                }
            ]
        }
    ]
}
```

:::info
Se `disks` non è specificato, **tutti** i dischi del gruppo verranno inclusi nel RAID hardware.

:::


Supponiamo ora che tu disponga di un server dedicato con 1 gruppo di dischi collegato al controller RAID hardware e 12 dischi in questo gruppo. Esempio con un RAID 10 hardware:

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "hardwareRaid": [
                {
                    "raidLevel": 10,
                    "arrays": 4
                }
            ]
        }
    ]
}
```

In questo esempio, tutti i 12 dischi verranno inclusi nel RAID hardware di livello 10. Ci saranno 4 gruppi di 3 dischi, ovvero 4 RAID 1 su 3 dischi, e i 4 gruppi saranno in RAID 0.

:::info
Il RAID hardware si trova a un livello non visibile dall'OS. Per questo motivo, tutti gli OS sono "compatibili" con il RAID hardware.

:::


Tutti i dischi inclusi nella configurazione del RAID hardware verranno visti dall'OS come un unico disco virtuale.

Di conseguenza, se hai incluso tutti i dischi del gruppo di dischi di destinazione in una configurazione RAID hardware, non sarà possibile configurare un RAID software al di sopra, poiché l'OS vede un solo disco virtuale.

### Partizionamento <a name="partitioning"></a>

Quando si parla di schema di partizionamento, ci si riferisce all'organizzazione dei dati sui dischi, ovvero a tutto ciò che si trova sopra il disco fisico (o il disco virtuale, se hai configurato un RAID hardware), fino al file system montato e visibile dall'OS, dai livelli più bassi a quelli più alti:

- Disco (disco fisico/virtuale, PD)
- Partizione (partizione fisica, PP)
- ZFS: vdev (zgroup, ZG), zpool (ZP), dataset ZFS (ZD), volume ZFS (ZV)
- [RAID software](/guides/bare-metal-cloud/dedicated-servers/raid-soft) (SR)
- LVM: volume fisico (VP), gruppo di volumi (VG), volume logico (LV)
- File system con punto di montaggio (FS)

La tabella seguente offre una panoramica dei diversi componenti del partizionamento e del modo in cui questi livelli interagiscono:

<img className="thumbnail" alt="Tabella che rappresenta i diversi livelli del partizionamento" src="/images/bare-metal-cloud/dedicated-servers/partitioning-ovh/partitioning-layers-table.png" loading="lazy" />

:::info
Nella tabella qui sopra, `/dev/zd1` rappresenta un volume ZFS (chiamato anche `zvol`). Si tratta di un disco virtuale situato al di sopra di un insieme di dati ZFS (ZD) e di uno zpool (ZP), che il sistema operativo considera un normale disco fisico (PD). Questa funzionalità non è disponibile sull'API OVHcloud e non ne prevediamo l'implementazione.

:::


#### OS e compatibilità del partizionamento <a name="os-partitioning-compatibility"></a>

Poiché la configurazione del partizionamento sarà visibile dall'OS, l'OS scelto per la reinstallazione influisce sulle possibilità di personalizzazione del partizionamento.

Nella sezione <code className="action">/dedicated/installationTemplate</code>, puoi ottenere dettagli come la compatibilità LVM e la disponibilità dei file system per un determinato OS:

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}"} />

Ad esempio:

```json
{
    "templateName": "debian13_64",
    "filesystems": [
        "btrfs",
        "ext4",
        "swap",
        "xfs",
        "zfs"
    ],
    ...
    "lvmReady": true,
    "noPartitioning": false,
    "softRaidOnlyMirroring": false
}
```

|Attributo|Descrizione|
|---|---|
|filesystems|File system compatibili con questo sistema operativo|
|lvmReady|Indica se questo sistema operativo supporta LVM o meno|
|noPartitioning|Se true, questo sistema operativo non supporta la personalizzazione del partizionamento|
|softRaidOnlyMirroring|Se true, questo sistema operativo supporta solo parzialmente la personalizzazione del partizionamento (possono essere configurati solo i RAID software di livello 0 e 1, assegnati ai primi 2 dischi del gruppo di dischi)|

La seguente chiamata API può essere utilizzata per elencare i diversi schemi di partizionamento di un determinato sistema operativo. La maggior parte dei sistemi operativi supporta la personalizzazione del partizionamento e dispone quindi di un solo schema chiamato "default". Solo alcuni di essi non supportano la personalizzazione del partizionamento (`noPartitioning` vale `true`) e **possono** quindi avere più schemi di partizionamento.

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}/partitionScheme"} />

Le seguenti chiamate API possono essere utilizzate per sapere quale partizionamento verrà applicato per impostazione predefinita se non viene specificata alcuna personalizzazione del partizionamento o se questa non è supportata dall'OS.

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}/partitionScheme/\{schemeName\}/partition"} />


<br />

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}/partitionScheme/\{schemeName\}/partition/\{mountpoint\}"} />

La tabella seguente offre una panoramica della compatibilità dei file system con i livelli di RAID e LVM nel contesto OVHcloud:

|File system|LVM|RAID 0|RAID 1|RAID 5|RAID 6|RAID 7|RAID 10|
|---|---|---|---|---|---|---|---|
|Btrfs, ext4, XFS|✅|✅|✅|✅|✅|❌|✅|
|ZFS¹|❌|✅|✅|✅|✅|✅|❌|
|swap|❌|⚠️²|❌|❌|❌|❌|❌|
|NTFS|❌|❌|✅³|❌|❌|❌|❌|

Quando una partizione swap di dimensione `s` viene definita su un server con un numero `n` di dischi, verranno create `n` partizioni di dimensione `s` su ciascun disco, senza alcun dispositivo RAID software sottostante.<br />
³ Il RAID nativo di Windows (quello configurato dall'installer OVHcloud) supporta il RAID 1, ma solo tra due dischi, mentre altre implementazioni ne consentono più di due.<br />

Tuttavia, l'<ApiLink>API OVHcloud</ApiLink> può darti un'idea dell'aspetto del partizionamento: per maggiori informazioni, consulta [OS e compatibilità del partizionamento](#os-partitioning-compatibility).<br />

Questa tabella è fornita solo a titolo informativo. La compatibilità LVM e, soprattutto, quella dei file system dipendono anche dall'OS (template OVHcloud) installato. Consulta la sezione [OS e compatibilità del partizionamento](#os-partitioning-compatibility) per maggiori dettagli.

#### Vdev ZFS e RAID standard <a name="raidz2RAID"></a>

ZFS non supporta i livelli di RAID standard. Utilizza dispositivi virtuali (vdev) per descrivere la tolleranza ai guasti all'interno di un gruppo di dispositivi. Consulta la [documentazione ufficiale di OpenZFS](https://openzfs.github.io/openzfs-docs/man/7/zpoolconcepts.7.html) (in inglese) per maggiori dettagli sui vdev.

Per rendere l'API OVHcloud il più semplice possibile, è necessario definire un RAID standard nell'API per i file system ZFS. Il livello di RAID standard verrà poi tradotto in una definizione di vdev equivalente. La tabella seguente illustra la traduzione dei diversi livelli di RAID proposti dall'API OVHcloud e ricorda le rispettive caratteristiche.

|RAID standard|Tipo di vdev equivalente|Numero minimo di dischi dati|Numero di dischi di parità|Numero minimo totale di dischi richiesti|
|---|---|---|---|---|
|RAID 0|striped vdev|1|0|1|
|RAID 1|mirror|2|0|2|
|RAID 5|raidz1|2|1|3|
|RAID 6|raidz2|3|2|5|
|RAID 7|raidz3|4|3|7|
|RAID 10|❌|4|0|4|

#### API e partizionamento

:::warning
Un partizionamento personalizzato, sebbene valido e accettato dall'<ApiLink>API OVHcloud</ApiLink>, può comunque impedire al server di avviarsi correttamente (ad esempio una combinazione insolita di file system e bootloader, o un problema di assemblaggio RAID/LVM/ZFS specifico della tua configurazione). In questo caso, sul server non verrà creato automaticamente alcun intervento del supporto: dopo l'ultimo riavvio verrà mostrato al cliente un messaggio esplicito. Consulta la sezione [Errori frequenti dei clienti](#errors) per maggiori dettagli.

:::

Esempio di installazione dell'OS con un partizionamento personalizzato:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "partitioning": {
                "disks": 2,
                "layout": [
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/boot",
                        "size": 1000,
                        "raidLevel": 0
                    },
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/",
                        "size": 0
                    }
                ]
            }
        }
    ]
}
```

`size` 0 significa che la partizione occuperà tutto lo spazio restante sui dischi interessati.

:::info
Al massimo 1 partizione può essere configurata per occupare lo spazio restante (dimensione 0).

:::


<br />

:::info
Se non specificato, `raidLevel` avrà il valore 1.

:::


In questo esempio, solo i primi 2 dischi del gruppo sono inclusi nel partizionamento (ovvero nel RAID software).

:::info
Il parametro `disks` può essere omesso se vuoi includere tutti i dischi del gruppo di dischi nel RAID software.

:::


Come puoi vedere, uno schema di partizionamento è un elenco di partizioni. Ecco un esempio di struttura di una partizione:

```json
{
    "mountPoint": "/var/lib/vz",
    "fileSystem": "ext4",
    "size": 0,
    "raidLevel": "1",
    "extras": {
        "lv": {
            "name": "data"
        }
    }
}
```

Il sotto-hash `extras` è facoltativo. Per il momento, può essere utilizzato per specificare che la partizione sarà un volume logico (LVM) e per indicare il nome di tale volume logico. Il sotto-hash può essere utilizzato anche per ZFS:

```json
{
    "mountPoint": "/",
    "fileSystem": "zfs",
    "size": 0,
    "raidLevel": "5",
    "extras": {
        "zp": {
            "name": "poule"
        }
    }
}
```

In questo esempio, il punto di montaggio `/` riguarda un dataset ZFS in uno zpool chiamato "poule" di tipo raidz1. Consulta la tabella [Vdev ZFS e RAID standard](#raidz2RAID) per ottenere la corrispondenza tra raidz e livelli di RAID standard.

:::info
Se non viene specificato alcun nome di zpool, questo verrà generato automaticamente. Per impostazione predefinita, l'algoritmo cerca di raggruppare i diversi dataset all'interno di uno stesso zpool, ad eccezione dei dataset contenenti `/` o `/boot`, che vengono collocati in zpool separati. In questo modo è possibile attivare sugli altri zpool funzionalità avanzate di ZFS incompatibili con il bootloader.

:::


<br />

:::info
Utilizzare un nome di zpool personalizzato può essere utile nei seguenti casi:

- raggruppare dataset con gli stessi livelli di RAID: utilizza lo stesso nome di zpool,
- forzare dataset con gli stessi livelli di RAID a trovarsi in zpool distinti: utilizza nomi diversi.

:::

### Cancellazione dei dati <a name="data-erasure"></a>

Per impostazione predefinita, i dischi di ogni gruppo di dischi del server vengono cancellati durante l'installazione dell'OS, indipendentemente dal fatto che il loro gruppo sia dichiarato o meno nella richiesta `storage`. Impostare `erase` su `false` per un gruppo di dischi è l'unico modo per conservarne i dati.

Anche i gruppi di dischi diversi da quello su cui viene installato l'OS possono essere dichiarati, ma solo per controllare se i loro dati vengono cancellati (`erase: true`) o conservati (`erase: false`).

L'OS viene installato sul gruppo di dischi che contiene gli attributi di installazione (`partitioning`, `hardwareRaid`); gli altri gruppi dichiarati contengono solo l'attributo `erase`. Se nessuno di essi contiene un attributo di installazione, l'OS viene installato sul gruppo di dischi predefinito, come descritto nella sezione [Gruppi di dischi](#disk-group).

Esempio con un server dotato di 2 gruppi di dischi: una semplice installazione dell'OS sul `diskGroupId` 1 (i cui dischi vengono cancellati implicitamente) e il `diskGroupId` 2 dichiarato solo per conservare i dati esistenti:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "diskGroupId": 1,
            "partitioning": {
                "schemeName": "default"
            }
        },
        {
            "diskGroupId": 2,
            "erase": false
        }
    ]
}
```

:::warning
All'elenco `storage` si applicano le seguenti restrizioni:

- Non è possibile impostare `erase: false` per il gruppo di dischi su cui viene installato l'OS.
- Non è possibile dichiarare più volte lo stesso `diskGroupId`.
- Non è possibile dichiarare più di un gruppo di dischi su cui installare l'OS. Per qualsiasi gruppo di dischi aggiuntivo, può essere definito solo l'attributo `erase`, senza installazione dell'OS, partizionamento o configurazione del RAID hardware.

:::

:::warning
Impostare `erase` su `false` conserva tutti i dati di questo gruppo di dischi, ma OVHcloud non può garantire che l'installazione dell'OS vada a buon fine: metadati di avvio residui, superblocchi `mdadm`, firme LVM o etichette ZFS provenienti da un'installazione precedente su questo gruppo di dischi (su uno qualsiasi dei suoi dischi) possono entrare in conflitto con la nuova installazione.

Se l'installazione non riesce per uno di questi motivi, non viene creato automaticamente alcun ticket di supporto. Al suo posto, viene mostrato al cliente un messaggio esplicito, durante il partizionamento o al primo avvio dell'OS installato. Consulta la sezione [Errori frequenti dei clienti](#errors) per maggiori dettagli.

:::

### Gestione degli errori

Gli errori di base nei dati di input del cliente vengono gestiti direttamente dall'API OVHcloud. Si tratta della situazione più comune e più semplice, poiché i clienti possono vedere l'errore in modo sincrono e riprovare immediatamente.

I dati di input del cliente relativi al partizionamento possono essere troppo specifici per essere verificati dall'API OVHcloud e richiedere quindi un tempo di elaborazione. Lo svantaggio è che i clienti vengono avvisati più tardi, durante il processo di reinstallazione del sistema operativo.

Questo stato è visibile tramite la barra di avanzamento dalla <ManagerLink to="/#/dedicated-servers/server">console OVHcloud</ManagerLink>.
Dall'<ApiLink>API OVHcloud</ApiLink>, questo stato può essere ottenuto con la seguente chiamata API:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/install/status"} />

Esistono 2 tipi di errori:

- **errori ovh**: non sei responsabile dell'errore; puoi reinstallare con un altro schema di partizionamento, ma OVHcloud dovrà correggere il difetto.
- **errori cliente**: hai richiesto uno schema di partizionamento che non può essere realizzato o che impedirebbe al server di avviarsi correttamente.

Nella sezione seguente ci concentreremo solo sui tipi di **errori cliente** nella fase di partizionamento, poiché sono utili solo ai clienti.

#### Errori frequenti dei clienti <a name="errors"></a>

La tabella seguente offre una panoramica degli errori cliente più noti e del modo di correggerli.

|Messaggio di errore|Dettagli|Soluzione/i|
|---|---|---|
|Partition of type `t` with mountpoint `m` cannot fill the disk.|Hai scelto che la partizione `swap` occupi il disco (o partizione di dimensione zero se definita tramite l'<ApiLink>API OVHcloud</ApiLink>): non lo consentiamo per evitare di creare partizioni `swap` inutilmente grandi.|- Definisci una dimensione fissa per la partizione `swap`.|
|`message`. Please adjust partitions so that the `p` partition fits on `n` disk(s)|Hai scelto una partizione con un RAID che richiede un numero di dischi che il server può fornire, ma alcuni dischi sono già pieni a causa di altre partizioni e/o di questa partizione.|- Se non l'hai già fatto per un'altra partizione, imposta la dimensione della partizione in modo che occupi il disco (o partizione di dimensione zero se definita tramite l'<ApiLink>API OVHcloud</ApiLink>).<br />- Riduci la dimensione di questa partizione in modo che si adatti ai dischi.<br />- Riduci la dimensione delle altre partizioni in modo che questa partizione si adatti ai dischi.|
|Error with MBR partition table: Partition `p` is larger than 2TiB and this server does not support GPT|Hai definito una partizione la cui dimensione supera 2TiB e stai applicando questo partizionamento a un server che non supporta GPT.|- Riduci la dimensione di questa partizione a 2TiB.<br />- Applica questo partizionamento a un altro server simile che supporta GPT.|
|Error with MBR partition table: partition `p` cannot end after 2 TiB (`interval stop`) and this server does not support GPT! OVHcloud also needs to add a `cloud-init size` cloud-init partition at the very end of the disk. Therefore all customer partitions must end before (2TiB - `cloud-init size`).|Aggiungiamo sistematicamente una partizione config-drive alla fine di un disco del server dedicato. L'ultima partizione del tuo partizionamento terminerà dopo la posizione 2TiB sul disco. Di conseguenza, se aggiungiamo una partizione config-drive dopo l'ultima partizione, questa dovrà iniziare dopo la posizione 2TiB sul disco di un server che non supporta GPT.|- Riduci la dimensione di questa partizione in modo che la somma totale di tutte le partizioni del disco sia inferiore a 2TiB.<br />- Non definire mai una partizione che occupi un disco (o partizione di dimensione zero se definita tramite l'<ApiLink>API OVHcloud</ApiLink>) per server con dischi più grandi di 2TiB che non supportano GPT.|
|`/boot` (or `/` if no `/boot` defined) partition cannot be larger than 2097151 MiB on this hardware|La partizione che contiene GRUB non deve superare 2TiB su questo tipo di controller RAID.|- Crea una partizione `/boot` separata con una dimensione inferiore a 2TiB (1GiB dovrebbe essere sufficiente).|
|`/boot` (or `/` if no `/boot` defined) partition type cannot be `XFS`|La partizione che contiene GRUB non supporta il file system `XFS` su questo sistema operativo. È generalmente il caso dei sistemi operativi della famiglia Debian (Debian, Proxmox, Ubuntu).|- Crea una partizione `/boot` separata con un file system diverso da `XFS`.<br />- Non creare una partizione `/boot` separata, ma scegli un file system diverso da `XFS` per la partizione `/`.|
|`Debian` does not provide a precompiled `ZFS` module and this server does not have enough memory to compile it (8 GiB minimum required). Please use a different file system.|Cerchiamo sempre di trovare il miglior equilibrio tra integrazione nell'ecosistema OVHcloud, compatibilità hardware e dimensione ridotta dell'immagine, fornendo al contempo un'immagine il più possibile simile all'immagine "cloud-ready" ufficiale fornita dall'editore. Poiché il modulo `ZFS` non è incluso nell'immagine ufficiale, non vogliamo appesantirla con questo modulo per i clienti che non utilizzano `ZFS`. Vogliamo tuttavia offrire un OS con `ZFS` pronto all'uso ai clienti che ne fanno richiesta. Per questo motivo, il modulo `ZFS` viene compilato e installato durante la reinstallazione e solo per i clienti che lo richiedono. Poiché la compilazione richiede memoria RAM in aggiunta a quella già utilizzata per far funzionare l'OS del rescue in `RAM`, abbiamo fissato la soglia a 8 GiB per garantire un buon funzionamento e una buona esperienza cliente.|- Elimina tutte le partizioni `ZFS` o passa a un file system diverso da `ZFS`.<br />- Scegli un OS che supporti `ZFS` in modo nativo, come Ubuntu o Proxmox.<br />- Utilizza un server con almeno 8 GiB di memoria RAM.|

Purtroppo, questa versione dei metadati di `md` non funziona quando la dimensione per disco supera 4 TiB.|- Riduci la dimensione di questa partizione in modo che non superi 4 TiB per disco.<br />- Disattiva il RAID software, limitando l'installazione dell'OS a un solo disco.<br />- Scegli un altro sistema operativo.|
|Partitioning failed. Leftover partitions from a previous install (on disk groups excluded from erasure) are likely conflicting with the new layout.|Metadati residui (tabella delle partizioni, superblocchi `mdadm`, firme LVM o ZFS) su un gruppo di dischi dichiarato con `erase: false` entrano in conflitto con il partizionamento richiesto.|- Imposta `erase: true` per questo gruppo di dischi se non hai più bisogno di conservarne i dati<br />- Cancella manualmente il gruppo di dischi prima di reinstallare|
|The server does not seem to have booted properly into the newly installed operating system. |The server does not seem to have booted properly into the newly installed operating system. This is likely related to the custom partitioning you requested; please check the KVM, if available.|Il partizionamento richiesto è accettato dall'<ApiLink>API OVHcloud</ApiLink>, ma produce un assemblaggio bootloader/file system/RAID da cui il server non riesce ad avviarsi.|- Consulta il KVM per individuare l'esatto problema di avvio<br />- Modifica il partizionamento (ad esempio la scelta del file system, il livello di RAID, la configurazione di `/boot`) e reinstalla|

#### Correzione automatica dei dati di input del cliente

Per migliorare l'esperienza cliente, ridurre il carico di lavoro del supporto OVHcloud ed evitare modifiche improvvise che potrebbero avere un impatto sul cliente, alcuni dati inseriti dal cliente vengono corretti o modificati automaticamente dal backend. La tabella seguente offre una panoramica di ciò che viene attualmente corretto/modificato automaticamente:

|Argomento|Descrizione|
|---|---|
|Raggruppamento ZP|Tutte le partizioni ZFS con lo stesso livello di RAID verranno raggruppate all'interno di uno stesso zpool (ZP), se possibile in base alla dimensione dei dischi e se non viene specificato alcun nome di zpool o se viene specificato lo stesso nome di zpool per tutte queste partizioni.|
|Raggruppamento LV|Tutte le partizioni di tipo `lv` con lo stesso livello di RAID verranno raggruppate all'interno di uno stesso VG (se possibile in base alla dimensione dei dischi).|
|Espansione VG|Nel caso di partizioni lv di livello RAID 0, il VG si estenderà su più PP (e quindi PD) e non verrà creato alcun dispositivo SR.|
|VG Riempimento del disco|Lo spazio su disco restante verrà occupato da un VG (se esiste un LV). La dimensione dei LV contenuti in questo VG non viene modificata.|
|Riduzione del livello di RAID|Se scegli una partizione con un livello di RAID che richiede più dischi di quanti ne abbia il server, il livello di RAID verrà ridotto automaticamente nel seguente ordine: 6, 10, 5, 1, 0 (oppure raidz3, raidz2, raidz, mirror, striped vdev per ZFS).|
|Riduzione della dimensione della PP|Se hai scelto una PP che richiede più spazio di quello disponibile sul server, la dimensione di questa PP verrà ridotta in modo che si adatti al disco. Nel caso in cui più PP richiedano più spazio di quello di cui dispone il sistema, lo script agirà solo sulla prima partizione e restituirà un errore più avanti nello script per la seconda partizione sovradimensionata. Inoltre, verrà generato un errore se hai impostato un'altra partizione in modo che occupi il disco tramite l'API OVHcloud.|
