## Objectif

Il existe différents scénarios dans lesquels vous pouvez avoir besoin de restaurer une sauvegarde. Cependant, OPCP ne permet pas de restaurer une partie seulement d'une sauvegarde : vous ne pouvez restaurer que la sauvegarde complète, avec l'ensemble de ses ressources.

La sauvegarde contient les types de ressources suivants :

- Bases de données
- Ressources tfstate
- PV Kubernetes
- Configuration du KMS

:::danger
Ce guide couvre uniquement le plan de contrôle. Toutes vos données et charges de travail doivent être restaurées séparément.
:::

:::warning
Cette procédure peut prendre beaucoup de temps. Attendez-vous à passer la majeure partie du temps à attendre la fin des opérations.
:::

:::info
Il est très utile d'exécuter les commandes dans une session `screen` ou `tmux`, afin de pouvoir suivre les logs ou corriger des problèmes dans une autre fenêtre. Les deux sont installés sur le contrôleur. Assurez-vous de savoir utiliser ces outils.
:::

## Prérequis

Plusieurs prérequis doivent être remplis avant de commencer la restauration à partir d'une sauvegarde :

- Un accès SSH à tous les contrôleurs OPCP, avec les droits `sudo`.
- Les identifiants des sauvegardes à partir desquelles vous souhaitez restaurer.
- Les parts de descellement (*unseal shares*) du KMS, qui ne figurent pas dans la sauvegarde elle-même car elles sont considérées comme des données très sensibles.
- Un accès aux buckets S3[^1] dans lesquels sont stockées les sauvegardes des bases de données.

### Préparer l'accès S3[^1]

Assurez-vous d'avoir accès aux buckets S3[^1] contenant les données de sauvegarde.

La première étape consiste à obtenir des identifiants disposant de droits complets en lecture, écriture et suppression sur le bucket S3[^1] contenant les sauvegardes des bases de données.

:::danger
Soyez prudent avec ces identifiants : ils permettent de supprimer entièrement vos sauvegardes.
:::

[`s3cmd`](https://s3tools.org/s3cmd) doit être installé et configuré sur votre poste de travail :

```bash
ACCESS_KEY_ID=your-access-key-id # remplacez par votre ID de clé d'accès
SECRET_ACCESS_KEY=your-access-key-secret # remplacez par votre clé secrète
REGION=your-s3-region # remplacez par votre région
cat <<EOF > $HOME/.s3cfg
[default]
access_key = ${ACCESS_KEY_ID}
secret_key = ${SECRET_ACCESS_KEY}
bucket_location = ${REGION}
host_base = s3.gra.io.cloud.ovh.net; remplacez par l'hôte S3 de base fourni par votre fournisseur
host_bucket = %(bucket)s.s3.gra.io.cloud.ovh.net; remplacez par l'URL S3 fournie par votre fournisseur
EOF
```

:::info
Consultez également la documentation de votre fournisseur S3[^1] concernant l'accès au stockage compatible S3[^1].
:::

Vérifiez votre accès en exécutant :

```bash
s3cmd ls
```

Vous obtenez la liste de tous les buckets S3[^1] auxquels vous avez accès. Le résultat est similaire à ceci :

```
2026-08-17 02:00  s3://dev-opcp-test-config
2026-08-06 07:25  s3://dev-opcp-test-db
2026-08-17 02:00  s3://dev-opcp-test-etcd-snapshots
2026-09-25 11:22  s3://opcp-pg-dev-opcp-test
2026-09-25 11:09  s3://opcp-pv-dev-opcp-test
2026-05-27 14:25  s3://opcp-release
2026-09-22 07:02  s3://opcp-release-dev
2026-08-17 14:31  s3://opcp-volumes-dev-opcp-test
```

Deux buckets sont particulièrement importants :

- Le bucket contenant les sauvegardes de vos bases de données
- Le bucket contenant vos sauvegardes Velero (`tfstate`, `pvs`, `kms-autounsealer-shares`)

Exécutez `opcp-cli config edit` pour vérifier la présence d'entrées personnalisées. S'il n'y en a pas, utilisez les noms générés par défaut :

- bases de données : `opcp-pg-{stage}-{env}`
- Velero : `opcp-volumes-{stage}-{env}`

Les valeurs de `stage` et `env` se trouvent également dans la configuration d'OPCP (`opcp-cli config edit`).

:::warning
Assurez-vous d'avoir sauvegardé les parts de descellement du KMS en lieu sûr. Sinon, vous ne pourrez pas effectuer la restauration.
:::

### Récupérer les identifiants des sauvegardes

Vous avez besoin d'un identifiant de sauvegarde pour les ressources `tfstate`, `pvs` et `kms`. Vous pouvez les récupérer de deux manières.

#### Sur un OPCP en fonctionnement

Récupérez vos dernières sauvegardes en exécutant :

```bash
BACKUP_FILE="backups_velero_$(date +%s).json"
BACKUP_NAMES=("tfstate-backup" "pvs-backup" "kms-autounsealer-shares-backup")
velero backup get -o json > "${BACKUP_FILE}"
for BACKUP_NAME in "${!BACKUP_NAMES[@]}"; do
  echo "${BACKUP_NAME}:"
  jq -r < "${BACKUP_FILE}" "[ .items[] | select(.metadata.labels.\"velero.io/schedule-name\" == \"${BACKUP_NAMES[$BACKUP_NAME]}\") | {name: .metadata.name, ts: .metadata.creationTimestamp|strptime(\"%Y-%m-%dT%H:%M:%SZ\")|mktime}]|sort_by(.ts)|reverse[0]|.name"
  echo "\n"
done
```

#### Depuis le bucket S3

Comme vous avez déjà préparé votre [accès S3](#préparer-laccès-s3), vous pouvez maintenant exécuter :

```bash
s3cmd ls s3://<your-pv-bucket-name>/backups/ # remplacez <your-pv-bucket-name> par le nom de votre bucket
```

Vous obtenez la liste de toutes les sauvegardes disponibles. Le suffixe numérique correspond à la date et à l'heure de création de la sauvegarde. Le résultat est similaire à ceci :

```
                          DIR  s3://opcp-pv-dev-opcp-test/backups/kms-autounsealer-shares-backup-20261002080019/
                          DIR  s3://opcp-pv-dev-opcp-test/backups/pvs-backup-20261002080019/
                          DIR  s3://opcp-pv-dev-opcp-test/backups/tfstate-backup-20261002080019/
```

## En pratique

:::info
Ignorez la première étape si vous effectuez la restauration sur une nouvelle installation d'OPCP. Dans ce cas, il vous suffit d'ignorer la partie `opcp-cli deploy` de l'installation.
:::

La première étape consiste à [réinitialiser OPCP](how-to-reset-opcp), à l'exception de la dernière étape, le [redéploiement d'OPCP](how-to-reset-opcp#redéployer-le-contrôleur). Ignorez-la pour l'instant : elle est traitée plus loin dans ce guide, dans le cadre de la restauration.

### Déplacer les sauvegardes des bases de données

L'étape suivante consiste à déplacer les sauvegardes des bases de données au sein du bucket S3[^1]. Pour pouvoir être restaurées, elles doivent se trouver sous le préfixe `/recovery` :

```bash
OPCP_DB_BACKUP_BUCKET=your-bucket-name # remplacez par le nom de votre bucket
s3cmd cp --recursive --exclude "recovery/*" --exclude "archived-backups/*" "s3://${OPCP_DB_BACKUP_BUCKET}/" "s3://${OPCP_DB_BACKUP_BUCKET}/recovery/"
```

Vérifiez que tous les fichiers ont bien été copiés :

```bash
s3cmd ls "s3://${OPCP_DB_BACKUP_BUCKET}/recovery/"
```

Enfin, toutes les sauvegardes des bases de données doivent être déplacées de la racine vers le préfixe `/archived-backups` :

```bash
s3cmd mv --recursive --exclude "recovery/*" --exclude "archived-backups/*" "s3://${OPCP_DB_BACKUP_BUCKET}/" "s3://${OPCP_DB_BACKUP_BUCKET}/archived-backups/$(date '+%Y-%m-%d_%Hh-%Mm')/"
```

Vérifiez qu'il ne reste que les préfixes `/archived-backups` et `/recovery` à la racine :

```bash
s3cmd ls "s3://${OPCP_DB_BACKUP_BUCKET}"
```

:::info
Soyez patient : la copie et le déplacement des données peuvent prendre du temps, car le volume peut être important.
:::

### Redéployer OPCP

Une fois toutes les sauvegardes des bases de données déplacées et votre configuration prête, vous pouvez lancer un redéploiement :

```bash
opcp-cli deploy --force-reconcile
```

:::warning
Les artefacts doivent être dans la même version qu'au moment de la sauvegarde. Dans le cas contraire, des complications peuvent survenir.
:::

Une fois le déploiement terminé, vérifiez que les bases de données non gérées par OpenTofu sont restaurées :

```bash
kubectl get Cluster -A
```

Attendez que tous les clusters de bases de données non gérés par OpenTofu soient disponibles.

```
NAMESPACE   NAME          AGE    INSTANCES   READY   STATUS                     PRIMARY
keycloak    keycloak-db   104s   1           1       Cluster in healthy state   keycloak-db-1
kms         kms-db        104s   1           1       Cluster in healthy state   kms-db-1
netbox      netbox-db     104s   1           1       Cluster in healthy state   netbox-db-1
```

Vous pouvez considérer que ces instances ont été restaurées à partir de la sauvegarde.

:::info
Cette étape peut prendre un certain temps.

La restauration peut cependant rester bloquée à ce stade. Vous devez alors réinitialiser le contrôleur et nettoyer les sauvegardes des bases de données en exécutant la commande suivante sur votre machine :

```bash
s3cmd rm --recursive --exclude "recovery/*" --exclude "archived-backups/*" "s3://${OPCP_DB_BACKUP_BUCKET}/" --force
```

Une fois cette opération terminée, vous pouvez relancer un [redéploiement](#redéployer-opcp).
:::

#### Restaurer les tfstate

Pour restaurer les `tfstate`, exécutez les commandes suivantes :

```bash
# 1. ensure_ks_ready : attendre que toutes les Kustomizations de flux-system soient Ready
while [[ $(kubectl get Kustomization -n flux-system | awk '{print $3}' | grep -Ev "READY|True" | wc -l) > 0 ]]; do
    sleep 1
done

# 2. suspend_tf
if flux get hr -n flux-system | grep -q "tofu-controller"; then
    flux suspend hr -n flux-system tofu-controller
fi
for tf in $(kubectl get Terraform -n flux-system -o jsonpath='{.items[*].metadata.name}'); do
    tfctl suspend $tf
done
while [[ $(kubectl get pods -n flux-system -o name | grep tf-runner | wc -l) > 0 ]]; do
    sleep 1
done
if flux get hr -n flux-system | grep -q "tofu-controller"; then
    kubectl scale --replicas=0 -n flux-system $(kubectl get rs -n flux-system -o name | grep tofu-controller)
fi
sleep 2

# 3. Supprimer les secrets TF state/plan et attendre leur disparition
kubectl -n flux-system delete secret $(kubectl -n flux-system get secrets -o name | grep -E '^secret/tfstate-default|^secret/tfplan-default' | cut -d '/' -f 2)
while [[ $(kubectl -n flux-system get secrets -o name | grep -E '^secret/tfstate-default|^secret/tfplan-default' | wc -l) > 0 ]]; do
    sleep 1
done

# 4. Restauration
velero restore create --from-backup "<TF_STATE_BACKUP>" --wait

# 5. Vérifier la restauration
velero describe restore <restore-id>
```

Une fois la restauration réussie, réactivez le `tofu-controller` et les ressources Terraform :

```bash
if flux get hr -n flux-system | grep -q "tofu-controller"; then
    flux resume hr -n flux-system tofu-controller
fi
for tf in $(kubectl get Terraform -n flux-system -o jsonpath='{.items[*].metadata.name}'); do
    tfctl resume $tf
done
```

Une fois le script terminé, supprimez ou commentez la variable `fleet_infra.vars.tofu_controller.suspend`, puis redéployez :

```bash
opcp-cli config edit
# commentez la variable fleet_infra.vars.tofu_controller.suspend
opcp-cli deploy --system
```

#### Restaurer les PV

Une fois les `tfstate` restaurés, vous pouvez poursuivre avec la restauration des PV :

```bash
# 1. ensure_ks_ready
while [[ $(kubectl get Kustomization -n flux-system | awk '{print $3}' | grep -Ev "READY|True" | wc -l) > 0 ]]; do
    sleep 1
done

# 2. suspend_tf (identique à la restauration des tfstate)
if flux get hr -n flux-system | grep -q "tofu-controller"; then
    flux suspend hr -n flux-system tofu-controller
fi
for tf in $(kubectl get Terraform -n flux-system -o jsonpath='{.items[*].metadata.name}'); do
    tfctl suspend $tf
done
while [[ $(kubectl get pods -n flux-system -o name | grep tf-runner | wc -l) > 0 ]]; do
    sleep 1
done
if flux get hr -n flux-system | grep -q "tofu-controller"; then
    kubectl scale --replicas=0 -n flux-system $(kubectl get rs -n flux-system -o name | grep tofu-controller)
fi
sleep 2

# 3. Suspendre les HelmReleases concernées
flux suspend hr -n monitoring kube-prometheus-stack
flux suspend hr -n kms ovhcloud-ssm

# 4. Passer l'emplacement de sauvegarde en lecture seule
kubectl patch backupstoragelocation backup-location --namespace velero --type merge --patch '{"spec":{"accessMode":"ReadOnly"}}'

# 5. Supprimer les workloads et les PVC
kubectl delete deploy -n monitoring kube-prometheus-stack-grafana
kubectl delete pvc -n monitoring kube-prometheus-stack-grafana
kubectl delete deploy -n glance glance-api
kubectl delete pvc -n glance glance-images
kubectl delete sts -n kms ovhcloud-ssm
kubectl delete deploy -n kms ovhcloud-ssm
kubectl delete pvc -n kms ovhcloud-ssm-sqlite-ovhcloud-ssm-0
kubectl delete deploy -n ironic ironic-conductor
kubectl delete pvc -n ironic ironic-shared

# 6. Boucles d'attente
while [[ $(kubectl get deploy -A | grep -E "kube-prometheus-stack-grafana|glance-api|ironic-conductor" | wc -l) > 0 ]]; do sleep 1; done
while [[ $(kubectl get sts -A | grep -E "ovhcloud-ssm" | wc -l) > 0 ]]; do sleep 1; done
while [[ $(kubectl get pvc -A | grep -E "kube-prometheus-stack-grafana|glance-images|ovhcloud-ssm-sqlite-ovhcloud-ssm-0|ironic-shared" | wc -l) > 0 ]]; do sleep 1; done
while [[ $(kubectl get pv -A | grep -E "kube-prometheus-stack-grafana|glance-images|ovhcloud-ssm-sqlite-ovhcloud-ssm-0|ironic-shared" | wc -l) > 0 ]]; do sleep 1; done
# get_pods : attendre la disparition de ces pods (supprimés manuellement par l'opérateur)
while [[ $(kubectl get pods -A -o name | grep -E "^pod/ironic-conductor|^pod/glance-api|^pod/ovhcloud-ssm|^pod/kube-prometheus-stack-grafana" | grep -Ev "netbox-initializers|-db" | wc -l) -gt 0 ]]; do
    kubectl get pods -A -o name | grep -E "^pod/ironic-conductor|^pod/glance-api|^pod/ovhcloud-ssm|^pod/kube-prometheus-stack-grafana" | grep -Ev "netbox-initializers|-db"
    sleep 1
done

# 7. Restauration
velero restore create --from-backup "<PV_BACKUP>" --wait # PV_BACKUP est l'identifiant de la sauvegarde des PV, obtenu parmi vos sauvegardes disponibles lors de l'étape de préparation.
```

Vérifiez l'état de la restauration :

```bash
velero describe restore <restore-id>
```

Une fois la restauration réussie, réactivez les ressources Terraform et HelmRelease :

```bash
if flux get hr -n flux-system | grep -q "tofu-controller"; then
    flux resume hr -n flux-system tofu-controller
fi
for tf in $(kubectl get Terraform -n flux-system -o jsonpath='{.items[*].metadata.name}'); do
    tfctl resume $tf
done
flux resume hr -n monitoring kube-prometheus-stack
flux resume hr -n kms ovhcloud-ssm
```

:::info
La restauration prend du temps et peut rester bloquée lors de la suppression des PVC. Suivez son avancement en exécutant `watch kubectl get pvc -A`.

Si la suppression est bloquée, vérifiez si le PVC est encore monté quelque part :

```bash
kubectl -n ironic describe pvc ironic-shared
```

#### Restaurer le KMS

Récupérez le nom du pod commençant par `ovhcloud-kms-setup-selfunseal` dans le namespace `kms` et consultez ses logs :

```bash
kubectl logs -n kms ovhcloud-kms-setup-selfunseal-7vg52
```

Vous devriez obtenir un résultat similaire à ceci :

```
Creating empty config file at /root/.ovh-kms/okms.yaml
KMS status: Sealed
KMS status: Sealed
KMS is sealed. Unsealing KMS...
Init unsealing KMS
Completed: false
Error: Seal key is incorrect or deprecated.
ID="5d0385bc-1ab8-4260-bfb4-3377e2b27ca1", Request-ID:"OVHKMS.5d0385bc-1ab8-4260-bfb4-3377e2b27ca1", Code=33624076, System=SSM, Component=General, Category=Internal
```

Cela s'explique par le fait que les secrets que vous venez de restaurer ne correspondent pas à l'instance SSM. Vous devez avoir conservé vos parts secrètes en lieu sûr. Si ce n'est pas le cas, le KMS ne peut pas être restauré.

Récupérez vos parts secrètes depuis leur emplacement sécurisé et adaptez-les en supprimant du fichier YAML les clés `creationTimestamp`, `uid` et `resourceVersion`, ainsi que `status` si elle est présente.

Appliquez ensuite les secrets avec `kubectl apply -f`.

Une fois cette opération réussie, supprimez le secret `kms-auto-unsealer-ccm-admin-certificate` avec `kubectl -n kms delete secret kms-auto-unsealer-ccm-admin-certificate`.

Vous pouvez enfin lancer la restauration :

```bash
# 1. Suspendre l'auto-unsealer et réduire ses réplicas à 0
flux suspend hr -n kms kms-auto-unsealer
kubectl scale --replicas=0 -n kms sts/kms-auto-unsealer

# 2. Restauration
velero restore create --from-backup "<KMS_SHARES_BACKUP>" --wait
```

Vérifiez l'état de la restauration :

```bash
velero describe restore <restore-id>
```

Une fois la restauration terminée avec succès, réactivez l'auto-unsealer et repassez-le à 1 réplica :

```bash
flux resume hr -n kms kms-auto-unsealer
kubectl scale --replicas=1 -n kms sts/kms-auto-unsealer
```

Une fois cette opération terminée, exécutez `flux reconcile ks apps` pour vous assurer que tous les éléments du namespace `kms` sont mis à jour et redémarrés, à l'exception du pod `kms-db`.

Une fois les parts restaurées, vous devez recréer le certificat Barbican. Vérifiez d'abord quel certificat recréer :
