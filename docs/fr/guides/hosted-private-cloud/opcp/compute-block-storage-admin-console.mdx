## Objectif

**Ce guide explique aux IT Admins comment déployer le service Compute and Block Storage depuis l'OPCP Admin Console, le configurer, le faire évoluer et l'activer pour des organisations.**

**Compute and Block Storage** fournit des machines virtuelles (instances), des volumes de stockage block persistants et des réseaux privés aux organisations de votre plateforme. Il repose sur OpenStack : Nova exécute les instances sur des hyperviseurs, et Cinder stocke les volumes dans un cluster Ceph. Les deux fonctionnent sur des hôtes bare metal de votre OPCP.

Ce guide couvre ce qui est propre à Compute and Block Storage. Les étapes générales (Service Catalog, déploiements de service, organisations) sont décrites dans notre guide « [OPCP Admin Console](/guides/hosted-private-cloud/opcp/admin-console-getting-started) ». L'utilisation du service par les utilisateurs d'une organisation est décrite dans notre guide « [Utiliser Compute and Block Storage](/guides/hosted-private-cloud/opcp/compute-block-storage-cloud-console) ».

## Prérequis

- Disposer d'un accès à l'OPCP Admin Console, comme décrit dans notre guide « [OPCP Admin Console](/guides/hosted-private-cloud/opcp/admin-console-getting-started) ».
- Disposer d'hôtes bare metal enrôlés dans OPCP Core, disponibles dans OpenStack et non utilisés par un autre service :
    - au moins **1 hôte pour le pool d'hôtes `compute`**, qui devient un hyperviseur. Ajoutez des hôtes pour augmenter la capacité, et pour que les instances continuent de fonctionner en cas de panne d'un hyperviseur. Chacun doit disposer d'un disque de données d'au moins 1 000 Gio. Les hôtes AMD EPYC doivent avoir leur mode NUMA réglé sur **NPS4**, consultez la section [Régler le mode NUMA des hôtes AMD EPYC](#régler-le-mode-numa-des-hôtes-amd-epyc) ;
    - au moins **3 hôtes pour le pool d'hôtes `storage`**, qui forment le cluster Ceph. Ceph conserve 3 copies de chaque volume, chacune sur un hôte différent. 3 hôtes suffisent pour une évaluation. En production, utilisez au moins **4 hôtes** : en cas de panne d'un hôte, Ceph peut alors restaurer la troisième copie de chaque volume sur les hôtes restants. Nous recommandons le serveur **HIGH-PERFORMANCE-STORAGE** du catalogue matériel OPCP : 2 disques NVMe de 1,92 To pour le système d'exploitation et 6 à 22 disques de données NVMe de 3,84 ou 7,68 To. Sur chaque hôte de stockage, les 2 plus petits disques de moins de 2 000 Gio portent le système d'exploitation en miroir, et les disques de données sont utilisés par Ceph.
- Disposer d'une organisation pour laquelle activer le service. Pour en créer une, consultez la section « [Créer une organisation](/guides/hosted-private-cloud/opcp/admin-console-getting-started#créer-une-organisation) ».

## En pratique

### Vue d'ensemble de l'architecture

| Composant | S'exécute sur | Rôle |
|-----------|---------------|------|
| **Control plane** | Le contrôleur OPCP | Déployé une fois par déploiement de service. Exécute les services OpenStack qui gèrent les instances et les volumes, ainsi qu'une interface web Horizon. |
| **Hyperviseurs** | Hôtes du pool d'hôtes `compute` | Exécutent les instances. Ils sont partagés par toutes les organisations pour lesquelles le service est activé. |
| **Cluster Ceph** | Hôtes du pool d'hôtes `storage` | Stocke les volumes de stockage block. |
| **Data plane** | Le contrôleur OPCP | Créé pour chaque organisation lorsque vous activez le service pour elle. Fournit à l'organisation son propre projet OpenStack, son accès via l'OPCP Cloud Console et sa propre interface web pour le service. |

Chaque organisation ne voit que ses propres instances, volumes et réseaux.

### Régler le mode NUMA des hôtes AMD EPYC

Sur les hôtes AMD EPYC, l'installation d'un hyperviseur nécessite le mode NUMA **NPS4** (quatre nœuds NUMA par socket, paramètre BIOS `NumaMemoryDomainsPerSocket`). Les hôtes sont souvent livrés en **NPS1**, et le déploiement ne modifie pas ce paramètre : réglez-le vous-même avant de sélectionner l'hôte pour le pool d'hôtes `compute`.

Vous avez besoin d'un [accès à OPCP via la CLI OpenStack](/guides/hosted-private-cloud/opcp/how-to-use-api-and-get-credentials) avec un compte administrateur. L'hôte ne doit pas être utilisé : son état de provisionnement est `available`.

1\. **Vérifiez le mode actuel.** `FourMemoryDomainsPerSocket` correspond à NPS4 : il n'y a rien à faire.

```bash
HOST=<nom ou UUID de l'hôte>
openstack baremetal node bios setting show "$HOST" NumaMemoryDomainsPerSocket
```

2\. **Appliquez NPS4.** Le paramètre BIOS est appliqué pendant un nettoyage manuel, qui redémarre l'hôte. `provide` remet ensuite l'hôte à l'état `available` :

```bash
openstack baremetal node manage "$HOST" --wait 300
openstack baremetal node clean "$HOST" --wait 3600 --clean-steps '[{"interface": "bios", "step": "apply_configuration", "args": {"settings": [{"name": "NumaMemoryDomainsPerSocket", "value": "FourMemoryDomainsPerSocket"}]}}]'
openstack baremetal node provide "$HOST" --wait 3600
```

3\. **Vérifiez à nouveau le mode** avec la commande de l'étape 1. Elle doit afficher `FourMemoryDomainsPerSocket`.

### Déployer le service

1. Accédez à <code className="action">Management</code> > <code className="action">Service Catalog</code> et ouvrez **Compute and Block Storage**. Cliquez sur <code className="action">New deployment</code>.
2. **Choisissez la version de votre service**, puis cliquez sur <code className="action">Next</code>.
3. **Affectez les pools d'hôtes** :
    - `compute` : sélectionnez les hôtes qui deviennent des hyperviseurs ;
    - `storage` : sélectionnez les hôtes qui forment le cluster Ceph.

    Un hôte ne peut appartenir qu'à un seul pool d'hôtes.

    <img className="thumbnail" alt="Affectation des hôtes d'un pool d'hôtes : projet OpenStack et liste des hôtes disponibles" src="/images/hosted-private-cloud/opcp/compute-block-storage-admin-console/deploy_host_pools.png" loading="lazy" />

4. **Configurez votre service**. Le service a deux paramètres, chacun avec une valeur par défaut adaptée à la plupart des déploiements. Consultez la section [Paramètres](#paramètres) ci-dessous.
5. Cliquez sur <code className="action">Deploy</code>.

:::warning
Les hôtes sélectionnés sont effacés et réinstallés pendant le déploiement.

:::

Le déploiement installe les hyperviseurs et le cluster Ceph. Il dure de plusieurs dizaines de minutes à quelques heures, selon le nombre d'hôtes. Le déploiement de service est `deploying`, puis `deployed`.

Une fois `deployed`, l'onglet <code className="action">Host pools</code> du déploiement de service liste les hôtes des pools d'hôtes `compute` et `storage`.

<img className="thumbnail" alt="Onglet Host pools d'un déploiement de service Compute and Block Storage, avec ses hôtes compute et storage" src="/images/hosted-private-cloud/opcp/compute-block-storage-admin-console/deployment_host_pools.png" loading="lazy" />

Les gabarits d'instance (gabarits `opcp-`) et l'agrégat d'hôtes qui les place sur les hyperviseurs sont fournis par OPCP. Chaque hyperviseur du pool d'hôtes `compute` rejoint cet agrégat lors de sa mise en place : les organisations peuvent donc créer des instances dès que le déploiement de service est `deployed`.

#### Paramètres

| Paramètre | Valeur par défaut | Description |
|-----------|-------------------|-------------|
| `horizon_enabled` | `true` | Déploie l'interface web Horizon. Les utilisateurs des organisations y accèdent via un lien dans l'OPCP Cloud Console, pour les cas que l'interface du service ne couvre pas encore. |
| `allow_uninstall_with_bound_nodes` | `false` | Autorise la suppression du déploiement de service alors que des hôtes sont encore utilisés. Les hôtes sont alors libérés et effacés. Laissez-le à `false`, sauf si le support OVHcloud vous demande de le modifier. |

### Outputs

Une fois le déploiement de service `deployed`, son onglet <code className="action">Outputs</code> affiche notamment les hôtes de chaque pool d'hôtes (`compute_nodes`, `storage_nodes`) et l'adresse d'Horizon (`horizon_url`).

Chaque service activé dispose de ses propres Outputs, utilisés par les utilisateurs de l'organisation. Ils sont affichés dans l'onglet <code className="action">Overview</code> du service dans l'OPCP Cloud Console :

| Output | Contenu |
|--------|---------|
| `Console` | Le lien vers l'interface web du service pour cette organisation. |
| `Horizon` | Le lien qui connecte les utilisateurs de l'organisation à Horizon, si `horizon_enabled` vaut `true`. |
| `OpenRC` | Un fichier `openrc.sh` pour la CLI OpenStack. Il ne contient aucun secret : les utilisateurs s'authentifient avec leur propre identifiant d'application (*application credential*). |

### Activer le service pour une organisation

Activez le déploiement de service pour chaque organisation qui a besoin d'instances, comme décrit dans la section « [Activer un service pour une organisation](/guides/hosted-private-cloud/opcp/admin-console-getting-started#activer-un-service-pour-une-organisation) ».

- Les hyperviseurs et le cluster Ceph sont partagés entre les organisations : l'étape du pool d'hôtes est marquée `not applicable`.
- Aucune propriété n'est à renseigner : le service récupère tout ce dont il a besoin dans les Outputs du déploiement de service.

Le service activé est `deploying`, puis `deployed`. Les utilisateurs de l'organisation trouvent alors **Compute and Block Storage** dans l'OPCP Cloud Console. Transmettez-leur notre guide « [Utiliser Compute and Block Storage](/guides/hosted-private-cloud/opcp/compute-block-storage-cloud-console) ».

### Faire évoluer le service

#### Ajouter des hôtes

Pour ajouter de la capacité, ouvrez le menu <code className="action">⋮</code> du déploiement de service et choisissez <code className="action">Expand capacity</code>, comme décrit dans la section « [Mise à l'échelle de la capacité](/guides/hosted-private-cloud/opcp/admin-console-getting-started#mise-à-léchelle-de-la-capacité) ». Dans la fenêtre, choisissez d'abord le pool d'hôtes à étendre, `compute` ou `storage`, puis sélectionnez les hôtes à ajouter.

<img className="thumbnail" alt="Fenêtre Expand capacity : choix du pool d'hôtes et liste des hôtes disponibles" src="/images/hosted-private-cloud/opcp/compute-block-storage-admin-console/expand_capacity.png" loading="lazy" />

- Un hôte ajouté au pool d'hôtes `compute` devient un nouvel hyperviseur.
- Un hôte ajouté au pool d'hôtes `storage` rejoint le cluster Ceph, et ses disques augmentent la capacité de stockage.

Un nouvel hyperviseur rejoint de lui-même l'agrégat d'hôtes des gabarits `opcp-` et exécute des instances une fois mis en place.

#### Retirer des hôtes

Le retrait d'hôtes d'un déploiement de service n'est pas pris en charge dans l'Alpha.

### Supprimer le service

1. Demandez aux organisations de supprimer toutes leurs instances et tous leurs volumes. Si une organisation ne peut pas le faire, par exemple parce que son administrateur a perdu son accès, supprimez-les à sa place comme décrit dans la section [Supprimer les instances et volumes d'une organisation](#supprimer-les-instances-et-volumes-dune-organisation).
2. Désactivez le service pour chaque organisation.
3. Supprimez le déploiement de service, comme décrit dans la section « [Désactiver un service ou supprimer un déploiement de service](/guides/hosted-private-cloud/opcp/admin-console-getting-started#désactiver-un-service-ou-supprimer-un-déploiement-de-service) ».

:::warning
Supprimez toutes les instances et tous les volumes avant de supprimer le déploiement de service. Des instances restées sur un hyperviseur bloquent la suppression du déploiement de service.

:::

#### Supprimer les instances et volumes d'une organisation

En tant qu'administrateur OPCP, vous pouvez supprimer vous-même les instances et les volumes d'une organisation avec la CLI OpenStack.

:::warning
Cette opération supprime définitivement les instances, les volumes et les snapshots de volumes de l'organisation. Convenez-en d'abord avec l'organisation.

:::

Vous avez besoin d'un [accès à la CLI OpenStack d'OPCP](/guides/hosted-private-cloud/opcp/how-to-use-api-and-get-credentials) avec un compte administrateur : les commandes ci-dessous lisent et suppriment des ressources dans tous les projets.

1\. **Identifiez les projets de l'organisation.** Chaque organisation dispose de son propre domaine Keystone, nommé `account-` suivi du nom de l'organisation :

```bash
openstack domain list
ORG_DOMAIN=account-<organisation>
openstack project list --domain "$ORG_DOMAIN"
```

2\. **Supprimez les instances, puis les volumes** de tous les projets de ce domaine. `--purge` supprime aussi les snapshots de chaque volume :

```bash
for project in $(openstack project list --domain "$ORG_DOMAIN" -f value -c ID); do
  for server in $(openstack server list --all-projects --project "$project" -f value -c ID); do
    openstack server delete --wait "$server"
  done
  for volume in $(openstack volume list --all-projects --project "$project" -f value -c ID); do
    openstack volume delete --purge "$volume"
  done
done
```

3\. **Vérifiez qu'il ne reste rien.** Les deux listes doivent être vides pour chaque projet :

```bash
for project in $(openstack project list --domain "$ORG_DOMAIN" -f value -c ID); do
  openstack server list --all-projects --project "$project"
  openstack volume list --all-projects --project "$project"
done
```

Si un volume est encore listé, il était probablement encore en cours de détachement d'une instance supprimée. Supprimez-le à nouveau avec `openstack volume delete --purge <volume-id>`.

### Limitations connues

L'Alpha présente les limitations connues suivantes :

| Limitation | Que faire |
|------------|-----------|
| Compute and Block Storage ne peut être déployé qu'une seule fois par plateforme : un second déploiement échoue. | Ne déployez le service qu'une seule fois par plateforme. |
| Un déploiement de service ne peut pas être mis à jour sur place. | Supprimez-le et déployez la nouvelle version. |
| La désactivation du service échoue pour une organisation dont le nom contient une espace. | Utilisez des noms d'organisation sans espace. |
| La suppression d'un déploiement de service laisse des ressources derrière elle, et le cluster Ceph est volontairement conservé. Un nouveau déploiement échoue tant qu'elles n'ont pas été nettoyées. | Contactez OVHcloud pour les faire nettoyer avant de redéployer. |

### Dépannage

| Ce que vous constatez | Que faire |
|-----------------------|-----------|
| Le déploiement est long, ou les premières tentatives d'installation d'un hyperviseur échouent. | Patientez : le déploiement réessaie automatiquement et réussit généralement à la deuxième ou troisième tentative. S'il reste en erreur, contactez OVHcloud. |
| L'installation d'un hyperviseur échoue sur un hôte AMD EPYC. | Vérifiez que le mode NUMA de l'hôte est réglé sur **NPS4**, consultez la section [Régler le mode NUMA des hôtes AMD EPYC](#régler-le-mode-numa-des-hôtes-amd-epyc), ou utilisez un autre hôte. |
| La suppression du déploiement de service ne se termine jamais. | Supprimez d'abord toutes les instances et tous les volumes (consultez la section [Supprimer le service](#supprimer-le-service)). Si la suppression est déjà bloquée, contactez OVHcloud. |
