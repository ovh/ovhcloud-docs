## Objectif

Le routage statique est la manière la plus simple de connecter votre réseau à OVHcloud lorsque vous disposez d’un ensemble de préfixes restreint et stable et que vous n’avez pas besoin d’un protocole de routage. Contrairement à BGP, il n’offre aucune bascule automatique — vous mettez à jour les routes vous-même lorsque votre réseau évolue — même si VRRP protège toujours la passerelle au sein d’une AZ. Configurer OVHcloud Connect en mode L3 avec routage statique implique deux niveaux de configuration :

1. **Configuration PoP** — La session L3 entre votre routeur et OVHcloud au niveau du Point de présence.
2. **Configuration supplémentaire AZ (network)** — Des routes statiques au sein de l’AZ OVHcloud pour la distribution des routes.

:::info
Si vous préférez le routage dynamique avec BGP, consultez [Configurer OVHcloud Connect L3 avec BGP](/guides/network/ovhcloud-connect/l3-bgp).
:::

### Quand utiliser le routage statique plutôt que BGP

| Critère | Routage statique | BGP |
|---|---|---|
| **Nombre de préfixes** | Faible (1 à 5 routes) | Élevé ou en croissance |
| **Topologie réseau** | Simple, chemin unique | Complexe, multi-chemins, multi-AZ |
| **Bascule** | Manuelle — vous devez mettre à jour les routes vous-même | Automatique — BGP reconverge |
| **Maintenance** | Les routes doivent être mises à jour manuellement lorsque les sous-réseaux changent | Les routes sont mises à jour dynamiquement |
| **Complexité** | Faible — aucun protocole de routage à gérer | Plus élevée — nécessite la configuration de BGP |

Utilisez le routage statique lorsque vous disposez d’une configuration simple avec un faible nombre de préfixes stables et que vous n’avez pas besoin d’une bascule automatique.

## Prérequis

- Un service OVHcloud Connect actif (statut `active`)
- OVHcloud Connect associé à un vRack — voir [Associer OVHcloud Connect à votre vRack](/guides/network/ovhcloud-connect/associate-vrack)
- Une configuration AZ créée — voir [Configurer le réseau vRack](/guides/network/ovhcloud-connect/vrack-network-setup)
- Un sous-réseau de peering /30 (par exemple `192.0.2.0/30`)
- Des identifiants de l’API OVHcloud (Application Key, Application Secret, Consumer Key). Consultez le guide [Premiers pas avec l’API OVHcloud](/guides/manage-and-operate/api/first-steps).

Connectez-vous à votre <ManagerLink to="/">espace client OVHcloud</ManagerLink> et ouvrez la section <code className="action">Bare Metal Cloud</code>, puis accédez à <code className="action">Network</code> > <code className="action">OVHcloud Connect</code>.

## Configurer le côté OVHcloud

Vous pouvez configurer le côté OVHcloud de la configuration L3 en routage statique depuis l’**espace client OVHcloud** ou avec l’**API OVHcloud**. Les deux méthodes aboutissent au même résultat. Ensuite, configurez les routes statiques correspondantes sur votre propre routeur.

### Depuis l’espace client OVHcloud

Configurez le service depuis la section <code className="action">Bare Metal Cloud</code> > <code className="action">Network</code> > <code className="action">OVHcloud Connect</code>. Ouvrez votre solution, puis :

1. **Associez un vRack** (si ce n’est pas déjà fait) : cliquez sur <code className="action">Associer un vRack</code> et sélectionnez un vRack existant.
2. **Ajoutez une configuration PoP** : dans le tableau `Configuration PoP`, cliquez sur <code className="action">Configurer le port</code> pour ouvrir le formulaire **Ajouter une configuration PoP**, réglez le **Type** sur **L3** et saisissez votre **ASN utilisateur**, l’**ASN OVHcloud** et un **sous-réseau /30** pour le lien PoP.
3. **Ajoutez une configuration d’Availability Zone (AZ)** : sous la section `Configuration AZ`, cliquez sur <code className="action">Ajouter un AZ</code>, sélectionnez une Availability Zone, puis saisissez l’**ASN OVHcloud** et un **sous-réseau /28** (ou plus large) issu de votre vRack.
4. **Ajoutez une configuration de routage** : sur l’Availability Zone, cliquez sur <code className="action">Règles de routage</code>, choisissez **Static**, puis saisissez :

   | Information | Description |
   |---|---|
   | Network Focus | Le préfixe de destination, en notation CIDR |
   | Next hop | Une adresse IP faisant office de passerelle dans la plage du sous-réseau |

   Vous pouvez ajouter plusieurs routes statiques dans la même Availability Zone en répétant cette étape.

Ajoutez ensuite les routes statiques correspondantes sur votre propre routeur (voir **Configurer les routes statiques sur votre routeur** ci-dessous).

### Depuis l’API OVHcloud

Les étapes suivantes configurent la même configuration L3 en routage statique par programmation.

#### Étape 1 — Identifier l’ID de votre interface

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/interface"} />


#### Étape 2 — Créer la configuration PoP (L3)

La configuration PoP établit la session L3 au niveau du Point de présence. Cette étape est identique que vous utilisiez BGP ou le routage statique au niveau de l’AZ.

<Api version="v1" section="/ovhCloudConnect" method="POST" route={"/ovhCloudConnect/\{serviceName\}/config/pop"} />

**Paramètres de la requête :**

| Paramètre | Type | Requis | Description |
|---|---|---|---|
| `interfaceId` | long | Oui | ID de l’interface OVHcloud Connect |
| `type` | string | Oui | `l3` pour le mode Layer 3 |
| `customerBgpArea` | long | Non | Votre numéro d’AS (toujours requis pour le L3 — utilisé pour le peering au niveau du PoP). Utilisez un ASN public ou un ASN privé dans la plage 64512-65534 (par exemple `64512`). |
| `subnet` | ipv4Block | Non | Sous-réseau de peering /30. La première IP est OVHcloud, la seconde est la vôtre. |

**Exemple de requête :**

```json
{
  "interfaceId": 101,
  "type": "l3",
  "customerBgpArea": 64512,
  "subnet": "192.0.2.0/30"
}
```

#### Étape 3 — Vérifier la configuration PoP

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}"} />


**Exemple de réponse :**

```json
{
  "id": 5678,
  "interfaceId": 101,
  "type": "l3",
  "customerBgpArea": 64512,
  "ovhBgpArea": 35540,
  "subnet": "192.0.2.0/30",
  "status": "active"
}
```

À partir de cette réponse :

| Paramètre | Valeur | Signification |
|---|---|---|
| **IP du pair OVHcloud** | `192.0.2.1` | Première IP du /30 |
| **Votre IP de pair** | `192.0.2.2` | Deuxième IP du /30 |

#### Étape 4 — Créer la configuration supplémentaire AZ (statique)

Après la configuration PoP et la configuration AZ, créez une **configuration supplémentaire network** pour définir des routes statiques au sein de l’AZ.

:::info
La configuration AZ (datacenter) doit déjà exister avant de pouvoir créer la configuration supplémentaire. Créez-la d’abord avec `POST .../config/pop/{popId}/datacenter` (en fournissant le sous-réseau /28 issu de votre vRack) — voir [Configurer le réseau vRack](/guides/network/ovhcloud-connect/vrack-network-setup). C’est ce qui fournit le `{datacenterId}` utilisé dans l’appel `/extra` ci-dessous.
:::

:::info
Avec le routage statique, **VRRP reste actif** sur le point de terminaison de l’AZ. Les équipements OVHcloud A et B partagent une passerelle virtuelle VRRP, qui correspond à la **première IP utilisable** du sous-réseau /28 de l’AZ (les routeurs OVHcloud A et B prennent les deux adresses suivantes ; les 3 premières IP du /28 sont réservées à OVHcloud). Pointez la passerelle par défaut de vos services vers cette IP virtuelle VRRP pour une bascule automatique entre les équipements.
:::

<Api version="v1" section="/ovhCloudConnect" method="POST" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/datacenter/\{datacenterId\}/extra"} />

**Paramètres de la requête :**

| Paramètre | Type | Requis | Description |
|---|---|---|---|
| `type` | string | Oui | `network` pour le routage statique |
| `nextHop` | ipv4 | Non | Adresse IP next-hop pour la route statique |
| `subnet` | ipv4Block | Non | Sous-réseau de destination pour la route statique |

**Exemple de requête — router votre sous-réseau on-premises via le lien OVHcloud Connect :**

```json
{
  "type": "network",
  "nextHop": "172.16.1.1",
  "subnet": "10.0.0.0/16"
}
```

**Ajouter plusieurs routes statiques**

Créez une configuration supplémentaire par sous-réseau de destination. Répétez l’appel `POST .../extra` avec un `subnet` différent à chaque fois :

```json
{
  "type": "network",
  "nextHop": "172.16.1.1",
  "subnet": "10.1.0.0/16"
}
```

**Vérifier la configuration supplémentaire**

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/datacenter/\{datacenterId\}/extra/\{extraId\}"} />

**Exemple de réponse :**

```json
{
  "id": 4568,
  "type": "network",
  "bgpNeighborArea": null,
  "bgpNeighborIp": null,
  "nextHop": "172.16.1.1",
  "subnet": "10.0.0.0/16",
  "status": "active"
}
```

**Lister toutes les configurations supplémentaires d’une AZ**

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/datacenter/\{datacenterId\}/extra"} />


## Configurer les routes statiques sur votre routeur

Configurez votre routeur physique avec des routes statiques pointant les sous-réseaux d’AZ OVHcloud vers l’IP de peering OVHcloud Connect.

Configurez BGP (ou des routes statiques) sur votre routeur de bordure conformément à la documentation de votre constructeur, en utilisant l’ASN, l’adresse IP du pair et le sous-réseau indiqués ci-dessus.

## Vérifier la connectivité

#### Depuis votre routeur

Consultez la documentation de votre constructeur pour vérifier les routes statiques et tester la connectivité vers les sous-réseaux d’AZ OVHcloud.

**Résultats attendus :**

| Vérification | Sortie attendue |
|---|---|
| **Routes statiques présentes** | Routes vers 172.16.x.x via 192.0.2.1 dans la table de routage |
| **Le ping aboutit** | Réponse depuis la passerelle du sous-réseau d’AZ OVHcloud |
| **Traceroute** | Le trafic passe par 192.0.2.1 (PoP OVHcloud) |

#### Depuis l’API OVHcloud

Vérifiez l’état de l’interface :

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/interface/\{id\}/status"} />

Vérifiez le statut de la configuration PoP :

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/status"} />

#### Lancer un diagnostic

<Api version="v1" section="/ovhCloudConnect" method="POST" route={"/ovhCloudConnect/\{serviceName\}/diagnostic"} />


Sélectionnez le diagnostic dont vous avez besoin — par exemple un test de peering BGP ou un diagnostic de routes. Consultez [Surveiller votre OVHcloud Connect](/guides/network/ovhcloud-connect/monitor) pour les diagnostics disponibles, ainsi que la [console API](https://api.ovh.com/console/#/ovhCloudConnect) pour le corps exact de la requête.

## Limites du routage statique

:::warning
Le routage statique présente des limites importantes par rapport à BGP :

- **Mises à jour manuelles requises.** Lorsque vous ajoutez ou modifiez des sous-réseaux, vous devez mettre à jour à la fois la configuration supplémentaire OVHcloud et la configuration de votre routeur.
- **Pas de répartition de charge.** Les routes statiques ne prennent pas en charge ECMP ni le traffic engineering. Le trafic suit un chemin unique.
- **Non recommandé pour le multi-AZ.** Pour les configurations multi-AZ résilientes, BGP est fortement recommandé — voir [Multi-AZ](/guides/network/ovhcloud-connect/multi-az).

:::
