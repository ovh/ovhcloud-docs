## Objectif

BGP vous offre un échange dynamique de routes et une bascule automatique entre votre réseau et OVHcloud : les routes sont apprises et retirées automatiquement au lieu d’être maintenues à la main et, avec deux PoP ou plus, ECMP est activé automatiquement pour répartir le trafic sur plusieurs chemins. La configuration d’OVHcloud Connect en mode L3 avec BGP implique deux niveaux de configuration :

1. **Configuration PoP** — La session eBGP entre votre routeur et OVHcloud au niveau du Point de présence.
2. **Configuration supplémentaire AZ (BGP)** — Le peering BGP au sein de l’AZ OVHcloud pour la distribution des routes.

:::info
Si vous préférez le routage statique au lieu de BGP, consultez [Configurer OVHcloud Connect L3 avec routage statique](/guides/network/ovhcloud-connect/l3-static).
:::

Pour comprendre la structure d’un service L3 aux niveaux PoP et AZ, et savoir quand préférer BGP au routage statique, consultez [Introduction à OVHcloud Connect](/guides/network/ovhcloud-connect/introduction#service-layer-3-l3).

## Prérequis

- Un service OVHcloud Connect actif (statut `active`)
- OVHcloud Connect associé à un vRack — voir [Associer OVHcloud Connect à votre vRack](/guides/network/ovhcloud-connect/associate-vrack)
- Une configuration AZ créée — voir [Configurer le réseau vRack](/guides/network/ovhcloud-connect/vrack-network-setup)
- Votre ASN (un ASN public ou un ASN privé compris dans la plage 64512–65534)
- Un sous-réseau de peering /30 (par exemple `192.0.2.0/30`)
- Des identifiants de l’API OVHcloud (Application Key, Application Secret, Consumer Key). Consultez le guide [Premiers pas avec l’API OVHcloud](/guides/manage-and-operate/api/first-steps).

Connectez-vous à votre <ManagerLink to="/">espace client OVHcloud</ManagerLink> puis ouvrez la section <code className="action">Bare Metal Cloud</code> et accédez à <code className="action">Network</code> > <code className="action">OVHcloud Connect</code>.

## Vue d’ensemble

<img className="thumbnail" alt="Implémentation OVHcloud Connect L3 : un domaine L3 (sous-réseau et ASN BGP) est configuré sur chaque PoP et chaque Availability Zone" src="/images/network/ovhcloud-connect/l3-bgp/occ-l3-implementation.png" loading="lazy" />

- **Niveau PoP** : une session eBGP entre votre routeur (votre ASN) et OVHcloud (l’ASN côté OVHcloud) sur un sous-réseau de peering /30.
- **Niveau AZ** : un voisin BGP configuré au sein de l’AZ pour distribuer les routes vers vos services OVHcloud.

## Configurer le côté OVHcloud

Vous pouvez configurer le côté OVHcloud de l’installation L3 BGP soit depuis l’**espace client OVHcloud**, soit avec l’**API OVHcloud**. Les deux méthodes aboutissent au même résultat. Ensuite, configurez la session BGP correspondante sur votre propre routeur.

### Depuis l’espace client OVHcloud

Configurez le service depuis la section <code className="action">Bare Metal Cloud</code> > <code className="action">Network</code> > <code className="action">OVHcloud Connect</code>. Ouvrez votre solution, puis :

1. **Associez un vRack** (si ce n’est pas déjà fait) : cliquez sur <code className="action">Associer un vRack</code> et sélectionnez un vRack existant.
2. **Ajoutez une configuration PoP** : dans le tableau `PoP configuration`, cliquez sur <code className="action">Configurer le port</code> pour ouvrir le formulaire **Ajouter une configuration PoP**, réglez le **Type** sur **L3**, puis renseignez :

   | Information | Description |
   |---|---|
   | User ASN | Votre numéro d’AS BGP, configuré sur votre routeur dans le PoP |
   | OVHcloud ASN | Le numéro d’AS configuré sur les routeurs OVHcloud Connect dans le PoP |
   | Subnetwork in /30 | Un bloc IPv4 /30 pour le lien entre votre routeur et le routeur OVHcloud dans le PoP |

3. **Ajoutez une configuration d’Availability Zone (AZ)** : dans la section `AZ configuration`, cliquez sur <code className="action">Ajouter un AZ</code>, sélectionnez une Availability Zone, puis renseignez l’**OVHcloud ASN** et un **sous-réseau /28** (ou plus large) issu de votre vRack.
4. **Ajoutez une configuration de routage** : sur l’Availability Zone, cliquez sur <code className="action">Règles de routage</code>, choisissez **BGP**, puis renseignez votre **User ASN** et l’**IP Neighbour** (l’IP du voisin BGP de votre routeur au sein du sous-réseau de l’AZ).

Configurez ensuite la session eBGP correspondante sur votre propre routeur (voir **Configurer BGP sur votre routeur** ci-dessous).

### Depuis l’API OVHcloud

Les étapes suivantes configurent la même installation L3 BGP de manière programmatique.

#### Étape 1 — Identifier l’ID de votre interface

Récupérez l’ID de l’interface pour votre service OVHcloud Connect :

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/interface"} />

#### Étape 2 — Créer la configuration PoP (L3)

La configuration PoP établit la session BGP L3 au niveau du Point de présence.

<Api version="v1" section="/ovhCloudConnect" method="POST" route={"/ovhCloudConnect/\{serviceName\}/config/pop"} />

**Paramètres de la requête :**

| Paramètre | Type | Requis | Description |
|---|---|---|---|
| `interfaceId` | long | Oui | ID de l’interface OVHcloud Connect |
| `type` | string | Oui | `l3` pour le mode Layer 3 |
| `customerBgpArea` | long | Non | Votre numéro d’AS (un ASN public ou un ASN privé compris dans la plage 64512–65534, par exemple `64512`) |
| `ovhBgpArea` | long | Non | L’ASN de l’instance de routage côté OVHcloud. Vous pouvez utiliser n’importe quel ASN sauf les valeurs réservées par OVHcloud par région (`65501` Europe, `65502` Canada, `65519` Asie) ; il doit différer de votre ASN client (par exemple `35540`). |
| `subnet` | ipv4Block | Non | Sous-réseau de peering /30 (par exemple `192.0.2.0/30`). La première IP est OVHcloud, la seconde est la vôtre. |

**Exemple de requête :**

```json
{
  "interfaceId": 101,
  "type": "l3",
  "customerBgpArea": 64512,
  "subnet": "192.0.2.0/30"
}
```

Le `resourceId` dans la réponse correspond à votre nouveau `popId`. Vous pouvez également le récupérer à tout moment en listant vos configurations PoP avec `GET .../config/pop`.

#### Étape 3 — Vérifier la configuration PoP

Une fois la tâche terminée :

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}"} />

**Exemple de réponse :**

```json
{
  "id": 5678,
  "interfaceId": 101,
  "type": "l3",
  "customerBgpArea": 64512,
  "ovhBgpArea": 35540,
  "subnet": "192.0.2.0/30",
  "status": "active"
}
```

À partir de cette réponse, notez :

| Paramètre | Valeur | Signification |
|---|---|---|
| **IP du pair OVHcloud** | `192.0.2.1` | Première IP du /30 — côté OVHcloud |
| **Votre IP de pair** | `192.0.2.2` | Deuxième IP du /30 — votre routeur |
| **ASN OVHcloud** | `35540` | La valeur `ovhBgpArea` (n’importe quel ASN sauf les valeurs réservées par région) |
| **Votre ASN** | `64512` | La valeur `customerBgpArea` |

Vérifiez l’état de la session BGP :

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/status"} />

#### Étape 4 — Créer la configuration supplémentaire AZ (BGP)

Après la configuration PoP et la [configuration AZ](/guides/network/ovhcloud-connect/vrack-network-setup), créez une **configuration supplémentaire BGP** pour activer la distribution des routes BGP au sein de l’AZ.

<img className="thumbnail" alt="Session BGP annonçant le réseau IP du vRack au routeur OVHcloud" src="/images/network/ovhcloud-connect/l3-bgp/occ-l3-bgpvrack.png" loading="lazy" />

<img className="thumbnail" alt="Topologie globale OVHcloud Connect L3 BGP" src="/images/network/ovhcloud-connect/l3-bgp/occ-l3-bgpglobal.png" loading="lazy" />

:::info
La configuration AZ (datacenter) doit déjà exister avant de pouvoir créer la configuration supplémentaire. Créez-la d’abord avec `POST .../config/pop/{popId}/datacenter` (en fournissant le sous-réseau /28 issu de votre vRack) — voir [Configurer le réseau vRack](/guides/network/ovhcloud-connect/vrack-network-setup). C’est ce qui fournit le `{datacenterId}` utilisé dans l’appel `/extra` ci-dessous.
:::

:::warning
L’activation de BGP au niveau de l’AZ **désactive VRRP** sur cette configuration AZ. BGP gère la bascule à la place. Vous devez établir une session BGP avec **les deux** équipements OVHcloud A et B (jusqu’à 4 pairs BGP par AZ). Par défaut, BFD (Bidirectional Forwarding Detection) est activé sur toutes les sessions BGP de l’AZ — il est fortement recommandé d’activer également BFD de votre côté pour une convergence plus rapide.
:::

<Api version="v1" section="/ovhCloudConnect" method="POST" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/datacenter/\{datacenterId\}/extra"} />

**Paramètres de la requête :**

| Paramètre | Type | Requis | Description |
|---|---|---|---|
| `type` | string | Oui | `bgp` pour le routage BGP |
| `bgpNeighborArea` | long | Non | Votre numéro d’AS pour le voisin BGP de l’AZ (utilisez le même ASN client qu’au niveau du PoP, par exemple `64512`) |
| `bgpNeighborIp` | ipv4 | Non | IP du routeur pour la session BGP au sein de l’AZ |

**Exemple de requête :**

```json
{
  "type": "bgp",
  "bgpNeighborArea": 64512,
  "bgpNeighborIp": "172.16.1.1"
}
```

Vérifiez la configuration supplémentaire :

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/datacenter/\{datacenterId\}/extra/\{extraId\}"} />

**Exemple de réponse :**

```json
{
  "id": 4567,
  "type": "bgp",
  "bgpNeighborArea": 64512,
  "bgpNeighborIp": "172.16.1.1",
  "nextHop": null,
  "subnet": null,
  "status": "active"
}
```

## Configurer BGP sur votre routeur

Configurez votre routeur physique pour établir la session eBGP avec OVHcloud au niveau du PoP. **Remplacez les valeurs d’exemple** par vos paramètres réels de configuration PoP (l’IP du pair OVHcloud, votre IP de pair et les deux ASN).

Configurez BGP (ou des routes statiques) sur votre routeur de périphérie conformément à la documentation de votre fournisseur, en utilisant l’ASN, l’adresse IP de pair et le sous-réseau indiqués ci-dessus.

## Vérifier la session BGP

#### Depuis votre routeur

Consultez la documentation de votre fournisseur pour vérifier l’état de la session BGP et les routes échangées avec OVHcloud.

**Résultats attendus :**

| Vérification | Sortie attendue |
|---|---|
| **État BGP** | `Established` |
| **Préfixes reçus** | Au moins 1 route depuis OVHcloud (vos sous-réseaux d’AZ) |
| **Préfixes envoyés** | Vos préfixes annoncés visibles |

#### Depuis l’API OVHcloud

Vérifiez les statistiques du PoP (préfixes acceptés) :

<Api version="v1" section="/ovhCloudConnect" method="GET" route={"/ovhCloudConnect/\{serviceName\}/config/pop/\{popId\}/statistics"} />

#### Lancer un diagnostic

Si la session ne s’établit pas, lancez un diagnostic de peering :

<Api version="v1" section="/ovhCloudConnect" method="POST" route={"/ovhCloudConnect/\{serviceName\}/diagnostic"} />

Sélectionnez le diagnostic dont vous avez besoin — par exemple un test de peering BGP ou un diagnostic de routes. Consultez [Surveiller votre OVHcloud Connect](/guides/network/ovhcloud-connect/monitor) pour connaître les diagnostics disponibles, et la [console API](https://api.ovh.com/console/#/ovhCloudConnect) pour le corps exact de la requête.

## Bonnes pratiques

- **Annoncez uniquement les préfixes que vous possédez.** Ne laissez pas fuiter des routes tierces via OVHcloud Connect.
- **Appliquez des filtres de préfixes.** Utilisez des prefix-lists à l’import et à l’export pour éviter les fuites de routes accidentelles.
- **Définissez des limites maximum-prefix.** Protégez votre routeur de la réception d’un nombre inattendu de routes.
- **Surveillez la session.** Configurez des alertes pour les flaps BGP et les coupures de session — voir [Surveiller votre connexion](/guides/network/ovhcloud-connect/monitor).
- **Pour les configurations redondantes.** Avec deux PoP ou plus, ECMP est activé automatiquement ; pour construire une topologie active/passive à la place, ajustez la sélection de chemin BGP avec l’AS-path prepending sur vos propres équipements — voir [Multi-AZ](/guides/network/ovhcloud-connect/multi-az). L’AS-path prepending est uniquement côté client, et le MED n’est **pas pris en charge** sur OVHcloud Connect.

## Dépannage

| Problème | Cause possible | Solution |
|---|---|---|
| BGP bloqué en `Active` | IP de pair ou ASN incorrect | Vérifiez les adresses IP et l’ASN des deux côtés. Utilisez `GET .../config/pop/{popId}` pour vérifier les valeurs côté OVHcloud. |
| BGP bloqué en `Idle` | Interface inactive ou pare-feu bloquant le TCP 179 | Vérifiez le lien physique et les règles de pare-feu. Utilisez `GET .../interface/{id}/status` pour vérifier l’état du lien. |
| Aucune route reçue | Instruction `network` manquante ou filtre de préfixes trop restrictif | Vérifiez la politique d’export et les commandes `network`. Lancez un diagnostic de routes (voir [Surveiller](/guides/network/ovhcloud-connect/monitor)). |
| La session tombe fréquemment (flapping) | Lien physique instable ou MTU non cohérent | Vérifiez les erreurs d’interface et les paramètres MTU. Utilisez `GET .../interface/{id}/statistics` pour consulter les compteurs d’erreurs. |
| Configuration PoP bloquée en statut `init` | Tâche encore en cours ou échouée | Vérifiez `GET .../task` pour les tâches en attente. |
