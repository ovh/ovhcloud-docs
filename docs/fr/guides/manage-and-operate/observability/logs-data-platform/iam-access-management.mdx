## Vue d'ensemble

Ce guide fournit les instructions pour configurer les droits d'accès sur l'IAM OVHcloud afin de gérer les permissions des différents composants de Logs Data Platform. Il vous donnera les bonnes pratiques pour gérer les droits accordés à vos utilisateurs et vous permettra de reproduire les fonctionnalités des rôles et permissions avec le système plus avancé des politiques. Ce guide utilise des fonctionnalités expliquées dans la [documentation de l'IAM](/guides/account-and-service-management/account-information/iam-policy-ui). Il est donc recommandé de la lire avant de poursuivre ce guide.

## Prérequis

- Un [compte OVHcloud](/guides/account-and-service-management/account-information/ovhcloud-account-creation)
- Un compte Logs Data Platform avec l'[IAM activé](/guides/manage-and-operate/observability/logs-data-platform/iam-presentation-faq)

[[cpnav:iam-identities-console]]

## Politiques et identités

Ce guide s'appuie sur les [utilisateurs locaux](/guides/account-and-service-management/account-information/ovhcloud-users-management) pour expliquer comment partager des ressources avec un autre utilisateur. Les politiques créées peuvent être appliquées à n'importe quelle identité OVHcloud via l'API OVHcloud. Vous pouvez utiliser ces politiques pour partager des données avec un utilisateur local, un autre compte utilisateur OVHcloud ou un client OAuth. Vous pouvez vous référer au guide spécifique [Politiques IAM avec l'API](/guides/account-and-service-management/account-information/iam-policies-api) pour recréer toutes ces politiques avec l'API.

L'identité verra un nouveau service apparaître dans son Logs Data Platform. Ce service contient les éléments Logs Data Platform partagés. Pour que le destinataire puisse voir les éléments partagés, nous devons partager avec lui une vue du service.

## Gestion des droits d'accès

Cette section détaille comment configurer des groupes d'utilisateurs locaux/d'identités et des politiques pour reproduire le comportement de l'ancien système de rôles.

### Créer un groupe pour les utilisateurs locaux

Par défaut, le groupe le moins privilégié disponible pour les utilisateurs locaux dispose d'un accès en lecture seule sur tous les produits de votre compte. Si vous souhaitez un compte encore plus restreint, capable uniquement de lire les données partagées depuis votre Logs Data Platform, nous vous conseillons de créer un groupe avec le privilège **Aucun** et d'y rattacher vos utilisateurs locaux. Accédez à <code className="action">Gestion des identités et accès</code> > <code className="action">Identités</code> > <code className="action">Groupes d'utilisateurs</code> dans la <ManagerLink to="/beta/#/iam/identities/groups">console OVHcloud</ManagerLink> et cliquez sur <code className="action">Créer un groupe</code> pour créer un tel groupe.

<img className="thumbnail" alt="Panneau Créer un groupe avec les champs Nom, Privilège et Description, le privilège Aucun sélectionné" src="/images/manage-and-operate/observability/logs-data-platform/iam-access-management/console/create_group.png" loading="lazy" />

Vous pouvez ensuite créer une politique avec les droits de base pour accéder à la console OVHcloud et l'attacher au groupe. Tous vos utilisateurs locaux pourront alors se connecter à la console OVHcloud. Accédez à <code className="action">Gestion des identités et accès</code> > <code className="action">Politiques</code> > <code className="action">Mes politiques</code> et cliquez sur <code className="action">Créer une politique</code> pour créer cette politique. Pour l'attacher au groupe d'utilisateurs, sélectionnez le groupe dans l'onglet <code className="action">Groupes</code> de la section **Identités**.

<img className="thumbnail" alt="Formulaire de création de politique avec la section Informations de la politique et l'onglet Groupes de la section Identités" src="/images/manage-and-operate/observability/logs-data-platform/iam-access-management/console/basic_policy_1.png" loading="lazy" />

Après avoir attaché le groupe, suivez les instructions de notre guide : [Comment créer une politique IAM pour permettre à un utilisateur de se connecter à la console OVHcloud](/guides/account-and-service-management/account-information/iam-control-panel-access).

Une fois le groupe configuré, vous pouvez alors créer les utilisateurs locaux.

### Créer un utilisateur local

La création d'un utilisateur local est entièrement documentée dans la [documentation dédiée](/guides/account-and-service-management/account-information/ovhcloud-users-management). N'oubliez pas d'attacher l'utilisateur au groupe en sélectionnant ce dernier dans le champ **Groupe principal** du panneau **Créer un utilisateur local**.

<img className="thumbnail" alt="Panneau Créer un utilisateur local avec les champs Groupe principal et Groupes supplémentaires" src="/images/manage-and-operate/observability/logs-data-platform/iam-access-management/console/create_user.png" loading="lazy" />

### Créer une politique pour le service

Vous devez maintenant créer une politique pour permettre à l'utilisateur local de voir le service Logs Data Platform dans la console OVHcloud. L'objectif ici est de n'avoir accès qu'au service, sans qu'aucune sous-ressource ne soit visible (c'est-à-dire aucun flux, tableau de bord, index, alias ou instance OpenSearch Dashboards). Accédez à <code className="action">Gestion des identités et accès</code> > <code className="action">Politiques</code> > <code className="action">Mes politiques</code> dans la <ManagerLink to="/beta/#/iam/policies/my-policies">console OVHcloud</ManagerLink> et cliquez sur <code className="action">Créer une politique</code> pour créer cette politique.

Ajoutez l'utilisateur local à votre politique dans l'onglet <code className="action">Utilisateurs</code> de la section **Identités**. Sélectionnez ensuite le type de produit **Logs Data Platform : Service** pour lister vos services dans la liste déroulante **Ressources** et afficher les actions de ce type de produit dans la section **Actions**, dans une liste intitulée **ldp**.

<img className="thumbnail" alt="Formulaire de création de politique avec un utilisateur local sélectionné dans l'onglet Utilisateurs de la section Identités" src="/images/manage-and-operate/observability/logs-data-platform/iam-access-management/console/create_policy_service_1.png" loading="lazy" />

La politique peut ensuite autoriser un accès en lecture seule au service choisi. Les utilisateurs ont besoin au minimum de ces actions de lecture de base pour voir le service Logs Data Platform dans la console OVHcloud. L'ensemble minimal d'actions, toutes situées dans la catégorie **READ** de la liste **ldp**, est listé ci-dessous :

```yaml
- ldp:apiovh:cluster/get
- ldp:apiovh:cluster/retention/get
- ldp:apiovh:encryptionKey/get
- ldp:apiovh:get
- ldp:apiovh:input/get
- ldp:apiovh:metrics/get
- ldp:apiovh:role/get
- ldp:apiovh:serviceInfos/get
- ldp:apiovh:services/form/get
- ldp:apiovh:services/get
- ldp:apiovh:token/get
- ldp:apiovh:url/get
```

<img className="thumbnail" alt="Section Actions avec la catégorie READ de la liste ldp sélectionnée" src="/images/manage-and-operate/observability/logs-data-platform/iam-access-management/console/create_policy_service_2.png" loading="lazy" />

Une fois la politique attachée à l'identité, les utilisateurs verront le nouveau service dans leur console OVHcloud, mais sans aucun élément disponible.

### Créer un groupe de sous-ressources

Tous les éléments créés par un Logs Data Platform (flux, tableaux de bord, etc.) sont matérialisés comme des sous-ressources du service LDP.
L'une des nouvelles fonctionnalités disponibles grâce à l'IAM est la possibilité de regrouper des sous-ressources dans un **groupe de ressources**. Un groupe de ressources permet de partager des ressources liées entre elles et constitue un moyen pratique de regrouper des éléments destinés à être utilisés ensemble. Par exemple : un flux et son tableau de bord associé, un alias et une instance OpenSearch Dashboards pour l'explorer, ou encore un alias avec tous les flux qui lui sont rattachés. Cette fonctionnalité est un bon moyen d'isoler complètement des sous-ressources et de vous éviter d'avoir à les gérer une par une dans toutes vos politiques.

Pour créer un groupe de ressources, accédez à <code className="action">Gestion des identités et accès</code> > <code className="action">Politiques</code> > <code className="action">Groupe de ressources</code> dans la <ManagerLink to="/beta/#/iam/policies/resource-groups">console OVHcloud</ManagerLink> et cliquez sur <code className="action">Créer un groupe de ressources</code>.

<img className="thumbnail" alt="Panneau Créer un groupe de ressources avec les champs Nom, Types de produit et Ressources" src="/images/manage-and-operate/observability/logs-data-platform/iam-access-management/console/create_rg.png" loading="lazy" />

Vous devez sélectionner le type de produit (**Logs Data Platform : Tableaux de bord**, **Logs Data Platform : Flux de données**, **Logs Data Platform : Alias**, **Logs Data Platform : Index**, **Logs Data Platform : OpenSearch Dashboards**) dans le champ **Types de produit**, puis sélectionner la ressource spécifique que vous souhaitez partager dans le champ **Ressources**.

### Créer une politique pour les sous-ressources

Cette politique est celle qui vous permet de reproduire effectivement les permissions des anciens rôles. Vous y attacherez des droits sur les API OVHcloud et des droits sur le backend (Graylog, OpenSearch) pour permettre aux identités de voir les éléments de leur service partagé et d'interagir avec eux dans les interfaces web et API correspondantes. Là encore, accédez à <code className="action">Gestion des identités et accès</code> > <code className="action">Politiques</code> > <code className="action">Mes politiques</code> dans la <ManagerLink to="/beta/#/iam/policies/my-policies">console OVHcloud</ManagerLink> pour créer une politique.

Comme pour la politique précédente, vous devez ajouter votre utilisateur local, et vous devez sélectionner le type de produit de votre ressource ou sous-ressource si vous souhaitez activer le panneau de sélection des actions pour ces sous-ressources spécifiques. Dans la section **Actions**, chaque type de produit sélectionné dispose de sa propre liste d'actions, intitulée par son nom technique (**ldp/dashboard**, **ldp/stream**, **ldp/index** ou **ldp/osd**).

<img className="thumbnail" alt="Quatre types de produit Logs Data Platform sélectionnés et un flux de données dans Ressources" src="/images/manage-and-operate/observability/logs-data-platform/iam-access-management/console/policy_sub_product_types.png" loading="lazy" />

:::warning

N'ajoutez pas de service Logs Data Platform à cette politique. Si vous le faites, cela donnera automatiquement accès à toutes les sous-ressources de ce service (c'est-à-dire tous les éléments LDP) aux utilisateurs locaux/identités ou groupes attachés à la politique. La politique de service précédente a été créée pour éviter ce comportement.

:::


Vous pouvez combiner des groupes de ressources et des ressources spécifiques dans une même politique. Toutes les actions attachées à la politique seront alors appliquées à toutes les sous-ressources concernées.
Chaque type de sous-ressource dispose de plusieurs actions. Par souci de concision, ce guide ne détaillera pas toutes les actions disponibles pour tous les éléments.

Voici quelques cas d'usage combinant plusieurs droits, qui peuvent tous coexister dans une même politique, illustrant la complexité rendue possible par les politiques IAM. Les actions commençant par **ldp:apiovh** sont des actions liées aux API OVHcloud (donc à la console OVHcloud). Les autres actions sont liées à leur backend spécifique : Graylog ou OpenSearch.

**Développez les exemples suivants pour afficher les actions correspondantes :**

- ldp:opensearch:index/read

### Aller plus loin avec les utilisateurs locaux

Les utilisateurs locaux sont utiles pour générer des jetons d'accès personnels (Personal Access Tokens, PAT). Ces jetons disposent d'une date d'expiration configurable et peuvent être utilisés pour interagir aussi bien avec les API OVHcloud qu'avec les backends de Logs Data Platform.

<Api version="v1" section="/me" method="POST" route={"/me/identity/user/\\{user\\}/token"} />

Grâce à l'IAM OVHcloud, vous pouvez ensuite déléguer les droits de création de sous-ressources (index, alias) à votre utilisateur local et interagir directement avec les API backend à l'aide de ces jetons d'accès personnels.

Les actions liées à la création d'éléments font partie des actions de service. Vous devrez les ajouter à une politique pour permettre à un utilisateur de créer des éléments avec son PAT.

:::info

Vous n'avez besoin d'autoriser aucune action des API OVHcloud pour permettre à un utilisateur local d'interagir avec les API des backends de Logs Data Platform (OpenSearch, Graylog, OpenSearch Dashboards).
Les utilisateurs locaux vous permettent de générer des jetons qui ne peuvent interagir qu'avec le backend, de manière similaire aux anciens jetons Logs Data Platform.

:::


Par exemple, ces deux droits permettent à un utilisateur local de créer des index/alias directement sur OpenSearch sans disposer d'aucun autre droit sur les API OVHcloud.
