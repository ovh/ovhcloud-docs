## Objectif

Le constructeur de workflows présente un [workflow](/guides/public-cloud/data-platform/dpe-workflows) sous forme de graphe d'actions. Au lieu de placer les actions dans des stages successifs, vous indiquez ce que chaque action attend : une action démarre lorsque les actions dont elle dépend ont réussi, ou échoué. Ce guide explique comment :

- ajouter des actions et définir ce que chacune attend ;
- regrouper des actions ;
- exécuter en parallèle des actions indépendantes ;
- définir des tentatives et un délai maximal sur une action ;
- décider de ce qui se passe lorsqu'une action échoue ;
- suivre une exécution ;
- créer le même workflow avec l'API.

## Prérequis

- Un accès au Data Processing Engine d'un projet Data Platform.
- Les [actions](/guides/public-cloud/data-platform/landing-page-dpe-actions) à enchaîner, déjà créées dans le Data Processing Engine.

## Créer un workflow

Dans le Data Processing Engine, allez dans **Workflows** et cliquez sur **Nouveau workflow**. Le workflow s'ouvre dans le constructeur.

<img className="thumbnail" alt="Constructeur de workflows vide avec Add your first action" src="/images/public-cloud/data-platform/product/dpe/workflows/picts/builder-empty.png" loading="lazy" />

1. Cliquez sur **Ajoutez votre première action**, puis choisissez l'action dans l'onglet **Action** du panneau.
2. Faites grandir le graphe depuis le menu **+** d'une action :
    - **Ajouter une action après** : une nouvelle action qui s'exécute lorsque celle-ci se termine ;
    - **Ajouter une action en parallèle** : une nouvelle action avec les mêmes dépendances et le même groupe que l'action sélectionnée ;
    - **Exécuter en cas d'échec** : une nouvelle action qui ne s'exécute que si celle-ci échoue.
3. Sélectionnez une action pour la paramétrer dans le panneau, qui a trois onglets : **Action**, **Dépendances** et **Options**. Voir les sections ci-dessous.
4. Nommez le workflow dans son onglet **Preferences**, puis cliquez sur **Créer**.

<img className="thumbnail" alt="Onglet Action du panneau, choix de l'action d'une nouvelle étape" src="/images/public-cloud/data-platform/product/dpe/workflows/picts/builder-choose-action.png" loading="lazy" />

Le graphe se dispose tout seul à partir des dépendances : vous ne placez pas les actions vous-même. Au-dessus du graphe, **Ajouter une action de premier niveau** ajoute une action qui démarre avec l'exécution, **Nouveau groupe** crée un groupe, **Annuler** revient sur la dernière modification et **Trouver une action** cherche par nom, id, groupe ou dépôt. La minicarte montre le graphe entier.

:::info
Les workflows créés avec des stages continuent de s'ouvrir dans l'éditeur par stages, décrit dans [Orchestrer des pipelines ETL avec les workflows de la Data Platform](/guides/public-cloud/data-platform/dpe-workflows).
:::

## Définir ce qu'une action attend

Dans l'onglet **Dépendances** d'une action, **S'exécute après** liste ce que l'action attend. Chaque ligne est une action ou un groupe du workflow, avec l'une de deux conditions :

- **réussit** : l'action attend que cette action, ou ce groupe, réussisse ;
- **échoue** : l'action attend que cette action échoue. C'est une route d'échec, voir [Quand une action échoue](#quand-une-action-échoue).

L'action démarre lorsque **toutes** ses lignes sont vraies. Une action sans ligne démarre au lancement de l'exécution.

Cliquez sur **Ajouter une action** pour ajouter une ligne : **Depuis ce workflow** attend une action ou un groupe déjà présent dans le graphe, **Nouvelle action** ajoute une nouvelle action placée avant celle-ci. **S'exécute avant** liste, en lecture seule, les actions et groupes qui attendent celle-ci.

Par exemple, si B et C attendent tous deux que A réussisse, et que D attend B et C, D ne démarre qu'une fois B et C réussis.

<img className="thumbnail" alt="Onglet Dépendances : l'action s'exécute après la réussite de toutes les actions du groupe Load sources" src="/images/public-cloud/data-platform/product/dpe/workflows/picts/builder-dependencies.png" loading="lazy" />

## Regrouper des actions

Un groupe rassemble des actions qui partagent les mêmes dépendances, et permet à d'autres actions de les attendre toutes à la fois.

1. Cliquez sur **Nouveau groupe**, donnez-lui un nom et cochez les actions à y placer, puis cliquez sur **Créer le groupe**. Les lignes **S'exécute après** communes à toutes les actions cochées passent au groupe.
2. Dans le panneau du groupe, les lignes **S'exécute après** s'appliquent à chaque action du groupe.
3. Pour qu'une action attende le groupe entier, ajoutez-lui une ligne **S'exécute après** sur le groupe, par exemple *Tout le groupe Chargement des sources* **réussit**. L'action démarre une fois que chaque action du groupe a réussi.

Le nom d'un groupe commence par une lettre et compte au plus 40 caractères : lettres, chiffres, espaces, `-` et `_`. **Dégrouper** conserve les actions et recopie les lignes **S'exécute après** du groupe sur chacune d'elles.

## Exécuter des actions en parallèle

Les actions qui ne s'attendent pas peuvent s'exécuter en même temps, mais seulement lorsque le workflow dispose de plusieurs instances. Un workflow s'exécute sur **une seule instance par défaut** : ses actions s'exécutent alors l'une après l'autre, dans un ordre qui respecte les dépendances, même si elles ne dépendent pas les unes des autres.

Pour exécuter en parallèle des actions indépendantes, augmentez le nombre d'instances du workflow dans son onglet **Preferences**, voir [Dimensionner vos tâches horizontalement](/guides/public-cloud/data-platform/dpe-jobs-resources#dimensionner-vos-tâches-horizontalement). Dans la section **Ressources**, le total vaut **Instances** × **Taille d'instance**, en DPU. Les mêmes champs apparaissent lorsque vous lancez le workflow. Chaque instance prend ses DPU sur le quota du projet : si le quota est atteint, l'exécution ne démarre pas.

<img className="thumbnail" alt="Section Ressources des préférences du workflow : instances, taille d'instance et total de DPU" src="/images/public-cloud/data-platform/product/dpe/workflows/picts/builder-resources.png" loading="lazy" />

## Tentatives et délai maximal

Dans l'onglet **Options** d'une action, sous **Tentatives et délai maximal** :

| Champ | Valeurs | Effet |
|---|---|---|
| **Tentatives** | 0 à 10, 0 par défaut | Nombre de nouvelles tentatives après un échec. L'exécution affiche chaque tentative |
| **Délai entre les tentatives** | 1 seconde à 60 minutes | Attente avant chaque nouvelle tentative. Disponible dès que **Tentatives** est supérieur à 0 |
| **Délai maximal** | Jusqu'à 24 heures. 0, la valeur par défaut, signifie **Pas de délai limite** | L'action est arrêtée et échoue si elle dure plus longtemps, avec le message « Action timed out after … » |

Une action qui échoue encore après sa dernière tentative, ou qui dépasse son délai maximal, est traitée comme décrit dans [Quand une action échoue](#quand-une-action-échoue).

## Quand une action échoue

Sous **En cas d'échec**, dans l'onglet **Options**, vous décidez de ce qui arrive au reste de l'exécution lorsque l'action échoue :

| Option | Actions qui attendent sa réussite | Ses routes d'échec | Le workflow |
|---|---|---|---|
| **Faire échouer le workflow** (par défaut) | Non exécutées | Exécutées | Se termine en échec |
| **Continuer** | Exécutées, comme si elle avait réussi | Exécutées | Se termine en échec |


<img className="thumbnail" alt="Onglet Options : tentatives et délai maximal, et En cas d'échec réglé sur Faire échouer le workflow" src="/images/public-cloud/data-platform/product/dpe/workflows/picts/builder-options.png" loading="lazy" />

Une route d'échec est une action qui attend l'échec de cette action (une ligne **échoue**, ou **Exécuter en cas d'échec** dans le menu **+**). Utilisez-la pour nettoyer, ou pour prévenir, lorsque quelque chose se passe mal.

Quelle que soit l'option, un workflow dont une action a échoué se termine en échec. **Continuer** permet seulement au reste du graphe de s'exécuter.

## Version d'une action

Dans l'onglet **Action**, **Version** choisit la version de son dépôt que le workflow exécute :

- **Version déployée** : la version déployée du dépôt ;
- **Dernière version** : la dernière version, qui change à chaque nouvelle version du dépôt.

Le panneau indique de quelle version il s'agit, par exemple « Exécute v1, la version déployée du dépôt ». **Afficher la version** montre le choix sur chaque action du graphe.

<img className="thumbnail" alt="Onglet Action avec le choix de la version : version déployée ou dernière version" src="/images/public-cloud/data-platform/product/dpe/workflows/picts/builder-version.png" loading="lazy" />

Lorsqu'un environnement ou les options d'exécution du workflow imposent une version, le champ l'affiche et ne peut pas être modifié ici.

## Vérifier le workflow

**Valider** vérifie le workflow avant que vous ne l'enregistriez, et liste chaque problème avec le nom de l'action concernée. Un workflow ne peut être enregistré que si :

- il contient au moins 1 action ;
- chaque action a été choisie ;
- aucune action n'est dans un groupe qui n'existe pas ;
- chaque groupe attendu par un élément contient au moins 1 action ;
- aucune action n'en attend une autre en boucle.

## Suivre une exécution

Lancez le workflow comme tout autre workflow : à la demande, avec un déclencheur ou par l'API. Pendant l'exécution, le graphe montre l'état de chaque action :

| État | Signification |
|---|---|
| **En attente** | Attend ses dépendances |
| **En cours** | S'exécute ; **En cours · tentative 2** après un premier échec avec tentatives |
| **Terminée** | A réussi |
| **Échec** | A échoué après sa dernière tentative, ou a dépassé son délai maximal |
| **Non exécutée** | Ignorée : une action qu'elle attendait n'a pas réussi |

Après l'exécution, le graphe conserve l'état de chaque action de la dernière exécution, et l'en-tête affiche la durée et le résultat de cette exécution. Un groupe indique combien de ses actions sont dans chaque état. Le graphe ne peut pas être modifié pendant l'exécution du workflow.

<img className="thumbnail" alt="Graphe après une exécution : groupe Load sources terminé, Check orders quality en échec, Publish orders to gold non exécutée, Notify the data team terminée" src="/images/public-cloud/data-platform/product/dpe/workflows/picts/builder-run-result.png" loading="lazy" />

Comme pour tout workflow, les logs sont dans le [Control Center](/guides/public-cloud/data-platform/control-center-logs-explorer), et vous pouvez [configurer une alerte](/guides/public-cloud/data-platform/control-center-alerting-job-execution) sur ses échecs.

## Créer un workflow avec l'API

Un workflow du constructeur est un workflow avec des `nodes` et des `groups` au lieu de `stages`. Envoyez-le à l'API du Data Processing Engine avec `POST /dpe/v3/workflows`, et lancez-le avec `POST /dpe/v3/workflows/{workflowId}/start`.

Chaque nœud a un `_id` que vous choisissez, de 24 caractères hexadécimaux, pour que les autres nœuds puissent y faire référence. Exemple : le chargement s'exécute en premier, le contrôle s'exécute si le chargement réussit, et le nettoyage s'exécute si le chargement échoue :

```json
{
  "display_name": "Charger et contrôler les commandes",
  "nodes": [
    {
      "_id": "6a1f00000000000000000001",
      "group": null,
      "requires": [],
      "action": {"action_id": "<id de l'action de chargement>", "repository": "<id du dépôt>", "repository_version_override": "deployed"},
      "params": {},
      "retries": {"count": 1, "delay": "30s"},
      "timeout": "900s",
      "stop_on_failure": true
    },
    {
      "_id": "6a1f00000000000000000002",
      "group": null,
      "requires": [{"node": "6a1f00000000000000000001", "group": null, "on": "success"}],
      "action": {"action_id": "<id de l'action de contrôle>", "repository": "<id du dépôt>", "repository_version_override": "deployed"},
      "params": {},
      "retries": {"count": 0, "delay": "0s"},
      "timeout": null,
      "stop_on_failure": true
    },
    {
      "_id": "6a1f00000000000000000003",
      "group": null,
      "requires": [{"node": "6a1f00000000000000000001", "group": null, "on": "failure"}],
      "action": {"action_id": "<id de l'action de nettoyage>", "repository": "<id du dépôt>", "repository_version_override": "deployed"},
      "params": {},
      "retries": {"count": 0, "delay": "0s"},
      "timeout": null,
      "stop_on_failure": true
    }
  ],
  "groups": []
}
```

| Champ | Contenu |
|---|---|
| `requires` | Ce que le nœud attend : une entrée par ligne, avec `node` ou `group` et `on`, `success` ou `failure` |
| `action.action_id` | L'identifiant exécutable de l'action (son champ `action_id`, pas son `_id`) |
| `action.repository_version_override` | `deployed` ou `latest` |
| `retries` | `count` (0 à 10) et `delay` en secondes, par exemple `30s` |
| `timeout` | En secondes, par exemple `900s`, ou `null` pour aucun délai maximal |
| `stop_on_failure` | `true` pour **Faire échouer le workflow**, `false` pour **Continuer** |
| `group` | Le `_id` du groupe du nœud, ou `null` |

Un groupe s'écrit `{"_id": "<24 caractères hexadécimaux>", "name": "<nom du groupe>", "requires": [...]}`. Un nœud attend un groupe entier avec `{"node": null, "group": "<id du groupe>", "on": "success"}`.

Pour exécuter en parallèle des nœuds indépendants, réglez `environment.fpu.instances` sur une valeur supérieure à 1.

:::warning
L'API ignore, sans erreur, les champs qu'elle ne connaît pas. Relisez le workflow après sa création pour vérifier qu'il contient ce que vous avez envoyé.
:::

L'état de chaque nœud pendant et après une exécution se trouve dans `execution.nodes` de `GET /dpe/v3/jobs/{executionId}`, avec son statut, son nombre de tentatives et son message d'erreur.
