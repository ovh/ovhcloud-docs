## Objectif

Ce tutoriel montre comment utiliser le système de versioning natif de la Platform ou comment configurer un repository Git pour suivre les modifications de vos [Data Processing Actions](/guides/public-cloud/data-platform/landing-page-dpe-actions).

  
## Introduction

### Prérequis

Pour suivre ce tutoriel, vous devez être familiarisé avec le [Data Processing Engine](/guides/public-cloud/data-platform/landing-page-dpe) et vous devriez idéalement avoir suivi le [guide de Démarrage](/guides/public-cloud/data-platform/landing-page-getting-started). L'essentiel est de savoir à quoi servent les [Actions](/guides/public-cloud/data-platform/landing-page-dpe-actions) et comment les utiliser.

### Aperçu des concepts

L'édition des actions est toujours en mode autosave. Lorsque vous essayez d'itérer sur des actions existantes, il est recommandé de créer plusieurs versions du code des actions. Cela vous permet d'introduire progressivement des variations pour expérimenter et tester votre travail, tout en gardant la version en production toujours intacte.

**Sur la Platform, ce versioning se produit au niveau des repositories**. Les repositories sont les onglets que vous voyez en haut de l'arborescence des Actions.

<img className="thumbnail" alt="repos" src="/images/public-cloud/data-platform/getting-further/versioning/picts/repos.png" loading="lazy" />

Vous ne pouvez pas versionner une action individuelle, mais tout un repository d'actions. Le panneau de versioning est accessible en haut à droite de l'en-tête du repository :

<img className="thumbnail" alt="Concepts overview — Versioning panel" src="/images/public-cloud/data-platform/getting-further/versioning/picts/versioning-panel.png" loading="lazy" />

Il existe 2 systèmes de versioning sur la Platform :

- le [système de contrôle de versions de la Data Platform](/guides/public-cloud/data-platform/dpe-actions-manage#utiliser-le-système-de-contrôle-de-version-de-la-platform) : le système de versioning par défaut sur tous les repositories
- le [versioning Git](/guides/public-cloud/data-platform/dpe-actions-manage#utiliser-un-repository-lié-à-git) : si vous décidez de synchroniser votre repository avec Git

Voyons maintenant comment tout cela fonctionne en pratique !

## Utiliser le système de contrôle de versions de la Platform

Par défaut, chaque repository d'actions sur la platform dispose d'un système de contrôle de versions intégré qui vous permet de gérer manuellement les différentes versions du code (c'est-à-dire des actions) qu'il contient.

Les repositories ont tous :

- une *deployed version*, qui est la version servie lors de l'[exécution du job](/guides/public-cloud/data-platform/landing-page-dpe-jobs). 
- une *editing version*, qui est la version en cours d'édition dans le panneau de l'éditeur.

:::info
Si votre repository n'a qu'*une seule version*, la version active est identique à la deployed version, ce qui signifie que vous éditez vos actions en production.
:::

Si votre repository a *deux versions ou plus*, la deployed version ne peut pas être éditée. Elle peut être consultée en mode lecture seule.

Les versions doivent être créées manuellement. Pour créer une nouvelle version du repository, ouvrez le panneau de versioning en haut à droite et cliquez sur l'icône **+**.

<img className="thumbnail" alt="Use the Platform version control system — Versioning fp1" src="/images/public-cloud/data-platform/getting-further/versioning/picts/versioning-fp1.png" loading="lazy" />

Choisissez la version à dupliquer pour créer la nouvelle version.

<img className="thumbnail" alt="Use the Platform version control system — Versioning fp2" src="/images/public-cloud/data-platform/getting-further/versioning/picts/versioning-fp2.png" loading="lazy" />

Après la création de la nouvelle version, la *deployed version* ne changera pas. Vous pouvez éditer directement la nouvelle version.

<img className="thumbnail" alt="Use the Platform version control system — Versioning fp3" src="/images/public-cloud/data-platform/getting-further/versioning/picts/versioning-fp3.png" loading="lazy" />

Cliquez sur le bouton **Play** pour définir une nouvelle version comme deployed version : la version du code utilisée lorsque les actions du repo sont exécutées.

<img className="thumbnail" alt="Use the Platform version control system — Versioning fp4" src="/images/public-cloud/data-platform/getting-further/versioning/picts/versioning-fp4.png" loading="lazy" />

## Utiliser un repository lié à Git

Chaque repository peut être lié à un repository Git externe, auquel cas les versions sont synchronisées avec les commits Git. Cela vous permet de mettre à jour et de tester les actions en continu sans affecter la version déployée en production.

### Lier un repository à Git

Pour lier votre repository sur la platform à Git, vous devez cliquer sur l'icône en forme d'engrenage pour éditer un repository existant ou en créer un nouveau. L'une ou l'autre de ces actions ouvrira la fenêtre de configuration du repository.

<img className="thumbnail" alt="img1" src="/images/public-cloud/data-platform/getting-further/versioning/picts/repository_configuration_window.png" loading="lazy" />

Cliquez sur *Connect to Git* pour développer la fenêtre.

<img className="thumbnail" alt="img1" src="/images/public-cloud/data-platform/getting-further/versioning/picts/repository_configuration_full.png" loading="lazy" />

Ici, la première chose à saisir est l'URL SSH du Repository.

On la trouve généralement dans les options de clonage de repository des solutions Git courantes. Sur GitHUB, par exemple, elle se trouve dans Code > Clone > SSH.

<img className="thumbnail" alt="github" src="/images/public-cloud/data-platform/getting-further/versioning/picts/github.png" loading="lazy" />

Cliquez ensuite sur *FETCH* pour récupérer les branches distantes et sélectionnez la branche que vous souhaitez utiliser.

Enfin, copiez la clé SSH publique indiquée en bas et collez-la dans la liste des clés SSH associées à votre compte sur votre solution Git. Pour GitHUB, vous pouvez suivre [ce tutoriel](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/adding-a-new-ssh-key-to-your-github-account).

### Committer et pousser

Après avoir modifié un objet dans un repo, votre repo affichera les changements non committés comme indiqué dans l'image ci-dessous. Vous pouvez les committer et les pousser en cliquant sur la flèche pointant vers le haut indiquée dans l'image.

<img className="thumbnail" alt="commit" src="/images/public-cloud/data-platform/getting-further/versioning/picts/commit_push.png" loading="lazy" />

:::info
En cas de conflit lors du push, vos changements ne seront pas poussés vers la branche que vous avez configurée ; ils seront à la place poussés vers une nouvelle branche portant le même nom que la branche actuelle avec un suffixe *_conflictN*, où N est le numéro du conflit. Par exemple, si votre branche s'appelle *current-branch* et que votre push provoque un conflit, la nouvelle branche s'appellera *current-branch_conflict1*. En cas de nouveau conflit lors d'un push suivant, la nouvelle branche s'appellera *current-branch_conflict2*.
:::

### Puller et merger

Récupérez les changements distants en cliquant sur la flèche pointant vers le bas indiquée dans l'image ; une fenêtre popup vous invitera à confirmer votre décision. Tous les changements non committés seront perdus et les deux branches seront fusionnées ensemble.

<img className="thumbnail" alt="pull" src="/images/public-cloud/data-platform/getting-further/versioning/picts/pull_merge.png" loading="lazy" />
