## Objectif

Vous avez décidé de vous lancer et vous venez de créer votre projet ! Bravo !

Et maintenant ? Par où commencer ?

En tant que premiers utilisateurs de notre platform, nous avons accumulé plusieurs années d'expérience dans la conduite de projets de données. Nous avons rassemblé une liste de bonnes pratiques, apprises au fil des années grâce à notre pratique des services, que nous sommes ravis de partager avec vous.

Les projets sur **Data Platform** vous permettent de rassembler une équipe et de travailler ensemble sur le même projet de données. 
Vous pouvez commencer par un simple chargement de fichiers et basculer sans effort vers un traitement de données quasi temps réel, en conservant votre méthodologie et en scalant facilement à mesure que votre projet grandit.  
Alors démarrez, itérez, et faites grandir votre projet étape par étape : votre projet répondra à vos besoins croissants.

Un projet type traverse souvent les **jalons principaux** suivants :

- Une [checklist](#checklist) rapide sur le cas d'usage et le périmètre du projet
- Donner un [accès à vos coéquipiers](#gestion-des-utilisateurs)
- Faire de manière itérative, et selon les besoins :
  - Adapter les [ressources du projet](#gérer-les-ressources) à vos besoins
  - Définir les [Data Sources](#collecter-des-données)
  - Concevoir les [Tables](#organiser-les-données)
  - Construire les [Actions et Workflows pour traiter les données](#traiter-les-données)
  - Construire les [Queries et Dashboards](#écrire-des-queries) pour visualiser vos données
  - Construire les [Apps & API](#construire-des-applications)
  - Donner [accès aux utilisateurs finaux](#donner-accès-à-votre-application)
  - [Monitorer les Jobs et Déploiements](#monitor)
  - Recueillir des retours

## Checklist

:::warning
Nous vous recommandons de suivre notre [guide de démarrage](/guides/public-cloud/data-platform/landing-page-getting-started) pour bien comprendre les composants clés du projet et les concepts de la Data Platform.
:::

Avant de vous lancer, voici quelques vérifications de base sur le périmètre et le calendrier de votre cas d'usage :

- Sources de données
  - De quelles données avez-vous besoin ?
  - Les données sont-elles disponibles ? Comment ? L'historique des données est-il disponible ?
  - Dimensionnement du stockage : quel volume de données et de calcul ce projet nécessitera-t-il ?
  - À quelle fréquence doit-il être rafraîchi ?
- Décrivez votre propre livre de données :
  - La « data story » : d'où viennent-elles ? Comment ont-elles été produites ? Quel est l'historique de votre flux de données ?
  - Champs de données : que signifient-ils ? à quoi servent-ils ?
  - Règles métier détaillées (sur les données)
  - KPI : comment les calculer ? que signifient-ils ?
- Que doit-on produire ?
  - Storyboard UX
  - API pour usage externe
  - Export de fichiers
- Détection et atténuation des risques
  - Qu'est-ce qui pourrait mal se passer ? Qu'y a-t-il de complexe dans votre projet ?
  - Identifier/anticiper les goulets d'étranglement ou obstacles possibles
- Identifier et tirer parti d'itérations courtes
 - Visualiser et vérifier les données le plus tôt possible
 - Publiez tôt, publiez souvent !

## Gestion des utilisateurs

Les projets facilitent le travail en équipe sur un même projet. Il existe deux niveaux de gestion d'équipe :

- Les [membres](/guides/public-cloud/data-platform/manage-organizations) de votre organisation Data Platform sont vos coéquipiers. Ils ont créé un compte Data Platform
- Les [utilisateurs](/guides/public-cloud/data-platform/iam-users) de votre projet sont soit des coéquipiers travaillant sur ce projet, soit des utilisateurs finaux de votre API et de vos apps
  - Les membres d'une organisation sont automatiquement ajoutés comme utilisateurs dans tous les projets de cette organisation. Les permissions doivent être accordées manuellement aux non-administrateurs.

Après avoir [ajouté votre équipe à votre organisation](/guides/public-cloud/data-platform/manage-organizations), consultez [comment leur donner des droits d'accès dans l'**Identity Access Manager**](/guides/public-cloud/data-platform/iam-users#gérer-les-utilisateurs-de-liam-du-projet) de chaque projet selon leurs compétences et permissions.

Les droits d'accès de vos utilisateurs finaux sont également gérés dans l'Identity Access Manager.

## Gérer les ressources

Les projets ont été conçus dès l'origine pour évoluer facilement à mesure que les besoins de votre projet de données changent. Vous pouvez **scaler horizontalement et verticalement** indépendamment n'importe quel composant de votre choix en quelques clics, par exemple vos [apps](/guides/public-cloud/data-platform/landing-page-app-services-apps).

Chaque composant de votre projet consommera des [ressources](/guides/public-cloud/data-platform/manage-pricing) lorsqu'il est activement en cours d'exécution (via un job ou un déploiement).

:::info
Même à l'arrêt, votre projet utilise par défaut quelques DPU. Vous pouvez gérer ce montant dans le [Control Center](/guides/public-cloud/data-platform/control-center-monitoring#les-panneaux-infrastructure-monitoring).
:::

[<span aria-hidden="true">↪</span> En savoir plus sur la consommation de ressources](/guides/public-cloud/data-platform/manage-pricing)

## Collecter des données

Jetez un œil aux [connecteurs disponibles](/guides/public-cloud/data-platform/connectors-sources-configure) et rappelez-vous qu'il est toujours possible d'écrire une [action personnalisée](/guides/public-cloud/data-platform/dpe-actions-custom) pour faire tout ce qui n'est pas déjà possible via l'interface.

Si vous devez gérer des fichiers dans votre projet, nous recommandons d'utiliser les [buckets du Lakehouse Manager](/guides/public-cloud/data-platform/lakehouse-manager-buckets) :

- organisez les buckets soit **par sujet** (référentiels par exemple), **par type de traitement** ou **par fournisseurs** selon vos besoins
- au sein d'un bucket, vous pouvez utiliser des **dossiers** pour mieux organiser vos fichiers
- lors de la définition d'une [source](/guides/public-cloud/data-platform/landing-page-connectors-sources), le connecteur *Data Platform Buckets* vous permet de sélectionner un bucket puis de sélectionner des fichiers comme sources
- si vous avez plusieurs fichiers dans le même bucket/dossier :
  - si chaque fichier est différent, vous pouvez les [analyser](/guides/public-cloud/data-platform/landing-page-connectors-analyzer) séparément et les utiliser comme source pour les [actions du Data Processing Engine](/guides/public-cloud/data-platform/landing-page-dpe-actions)
  - si tous les fichiers doivent être traités de la même manière : il vous suffit d'en sélectionner un à **analyser**, vous l'utiliserez comme source et [utiliserez la segmentation sur un ensemble de fichiers](/guides/public-cloud/data-platform/tutorials-segmentation-files) pour les traiter
- consultez [comment envoyer des fichiers vers les buckets avec des outils compatibles S3<sup>1</sup>](/guides/public-cloud/data-platform/tutorials-bucket-s3-access) pour l'intégrer à votre process interne

## Analyser les données et définir des règles de blueprint

Une fois vos sources configurées, prenez le temps de les [analyser](/guides/public-cloud/data-platform/landing-page-connectors-analyzer) et de configurer des règles de nettoyage de base appelées [règles de blueprint](/guides/public-cloud/data-platform/connectors-analyzer-blueprint-rules). Cela peut aider à corriger des problèmes courants comme :

- le formatage de dates
- le formatage de nombres
- le nettoyage de chaînes de caractères
- ignorer les lignes incomplètes
- ... et bien plus encore

À long terme, cette étape vous fera gagner beaucoup de temps !

## Organiser les données

La [page Tables](/guides/public-cloud/data-platform/lakehouse-manager-tables) est l'endroit où vous [préparez le schéma de votre base de données](/guides/public-cloud/data-platform/getting-started-organize-data#organiser-vos-données-en-tables).

### Tables

- Nous recommandons d'utiliser un préfixe selon le type de données :
  - `ref_` : pour les référentiels et données stables, sans information temporelle
  - `raw_` : données importées *telles quelles* avec des changements minimaux. Cela peut être utilisé pour retracer les problèmes de données
  - `prm_` : tables primaires, c'est-à-dire des données de qualité améliorée issues de `raw_`
  - `fct_` : consolidation des `facts` provenant de plusieurs `prim_` et `ref_` dans une `scale` commune
  - `agr_` : agrégation de données selon une `scale` différente (par exemple `datetime` vers `date` ou `date` vers `year`)
    - elles sont généralement conçues pour optimiser les requêtes
    - construisez une table `agr_` par **granularité de scale** en ajoutant tous les attributs nécessaires
    - puis ajoutez des noms d'attributs qui indiquent la granularité (`agr_station_yearmonth`, `agr_movie_date`)
  - `tmp_` : tables temporaires utilisées pour le traitement (marquez-les comme **non requêtables**)
  - `mlm_` : pour les tables utilisées dans un modèle de machine learning
- Donnez des noms clairs qui décrivent ce que représente une ligne de données
- Définissez des [index](/guides/public-cloud/data-platform/lakehouse-manager-manage-tables) pour accélérer les opérations sur les données

### Attributs

Utilisez l'[onglet Attributs](/guides/public-cloud/data-platform/lakehouse-manager-attributes) pour examiner tous les attributs, dans quelles tables ils sont utilisés, quelles Actions DPE les utilisent, etc.

Voici quelques bonnes pratiques concernant les attributs (c'est-à-dire les noms de champs dans les tables) :

- type d'attribut : choisissez entre *dimension* ou *measure*
  - *dimension* : information qualitative qui peut être utilisée pour scaler, filtrer, etc. mais pas sommée.
  - *measure* : information numérique qui peut, la plupart du temps, être sommée, comptée, moyennée, etc.
- nommage des attributs :
  - utilisez un *préfixe* pour les distinguer (ex. `client_`, `fb_`, `site_`)
  - nommez les attributs `measure` de façon à indiquer une fenêtre temporelle :
    - `_nb_` : nombre pour ce jour
    - `_total_` : valeur pour ce jour
    - `_diff_` : différence par rapport au jour précédent
    - ...
  - indiquez clairement ce dont il s'agit (c'est-à-dire `_amount_`, `_ticket_`, `_fans_`)
  - indiquez l'unité de mesure si elle n'est pas évidente (c'est-à-dire `_g`, `_kg`, `_wh`, `_kwh`, `_eur`, `_usd`)

:::warning
Il est très important d'**utiliser le même nom et le même type d'attribut** dans toutes les tables pour **désigner la même information**. Ainsi, lors de l'exécution d'une query dans l'[Analytics Manager](/guides/public-cloud/data-platform/landing-page-analytics-manager), celui-ci vérifie dynamiquement l'objet le plus adapté pour les champs requis.
:::

### Explorer

Utilisez l'[Explorer](/guides/public-cloud/data-platform/lakehouse-manager-explorer) pour vérifier rapidement le contenu des tables.

## Traiter les données

Le [Data Processing Engine (DPE)](/guides/public-cloud/data-platform/landing-page-dpe) est utilisé pour construire des [actions](/guides/public-cloud/data-platform/landing-page-dpe-actions) qui sont le cœur de votre flux de données physique. Elles peuvent s'exécuter seules ou être organisées en groupes appelés [workflows](/guides/public-cloud/data-platform/dpe-workflows).

### Actions

Assurez-vous d'examiner en détail les [types d'actions](/guides/public-cloud/data-platform/landing-page-dpe-actions) fournis.

Si vous devez aller plus loin, commencez à écrire une [Custom Action](/guides/public-cloud/data-platform/dpe-actions-custom) en utilisant notre [SDK](/guides/public-cloud/data-platform/landing-page-developers-python-sdk) pour interagir avec le reste de votre projet en tirant parti de **Python** ou **PySpark**.

:::info
Utilisez les [notebooks](/guides/public-cloud/data-platform/dpe-notebooks) pour prototyper rapidement une Custom Action, puis exportez-la vers le Data Processing Engine
:::

- Pour les [Aggregate Actions](/guides/public-cloud/data-platform/dpe-actions-aggregate) :
  - `scale` : doit avoir la même granularité que la clé primaire de la table de destination
  - **vérifiez bien vos règles de jointure de tables** : c'est la principale source d'erreurs
- Réglez le **niveau de log** de manière appropriée selon le cycle de vie (c'est-à-dire `debug` si nécessaire, `info` sinon)
- Utilisez **Auto flush all** pour vider tous les caches et visualiser les mises à jour apportées par l'action sur les datasets

### Utiliser Repositories et Versions

À mesure que votre projet grandit, n'oubliez pas que vous pouvez organiser les actions dans des [repositories utilisant des versions](/guides/public-cloud/data-platform/dpe-actions-manage#gérer-les-actions) selon vos besoins.

:::info
Les actions sont listées par ordre alphabétique : vous pouvez ajouter des préfixes tels que des nombres pour mieux les organiser.
:::

### Utiliser la segmentation

Pour tirer pleinement parti de la puissance du DPE de la Data Platform, utilisez la [Segmentation](/guides/public-cloud/data-platform/dpe-jobs-segmentation) pour paralléliser les tâches de calcul au niveau d'une action.

### Utiliser un périmètre

Pour limiter une action ou un workflow à un sous-ensemble de vos données, par exemple les 30 derniers jours, utilisez l'option [Perimeter](/guides/public-cloud/data-platform/dpe-jobs-perimeter).

## Écrire des queries

Utilisez des dossiers et des repositories pour organiser les [queries](/guides/public-cloud/data-platform/analytics-manager-queries) sauvegardées dans l'[Analytics Manager](/guides/public-cloud/data-platform/landing-page-analytics-manager).

Par exemple :

- *Data Quality* : queries pour vérifier la qualité des données
- *Data Analysis* : queries pour visualiser les caractéristiques de base
- *App-xxx* : préparer des queries à utiliser dans votre application
  - Cela vous permet de mettre à jour le schéma de la base de données et les queries sans avoir à déployer une nouvelle version de l'app 
  - Donnez des noms clairs et descriptifs à vos queries

### Query Engine

- moteur SQL unifié sur plusieurs bases de données
- [Explorer](/guides/public-cloud/data-platform/lakehouse-manager-explorer) dans le Lakehouse Manager

## Construire des applications

Prenez le temps de comprendre les [Application Services](/guides/public-cloud/data-platform/landing-page-app-services) et les [paramètres](/guides/public-cloud/data-platform/app-services-apps-deploy#paramètres-de-lapplication) possibles.

### Conseils utiles

- Concevez un storyboard avant de démarrer votre projet
- Assurez-vous que vos `dynamic parameters` sont présents dans toutes les tables que vous devez requêter
- Utilisez le **label de l'objet** dans les **Tables** pour la traduction automatique
- Tirez parti des [Formatters](/guides/public-cloud/data-platform/app-services-apps-formatter) et des [Translations](/guides/public-cloud/data-platform/app-services-apps-translations)
- Tirez parti des [Style templates](https://docs.dataplatform.ovh.net/#/en/technical/sdk/app/charts/template) pour rationaliser le développement de vos Apps

Un cycle de développement d'application typique est le suivant :

1. Concevez un storyboard
  - vérifiez que les données sont disponibles
  - identifiez les `dynamic parameters`
  - identifiez les *charts* et *custom components* nécessaires
2. Analytics Manager : préparez et vérifiez les queries nécessaires
3. Implémentez une première version dans l'UI
  - configurez les `dynamic parameters`
  - configurez les `dashboards` et `menus`
  - configurez les `charts` disponibles selon les besoins
  - configurez les `dictionaries`, `formatters` et `translations`
4. Améliorez cette version
  - Adaptez le CSS selon les besoins
  - Tirez parti des [Style templates](https://docs.dataplatform.ovh.net/#/en/technical/sdk/app/charts/template)
  - Implémentez votre propre [custom chart](https://docs.dataplatform.ovh.net/#/en/technical/sdk/app/custom-chart) ou [custom component](https://docs.dataplatform.ovh.net/#/en/technical/sdk/app/custom-component) selon les besoins
5. Testez et itérez à nouveau
6. Donnez accès à davantage d'utilisateurs

### Personnaliser davantage votre application

L'application repose sur le framework ReactJS. Nous vous recommandons vivement de suivre notre [guide sur la personnalisation avancée des apps](/guides/public-cloud/data-platform/tutorials-app-development).

### Repositories Git

Il est généralement recommandé de [synchroniser votre application avec un repository Git](/guides/public-cloud/data-platform/app-services-apps-git-integration) et de déployer deux applications :

- `my-develop` : synchronisée avec votre branche **develop**
- `my-master` : synchronisée avec votre branche **master**

### Noms de domaine personnalisés

Par défaut, votre application est disponible à :
```yaml
https://my-project.eu.dataplatform.ovh.net/my-develop-app/
```

Vous pouvez facilement le modifier dans les [paramètres de l'App](/guides/public-cloud/data-platform/app-services-apps-deploy#paramètres-de-lapplication) pour qu'elle soit à :
```yaml
https://my-beautiful-app.eu.dataplatform.ovh.net/
```
Si vous avez besoin d'une personnalisation supplémentaire, vous pouvez enregistrer [votre propre domaine et fournir vos propres certificats SSL](/guides/public-cloud/data-platform/app-services-apps-custom-domain) :
```yaml
https://my-beautiful-app.example.com/
```

## Donner accès à votre application

Par défaut, chaque `Application` créée dans **Application Services** possède sa contrepartie dans l'**Identity Access Manager**. 

- [Application Services](/guides/public-cloud/data-platform/landing-page-app-services)
  - il gère l'instance qui sera déployée et exécutée
  - il est lié à une **Application de l'Identity Application Manager**
  - il utilisera la configuration de cette **IAM App** concernant les **Auth Providers**, **Users**, etc.
- [Identity Access Manager](/guides/public-cloud/data-platform/iam-application-authentication), vous pouvez définir :
  - Logo
  - Titre de l'application
  - Fournisseur d'authentification autorisé

Ajoutez tous les [utilisateurs finaux](/guides/public-cloud/data-platform/iam-users) qui auront accès à votre application (en utilisant des [fournisseurs d'authentification](/guides/public-cloud/data-platform/iam-auth-providers) si votre entreprise dispose d'un fournisseur SSO), et utilisez les [rôles](/guides/public-cloud/data-platform/iam-roles-conditions) et [groupes](/guides/public-cloud/data-platform/iam-groups) pour gérer le contrôle d'accès aux données.
