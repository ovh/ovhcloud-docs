## Objectif

Ce guide rassemble les bonnes pratiques de sécurité à appliquer lors de l'intégration du SDK Seald. Il couvre la protection des secrets JWT, la sécurisation du stockage des identités, et la gestion des clés cryptographiques.

## Prérequis

- Le SDK Seald installé et initialisé. Consultez le guide [Installer le SDK Seald](/guides/public-cloud/seald/seald-install-sdk).
- Une méthode de protection d'identité en place (SSKS Password ou SSKS 2MR).

## En pratique

### Protéger les secrets JWT

- **Stockez le `JWTSecret` uniquement côté backend**, dans un gestionnaire de secrets ou une variable d'environnement. Ne l'exposez jamais dans le code frontend ni dans le contrôle de version.
- **Utilisez des `jti` uniques** (par exemple un UUID v4) pour tous les JWT d'inscription et de création de session. Un JWT sans `jti` est réutilisable jusqu'à son expiration, ce qui ouvre la porte à des attaques par rejeu.
- **Définissez des durées de vie courtes** : par défaut, un JWT expire 10 minutes après sa date `iat`. N'augmentez pas cette durée sauf nécessité absolue.
- **Restreignez les permissions** : créez des `JWTSecret` avec les permissions minimales nécessaires plutôt que d'utiliser `PERMISSION_ALL = -1`.

### Sécuriser les identités SSKS

- **Préférez SSKS 2MR à SSKS Password** pour les applications nécessitant une récupération de compte. SSKS 2MR divise l'identité entre votre backend et les serveurs SSKS, de sorte qu'aucune des deux parties ne peut reconstruire l'identité seule.
- **Affichez le `authFactor` à l'utilisateur** avant d'appeler `saveIdentity`. Cela permet à l'utilisateur de confirmer que la valeur correspond à son adresse e-mail ou numéro de téléphone attendu, prévenant ainsi une attaque MITM côté serveur.
- **N'envoyez jamais `fake_otp: true` en production**. Cette option contourne l'envoi du challenge SSKS et permettrait à votre serveur d'usurper l'identité des utilisateurs.
- **Normalisez les facteurs d'authentification** (adresses e-mail, numéros de téléphone) avant de les envoyer à SSKS, selon les règles de normalisation de l'API SSKS.

### Sécuriser le stockage local

- **Utilisez `databaseRawKey`** plutôt que `databaseKey` si votre backend stocke une clé brute de 64 octets, afin d'éviter la dérivation scrypt et réduire la surface d'attaque.
- **Générez une `databaseKey` différente par session** (et non par appareil) et incluez l'ID de session dans le `databasePath` pour éviter les collisions.
- **Si `databasePath` est défini mais `databaseKey` est omis**, le SDK utilise une clé fixe dérivée de l'`appId`, ce qui est non sécurisé. Évitez cette configuration en production.

### Gérer les identités exportées

- **Les buffers d'identité exportés (`exportIdentity`) contiennent des clés privées en clair.** Stockez-les chiffrés dans un système à accès contrôlé.
- **Limitez le nombre de sous-identités** par utilisateur. Un très grand nombre de sous-identités (plusieurs dizaines) peut dégrader les performances. Préférez réutiliser une identité stockée sur SSKS plutôt que d'en créer une nouvelle à chaque connexion.

### Protéger les clés cryptographiques avancées

- **`rawOverEncryptionKey`** (GroupTMRTemporaryKey, TMR Access) : utilisez une clé différente pour chaque invitation, même si le même administrateur invite le même facteur d'authentification. Stockez-la côté backend avec une politique d'accès stricte.
- **`rawSecret` / `rawSymKey`** (SymEncKey) : ces valeurs ne doivent jamais être transmises à votre serveur. Le canal de transmission au destinataire (QRCode, lien sécurisé, etc.) est de votre responsabilité.
- **`twoManRuleKey`** : stockez-la côté backend en la liant à l'utilisateur concerné, avec une politique d'accès au moins aussi stricte que vos autres données sensibles.

### Utiliser SSKS Password en combinaison avec l'authentification applicative

:::warning
Si vous utilisez le même mot de passe pour SSKS Password et pour l'authentification de votre application, **ne transmettez jamais le mot de passe brut à votre serveur**. Dérivez-le côté client (avec scrypt ou PBKDF2) avant tout appel serveur. Votre backend ne verrait alors qu'une valeur dérivée, incapable de reconstituer la clé de chiffrement SSKS.
:::
