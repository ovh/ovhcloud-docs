## Objectif

Ce guide présente les différences entre l'environnement de staging Seald (disponible par défaut lors de la création d'un compte) et les serveurs de production. Il explique pourquoi le staging ne doit jamais être utilisé pour des données réelles, et ce qu'il faut préparer avant de basculer en production.

## Prérequis

- Un compte Seald actif en environnement de staging.
- Avoir testé votre intégration SDK sur l'environnement de staging.

:::warning
Les données de l'environnement de staging ne peuvent pas être migrées vers un environnement de production. Créez un compte de production **avant** de commencer à chiffrer de véritables données confidentielles. Pour cela, [contactez l'équipe Seald](mailto:contact@seald.io).
:::

## En pratique

Cette section décrit les différences techniques entre staging et production, et les actions à effectuer pour migrer.

### Étape 1 — Comprendre les différences entre staging et production

| Dimension | Staging | Production |
|-----------|---------|------------|
| **Déploiement** | Serveur unique, aucune tolérance aux pannes | Répliqué, haute disponibilité, basculement automatique |
| **Persistance des données** | Non garantie — remise à zéro possible sans préavis | Sauvegardes régulières vers des sites distants |
| **`fake_otp`** | Disponible (challenge fixé à `'aaaaaaaa'`) | Bloqué — retourne une erreur `406 Not Acceptable` |
| **`full_forget`** | Disponible (suppression complète d'identités SSKS) | Non disponible |
| **SLA** | Aucun | Défini contractuellement |

### Étape 2 — Supprimer les options réservées au staging

Avant de basculer en production, retirez toutes les options spécifiques au staging de votre code :

**`fake_otp: true`** — ne doit jamais être envoyé en production. Cette option contourne l'envoi du challenge SSKS 2MR, ce qui permettrait à votre serveur d'usurper l'identité des utilisateurs et briserait les garanties du chiffrement de bout en bout :

```python
# À supprimer avant la mise en production
result = requests.post(
    "https://SSKS_URL/tmr/back/challenge_send",
    json={
        "create_user": True,
        "user_id": str(utilisateur.id),
        "auth_factor": {"type": "EM", "value": utilisateur.email},
        # "fake_otp": True  <-- supprimer cette ligne
    },
    headers={"X-SEALD-APPID": "VOTRE_APP_ID", "X-SEALD-APIKEY": "VOTRE_API_KEY"}
)
```

### Étape 3 — Obtenir les credentials de production

Un compte de production Seald fournit de nouveaux credentials (`appId`, `apiURL`, `keyStorageURL`, `ssksAppId`, `ssksAppKey`) distincts de ceux du staging. Mettez à jour les variables d'environnement de votre application et de votre backend avec ces nouvelles valeurs.

### Étape 4 — Tester la procédure de réversibilité (recommandé)

Avant de déployer en production, testez la [procédure de réversibilité](/guides/public-cloud/seald/seald-reversibility) sur votre environnement de staging. Cela vous assure de pouvoir récupérer vos données chiffrées si vous deviez un jour arrêter d'utiliser le SDK Seald.

> [!INFO]
> Seald peut mettre en place un export régulier des données vers un Object Storage S3 sous votre contrôle. Contactez le [support Seald](mailto:support@seald.io) pour en faire la demande.
