## Questions générales

### Qu'est-ce que le chiffrement de bout en bout avec Seald ?

Le chiffrement de bout en bout (E2EE) signifie que les données sont chiffrées sur l'appareil de l'expéditeur et ne peuvent être déchiffrées que sur l'appareil du destinataire. Seald implémente ce paradigme via des identités cryptographiques locales : votre serveur ne voit jamais les données en clair ni les clés privées.

### Seald est-il compatible avec mon framework JavaScript ?

Le SDK Seald (`@seald-io/sdk`) fonctionne dans les navigateurs modernes, Node.js, Electron, et React Native. Pour les navigateurs, une configuration Webpack est nécessaire pour les polyfills Node.js. Consultez le guide [Installer le SDK Seald](/guides/public-cloud/seald/seald-install-sdk).

### Quelle est la différence entre le staging et la production ?

L'environnement de staging est à serveur unique, sans garantie de persistance des données, et autorise des fonctionnalités de développement comme `fake_otp`. La production est répliquée, hautement disponible, avec des sauvegardes régulières. Les données de staging ne peuvent pas être migrées vers la production. Consultez le guide [Passer du serveur de staging à la production](/guides/public-cloud/seald/seald-staging-to-production).

## Identités et sous-identités

### Combien de sous-identités puis-je créer par utilisateur ?

Il n'y a pas de limite stricte, mais les performances des opérations de chiffrement se dégradent au-delà d'une trentaine de sous-identités. Pour les utilisateurs fréquents, préférez réutiliser une identité stockée sur SSKS plutôt que d'en créer une nouvelle à chaque connexion.

### Que se passe-t-il si un utilisateur perd tous ses appareils ?

Avec SSKS Password, il n'y a pas de récupération possible si le mot de passe est inconnu. Avec SSKS 2MR, la récupération est possible en combinant le `twoManRuleKey` de votre backend et le challenge envoyé au facteur d'authentification (e-mail ou SMS) de l'utilisateur. Consultez le guide [Protéger les identités Seald avec SSKS 2MR](/guides/public-cloud/seald/seald-ssks-2mr).

### Puis-je associer un identifiant personnalisé à une identité Seald ?

Oui, via le mécanisme de `connector`. Le connector doit respecter le format `${IDENTIFIANT}@${APP_ID}` et le type `AP`. Il est stocké en clair dans la base de données Seald — évitez d'utiliser une donnée personnelle comme une adresse e-mail. Un UUID est recommandé.

## Chiffrement et sessions

### Quelle est la différence entre `encryptFile` et une `EncryptionSession` ?

`sdk.encryptFile` crée une nouvelle session de chiffrement pour chaque fichier. Une `EncryptionSession` partage la même clé entre tous les fichiers et messages chiffrés dans cette session, ce qui réduit le nombre d'appels réseau et simplifie la gestion des destinataires. La contrepartie : vous ne pouvez pas gérer les droits au niveau d'un fichier individuel, seulement au niveau de la session entière.

### Comment ajouter un destinataire à une session existante ?

Tout destinataire ayant le droit `forward` peut appeler `session.addRecipients`. Ce droit est accordé par défaut. En revanche, seul le créateur de la session a le droit `revoke` par défaut.

### Est-ce que les métadonnées sont chiffrées ?

Non. Le champ `metadata` passé à `createEncryptionSession` est stocké en clair sur les serveurs Seald et visible dans le tableau de bord d'administration. N'y incluez pas de données sensibles.

## Groupes

### L'ajout d'un membre à un groupe lui donne-t-il accès aux données passées ?

Oui. Lorsqu'un utilisateur est ajouté à un groupe, il obtient immédiatement accès à toutes les données précédemment chiffrées pour ce groupe.

### Dois-je appeler `renewGroupKey` après chaque suppression de membre ?

Oui. Sans renouvellement des clés, le membre supprimé peut encore déchiffrer les futures données ajoutées au groupe. Appelez `instanceSDKAdmin.renewGroupKey(group.id)` immédiatement après chaque `removeGroupMembers`.

### Un utilisateur peut-il rejoindre un groupe avant d'avoir une identité Seald ?

Oui, via les clés temporaires TMR de groupe (`createGroupTMRTemporaryKey`). L'administrateur crée une clé temporaire associée à un facteur d'authentification (e-mail ou SMS). Une fois que l'utilisateur a une identité, il convertit cette clé via `convertGroupTMRTemporaryKey`. Consultez le guide [Créer et gérer des groupes Seald SDK](/guides/public-cloud/seald/seald-groups).

## Sécurité et réversibilité

### Mon serveur peut-il accéder aux données chiffrées ?

Avec le SDK standard, non — sauf si vous lui accordez explicitement des droits via `addRecipients`. Avec SSKS 2MR, une compromission simultanée de votre backend et des serveurs SSKS exposerait théoriquement les identités. Avec SSKS Password, votre serveur ne peut pas reconstituer la clé de chiffrement sans le mot de passe de l'utilisateur.

### Puis-je récupérer les données si je cesse d'utiliser Seald ?

Oui, via l'outil de réversibilité (`@seald-io/reversibility-tools`). Cette procédure nécessite un export fourni par l'équipe Seald et certaines données de votre backend. Consultez le guide [Déchiffrer des données avec l'outil de réversibilité](/guides/public-cloud/seald/seald-reversibility).
