## Objectif

Par défaut, le SDK Seald ne stocke sa base de données d'identité qu'en mémoire volatile. Lorsque l'utilisateur ferme et rouvre le navigateur, l'identité est perdue et doit être récupérée à nouveau depuis SSKS. L'activation d'une base de données locale persistante met en cache l'identité dans le stockage du navigateur, chiffrée par une clé fournie par votre backend. Cela améliore l'expérience utilisateur en supprimant la nécessité de récupérations d'identité répétées.

## Prérequis

- Le package `@seald-io/sdk` installé. Consultez le guide [Installer le SDK Seald](/guides/public-cloud/seald/seald-install-sdk).
- Un backend capable de générer et de stocker une `databaseKey` par session utilisateur.
- Une méthode de protection d'identité (SSKS Password ou SSKS 2MR) pour la récupération initiale de l'identité.

## En pratique

Cette section explique comment activer la base de données persistante et comment utiliser une clé brute pour de meilleures performances.

### Étape 1 — Générer une `databaseKey` sur votre backend

Votre backend doit générer une `databaseKey` aléatoire cryptographiquement sûre et l'associer à la session de l'utilisateur. Retournez-la au frontend lors de l'authentification.

```javascript
// Exemple de backend Node.js
const crypto = require('node:crypto')
const util = require('util')
const randomBytes = util.promisify(crypto.randomBytes)

const keyBuffer = await randomBytes(32)
const databaseKey = keyBuffer.toString('hex') // toute chaîne est valide pour databaseKey
```

Utilisez une `databaseKey` différente pour chaque session utilisateur (pas par appareil) afin que chaque session ait sa propre base de données chiffrée. Changer la clé lors d'une nouvelle session signifie qu'un nouveau `databasePath` doit également être utilisé.

### Étape 2 — Initialiser le SDK avec `databasePath` et `databaseKey`

Passez à la fois `databaseKey` et un `databasePath` unique lors de la construction de l'instance du SDK. Incluez l'ID de session dans le chemin pour garantir l'unicité par session :

```javascript
import SealdSDK from '@seald-io/sdk'

const seald = SealdSDK({
  appId,
  apiURL,
  databaseKey,                                      // fourni par votre backend
  databasePath: `seald-session-${idSession}`        // unique par session
})
await seald.initialize()
```

Le SDK lit automatiquement la base de données chiffrée depuis le stockage local du navigateur au démarrage et écrit les modifications. Aucun code supplémentaire n'est nécessaire.

:::warning
Si `databasePath` est défini mais `databaseKey` est omis, le SDK utilise une clé de chiffrement fixe dérivée de l'`appId`. C'est non sécurisé et doit être évité en production.
:::

### Étape 3 — Utiliser `databaseRawKey` pour une initialisation plus rapide (optionnel)

La `databaseKey` est dérivée via scrypt au démarrage, ce qui ajoute quelques centaines de millisecondes. Si votre backend stocke 64 octets aléatoires cryptographiquement sûrs (encodés en Base64), vous pouvez les passer comme `databaseRawKey` pour contourner la dérivation :

```javascript
// Backend : générer une clé brute
const rawKeyBuffer = await randomBytes(64)
const databaseRawKey = rawKeyBuffer.toString('base64')
// Stocker databaseRawKey dans la session de l'utilisateur

// Frontend
const seald = SealdSDK({
  appId,
  apiURL,
  databaseRawKey,                                // exactement 64 octets, encodés en Base64
  databasePath: `seald-session-${idSession}`
})
await seald.initialize()
```

> [!INFO]
> `databaseRawKey` doit être exactement 64 octets encodés en Base64, provenant d'une source aléatoire cryptographiquement sûre. En cas de doute, utilisez `databaseKey` — elle accepte n'importe quelle chaîne et gère automatiquement la dérivation.
