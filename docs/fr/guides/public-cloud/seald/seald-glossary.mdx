## Objectif

Ce glossaire est une référence pour tous les termes techniques utilisés dans la documentation Seald. Consultez-le chaque fois que vous rencontrez un concept inconnu lors de l'intégration du SDK Seald.

Pour une introduction de haut niveau à Seald, consultez la [présentation de Seald](/guides/public-cloud/seald/seald-overview). Pour les instructions d'installation, consultez [Installer le SDK Seald](/guides/public-cloud/seald/seald-install-sdk).

## Glossaire

### Configuration du SDK

| Terme | Définition |
|-------|-----------|
| **appId** | UUID qui identifie de façon unique votre application Seald. Il est public et peut être inclus en toute sécurité dans le code frontend. Vous le récupérez depuis le tableau de bord d'administration Seald. |
| **apiURL** | URL du serveur API Seald. Requis pour les environnements de staging ; peut être omis en production car le SDK utilise par défaut l'URL de production. |
| **keyStorageURL** | URL du serveur SSKS (voir [SSKS](#stockage-didentité)). Requis pour les environnements de staging ; peut être omis en production. |
| **JWTSecretId** | Identifiant d'un secret JWT, utilisé comme champ `iss` (émetteur) dans les jetons signés. Il est public et peut être inclus dans le code frontend. Vous le récupérez depuis le tableau de bord d'administration Seald. |
| **JWTSecret** | Valeur secrète utilisée pour signer les JWT (algorithme HS256). Cette valeur doit rester exclusivement côté serveur et ne doit jamais être exposée dans le code frontend ou dans des bundles côté client. |

### Modèle d'identité

| Terme | Définition |
|-------|-----------|
| **Identité Seald** | Clé privée cryptographique générée localement sur l'appareil d'un utilisateur. Elle représente la capacité de l'utilisateur à chiffrer et déchiffrer des données. Toutes les identités appartenant au même utilisateur sont liées par une chaîne de signatures cryptographiques. |
| **sealdId** | Identifiant unique d'une identité Seald. Vous l'utilisez pour désigner les destinataires lors de la création ou de la gestion des sessions de chiffrement. |
| **Sous-identité** | Identité supplémentaire pour le même utilisateur, généralement une par appareil. Elle est créée à partir d'une identité existante, peut déchiffrer tout ce que l'identité parente peut déchiffrer, et est liée à celle-ci via une chaîne de signatures cryptographiques. |
| **Connecteur** | Identifiant personnalisé au niveau de l'application, attaché à une identité Seald, au format `${IDENTIFIER}@${APP_ID}`. Les connecteurs permettent à votre application de rechercher des identités Seald à l'aide de vos propres identifiants utilisateur plutôt que des valeurs `sealdId`. |
| **signupJWT** | JWT de courte durée avec le scope `JOIN_TEAM` (permission `3`), généré par votre backend et passé à `sdk.initiateIdentity()`. Il autorise la création d'une nouvelle identité Seald pour un utilisateur. |

### Stockage d'identité

| Terme | Définition |
|-------|-----------|
| **SSKS (Seald SDK Key Storage)** | Serveur géré par Seald pour stocker de façon sécurisée les identités utilisateur chiffrées. Il agit comme un séquestre de clés qui ne peut pas reconstruire les identités seul — le matériel de déchiffrement reste avec l'utilisateur ou le backend applicatif. |
| **Protection par mot de passe** (`@seald-io/sdk-plugin-ssks-password`) | Mode de stockage d'identité dans lequel l'identité est chiffrée avec un dérivé du mot de passe de l'utilisateur et stockée sur SSKS. La réinitialisation du mot de passe n'est pas possible sans perte de données permanente. |
| **Règle des deux hommes (2MR)** (`@seald-io/sdk-plugin-ssks-2mr`) | Mode de stockage d'identité dans lequel l'identité est divisée : une part (`twoManRuleKey`) est détenue par le backend applicatif, et l'autre (`encryptedIdentity`) est détenue par SSKS. Aucune des deux parties ne peut reconstruire l'identité seule. |
| **twoManRuleKey** | Clé secrète détenue par le backend applicatif en mode 2MR. Elle doit comporter au moins 64 octets de données aléatoires cryptographiquement sûres. Utilisez `rawTwoManRuleKey` pour ignorer la dérivation scrypt. |
| **rawTwoManRuleKey** | Variante de `twoManRuleKey` qui ignore la dérivation scrypt (plus rapide). Elle doit être l'encodage Base64 d'exactement 64 octets aléatoires cryptographiquement sûrs. |
| **authFactor** | Identifiant utilisateur permettant de s'authentifier auprès de SSKS en mode 2MR. Généralement une adresse e-mail (`type: 'EM'`) ou un numéro de téléphone (`type: 'SMS'`). La valeur doit être normalisée avant utilisation. |
| **challenge** | Code à usage unique envoyé à l'`authFactor` de l'utilisateur (par e-mail ou SMS) lors de l'authentification 2MR. Il est valide pendant 6 heures et ne doit jamais être transmis au backend applicatif. |
| **databaseKey** | Clé symétrique générée et détenue par le backend applicatif, utilisée pour chiffrer la base de données locale persistante du SDK dans le navigateur ou sur l'appareil. |
| **databaseRawKey** | Variante de `databaseKey` qui ignore la dérivation scrypt. Elle doit être l'encodage Base64 d'exactement 64 octets aléatoires cryptographiquement sûrs. |
| **Export/import manuel** | Export direct d'une identité sous forme de Buffer via `sdk.exportIdentity()`, et import correspondant via `sdk.importIdentity()`. L'application est responsable de la sécurisation du buffer exporté. |

### Chiffrement

| Terme | Définition |
|-------|-----------|
| **Session de chiffrement** | Clé symétrique partagée créée par `sdk.createEncryptionSession()`. Tous les messages et fichiers chiffrés avec la même session partagent la même clé et la même liste de destinataires. Chaque session est identifiée par un `sessionId`. |
| **sessionId** | Identifiant unique d'une session de chiffrement. Il n'est pas secret et peut être stocké dans votre base de données applicative pour récupérer la session ultérieurement. |
| **Destinataire** | Utilisateur ou groupe dont l'identité Seald est listée lors de la création ou de la mise à jour d'une session de chiffrement. Seuls les destinataires peuvent déchiffrer les données chiffrées avec cette session. |
| **encryptForSelf** | Option de `createEncryptionSession()` qui vaut `true` par défaut. Lorsqu'elle est définie à `false`, l'identité de l'utilisateur courant n'est pas directement ajoutée comme destinataire — utile lorsque l'utilisateur est déjà membre d'un groupe qui est lui-même destinataire. |
| **Droits** | Permissions par destinataire sur une session de chiffrement : `read` (peut déchiffrer), `forward` (peut ajouter des destinataires), et `revoke` (peut révoquer des destinataires et fermer la session). Par défaut, seul le créateur de la session dispose des droits `revoke`. |

### Groupes

| Terme | Définition |
|-------|-----------|
| **Groupe** | Collection nommée d'identités Seald. Vous chiffrez pour le groupe une seule fois, et tous les membres actuels peuvent déchiffrer. Les membres peuvent être ajoutés ou supprimés, et la clé de groupe peut être renouvelée après la suppression d'un membre sensible. |
| **Administrateur de groupe** | Membre du groupe ayant la permission d'ajouter ou de supprimer des membres, de modifier le statut d'administrateur et de renouveler la clé de groupe. |
| **renewGroupKey** | Opération qui fait tourner la clé symétrique du groupe. Vous devriez l'appeler après la suppression d'un membre sensible pour vous assurer qu'il ne peut plus déchiffrer les futures données chiffrées pour le groupe. |

### Autorisation JWT

| Terme | Définition |
|-------|-----------|
| **JWT (JSON Web Token)** | Jeton signé HS256 généré par votre backend et passé aux fonctions du SDK qui nécessitent une autorisation. Les scopes contrôlent quelles opérations chaque jeton autorise. |
| **Scope** | Permission encodée dans un JWT. Les scopes clés sont : `3` = `JOIN_TEAM` (création d'identité), `4` = `ADD_CONNECTOR` (ajout d'un connecteur à une identité), `0` = `ANONYMOUS_CREATE_SESSION`, `1` = `ANONYMOUS_FIND_KEYS`, et `5` = `ANONYMOUS_FIND_SYMENCKEY`. |
| **jti (JWT ID)** | Nonce unique inclus dans chaque JWT, utilisé pour prévenir les attaques par rejeu. Il doit être globalement unique par jeton. |

### Fonctionnalités avancées

| Terme | Définition |
|-------|-----------|
| **SDK anonyme** (`@seald-io/sdk-anonymous`) | Package permettant à un service backend de chiffrer des données sans identité Seald. Il utilise des JWT avec des scopes anonymes pour l'autorisation. |
| **TmrAccess (Two-Man Rule Access)** | Mécanisme permettant d'accorder à un utilisateur l'accès à une session de chiffrement via un challenge 2MR (e-mail ou SMS), sans que l'utilisateur ait encore une identité Seald. |
| **SymEncKey (Clé de chiffrement symétrique)** | Mécanisme permettant d'accéder à une session de chiffrement à l'aide d'un secret partagé — un mot de passe ou une paire de clés brutes — sans être un destinataire direct basé sur une identité. |
| **GroupTMRTemporaryKey** | Mécanisme permettant à un administrateur de groupe d'inviter un utilisateur à rejoindre un groupe via un challenge 2MR, avant que l'utilisateur ait créé une identité Seald. |
| **Outil de réversibilité** (`@seald-io/reversibility-tools`) | Package npm permettant le déchiffrement en masse de toutes les données stockées dans une application Seald, à l'aide d'exports fournis par le support Seald. |

### Environnements

| Terme | Définition |
|-------|-----------|
| **Staging** | Environnement de test sur un seul serveur, hébergé sur `dashboard.staging-0.seald.io`. Sans SLA et sans garantie de persistance des données. Prend en charge `fake_otp: true` pour les tests sans envoi de vrais challenges par e-mail ou SMS. |
| **Production** | Environnement répliqué à haute disponibilité avec sauvegardes régulières. L'option `fake_otp` est bloquée en production. Contactez Seald pour créer un compte de production. |
| **fake_otp** | Fonctionnalité de test disponible uniquement en staging. Lorsqu'elle est définie à `true` dans l'appel API backend SSKS, aucun message de challenge n'est envoyé ; la valeur de challenge attendue est fixée à `'aaaaaaaa'`. |
