## Objectif

Ce guide recense les erreurs et comportements inattendus les plus fréquents lors de l'intégration du SDK Seald et explique comment les résoudre.

## Prérequis

- Le SDK Seald installé. Consultez le guide [Installer le SDK Seald](/guides/public-cloud/seald/seald-install-sdk).
- Accès aux logs du SDK et de votre backend.

## En pratique

### Erreur : `JWT already used` ou `Invalid JWT`

**Symptôme :** `initiateIdentity` ou `saveIdentity` échoue avec une erreur JWT invalide ou déjà utilisé.

**Causes possibles :**
- Le JWT a déjà été consommé (un `jti` identique a été utilisé une fois).
- L'horloge du serveur backend n'est pas synchronisée : le champ `iat` du JWT dépasse la tolérance de quelques secondes.
- Le `JWTSecretId` ou `JWTSecret` ne correspondent pas à ceux configurés dans le tableau de bord Seald.

**Solution :**
- Vérifiez que chaque JWT d'inscription est généré avec un `jti` unique (UUID v4 recommandé).
- Synchronisez l'horloge du serveur backend avec NTP.
- Vérifiez la correspondance entre vos variables d'environnement et les secrets affichés dans le tableau de bord Seald.

---

### Erreur : `Request throttled, retry after {N}s`

**Symptôme :** `ssksPassword.retrieveIdentity` retourne une erreur de limitation de débit.

**Cause :** Le mot de passe a été saisi incorrectement plusieurs fois de suite, déclenchant la protection anti-brute-force de SSKS.

**Solution :** Attendez la durée indiquée dans le message d'erreur avant de réessayer. Informez l'utilisateur du délai restant dans votre interface.

---

### Erreur : `406 Not Acceptable` sur `challenge_send`

**Symptôme :** L'appel backend à `POST /tmr/back/challenge_send/` retourne 406.

**Cause :** `fake_otp: true` est présent dans le corps de la requête et l'environnement est la production.

**Solution :** Retirez `fake_otp: true`. Cette option est réservée au staging. Consultez le guide [Passer du serveur de staging à la production](/guides/public-cloud/seald/seald-staging-to-production).

---

### Comportement : L'utilisateur doit ressaisir son identité à chaque session

**Symptôme :** L'identité est perdue au rechargement de la page ou à la réouverture du navigateur.

**Cause :** La base de données locale persistante n'est pas activée (comportement par défaut : stockage en mémoire volatile).

**Solution :** Activez la base de données persistante en fournissant `databasePath` et `databaseKey` à l'initialisation du SDK. Consultez le guide [Configurer une base de données locale persistante](/guides/public-cloud/seald/seald-local-database).

---

### Comportement : Initialisation du SDK lente

**Symptôme :** L'appel à `seald.initialize()` ou `createSubIdentity()` prend plusieurs secondes.

**Cause :** La génération de clés cryptographiques (RSA 4096) est coûteuse en CPU.

**Solution :** Pré-générez les clés en arrière-plan avant d'en avoir besoin :

```javascript
seald.preGenerateIdentityKeys(1)
// … autres tâches …
const { subIdentity } = await seald.createSubIdentity() // plus rapide
```

De même, si vous utilisez `databaseKey` (chaîne arbitraire), elle est dérivée via scrypt à chaque démarrage. Utilisez `databaseRawKey` (64 octets aléatoires en Base64) pour éviter cette dérivation. Consultez le guide [Configurer une base de données locale persistante](/guides/public-cloud/seald/seald-local-database).

---

### Erreur : Impossible de déchiffrer après suppression d'un membre d'un groupe

**Symptôme :** Un utilisateur récemment supprimé d'un groupe peut encore déchiffrer des messages.

**Cause :** Le renouvellement des clés de groupe n'a pas été effectué après la suppression.

**Solution :** Après chaque `removeGroupMembers`, appelez `renewGroupKey` depuis une instance d'administrateur :

```javascript
await instanceSDKAdmin.renewGroupKey(group.id)
```

---

### Comportement : Récupération d'identité qui échoue en tests automatisés

**Symptôme :** `ssksPassword.retrieveIdentity` ou `ssks2MR.retrieveIdentity` échoue lorsqu'il est appelé en parallèle pour le même utilisateur.

**Cause :** Deux récupérations simultanées pour le même utilisateur peuvent entrer en conflit côté SSKS.

**Solution :** Attendez qu'une récupération soit entièrement terminée avant d'en démarrer une autre pour le même utilisateur. Dans les tests automatisés, séquentialisez ces appels.

---

### Problème : Webpack ne trouve pas les modules du SDK

**Symptôme :** Erreurs de type `Module not found` ou `Can't resolve` en environnement navigateur.

**Cause :** Le SDK Seald requiert certains polyfills Node.js qui ne sont pas inclus par défaut dans Webpack 5.

**Solution :** Ajoutez les `resolve.fallback` nécessaires dans votre configuration Webpack. Consultez le guide [Installer le SDK Seald](/guides/public-cloud/seald/seald-install-sdk) pour la configuration complète.
