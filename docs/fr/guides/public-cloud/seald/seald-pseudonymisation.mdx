## Objectif

Ce guide explique comment identifier les données éligibles au chiffrement côté client et présente trois stratégies pour rendre éligibles des données qui, a priori, nécessitent un traitement côté serveur : le déport de fonctionnalités côté client, l'octroi temporaire de droits, et la pseudonymisation.

## Prérequis

- Une compréhension des principes du chiffrement de bout en bout. Consultez le guide [Qu'est-ce que Seald](/guides/public-cloud/seald/seald-overview).
- Le SDK Seald installé et initialisé. Consultez le guide [Installer le SDK Seald](/guides/public-cloud/seald/seald-install-sdk).

## En pratique

### Stratégie 1 — Déporter des fonctionnalités côté client

Certaines fonctionnalités historiquement implémentées côté serveur peuvent être déplacées côté client, notamment grâce aux navigateurs modernes et aux performances des appareils. Le serveur n'a alors plus besoin d'accéder aux données en clair.

**Exemples concrets :**

- **Génération de fichier PDF** : au lieu d'utiliser FPDF côté serveur, utilisez une bibliothèque comme [pdf-lib](https://pdf-lib.js.org/) directement dans le navigateur. Le PDF est généré et chiffré avec Seald avant d'être envoyé au serveur, qui ne reçoit que la version chiffrée.

- **Recherche dans du texte** : pour un corpus de taille raisonnable (historique de messages, par exemple), l'index de recherche peut être généré côté client avec une bibliothèque comme [minisearch](https://github.com/lucaong/minisearch). L'index est ensuite chiffré et stocké sur le serveur ; le backend ne voit jamais le texte en clair.

### Stratégie 2 — Octroi temporaire de droits

Quand une fonctionnalité nécessite absolument l'accès aux données côté serveur, il est possible d'octroyer *temporairement* des droits de déchiffrement à ce serveur pour la durée de l'opération, puis de les révoquer immédiatement après.

Cette stratégie limite la fenêtre d'exposition : en cas de compromission du serveur, seules les données accessibles pendant l'attaque sont exposées, pas les données déjà révoquées.

**Exemple — Archivage chiffré après analyse :**

1. Le serveur reçoit la donnée en clair et effectue son analyse (OCR, machine learning, etc.).
2. Le serveur chiffre immédiatement la donnée avec l'[Anonymous SDK](/guides/public-cloud/seald/seald-anonymous-encryption) pour les utilisateurs habilités.
3. La clé de chiffrement n'est pas conservée par le serveur.
4. Les utilisateurs déchiffrent côté client.

**Exemple — Octroi a posteriori pour une durée limitée :**

1. Le client octroie des droits à l'identité de service du backend via `session.addRecipients`.
2. Le backend déchiffre, effectue son traitement, rechiffre le résultat pour les utilisateurs habilités.
3. Le client révoque les droits du backend via `session.revokeRecipients`.

### Stratégie 3 — Pseudonymiser les données

La pseudonymisation consiste à diviser un jeu de données en deux sous-ensembles :

- **Données non identifiantes** : exploitées côté serveur pour les fonctionnalités métier.
- **Données identifiantes** : chiffrées côté client, accessibles uniquement aux personnes habilitées.

Un identifiant unique aléatoire (pseudonyme) lie les deux sous-ensembles, rendant l'opération réversible pour les personnes autorisées.

```javascript
// Côté client — lors de la saisie d'un formulaire
const pseudonyme = crypto.randomUUID()

// Données non identifiantes envoyées au serveur en clair
const donneesNonIdentifiantes = { pseudonyme, statut: 'actif', categorie: 'A' }

// Données identifiantes chiffrées avec Seald pour les personnes habilitées
const donneesIdentifiantesChiffrees = await seald.encryptFile(
  Buffer.from(JSON.stringify({ pseudonyme, nom: 'Dupont', email: 'dupont@exemple.fr' }), 'utf8'),
  { sealdIds: [sealdIdResponsable] },
  { filename: `${pseudonyme}.json` }
)

// Envoyer les deux au serveur
await API.enregistrer({ donneesNonIdentifiantes, donneesIdentifiantesChiffrees })
```

> [!INFO]
> Cette stratégie est explicitement recommandée par le RGPD (article 32) comme mesure technique appropriée pour réduire les risques liés au traitement des données personnelles.
