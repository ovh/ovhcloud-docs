## Objectif

Ce guide documente les limites techniques connues et les contraintes d'utilisation du SDK Seald à prendre en compte lors de la conception et du déploiement de votre application.

## En pratique

### Limites liées aux identités

| Limite | Valeur | Note |
|--------|--------|------|
| Sous-identités par utilisateur | ~30 recommandées | Au-delà, les performances des opérations de chiffrement se dégradent |
| JWT d'inscription (`jti` requis) | 1 utilisation | Un JWT avec `jti` défini est à usage unique |
| Durée de validité d'un JWT | 10 min (par défaut) | Configurable via le champ `exp` |
| Format du `connector` | `${IDENTIFIANT}@${APP_ID}` | Type `AP` obligatoire |

:::warning
Avoir plusieurs dizaines de sous-identités pour un même utilisateur peut ralentir les opérations. Préférez réutiliser une identité stockée sur SSKS plutôt que d'en créer une nouvelle à chaque connexion.
:::

### Limites liées aux groupes

| Limite | Comportement |
|--------|-------------|
| Renouvellement de clé requis après suppression | `renewGroupKey` doit être appelé manuellement après chaque `removeGroupMembers` pour révoquer l'accès futur |
| Membres lors de la création | Au moins un membre et un administrateur — les deux listes doivent inclure l'utilisateur créateur |
| `setGroupAdmin` | Un groupe doit toujours avoir au moins un administrateur actif |

### Limites liées aux sessions de chiffrement

| Limite | Valeur | Note |
|--------|--------|------|
| Cache TTL | Configurable | Valeur `0` par défaut (cache désactivé), `-1` pour une conservation sans expiration |
| Format des messages chiffrés en mode `raw` | Pas de `sessionId` inclus | Le `sessionId` doit être stocké séparément pour récupérer la session |
| Révocation | Créateur de la session uniquement (par défaut) | Le droit `revoke` peut être accordé à d'autres destinataires |

### Limites liées au stockage local

| Limite | Valeur | Note |
|--------|--------|------|
| `databaseKey` | Toute chaîne | Dérivée via scrypt — ajoute ~quelques centaines de ms au démarrage |
| `databaseRawKey` | Exactement 64 octets encodés en Base64 | Contourne la dérivation scrypt pour une initialisation plus rapide |
| `createLocalStorageEncryptionSessionCache` | Navigateur uniquement | Nécessite `databasePath` + `databaseKey` |

:::warning
Si `databasePath` est défini sans `databaseKey`, le SDK utilise une clé de chiffrement fixe dérivée de l'`appId`. Cette configuration est non sécurisée et ne doit pas être utilisée en production.
:::

### Limites liées au chiffrement anonyme

| Limite | Note |
|--------|------|
| JWT de récupération des clés | Pas de `jti` recommandé — la requête peut être paginée (plusieurs appels API) |
| JWT de création de session | `jti` requis — usage unique |
| `owner` | Obligatoire pour la création de session anonyme |

### Limites liées aux SymEncKeys

| Limite | Note |
|--------|------|
| Disponibilité | SDK JavaScript uniquement — pas encore disponible sur Android, iOS, Flutter |
| Droits via SymEncKey | Gestion d'accès (`addRecipients`, `revokeRecipients`, etc.) non disponible — passez d'abord par `selfAddToEncryptionSessionWithSymEncKey` |

### Limites de l'environnement de staging

| Limite | Note |
|--------|------|
| Persistance des données | Non garantie — remise à zéro possible sans préavis |
| `fake_otp` | Disponible en staging uniquement — bloqué en production |
| Migration staging → production | Impossible — les données ne peuvent pas être migrées |

### Contraintes React Native

Les dépendances paires suivantes doivent être installées pour utiliser le SDK Seald en React Native :

| Package | Version |
|---------|---------|
| `@react-native-async-storage/async-storage` | `2.1.0` |
| `@seald-io/react-native-scrypt` | `1.2.3` |
| `react-native-quick-crypto` | `0.7.11` |
| `@craftzdog/react-native-buffer` | `6.0.5` |
| `react-native-quick-base64` | `2.1.2` |
| `readable-stream` | `4.7.0` |
