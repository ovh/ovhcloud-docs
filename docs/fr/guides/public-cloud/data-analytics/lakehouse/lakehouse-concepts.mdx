## Objectif

**Ce guide décrit les éléments qui composent un Lakehouse et la façon dont ils s'articulent.**

## En pratique

### Le Lakehouse et ses données

Un **Lakehouse** est situé dans une région de votre projet Public Cloud. Il conserve vos données dans des tables **Apache Iceberg**, un format de table ouvert, dans un bucket OVHcloud Object Storage géré pour vous. Plusieurs moteurs peuvent lire et écrire les mêmes tables en même temps : une table écrite en Python est immédiatement visible en SQL, et inversement.

Les données sont organisées sur trois niveaux :

| Niveau | Description | Exemple |
|---|---|---|
| **Catalogue** | Conteneur de premier niveau. Les moteurs se connectent à un catalogue par son nom. Un Lakehouse peut contenir plusieurs catalogues, par exemple un par équipe ou par environnement. | `sales` |
| **Schéma** | Regroupe des tables à l'intérieur d'un catalogue (un *namespace* dans Iceberg). | `raw` |
| **Table** | Une table Iceberg, créée en SQL ou avec un client Iceberg. Chaque modification est conservée sous forme de snapshot de la table. | `orders` |

Vous créez les catalogues et les schémas dans la console OVHcloud ou par l'API. Les tables sont créées par vos moteurs (SQL, Python, DuckDB, etc.).

### Points d'accès

La section **Détails de connexion** de l'onglet **Vue d'ensemble** liste les moyens d'accéder aux données :

- **Catalogue Iceberg REST** : pour tout outil compatible avec le protocole Iceberg REST (PyIceberg, DuckDB, Spark, Trino, etc.). Les requêtes indiquent le realm du Lakehouse dans l'en-tête `Polaris-Realm`.
- **Point d'accès SQL** : un point d'accès compatible Trino (JDBC ou HTTPS) fourni avec le Lakehouse. Chaque catalogue y est exposé sous son propre nom de catalogue SQL, indiqué dans les détails de connexion.
- **S3**<sup>1</sup> : le bucket qui stocke les fichiers des tables, pour les outils qui les lisent ou les écrivent directement.
- **Console de données** : une interface web pour parcourir les catalogues, lancer des requêtes SQL, charger des fichiers et consulter l'historique des requêtes.

### Utilisateurs, rôles et identifiants

L'accès aux données se gère à l'intérieur du Lakehouse :

- Un **utilisateur** est une personne (type **Utilisateur**) ou une application (type **Compte de service**). Les utilisateurs peuvent être réunis en **groupes**.
- Un **rôle** donne des privilèges sur les données : lecture (`BROWSE`, `SELECT`), écriture (`INSERT`, `UPDATE`, `DELETE`) et structure (`CREATE_TABLE`, `ALTER`, `DROP`). Six rôles sont fournis (**Lakehouse Admin**, **Data Owner**, **Data Editor**, **Data Viewer**, **Metadata Viewer**, **User Admin**) et vous pouvez créer des rôles personnalisés.
- Un rôle est **attribué** à un utilisateur, un compte de service ou un groupe. Un rôle par défaut peut être limité à un catalogue lors de son attribution.
- Un **identifiant** est un ID client et un secret client qui agissent avec les droits des rôles de l'utilisateur. Il peut aussi inclure une clé d'accès S3. Un identifiant expire au bout de 10 minutes à 90 jours par l'API (7, 30, 60 ou 90 jours dans la console OVHcloud) et peut être révoqué à tout moment.

:::info
Les rôles du Lakehouse ne contrôlent que l'accès aux données. La gestion du Lakehouse lui-même (créer des catalogues, des utilisateurs ou des rôles, attribuer des rôles) relève d'OVHcloud IAM, comme pour toute autre ressource de votre projet.

:::

### Calcul

Les requêtes SQL s'exécutent sur un **pool de calcul** :

- Par défaut, elles s'exécutent sur le **pool de calcul partagé** de la région.
- Vous pouvez ajouter un **pool de calcul dédié**, dimensionné selon vos besoins et réservé à votre Lakehouse. Il se met en veille après une période sans requête et se réveille à la requête suivante.

L'adresse SQL du Lakehouse reste la même dans les deux cas. Consultez le guide « [Lakehouse - Utiliser un pool de calcul dédié](/guides/public-cloud/data-analytics/lakehouse/lakehouse-compute-pools) ».

Les outils connectés au catalogue Iceberg REST (Python, DuckDB, etc.) utilisent leur propre capacité de calcul, pas un pool de calcul.

### Accès réseau

Par défaut, toute adresse peut joindre le Lakehouse, à condition que le client dispose d'un identifiant valide. Vous pouvez restreindre l'accès à une liste d'adresses IP. Consultez le guide « [Lakehouse - Restreindre l'accès réseau](/guides/public-cloud/data-analytics/lakehouse/lakehouse-network-access) ».
