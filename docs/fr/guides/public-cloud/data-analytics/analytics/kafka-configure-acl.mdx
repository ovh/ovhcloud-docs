## Objectif

Apache Kafka est une plateforme open source distribuée de streaming d'événements, conçue pour le traitement de données en temps réel et à grande échelle, avec une scalabilité et une durabilité élevées ainsi qu'une faible latence.

Un utilisateur Kafka n'a aucun accès à vos topics tant que vous ne lui en accordez pas avec une liste de contrôle d'accès (ACL). Ce guide explique comment créer des ACL de topic depuis l'espace client OVHcloud ou l'API OVHcloud, et des ACL Schema Registry depuis l'API OVHcloud.

## Prérequis

- Disposer d'un [projet Public Cloud](/links/public-cloud/public-cloud) dans votre compte OVHcloud
- Disposer d'un [service Kafka](/guides/public-cloud/data-analytics/analytics/kafka-create-cluster) [acceptant les connexions entrantes](/guides/public-cloud/data-analytics/analytics/kafka-incoming-connections), avec au moins un utilisateur et un topic
- Disposer d'un accès à l'[API OVHcloud](/guides/manage-and-operate/api/first-steps) (pour les étapes via l'API)

## En pratique

### Accès par défaut

À la création de votre service, l'utilisateur admin préconfiguré `avnadmin` dispose de la permission `admin` sur tous les topics (`*`) et peut écrire dans le Schema Registry une fois celui-ci activé.

Tout utilisateur que vous créez ensuite n'a **aucun accès**. Tant que vous n'ajoutez pas d'ACL pour cet utilisateur, la production ou la consommation de messages sur un topic échoue avec l'erreur `TOPIC_AUTHORIZATION_FAILED`.

Nous vous recommandons de créer un utilisateur par application et de ne lui accorder que les topics et la permission dont elle a besoin.

### Permissions

Pour un utilisateur et un topic (ou tous les topics avec `*`), vous pouvez accorder l'une des permissions suivantes :

- **admin** : accès complet au topic, y compris sa gestion
- **read** : consommer les messages du topic
- **write** : produire des messages dans le topic
- **readwrite** : produire et consommer des messages

La liste des permissions disponibles sur votre service est également renvoyée par l'API :

<Api version="v1" section="/cloud" method="GET" route={"/cloud/project/\{serviceName\}/database/kafka/\{clusterId\}/permissions"} />

```json
{
  "names": ["admin", "read", "write", "readwrite"],
  "topic": ["admin", "read", "write", "readwrite"],
  "schemaRegistry": ["schema_registry_read", "schema_registry_write"]
}
```

    ```json
    {
      "username": "app-orders",
      "topic": "orders",

    }
    ```

    L'API renvoie l'ACL avec son identifiant :

    ```json
    {
      "id": "1f2e3d4c-5b6a-4789-9abc-def012345678",
      "username": "app-orders",
      "topic": "orders",
      "permission": "readwrite"
    }
    ```

    Listez et supprimez les ACL :

    <Api version="v1" section="/cloud" method="GET" route={"/cloud/project/\{serviceName\}/database/kafka/\{clusterId\}/topicAcl"} />

    <Api version="v1" section="/cloud" method="DELETE" route={"/cloud/project/\{serviceName\}/database/kafka/\{clusterId\}/topicAcl/\{aclId\}"} />

    :::info
    Les anciennes routes `/acl` gèrent les mêmes ACL que les routes `/topicAcl`.

### Configurer les ACL Schema Registry avec l'API

Une fois le [Schema Registry activé](/guides/public-cloud/data-analytics/analytics/kafka-enable-schema-registry), un utilisateur a également besoin d'une ACL Schema Registry pour lire ou enregistrer des schémas.

Deux permissions sont disponibles :

- **schema_registry_read** : lire les schémas
- **schema_registry_write** : lire et enregistrer des schémas

La ressource est :

- `Subject:<nom du subject>`, par exemple `Subject:orders-value`, ou `Subject:*` pour tous les subjects ;
- `Config:`, pour la configuration globale de compatibilité du Schema Registry.

Par défaut, `avnadmin` dispose de la permission `schema_registry_write` sur `Config:` et sur `Subject:*`.

Créez une ACL Schema Registry :

<Api version="v1" section="/cloud" method="POST" route={"/cloud/project/\{serviceName\}/database/kafka/\{clusterId\}/schemaRegistryAcl"} />

```json
{
  "username": "app-orders",
  "resource": "Subject:orders-value",
  "permission": "schema_registry_write"
}
```

Avec cette ACL, `app-orders` peut enregistrer des schémas pour le subject `orders-value`. Le Schema Registry se comporte ainsi pour tout utilisateur :

- sans aucune ACL Schema Registry, chaque requête renvoie `401 Unauthorized` ;
- un subject non couvert par ses ACL est signalé comme introuvable (`404`).

Listez et supprimez les ACL Schema Registry :

<Api version="v1" section="/cloud" method="GET" route={"/cloud/project/\{serviceName\}/database/kafka/\{clusterId\}/schemaRegistryAcl"} />

<Api version="v1" section="/cloud" method="DELETE" route={"/cloud/project/\{serviceName\}/database/kafka/\{clusterId\}/schemaRegistryAcl/\{aclId\}"} />
