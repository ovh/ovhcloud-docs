## Objectif

Public Cloud Databases d'OVHcloud peut être déployé selon différentes architectures pour répondre à des besoins variés en matière de disponibilité et de résilience. Ce guide vous accompagne spécifiquement dans la migration de votre service de base de données existant, d'une configuration à une seule zone de disponibilité (1 AZ) vers une architecture à 3 AZ (trois zones de disponibilité). Vous découvrirez les étapes détaillées pour réaliser ce transfert, garantissant une haute disponibilité et une meilleure tolérance aux pannes pour vos applications critiques.

## Prérequis

- Un [projet Public Cloud](/links/public-cloud/public-cloud) dans votre compte OVHcloud
- Un accès à l'<ApiLink>API OVHcloud</ApiLink>
- Un service de base de données existant déployé dans une seule zone de disponibilité (1 AZ)
- Une région 3 AZ activée dans votre projet Public Cloud

## Pourquoi passer à une architecture 3 AZ ?

La migration de votre service de base de données vers un déploiement 3 AZ améliore considérablement sa résilience, sa haute disponibilité et ses capacités de reprise après sinistre. Dans une configuration 3 AZ, à condition que votre service s'exécute sur plusieurs nœuds, vos données sont répliquées de façon synchrone sur trois zones de disponibilité distinctes au sein d'une même région. Cette architecture garantit qu'en cas de panne dans une zone, votre service de base de données peut basculer automatiquement vers une autre zone opérationnelle avec un temps d'indisponibilité minimal et sans perte de données.

Pour plus d'informations sur les modes de déploiement et leurs spécifications techniques, veuillez consulter notre guide dédié : Comparaison des modes de déploiement de Public Cloud Databases - Comprendre les architectures 3 AZ / 1 AZ.

Voici la liste des régions actuellement prises en charge en 1 AZ et 3 AZ pour les services de base de données :

## Réversibilité

La migration d'une région à AZ unique vers une région Multi-AZ est réversible — les services peuvent être migrés de nouveau vers une région à AZ unique.

## En pratique

### Déplacer un service de base de données vers une architecture 3 AZ

<Tabs>
<Tab label="Depuis la console OVHcloud">

Dans le menu de gauche de votre projet Public Cloud, cliquez sur votre moteur sous **Bases de données**, puis sur le nom de votre service de base de données. Ouvrez l'onglet <code className="action">Sauvegardes</code>.

Cliquez sur le bouton <code className="action">...</code> de la sauvegarde à partir de laquelle vous souhaitez dupliquer le service, puis sur <code className="action">Dupliquer</code>. Le panneau **Dupliquer un cluster** s'ouvre.

Saisissez le **Nom du nouveau cluster**. Sous **Source de la copie**, conservez **À partir d’une sauvegarde** et sélectionnez la sauvegarde.

Sous **Configuration du nouveau cluster**, sélectionnez une **région 3 AZ** sous **Région**, une **Offre**, le **Type de nœud** qui hébergera le service, les **Nœuds** et la capacité de **Stockage**.

Les restrictions IP du service d'origine sont appliquées au nouveau service. Vous pourrez les vérifier une fois le service créé, dans la section **Restrictions d’IP** de son onglet <code className="action">Configuration</code>.

Vérifiez le prix estimé en bas du panneau, puis cliquez sur <code className="action">Créer la copie</code>.

</Tab>
<Tab label="Depuis l'API OVHcloud">

:::info
Pour interagir avec vos services Public Cloud Databases via l'API OVHcloud, assurez-vous d'avoir d'abord maîtrisé les bases en consultant notre guide : Public Cloud Databases - Prise en main des API.
:::

Pour retrouver l'identifiant de sauvegarde d'un service, utilisez l'appel API suivant :

<Api version="v1" section="/cloud" method="GET" route={"/cloud/project/\\{serviceName\\}/database/postgresql/\\{clusterId\\}/backup"} />

Cet appel récupère la liste des sauvegardes du service concerné. Elles sont classées de la plus récente à la plus ancienne.

Si vous souhaitez consulter les informations d'une sauvegarde en particulier, vous pouvez utiliser cet appel API :

<Api version="v1" section="/cloud" method="GET" route={"/cloud/project/\\{serviceName\\}/database/postgresql/\\{clusterId\\}/backup/\\{backupId\\}"} />

Pour créer votre nouveau service à partir d'une sauvegarde, utilisez l'appel API suivant :

<Api version="v1" section="/cloud" method="POST" route={"/cloud/project/\\{serviceName\\}/database/postgresql"} />

Voici un exemple de `body` pour cet appel API :

:::

  },

### Valider le déploiement

Une fois votre nouveau service de base de données 3 AZ provisionné avec succès, il est essentiel de valider son déploiement et de vous assurer que vos applications peuvent s'y connecter.

1. Testez la connexion à votre nouveau service :
    1. Utilisez un client de base de données (par exemple, psql pour PostgreSQL, mysql pour MySQL) ou un script simple pour vérifier que vous pouvez vous connecter à l'endpoint du nouveau service 3 AZ à l'aide de ses identifiants.
    2. Confirmez que vos données ont bien été migrées et sont accessibles.
2. Configurez votre application pour utiliser le nouveau service :
    1. Mettez à jour les fichiers de configuration ou les variables d'environnement de votre application pour pointer vers la chaîne de connexion du nouveau service de base de données 3 AZ (hôte, port, nom d'utilisateur, mot de passe).
    2. Redémarrez votre application pour appliquer les modifications.
    3. Testez en profondeur le fonctionnement de votre application pour vous assurer qu'elle fonctionne correctement avec le nouvel endpoint de base de données.

### Nettoyage

Une fois que vous avez pleinement validé le bon fonctionnement de votre application avec le nouveau service de base de données 3 AZ, et que vous êtes certain que toutes les données ont été transférées et sont accessibles, vous pouvez procéder à la suppression de l'ancien service 1 AZ.

Cette étape est essentielle pour éviter des coûts inutiles et conserver une infrastructure propre.

Suivez ces instructions pour supprimer l'ancien service 1 AZ :

<Tabs>
<Tab label="Depuis la console OVHcloud">

Ouvrez l'ancien service, puis son onglet <code className="action">Configuration</code>. Dans la section **Zone de danger**, cliquez sur <code className="action">Supprimer</code>, saisissez `TERMINATE` pour confirmer, puis cliquez sur <code className="action">Supprimer</code>. Si la protection contre la suppression est activée, désactivez-la d'abord dans la section **Configuration** du même onglet.

</Tab>
<Tab label="Depuis l'API OVHcloud">

Pour supprimer votre service, utilisez l'appel API suivant :

<Api version="v1" section="/cloud" method="DELETE" route={"/cloud/project/\\{serviceName\\}/database/postgresql/\\{clusterId\\}"} />
  </Tab>
</Tabs>
