## Objectif

Cette page présente les capacités techniques et les limitations de l'offre Public Cloud Analytics pour Kafka.

Nous améliorons continuellement nos offres. Vous pouvez suivre et proposer des idées à ajouter à notre roadmap sur [https://github.com/orgs/ovh/projects/16/views/5](https://github.com/orgs/ovh/projects/16/views/5).

## Capacités et limitations

### Régions prises en charge et multi-AZ

L'offre Public Cloud Analytics est disponible dans les régions suivantes :

- `BHS` (Beauharnois, Canada)
- `DE` (Francfort, Allemagne)
- `GRA` (Gravelines, France)
- `SBG` (Strasbourg, France)
- `SGP` (Singapour, Singapour)
- `EU-WEST-PAR` (Paris, France)
- `EU-SOUTH-MIL` (Milan, Italie)
- `UK` (Londres, Royaume-Uni)
- `WAW` (Varsovie, Pologne)
- `RBX` (Roubaix, France)
- `AP-SOUTH-MUM` (Mumbai, Inde)

### Versions de Kafka

L'offre Public Cloud Analytics prend en charge les versions Kafka suivantes :

- Kafka 3.8 (bientôt obsolète)
- Kafka 3.9
- Kafka 4.0
- Kafka 4.1

Veuillez consulter le [guide sur la politique de cycle de vie d'Analytics](/guides/public-cloud/data-analytics/analytics/lifecycle-policy) pour connaître les recommandations concernant les mises à niveau de version et les annonces de fin de vie des versions majeures. Vous pouvez également suivre le cycle de publication de Kafka sur leur page officielle : [https://kafka.apache.org/downloads](https://kafka.apache.org/downloads)

### Clients Kafka

Vous pouvez utiliser n'importe lequel des clients recommandés par Kafka pour accéder à votre cluster.

Kafka Connect et Kafka Mirrormaker 2 sont disponibles chez OVHcloud.

### Plans

Différents plans sont disponibles :

- **Business/Production** : 3 nœuds
- **Enterprise/Advanced** : 6 nœuds

Le plan choisi affecte le nombre de nœuds que votre cluster peut exécuter, le SLA, ainsi que quelques autres fonctionnalités comme la rétention des sauvegardes.

### Ressources matérielles

#### Stockage flexible

Vous pouvez augmenter le stockage de votre cluster jusqu'au maximum autorisé pour une référence donnée. Veuillez consulter le [guide sur le redimensionnement du stockage de votre cluster](/guides/public-cloud/data-analytics/analytics/resize-cluster-storage) pour plus d'informations.

#### Mise à niveau du modèle de nœud

Vous pouvez mettre à niveau le modèle de nœud de votre cluster pour augmenter vos ressources matérielles. Cette opération n'entraîne aucune interruption de service, mais sachez que vous ne pourrez pas revenir en arrière une fois le modèle de nœud modifié.

#### Type de disque

Le type de stockage disponible peut varier en fonction de la région où se trouve votre cluster : consultez la page [Disponibilité des produits Public Cloud](/links/public-cloud/regions-pci) pour plus d'informations sur la disponibilité des types de Block Storage selon la région. Ainsi, votre cluster peut reposer par exemple sur un Block Storage de type *High Speed* ou *High Speed Gen2*.

Par ailleurs, les caractéristiques de performance des différentes offres de stockage peuvent varier en fonction, par exemple, de la taille de stockage utilisée par votre cluster : *High Speed* peut offrir de meilleures performances IOPS que *High Speed Gen2* pour certaines tailles de disque. Consultez la page [Block Storage](/links/public-cloud/block-storage) pour plus d'informations sur ces caractéristiques de performance.

Public Cloud Analytics sélectionnera le type de disque le plus efficace pour votre cluster en fonction des paramètres de celui-ci.

#### Stockage effectif

La taille de disque indiquée ci-dessus correspond à la taille totale du disque de la machine sous-jacente. Cependant, une petite partie de cet espace est réservée à l'installation du système d'exploitation.

Nous mettons tout en œuvre pour éviter les situations de « disque plein » qui pourraient nuire à la santé du cluster. Par conséquent :

1. Lorsqu'un niveau d'utilisation du disque préoccupant est atteint, un e-mail d'avertissement est envoyé.
2. Lorsqu'un niveau d'utilisation du disque préoccupant est atteint, le service passe à l'état « DISK_FULL » et en mode « lecture seule », ce qui signifie qu'aucune écriture supplémentaire n'est possible.
3. Vous avez alors la possibilité de passer à un plan de service supérieur offrant davantage de stockage.

Consultez la [documentation sur la gestion des situations de « disque plein »](/guides/public-cloud/data-analytics/analytics/handling-disk-full) pour plus d'informations.

### Fonctionnalités

#### Network

Les clusters Kafka sont accessibles via un port aléatoire, attribué lors de la création du cluster. Une fois votre cluster à l'état **RUNNING**, l'URI de service affichera le port à utiliser.

Le réseau public ainsi que le réseau privé (vRack) peuvent être utilisés pour toutes les offres.

Le trafic entrant et sortant est inclus dans les plans de service et non facturé à l'usage.

L'adresse IP du service d'analytics est susceptible de changer périodiquement. Il est donc conseillé de ne pas se baser sur ces IPs pour une quelconque configuration, telle qu'une politique de connexion ou de trafic sortant. Utilisez plutôt l'enregistrement DNS fourni et mettez en œuvre des politiques de trafic sortant basées sur des CIDR pour une gestion réseau plus robuste et flexible.

##### Considérations relatives au réseau privé

Voici quelques éléments à prendre en compte lors de l'utilisation d'un réseau privé :

- Les ports réseau sont créés dans le réseau privé de votre choix. Par conséquent, d'autres opérations sur ce réseau peuvent être restreintes - par exemple, vous ne pourrez pas supprimer le réseau si vous n'avez pas préalablement arrêté les services Public Cloud Analytics.
- Lors d'une connexion depuis un sous-réseau externe, la passerelle IP OpenStack doit être activée sur le sous-réseau utilisé pour le service Analytics. Le client est responsable de toute autre configuration réseau personnalisée.
- Le dimensionnement du sous-réseau doit prendre en compte les nœuds de service, les autres services colocalisés dans le même sous-réseau, ainsi qu'une réserve d'adresses IP disponibles supplémentaires à des fins de maintenance. Un dimensionnement insuffisant des sous-réseaux peut entraîner des difficultés opérationnelles et des dysfonctionnements des services.
- Les annonces de routes des sous-réseaux OpenStack ne seront pas appliquées à vos services.
- Vous ne pouvez créer des services en réseau privé que si vous êtes le propriétaire d'origine du réseau. Vous ne pouvez pas créer de services en réseau privé sur un réseau partagé.

##### IPs autorisées

Une fois votre service opérationnel, vous pourrez spécifier des adresses IP (ou blocs CIDR) pour autoriser le trafic entrant. Jusque-là, votre service sera inaccessible.

#### Nombre maximal de connexions simultanées

Le nombre de connexions simultanées dans Public Cloud Analytics pour Kafka dépend de la mémoire totale disponible sur le nœud.
Nous autorisons environ 100 connexions par 4 Go de RAM, avec un plafond de 1000 connexions actives maximum.

Ainsi, par exemple, sur un serveur disposant de 7 Go de mémoire, vous obtiendrez environ 200 connexions, et avec 15 Go de mémoire, vous obtiendrez 400 connexions.

#### Schema registry

Le schema registry est pris en charge et peut être activé sur un service Kafka en cours d'exécution en définissant `schemaRegistry` sur `true` via un appel API :

#### Paramètres avancés

Vous pouvez personnaliser davantage votre Kafka en utilisant des paramètres avancés. Consultez la [documentation de référence sur les paramètres avancés](/guides/public-cloud/databases/kafka-advanced-parameters-references) pour plus d'informations sur les paramètres pris en charge.

#### Sauvegardes

Kafka est un outil de streaming. Nous ne sauvegardons pas les données Kafka.

#### Logs et métriques

Les logs et les métriques sont disponibles via le Control Panel et l'API. De plus, une intégration inter-services peut être configurée pour exploiter vos logs et métriques dans d'autres services Public Cloud Database. Vous pourrez alors consulter vos logs Kafka dans Opensearch et vos métriques dans le service Dashboards (les métriques doivent d'abord être exportées vers un moteur compatible avec les séries temporelles, tel que PostgreSQL). Consultez la [documentation sur l'intégration inter-services](/guides/public-cloud/databases/databases-cross-service-integration) pour plus d'informations.

- **Rétention des logs** : 1000 lignes de logs
- **Rétention des métriques** : 1 mois calendaire

Veuillez noter que si le service d'analytics est supprimé, les logs et métriques sont également automatiquement supprimés.

#### Utilisateurs et rôles

La création d'utilisateurs est possible via le Control Panel et l'API.

Vous pouvez spécifier un nom d'utilisateur pour chaque utilisateur. Par défaut, le rôle est **admin**.

#### Topics

La création de topics est possible via le Control Panel et l'API.

Pour chaque topic, vous pouvez spécifier :

- Un nom de topic ;
- Le facteur de réplication ;
- Le nombre de partitions ;
- La taille des partitions ;
- Le temps de rétention ;
- La réplication minimale synchronisée (in-sync) ;
- La politique de suppression.
