## Objectif

Les bases de données Public Cloud d'OVHcloud proposent différentes générations pour répondre à des besoins variés en matière de performance, de scalabilité et de fonctionnalités. Ce guide est spécifiquement conçu pour vous accompagner dans la migration de votre service de base de données existant de la **Gen 2** vers la **Gen 3**. Vous y découvrirez les étapes détaillées pour effectuer cette mise à niveau, en profitant de performances améliorées, de fonctionnalités enrichies et d'une meilleure fiabilité pour vos applications critiques.

## Prérequis

- Un [projet Public Cloud](/links/public-cloud/public-cloud) dans votre compte OVHcloud
- Un service de base de données Gen 2 existant et déployé
- Un accès à l'<ApiLink>API OVHcloud</ApiLink> (facultatif)

## Pourquoi migrer vers la Gen 3 ?

La mise à niveau de votre service de base de données de la Gen 2 vers la Gen 3 apporte des améliorations significatives en matière de performance, de scalabilité et de fiabilité. Les bases de données Gen 3 sont conçues avec des architectures améliorées et une gestion optimisée des ressources, permettant à vos applications critiques de fonctionner plus efficacement et avec une meilleure tolérance aux pannes.

[[cpnav:publiccloud-databases]]

## En pratique

Les bases de données Public Cloud d'OVHcloud existent en plusieurs générations qui reflètent l'évolution de leur infrastructure sous-jacente.

- Les flavors de Gen 2 sont nommés DB2-X pour MongoDB et DB1-X pour les autres moteurs de base de données. Ils reposent sur les familles Compute Instance General Purpose B2 et Discovery D2.
- Les flavors de Gen 3 suivent la même convention de nommage que Compute Instance General Purpose B3 (b3-X), sur lequel ils sont construits.

La Gen 3 offre de meilleures performances, une meilleure scalabilité et une meilleure fiabilité que la Gen 2.

### Migrer un service de base de données de la Gen 2 vers la Gen 3

<Tabs>
  <Tab label="Depuis la console OVHcloud">
    Dans le menu de gauche de votre projet Public Cloud, cliquez sur votre moteur sous **Bases de données**, puis sur le nom de votre service de base de données. Ouvrez l'onglet <code className="action">Sauvegardes</code>.
    
    Cliquez sur le bouton <code className="action">...</code> de la sauvegarde à partir de laquelle vous souhaitez dupliquer le service, puis sur <code className="action">Dupliquer</code>. Le panneau **Dupliquer un cluster** s'ouvre.
    
    Saisissez le **Nom du nouveau cluster**. Sous **Source de la copie**, conservez **À partir d’une sauvegarde** et sélectionnez la sauvegarde.
    
    Sous **Configuration du nouveau cluster**, sélectionnez la **Région** et, si besoin, la **Version** Gen 3, une **Offre**, le **Type de nœud** qui hébergera le service, les **Nœuds** et la capacité de **Stockage**.
    
    :::info
    
    Correspondance des plans et points à considérer lors de la migration vers la Gen 3 :
    
    - Business (Gen 2) -> Production (Gen 3)
    - Enterprise (Gen 2) -> Advanced (Gen 3)
    - Essential (Gen 2) -> Pas d'équivalent direct en Gen 3. Les plans Essential utilisaient un seul nœud, alors que tous les plans Gen 3 disposent d'un minimum de 2 nœuds.
    
    Migrer depuis un plan `Essential` nécessitera de sélectionner un plan différent en Gen 3, ce qui augmente le coût en raison du nœud supplémentaire. Même pour les plans Business et Enterprise, les nœuds Gen 3 offrent une redondance et des performances supérieures (2 à 3 nœuds selon le plan).
    
    :::
    
    Les restrictions IP du service d'origine sont appliquées au nouveau service. Vous pourrez les vérifier une fois le service créé, dans la section **Restrictions d’IP** de son onglet <code className="action">Configuration</code>.
    
    Vérifiez le prix estimé en bas du panneau, puis cliquez sur <code className="action">Créer la copie</code>.
  </Tab>
  <Tab label="Depuis l'API OVHcloud">
    :::info

    Pour interagir avec vos services de bases de données Public Cloud via l'API OVHcloud, assurez-vous d'abord de maîtriser les bases en consultant notre guide : Public Cloud Databases - Premiers pas avec les API.

    :::

    
    Pour trouver l'ID de sauvegarde d'un service, utilisez l'appel API suivant :
    
    <Api version="v1" section="/cloud" method="GET" route={"/cloud/project/\\{serviceName\\}/database/postgresql/\\{clusterId\\}/backup"} />
Cet appel récupère la liste des sauvegardes du service concerné. Elles sont listées de la plus récente à la plus ancienne.
    
    Si vous souhaitez vérifier les informations d'une sauvegarde en particulier, vous pouvez utiliser cet appel API :
    
    <Api version="v1" section="/cloud" method="GET" route={"/cloud/project/\\{serviceName\\}/database/postgresql/\\{clusterId\\}/backup/\\{backupId\\}"} />
Pour créer votre nouveau service à partir d'une sauvegarde, utilisez l'appel API suivant :
    
    <Api version="v1" section="/cloud" method="POST" route={"/cloud/project/\\{serviceName\\}/database/postgresql"} />
Exemple de `body` pour cet appel API :
    
    :::warning

    Le champ nommé `backup` est obsolète et remplacé par `forkFrom`.

    :::

    
    ```console
    {
      "description": "laughable-peebles",                      # Nom du nouveau service
      "nodesPattern": {                                        # Configuration du service
        "flavor": "b3-8",
        "number": 2,
        "region": "EU-WEST-PAR"
      },
      "plan": "production",                                    # Plan du service
      "disk": {
        "size": 160                                            # Taille du disque du service
      },
      "version": "17",
      "ipRestrictions": [                                      # Paramètres de connectivité
        {
          "ip": "1.2.3.4/32",
          "description": ""
        }
      ],
      "forkFrom": {
        "serviceId": "********-****-****-****-ce179babccf3",   # L'identifiant du service d'origine auquel appartient cette sauvegarde
        "backupId": "********-****-****-****-3684de51065d"     # L'identifiant de la sauvegarde précédemment récupérée
      }
    }
    ```
  </Tab>
</Tabs>


### Valider le déploiement

Une fois votre nouveau service de base de données Gen 3 provisionné avec succès, il est essentiel de valider son déploiement et de vous assurer que vos applications peuvent s'y connecter.

1. Testez la connexion à votre nouveau service :
    1. Utilisez un client de base de données (par exemple, psql pour PostgreSQL, mysql pour MySQL) ou un script simple pour vérifier que vous pouvez vous connecter au nouvel endpoint du service Gen 3 à l'aide de ses identifiants.
    2. Confirmez que vos données ont bien été restaurées à partir de la sauvegarde et qu'elles sont accessibles.
2. Configurez votre application pour utiliser le nouveau service :
    1. Mettez à jour les fichiers de configuration ou les variables d'environnement de votre application pour pointer vers la nouvelle chaîne de connexion du service de base de données Gen 3 (hôte, port, nom d'utilisateur, mot de passe).
    2. Redémarrez votre application pour appliquer les changements.
    3. Testez minutieusement le fonctionnement de votre application pour vous assurer qu'elle fonctionne correctement avec le nouvel endpoint de base de données.

### Nettoyage

Une fois que vous avez entièrement validé que votre application fonctionne correctement avec le nouveau service de base de données Gen 3, et que vous êtes certain que toutes les données ont été transférées et sont accessibles, vous pouvez procéder à la suppression de l'ancien service Gen 2.

Cette étape est essentielle pour éviter des coûts inutiles et maintenir une infrastructure propre.

Suivez ces instructions pour supprimer l'ancien service 1-AZ :

<Tabs>
  <Tab label="Depuis la console OVHcloud">
    Ouvrez l'ancien service, puis son onglet <code className="action">Configuration</code>. Dans la section **Zone de danger**, cliquez sur <code className="action">Supprimer</code>, saisissez `TERMINATE` pour confirmer, puis cliquez sur <code className="action">Supprimer</code>. Si la protection contre la suppression est activée, désactivez-la d'abord dans la section **Configuration** du même onglet.
  </Tab>
  <Tab label="Depuis l'API OVHcloud">
    Pour supprimer votre service, utilisez l'appel API suivant :
    
    <Api version="v1" section="/cloud" method="DELETE" route={"/cloud/project/\\{serviceName\\}/database/postgresql/\\{clusterId\\}"} />
</Tab>
</Tabs>
