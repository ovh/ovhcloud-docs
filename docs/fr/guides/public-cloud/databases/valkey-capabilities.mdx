## Objectif

Cette page présente les capacités techniques et les limitations de l'offre Public Cloud Databases pour Valkey.

Nous améliorons continuellement nos offres. Vous pouvez suivre et proposer des idées à ajouter à notre roadmap sur [https://github.com/orgs/ovh/projects/16/views/5](https://github.com/orgs/ovh/projects/16/views/5).

## Capacités et limitations

### Régions prises en charge et multi-AZ

L'offre Public Cloud Databases est disponible dans toutes les régions Public Cloud 1-AZ et 3-AZ.

Les nœuds de la base de données doivent se trouver dans la même région.

### Versions de Valkey

L'offre Public Cloud Databases utilise les versions suivantes de Valkey :

- Valkey 8.1
- Valkey 9.1

Veuillez consulter le [guide sur la politique de cycle de vie des SGBD](/guides/public-cloud/databases/lifecycle-policy) pour connaître les recommandations concernant les mises à niveau de version et les annonces de fin de vie des versions majeures. Vous pouvez également suivre le cycle de publication de Valkey sur sa page officielle : [https://valkey.io/topics/releases/](https://valkey.io/topics/releases/).

### Clients Valkey

Vous pouvez utiliser n'importe lequel des [clients Valkey](https://valkey.io/clients/) pour accéder à votre service, à condition qu'il prenne en charge TLS.

### Plans

Deux plans sont disponibles :

- **Discovery** : 1 nœud
- **Production** : 2 nœuds (un nœud primaire et un nœud réplica)

Le plan choisi affecte le nombre de nœuds que votre cluster peut exécuter, le SLA, ainsi que quelques autres fonctionnalités comme la rétention des sauvegardes.

#### Type de licence

Valkey est fourni sous licence BSD 3-Clause.

Plus d'informations sur [https://valkey.io/topics/license/](https://valkey.io/topics/license/).

### Ressources matérielles

Pour plus d'informations sur les types de nœuds et les tarifs, veuillez consulter la [page des tarifs](/links/public-cloud/prices).

### Fonctionnalités

#### Réseau

L'hôte et le port de votre service sont affichés dans la section <code className="action">Informations de connection</code> de l'onglet <code className="action">Dashboard</code> de votre service, dans l'espace client.

Le réseau public ainsi que le réseau privé (vRack) peuvent être utilisés pour toutes les offres.

Le trafic entrant et sortant est inclus dans les plans de service et non facturé à l'usage.

L'adresse IP du service de base de données est susceptible de changer périodiquement. Il est donc conseillé de ne pas se baser sur ces IPs pour une quelconque configuration, telle qu'une politique de connexion ou de trafic sortant. Utilisez plutôt l'enregistrement DNS fourni et mettez en œuvre des politiques de trafic sortant basées sur des CIDR pour une gestion réseau plus robuste et flexible.

##### Considérations relatives au réseau privé
Voici quelques éléments à prendre en compte lors de l'utilisation d'un réseau privé :

- Les ports réseau sont créés dans le réseau privé de votre choix. Par conséquent, d'autres opérations sur ce réseau peuvent être restreintes - par exemple, vous ne pourrez pas supprimer le réseau si vous n'avez pas préalablement arrêté les services Public Cloud Databases.
- Lors d'une connexion depuis un sous-réseau externe, la passerelle IP OpenStack doit être activée sur le sous-réseau utilisé pour le service Database. Le client est responsable de toute autre configuration réseau personnalisée.
- Le dimensionnement du sous-réseau doit prendre en compte les nœuds de service, les autres services colocalisés dans le même sous-réseau, ainsi qu'une réserve d'adresses IP disponibles supplémentaires à des fins de maintenance. Un dimensionnement insuffisant des sous-réseaux peut entraîner des difficultés opérationnelles et des dysfonctionnements des services.
- Les annonces de routes des sous-réseaux OpenStack ne seront pas appliquées à vos services.
- Vous ne pouvez créer des services en réseau privé que si vous êtes le propriétaire d'origine du réseau. Vous ne pouvez pas créer de services en réseau privé sur un réseau partagé.

##### IPs autorisées

Une fois votre service opérationnel, vous pourrez spécifier des adresses IP (ou blocs CIDR) pour autoriser le trafic entrant. Jusque-là, votre service sera inaccessible. 

#### Chiffrement TLS

TLS est obligatoire : les connexions en clair sont refusées. Utilisez une URI de connexion de la forme `valkeys://<username>:<password>@<host>:<port>`.

Le certificat du serveur est signé par une autorité de certification publique : vous n'avez pas besoin de télécharger de certificat CA. Laissez la vérification du certificat activée dans votre client.

Consultez le [guide de connexion avec la CLI](/guides/public-cloud/databases/valkey-connect-cli) pour un exemple.

#### Nombre maximal de connexions simultanées

Le nombre de connexions simultanées dans Public Cloud Databases pour Valkey dépend de la mémoire totale disponible sur le serveur. Nous autorisons 4 connexions par mégaoctet de RAM (soit 4096 connexions par Go de RAM), avec un minimum de 10000 connexions, même sur les serveurs les plus petits.

Ainsi, par exemple, sur un serveur disposant de 8 Go de mémoire, vous obtiendrez jusqu'à 8 \* 4096 = 32768 connexions simultanées.

#### Mémoire et éviction

Lorsque la mémoire de votre service est pleine, son comportement dépend du paramètre avancé `valkey_maxmemory_policy`. Avec la valeur par défaut, `noeviction`, Valkey ne supprime aucune clé et **refuse les commandes d'écriture** tant que de la mémoire n'a pas été libérée. Les autres valeurs (`allkeys-lru`, `allkeys-lfu`, `allkeys-random`, `volatile-lru`, `volatile-lfu`, `volatile-random`, `volatile-ttl`) évincent des clés pour faire de la place aux nouvelles données, ce qui correspond généralement à l'usage d'un cache.

Consultez la [documentation de référence sur les paramètres avancés](/guides/public-cloud/databases/valkey-advanced-parameters-references) pour modifier cette politique.

#### Persistance

La persistance est contrôlée par le paramètre avancé `valkey_persistence` :

- `rdb` : Valkey écrit des snapshots RDB sur disque, utilisés pour les sauvegardes.
- `off` : aucun snapshot RDB n'est écrit. Les sauvegardes et les forks sont indisponibles, et **toutes les données sont perdues** si le service redémarre ou est arrêté.

La persistance AOF (Append Only File) n'est pas disponible.

#### Paramètres avancés

Vous pouvez personnaliser davantage votre service en utilisant des paramètres avancés. Consultez la [documentation de référence sur les paramètres avancés](/guides/public-cloud/databases/valkey-advanced-parameters-references) pour plus d'informations sur les paramètres pris en charge.

Notez que la modification de certains paramètres avancés peut redémarrer le service.

#### Sauvegardes

Les clusters du plan *Discovery* sont automatiquement sauvegardés toutes les 12 heures. La rétention des sauvegardes est de 1 jour.

Les clusters du plan *Production* sont automatiquement sauvegardés toutes les 12 heures. La rétention des sauvegardes est de 3 jours.

Les copies de sauvegarde sont stockées dans deux régions.

Consultez le [guide sur les sauvegardes automatiques](/guides/public-cloud/databases/backups) pour plus d'informations.

#### Logs et métriques

Les logs et les métriques sont disponibles via le Control Panel, l'API, et peuvent être transférés vers Logs Data Platform. Pour les instructions de configuration, consultez le [guide Public Cloud Databases - Comment configurer le transfert des logs](/guides/public-cloud/databases/logs-to-customers).

- **Rétention des logs** : 1000 lignes de logs
- **Rétention des métriques** : 1 mois calendaire

Veuillez noter que si l'instance de base de données est supprimée, les logs et métriques sont également automatiquement supprimés.

#### Utilisateurs et rôles

Les utilisateurs peuvent être créés, modifiés et supprimés, et leur mot de passe réinitialisé, via le Control Panel et l'API. Les modifications d'ACL s'appliquent immédiatement, sans reconnexion.

Pour chaque utilisateur, vous pouvez spécifier :

- Le nom d'utilisateur
- Les clés (comme « cache:* »)
- Les catégories (comme « +@read »)
- Les commandes (comme « +get -flushall »)
- Les canaux (comme « news:* »)

Consultez le [guide sur les utilisateurs et les ACL](/guides/public-cloud/databases/valkey-update-acls) pour plus d'informations.

Vous pouvez consulter la documentation officielle de Valkey sur les commandes : [https://valkey.io/commands/](https://valkey.io/commands/).

Voici la liste des commandes non prises en charge :

- bgrewriteaof
- cluster
- command
- debug
- failover
- migrate
- slaveof
- acl
- bgsave
- config
- replicaof
- lastsave
- save
- shutdown
- monitor

Les scripts Lua (`EVAL`, `EVALSHA`, `SCRIPT`) et les fonctions (`FUNCTION`, `FCALL`) sont pris en charge.

#### Autres limitations

- Le mode cluster (sharding) n'est pas pris en charge.
- La persistance AOF n'est pas disponible (voir [Persistance](#persistance)).
- La commande `CONFIG` n'est pas disponible : utilisez les [paramètres avancés](/guides/public-cloud/databases/valkey-advanced-parameters-references) à la place.
- Les bases de données logiques sont prises en charge avec `SELECT <n>`. Leur nombre est défini par le paramètre avancé `valkey_number_of_databases` (jusqu'à 128).
