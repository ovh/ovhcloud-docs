## Objectif

Ce guide explique comment transférer les données d'un replica set MongoDB existant vers un service Public Cloud Databases pour MongoDB. Il couvre deux méthodes :

- **mongodump et mongorestore** : une copie ponctuelle. Les écritures sur la source doivent être arrêtées pendant la copie, ce qui implique une interruption de service.
- **mongosync** : une synchronisation continue, suivie d'une bascule lorsque la cible a rattrapé la source. L'interruption se limite à la bascule.

**Ce guide explique comment préparer le service cible, exécuter chaque méthode et vérifier le résultat.**

## Prérequis

- Un [projet Public Cloud](/links/public-cloud/public-cloud) dans votre compte OVHcloud
- Un [service Public Cloud Databases pour MongoDB](/guides/public-cloud/databases/getting-started) dont la version de MongoDB est égale ou supérieure à celle de la source
- Un déploiement MongoDB source fonctionnant en replica set
- Une machine pouvant joindre la source et la cible, pour exécuter les outils de migration

## En pratique

### Avant de commencer

#### Les utilisateurs ne sont pas migrés

Sur Public Cloud Databases pour MongoDB, les utilisateurs se gèrent uniquement depuis l'espace client OVHcloud ou l'API OVHcloud. Un utilisateur créé autrement, par exemple avec `createUser` ou restauré par `mongorestore --restoreDbUsersAndRoles`, est accepté par MongoDB, puis supprimé automatiquement quelques minutes plus tard.

Avant de basculer vos applications, créez leurs utilisateurs sur le service cible depuis l'onglet <code className="action">Utilisateurs</code>, avec les rôles dont ils ont besoin. N'utilisez pas les options `--dumpDbUsersAndRoles` et `--restoreDbUsersAndRoles`, et ne restaurez pas la base `admin`.

#### Autoriser la machine de migration

Dans l'espace client OVHcloud, ouvrez votre service, puis l'onglet <code className="action">Configuration</code>. Dans la section `IPs`, ajoutez l'adresse IP publique de la machine qui exécute les outils de migration, puis cliquez sur <code className="action">Sauvegarder les modifications</code>.

#### Créer un utilisateur de migration

Dans l'onglet <code className="action">Utilisateurs</code>, cliquez sur <code className="action">Ajouter un utilisateur</code>, saisissez un nom d'utilisateur, ajoutez les rôles ci-dessous, puis cliquez sur <code className="action">Créer un utilisateur</code>. Notez le mot de passe affiché : il ne pourra pas être récupéré par la suite.

| Méthode | Rôles de l'utilisateur de migration |
|---|---|
| mongodump et mongorestore | `readWriteAnyDatabase@admin`, `restore@admin` |
| mongosync | `backup@admin`, `clusterManager@admin`, `clusterMonitor@admin`, `readWriteAnyDatabase@admin`, `restore@admin` |

Supprimez cet utilisateur une fois la migration terminée.

#### Construire la chaîne de connexion cible

Copiez l'URI `mongodb+srv://` depuis la section `Informations de connection` de l'onglet <code className="action">Dashboard</code>. Pour les outils de migration, remplacez le chemin `/admin` par un paramètre `authSource=admin` :

```bash
mongodb+srv://<username>:<password>@<srv-hostname>/?authSource=admin&tls=true
```

:::warning
Si vous conservez `/admin` dans le chemin, `mongorestore` considère `admin` comme base cible et ignore vos autres bases.
:::

### Méthode 1 : mongodump et mongorestore

Installez les [MongoDB Database Tools](https://www.mongodb.com/docs/database-tools/installation/) sur la machine de migration.

1. Arrêtez les écritures de vos applications sur la source.

2. Exportez les bases de la source :

    ```bash
    mongodump --uri "<source-uri>" --out dump
    ```

    Le dossier `dump` contient un sous-dossier par base, y compris `admin`.

3. Importez-les dans la cible, en excluant la base `admin` :

    ```bash
    mongorestore --uri "mongodb+srv://<username>:<password>@<srv-hostname>/?authSource=admin&tls=true" \
      --nsExclude 'admin.*' \
      dump
    ```

    Les collections et leurs index sont recréés sur la cible. La dernière ligne de la sortie indique le nombre de documents restaurés et le nombre de documents en échec.

4. Si vous relancez l'import, les documents déjà présents sur la cible ne sont pas écrasés : ils sont comptés en échec. Ajoutez l'option `--drop` pour supprimer chaque collection avant de la restaurer :

    ```bash
    mongorestore --uri "mongodb+srv://<username>:<password>@<srv-hostname>/?authSource=admin&tls=true" \
      --nsExclude 'admin.*' \
      --drop \
      dump
    ```

5. [Vérifiez le résultat](#vérifier-les-données-migrées), puis faites pointer vos applications vers la cible.

### Méthode 2 : mongosync

[mongosync](https://www.mongodb.com/docs/cluster-to-cluster-sync/current/reference/mongosync/) copie les données, puis applique les modifications faites sur la source jusqu'à ce que vous validiez la migration. Consultez ses [limitations](https://www.mongodb.com/docs/cluster-to-cluster-sync/current/reference/limitations/) et sa [compatibilité de versions](https://www.mongodb.com/docs/cluster-to-cluster-sync/current/reference/supported-server-version/) avant de commencer.

Sur la source, mongosync a besoin d'un utilisateur, avec l'authentification activée, disposant des privilèges listés dans la [documentation de mongosync](https://www.mongodb.com/docs/cluster-to-cluster-sync/current/connecting/onprem-to-onprem/). Si la source n'a pas d'authentification, la demande de démarrage échoue avec `Missing privileges: Source: AnyDB: [changeStream]`.

1. Téléchargez [mongosync](https://www.mongodb.com/try/download/mongosync) sur la machine de migration, puis démarrez-le :

    ```bash
    mongosync \
      --cluster0 "<source-uri>" \
      --cluster1 "mongodb+srv://<username>:<password>@<srv-hostname>/?authSource=admin&tls=true"
    ```

    mongosync écoute sur le port `27182` de la machine locale et attend des instructions.

2. Dans un autre terminal, démarrez la synchronisation :

    ```bash
    curl -X POST localhost:27182/api/v1/start \
      --data '{"source":"cluster0","destination":"cluster1"}'
    ```

    La réponse est `{"success":true}`.

3. Suivez la progression :

    ```bash
    curl localhost:27182/api/v1/progress
    ```

    Une fois la copie initiale terminée, `state` vaut `RUNNING` et `canCommit` vaut `true`. À partir de là, les insertions, mises à jour et nouvelles collections créées sur la source sont appliquées à la cible. Le champ `lag` indique, en secondes, le retard de la cible sur la source.

4. Lorsque vous êtes prêt à basculer, arrêtez les écritures de vos applications sur la source, attendez que `lagTimeSeconds` vaille `0`, puis validez :

    ```bash
    curl -X POST localhost:27182/api/v1/commit --data '{}'
    ```

5. Interrogez de nouveau la progression. Lorsque `state` vaut `COMMITTED` et `canWrite` vaut `true`, la cible est prête : arrêtez mongosync avec `Ctrl+C`, puis faites pointer vos applications vers la cible.

6. mongosync laisse ses métadonnées dans une base `__mdb_internal_mongosync` sur la cible. Supprimez ses collections avec l'utilisateur de migration, par exemple avec mongosh :

    ```javascript
    const meta = db.getSiblingDB("__mdb_internal_mongosync");
    meta.getCollectionNames().forEach((name) => meta.getCollection(name).drop());
    ```

### Vérifier les données migrées

Connectez-vous à la cible avec [mongosh](/guides/public-cloud/databases/mongodb-connect-cli) et comparez avec la source, pour chaque collection, le nombre de documents et les index :

```javascript
use <database>
db.<collection>.countDocuments({})
db.<collection>.getIndexes()
```

Vérifiez ensuite que les utilisateurs de vos applications existent sur la cible, avec les bons rôles, et supprimez l'utilisateur de migration.
