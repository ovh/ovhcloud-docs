## Objectif

Utilisez `solaria-3` sur [AI Endpoints](/links/public-cloud/ai-endpoints) pour transcrire de l’audio en temps réel avec l’**API Gladia Live V2**. L’API native fournit des transcriptions partielles, des segments de parole définitifs et des étiquettes de locuteurs. Ce guide explique comment créer une session, transmettre l’audio, terminer la session et récupérer les résultats à l’aide de HTTP, de WebSockets et des SDK officiels Gladia.

Pour transcrire un fichier audio local sans intégration WebSocket, consultez la [passerelle de transcription de fichiers compatible OpenAI](/guides/public-cloud/ai-machine-learning/ai-endpoints-audio-models#gladia-compatibility), qui propose des exemples avec Python `requests`, le client OpenAI et cURL. Elle prend en charge un ensemble plus restreint de paramètres et ne transmet pas les réponses en flux continu.

## Prérequis

- Une **clé d’accès API AI Endpoints**, créée en suivant le guide « [AI Endpoints - Premiers pas](/guides/public-cloud/ai-machine-learning/ai-endpoints-getting-started) ».
- Un court enregistrement audio.
- Python ou Node.js pour les exemples facultatifs avec les SDK.
- Pour le protocole brut : cURL, `jq` et un client WebSocket.
- Facultatif : [FFmpeg](https://ffmpeg.org/download.html) pour convertir un fichier existant pour les exemples.

## Endpoint et authentification

Utilisez votre clé d’accès AI Endpoints, et non une clé API du service SaaS Gladia.

```bash
export AI_ENDPOINTS_BASE_URL="https://oai.endpoints.kepler.ai.cloud.ovh.net"
export OVH_AI_ENDPOINTS_ACCESS_TOKEN="<votre-cle-acces-ai-endpoints>"
```

Pour les requêtes natives `/gladia/*`, transmettez votre clé d’accès AI Endpoints dans l’en-tête `x-gladia-key`. Vous pouvez également utiliser `Authorization: Bearer <token>`. Pour les requêtes anonymes, omettez ces deux en-têtes. Ces méthodes d’authentification s’appliquent uniquement aux routes `/gladia/*` ; les routes compatibles OpenAI `/v1/*` ne changent pas et utilisent l’authentification Bearer. L’URL de base de l’API native est `$AI_ENDPOINTS_BASE_URL/gladia`, **sans `/v1`**.

Avec un SDK, définissez `api_key` (Python) ou `apiKey` (JavaScript) sur votre clé d’accès AI Endpoints. Le SDK l’envoie dans l’en-tête `x-gladia-key` ; aucune valeur fictive ni en-tête d’autorisation personnalisé n’est nécessaire.

## Exemples avec les SDK officiels

Ces exemples créent une session, transmettent un **court enregistrement local au rythme du temps réel**, arrêtent l’enregistrement, attendent la fin du traitement et interrogent le résultat final avec une durée maximale d’attente. Les délais d’expiration sont définis côté client ; ils ne correspondent pas aux durées de session autorisées par le service. Ces exemples utilisent un enregistrement source en anglais : adaptez `language_config` à la langue de votre fichier.

### Préparer l’audio pour ces exemples

Pour simplifier, ces exemples utilisent de l’audio **PCM mono à 16 kHz sur 16 bits**. Ce n’est pas le seul format pris en charge : l’encodage, la fréquence d’échantillonnage, la profondeur en bits et le nombre de canaux de la session doivent correspondre à l’audio envoyé. Python lit un conteneur WAV ; Node.js lit des données PCM sans en-tête.

Si nécessaire, convertissez un enregistrement existant avec ffmpeg. Choisissez la sortie correspondant à votre exemple :

```bash
# Python : PCM dans un conteneur WAV
ffmpeg -i input.m4a -ar 16000 -ac 1 -c:a pcm_s16le audio.wav
# Node.js : PCM sans en-tête
ffmpeg -i input.m4a -ar 16000 -ac 1 -c:a pcm_s16le -f s16le audio.s16le
```

Pour l’[envoi de fichiers via l’API compatible OpenAI](#envoi-de-fichiers-via-lapi-compatible-openai), les fichiers compressés pris en charge peuvent être envoyés directement, sans conversion locale.

            language_config=LiveV2LanguageConfig(languages=["en"]),
            messages_config=LiveV2MessagesConfig(receive_final_transcripts=True),
        ))

        def on_message(message):
            data = getattr(message, "data", None)
            if getattr(message, "type", None) == "transcript" and getattr(data, "is_final", False):
                print(data.utterance.text)

        session.on("message", on_message)
        try:
            if not session.wait_until_ready(timeout=30):
                raise RuntimeError("La session de transcription n’est pas prête")
            while chunk := audio.readframes(1600):
                if session.status in ("ending", "ended"):
                    raise RuntimeError("La session s’est terminée avant l’envoi de tout l’audio")
                session.send_audio(chunk)
                time.sleep(len(chunk) / (16000 * 2))
            session.stop_recording()
            if not session.join(timeout=180):
                raise TimeoutError("La session ne s’est pas terminée dans le délai imparti")

            deadline = time.monotonic() + 180
            while time.monotonic() < deadline:
                result = live.get(session.session_id)
                if result.status == "done":
                    print(result.result.transcription.full_transcript)
                    break
                if result.status == "error":
                    raise RuntimeError("La transcription en temps réel a échoué")
                time.sleep(2)
            else:
                raise TimeoutError("Le résultat n’est pas disponible dans le délai imparti")
        finally:
            if session.status != "ended":
                session.end_session()

## Protocole natif de transcription en temps réel

### 1. Créer une session

Cet exemple utilise un enregistrement en anglais au format **PCM mono à 16 kHz, signé sur 16 bits en petit-boutiste (little-endian)**. Adaptez `language_config` à la langue de votre audio.

Précisez explicitement `model: "solaria-3"` dans chaque requête de création de session, sans vous fier au modèle par défaut. Le format de votre audio — encodage, fréquence d’échantillonnage, profondeur en bits et nombre de canaux — doit correspondre aux échantillons envoyés.

```bash
SESSION=$(curl --fail-with-body --silent --show-error --max-time 30 \
  "$AI_ENDPOINTS_BASE_URL/gladia/v2/live?region=eu-west" \
  -H "x-gladia-key: $OVH_AI_ENDPOINTS_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"model":"solaria-3","encoding":"wav/pcm","sample_rate":16000,"bit_depth":16,"channels":1,"language_config":{"languages":["en"]},"messages_config":{"receive_partial_transcripts":true,"receive_final_transcripts":true}}')
SESSION_ID=$(printf '%s' "$SESSION" | jq -er '.id')
WEBSOCKET_URL=$(printf '%s' "$SESSION" | jq -er '.url')
```

Une réponse réussie renvoie le code `201` et contient les champs `id` et `url`. **L’URL WebSocket renvoyée est signée : conservez-la telle quelle et traitez-la comme un identifiant d’accès confidentiel.** Ne consignez pas dans les journaux la réponse, l’URL ou les erreurs du SDK susceptibles de la contenir. N’ajoutez pas `/gladia` ou `/v1` à cette URL.

### 2. Envoyer l’audio et recevoir les événements

Connectez un client WebSocket à `WEBSOCKET_URL` ou utilisez l’un des [exemples de SDK ci-dessus](#exemples-avec-les-sdk-officiels), qui crée sa propre session. Pour la configuration ci-dessus :

1. Envoyez des **échantillons PCM bruts sous forme de messages WebSocket binaires**, et non un en-tête WAV ou des données MP3 compressées. L’en-tête d’un fichier WAV doit être retiré ; le module Python `wave` s’en charge dans l’exemple ci-dessus.
2. Transmettez l’audio à un rythme proche du temps réel. Par exemple, 3 200 octets représentent 100 ms d’audio mono à 16 kHz sur 16 bits.
3. Lisez les événements en parallèle de l’envoi de l’audio. Pour `type="transcript"`, examinez `data.is_final` et `data.utterance.text`. Les transcriptions partielles peuvent évoluer : remplacez les transcriptions partielles précédentes ayant le même `data.id`, plutôt que d’ajouter des doublons.
4. Une fois tout l’audio envoyé, transmettez le message texte `{"type":"stop_recording"}`. Continuez à lire les événements jusqu’à la fin du post-traitement et à la fermeture de la connexion WebSocket. **Un segment de parole définitif ne marque pas la fin de la session.** Ne fermez pas la connexion immédiatement après l’arrêt de l’enregistrement.

Le [guide de démarrage Gladia Live](https://docs.gladia.io/chapters/live-stt/quickstart) décrit le protocole sous-jacent. Les limitations du service présentées dans ce guide prévalent sur les exemples du service SaaS Gladia. Pour envoyer un fichier via HTTP, utilisez plutôt l’[exemple de la passerelle avec Python requests](/guides/public-cloud/ai-machine-learning/ai-endpoints-audio-models#gladia-compatibility).

### 3. Récupérer le résultat

Après avoir terminé la session ci-dessus, récupérez son résultat avec la même clé d’accès API :

```bash
curl --fail-with-body --max-time 30 \
  "$AI_ENDPOINTS_BASE_URL/gladia/v2/live/$SESSION_ID" \
  -H "x-gladia-key: $OVH_AI_ENDPOINTS_ACCESS_TOKEN"
unset SESSION WEBSOCKET_URL
```

Le champ `status` du résultat vaut `queued`, `processing`, `done` ou `error`. S’il vaut `queued` ou `processing`, interrogez à nouveau l’API en espaçant les requêtes et en fixant une durée maximale d’attente. Le statut `done` indique que le traitement est terminé ; arrêtez les requêtes et gérez l’échec si le statut vaut `error`. Le booléen `failed` présent dans le détail de la session n’est pas un statut du résultat. La transcription complète est disponible dans `result.transcription.full_transcript`.

Les résultats sont isolés par projet authentifié ou par adresse IP anonyme. Réutilisez une clé du même projet ou la même adresse IP pour un accès anonyme. Une ressource inaccessible ou qui ne vous appartient pas renvoie `404`.

## Intelligence audio

Précisez explicitement `"model": "solaria-3"` lors de la création d’une session : les SDK peuvent utiliser `solaria-1` par défaut. Les fonctionnalités ci-dessous sont disponibles via l’API native en temps réel, et non via la passerelle de fichiers compatible OpenAI. `audio_to_llm` et la génération de résumés restent indisponibles.

### Configurer les fonctionnalités et lire les résultats

Regroupez les fonctionnalités activées dans un seul objet `realtime_processing`, en respectant les chemins des champs ci-dessous. Les champs natifs `diarization` et `diarization_config` restent à la racine du corps JSON, comme indiqué dans [Diarisation et latence](#diarisation-et-latence). Avec le SDK Python 2.2 ou ultérieur, utilisez un dictionnaire pour les champs Enterprise absents de l’initialiseur typé.

| Fonctionnalité | Champs de création de session | Résultats à lire |
| :--- | :--- | :--- |
| Vocabulaire personnalisé | Dans `realtime_processing` : `"custom_vocabulary": true` et `"custom_vocabulary_config": {"vocabulary": ["OVHcloud"], "default_intensity": 0.4}` | Termes privilégiés dans les événements `transcript` définitifs. Le vocabulaire utilise la similarité phonétique ; comparez avec une transcription sans configuration, à partir d’un audio contenant les termes. |
| Orthographe personnalisée | Dans `realtime_processing` : `"custom_spelling": true` et `"custom_spelling_config": {"spelling_dictionary": {"OVHcloud": ["OVH cloud"]}}` | Remplacements littéraux dans les transcriptions définitives. Les clés du dictionnaire sont les graphies souhaitées ; les valeurs sont les variantes à remplacer. |
| Ponctuation et casse | À la racine : `"punctuation": true` | Texte définitif dans `data.utterance.text` ; comparez avec `text_raw` lorsqu’il est présent. Un même paramètre contrôle la ponctuation et la casse. |
| Nombres en chiffres | À la racine : `"numerals": true` | Nombres normalisés dans `data.utterance.text`. Utilisez des paroles contenant des quantités, des dates ou des montants. |
| Entités nommées | Dans `realtime_processing` : `"named_entity_recognition": true` | Événements `named_entity_recognition` : `data.results[]` contient `entity_type`, `text`, un score et des positions. Les segments définitifs peuvent également contenir `utterance.entities[]` et des balises d’entités dans le texte. |
| Masquage des données personnelles | À la racine : `"pii": true` | Texte définitif masqué dans `data.utterance.text`, événements `pii` et métadonnées des entités. Le masquage supprime les transcriptions partielles, même si elles sont demandées. Ce champ Enterprise en temps réel est distinct de `pii_redaction` pour les enregistrements. |
| Détection de fin de tour | À la racine : `"end_of_turn": true` | Événements `end_of_turn` : `data.probability`, `reason`, `end` et `speech_duration`. L’événement peut précéder la transcription définitive. Le paramètre `endpointing`, fondé sur le silence, et les événements `speech_end` n’indiquent pas une fin de tour sémantique. |
| Sentiments et émotions | Dans `realtime_processing` : `"sentiment_analysis": true` | Événements `sentiment_analysis` : `data.results[]` contient `sentiment`, `emotion`, `text` et des horodatages. |
| Diarisation | À la racine : `"diarization": true`, éventuellement `"diarization_config": {"max_speakers": 3}` | `data.utterance.speaker` et `data.utterance.words[].speaker` dans les transcriptions définitives. Utilisez un audio mono ; les nombres de locuteurs configurés sont des indications, pas des garanties. |
| Traduction | Dans `realtime_processing` : `"translation": true` et `"translation_config": {"target_languages": ["fr"]}` | Événements `translation` : `data.target_language` et `data.translated_utterance.text`. Associez la traduction au segment source à l’aide de `data.utterance_id`. |

Par exemple, ajoutez ces paramètres de traduction au corps de création de la session pour traduire l’audio source en français :

```json
{
  "model": "solaria-3",
  "messages_config": {
    "receive_realtime_processing_events": true,
    "receive_final_transcripts": true
  },
  "realtime_processing": {
    "translation": true,
    "translation_config": {"target_languages": ["fr"]}
  }
}
```

Activez `messages_config.receive_realtime_processing_events: true` pour recevoir les événements d’intelligence audio et conservez `receive_final_transcripts: true`. Les événements associés aux fonctionnalités peuvent arriver après la transcription source : continuez à lire jusqu’à la fin de la session. Appliquez la configuration lors de la création d’une nouvelle session.

Pour plus de détails sur les concepts et les paramètres, consultez [Gladia Audio Intelligence](https://docs.gladia.io/chapters/audio-intelligence). Certains exemples de cette documentation concernent les enregistrements ou le service SaaS Gladia : respectez le placement des champs pour le temps réel et les limitations présentées dans ce guide. Affichez les transcriptions et les entités comme du texte non fiable, et non comme du HTML, et évitez de journaliser des données personnelles lorsque le masquage PII est activé.

### Diarisation et latence

La diarisation attribue des étiquettes de locuteurs à la transcription. Pour les requêtes natives de transcription en temps réel, ajoutez `"diarization": true` à la racine du corps JSON et, si nécessaire, `"diarization_config": {"min_speakers": 2, "max_speakers": 4}`. Utilisez un audio mono ; les nombres de locuteurs configurés sont des indications, pas des garanties.

Avec `gladiaio-sdk>=2.2`, transmettez un dictionnaire Python à `live.start_session()` pour envoyer les champs de diarisation Enterprise absents de `LiveV2InitRequest`. En JavaScript, ajoutez les mêmes champs à l’objet transmis à `live.startSession()`.

Dans l’[exemple du SDK Python ci-dessus](#exemples-avec-les-sdk-officiels), remplacez l’initialisation de la session et la fonction `on_message` par le code suivant. Conservez le reste de l’exemple sans modification :

```python
session = live.start_session({
  "model": "solaria-3",
  "encoding": "wav/pcm", "sample_rate": 16000,
  "bit_depth": 16, "channels": 1,
  "language_config": {"languages": ["en"]},
  "messages_config": {"receive_final_transcripts": True},
  "diarization": True,
  "diarization_config": {"max_speakers": 3},
})

def on_message(message):
  if message.type == "transcript" and message.data.is_final:
    utterance = message.data.utterance
    print(f"Locuteur {utterance.speaker} : {utterance.text}")
```

L’exemple du SDK ci-dessus gère le rythme d’envoi de l’audio et attend les résultats finaux après `stop_recording()`. Ne transmettez pas `diarization` comme mot-clé au constructeur typé.

:::warning
La diarisation distingue les voix, mais n’identifie pas les personnes, et **augmente la latence de traitement**, notamment pour les résultats finaux. Les étiquettes de locuteurs au niveau des mots sont plus précises qu’une étiquette unique pour un segment de parole contenant plusieurs locuteurs. Utilisez les résultats natifs pour obtenir ces étiquettes : la passerelle compatible OpenAI ne les inclut pas dans sa réponse formatée.
:::

## Envoi de fichiers via l’API compatible OpenAI

La route compatible OpenAI `POST /v1/audio/transcriptions` sert de **passerelle entre un fichier et une session en temps réel** pour `solaria-3` : envoyez un fichier audio local au format multipart, puis le service le décode en PCM mono à 16 kHz, le transmet à une session Gladia à un rythme proche du temps réel et renvoie une transcription complète. Votre application n’a pas à gérer de connexion WebSocket. Il ne s’agit pas de l’API native Gladia pour les enregistrements, et la réponse HTTP n’est pas transmise en flux continu.

Consultez le guide « [Transcription audio avec l’API compatible OpenAI](/guides/public-cloud/ai-machine-learning/ai-endpoints-audio-models) » pour les exemples avec cURL, Python `requests` et le client OpenAI, les paramètres pris en charge et les formats de réponse. Pour Gladia, précisez `model: "solaria-3"` ; ne réutilisez pas les options spécifiques à Whisper telles quelles. Pour une transcription interactive et les résultats d’intelligence audio, utilisez l’API native présentée ci-dessus. La passerelle n’expose pas ces résultats natifs et ne conserve pas la séparation des canaux.

Les fichiers compressés pris en charge peuvent être envoyés directement, sans conversion locale. Prévoyez un délai d’expiration côté client couvrant la durée de l’enregistrement ainsi que les temps d’envoi et de traitement. Consultez [Quotas et erreurs](#quotas-et-erreurs) pour les limites des fichiers et des requêtes.

## Quotas et erreurs

| Limite | Anonyme | Authentifié avec une clé d’accès API |
| :--- | :--- | :--- |
| Débit des requêtes HTTP | 2 requêtes par minute, par IP et par modèle | 400 requêtes par minute, par projet Public Cloud et par modèle |
| Sessions de transcription en temps réel simultanées | 1 session par IP | 25 sessions par projet Public Cloud |
| Durée maximale d’une session native de transcription en temps réel | 60 secondes | 8 heures |
| Taille maximale d’un fichier via la passerelle Gladia compatible OpenAI | 10 Mio | 2 048 Mio |
| Durée maximale d’un fichier via la passerelle Gladia compatible OpenAI | 60 secondes | 10 800 secondes (3 heures) |

La limite native correspond à la **durée réelle écoulée depuis la création de la session avec `POST /gladia/v2/live`**, et non depuis l’ouverture de la connexion WebSocket ni à la quantité d’audio transmise. Par exemple, si la connexion WebSocket d’une session anonyme est ouverte 20 secondes après sa création, il ne reste que 40 secondes pour transmettre l’audio. À l’expiration, le service arrête proprement l’enregistrement avec `stop_recording`, ce qui permet de produire les transcriptions finales. Le client doit cesser d’envoyer de l’audio et continuer à lire les événements jusqu’à la fin du traitement et à la fermeture de la connexion.

Cette limite de session est indépendante des limites appliquées aux fichiers via la passerelle Gladia compatible OpenAI. Cette passerelle utilise une session en temps réel, mais applique ses propres limites de taille et de durée des fichiers. `maximum_duration_without_endpointing` contrôle le moment où un segment de parole est finalisé ; il ne modifie pas les limites de durée de session ou de fichier. Les utilisateurs partageant une même adresse IP publique derrière un NAT partagent également une identité anonyme. Plusieurs clés API d’un même projet ne créent pas de quotas distincts. La fermeture d’une session libère un emplacement dans le quota de sessions simultanées ; les requêtes GET de récupération des résultats ne créent pas de session.

La consommation native multicanal est mesurée en **durée audio multipliée par le nombre de canaux**.

La requête multipart complète, y compris les données supplémentaires liées à ce format, doit également respecter les limites de taille du corps HTTP et de la passerelle d’entrée. Les limites de fichiers Gladia ci-dessus s’appliquent uniquement à la passerelle Gladia compatible OpenAI, et non aux modèles Whisper ni aux routes natives de transcription en temps réel.

### Limitations du service

| Fonctionnalité | Disponibilité sur cet endpoint |
| :--- | :--- |
| Transcription native en temps réel | `POST /gladia/v2/live`, l’URL WebSocket renvoyée et `GET /gladia/v2/live/{id}`. |
| Envoi de fichiers et transcription native d’enregistrements | Désactivés, notamment `/gladia/v2/upload`, `/gladia/v2/pre-recorded` et `/gladia/v2/transcription`. N’utilisez pas les méthodes de transcription d’enregistrements du SDK. La passerelle compatible OpenAI accepte néanmoins le contenu binaire des fichiers. |
| Région | Europe uniquement. Omettez `region` ou utilisez `?region=eu-west` lors de la création de la session. `us-west` renvoie `400`. |
| Callbacks et webhooks | Désactivés ; leur configuration renvoie `501`. Recevez les événements WebSocket et récupérez les résultats à la place. |
| URL audio distantes | Bloquées. Transmettez des échantillons audio en flux ou envoyez le contenu binaire d’un fichier via la passerelle, plutôt qu’une URL `audio_url` externe. |
| Suppression d’une session | `DELETE /gladia/v2/live/{id}` renvoie `202` une fois la session tracée. Sinon, l’API renvoie `409` ; patientez avant de réessayer. Utilisez une clé du même projet ou la même adresse IP pour un accès anonyme. |

Seules les routes de transcription en temps réel répertoriées ici sont disponibles, **et non l’ensemble de l’API Gladia**.

## Dépannage

Commencez par de courts échantillons audio. Si une requête d’envoi de fichier renvoie `413 Payload Too Large`, vérifiez la taille du fichier, la durée de l’enregistrement et la taille de la requête multipart complète avant de réessayer.

| Code | Action |
| :--- | :--- |
| `400` | Vérifiez les paramètres, la région et les métadonnées, et assurez-vous que l’audio envoyé est valide et peut être décodé. Ne définissez pas de clés `custom_metadata` réservées, telles que `project_id` ou `request_id`. |
| `403` | Supprimez une option native désactivée, telle que la génération de résumés ou `audio_to_llm`. |
| `404` | Vérifiez la route, l’identifiant de la ressource et vos droits d’accès à cette ressource. |
| `405` | La méthode n’est pas prise en charge. |
| `409` | La session ne peut pas encore être supprimée. Patientez avant de réessayer. |
| `413` | La limite de taille ou de durée des fichiers Gladia, ou la limite du corps HTTP ou de la passerelle d’entrée pour la requête multipart complète, a été dépassée. Réduisez la taille du fichier ou la durée de l’enregistrement selon le cas avant de réessayer. |
| `429` | Espacez vos tentatives : la limite de débit des requêtes ou de sessions simultanées a été dépassée. Fermez les sessions abandonnées avant de réessayer d’en créer une. |
| `501` | Supprimez les champs non pris en charge, les callbacks ou les URL externes interdites. |
| `502` | Une requête vers Gladia ou un traitement de la passerelle a échoué ou dépassé le délai imparti. Vérifiez l’état de la session avant de réessayer. |
