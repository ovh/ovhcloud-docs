## Objectif

Le service OVHcloud Managed Kubernetes vous fournit des clusters Kubernetes sans les contraintes liées à leur installation ou à leur exploitation.
Chez OVHcloud, nous souhaitons vous proposer les meilleurs produits et services, c'est pourquoi nous vous donnons la possibilité de personnaliser les composants managés de votre Kubernetes : CoreDNS, IPVS, et même les [plugins d'admission de l'API server](https://kubernetes.io/docs/reference/access-authn-authz/admission-controllers/) à activer et désactiver sur vos clusters OVHcloud Managed Kubernetes.

Dans ce guide, nous allons vous montrer comment activer et désactiver les plugins d'admission de l'API server, mais vous pouvez suivre ce guide pour d'autres personnalisations de la configuration du cluster OVHcloud Managed Kubernetes.

## Prérequis 

- Un cluster OVHcloud Managed Kubernetes

## En pratique

:::warning
Seul le plugin d'admission `AlwaysPullImages` est personnalisable pour le moment. Il est activé par défaut pour des raisons de sécurité, mais peut être désactivé pour éviter une utilisation excessive des registres Docker (par exemple pour éviter d'atteindre la limite de débit de téléchargement de Docker Hub).
Le plugin d'admission `NodeRestriction` est activé par défaut et doit rester activé pour des raisons de sécurité.
:::


### Configurer les plugins d'admission de l'API server via l'API

#### L'Explorateur d'API

Pour simplifier les choses, nous utilisons l'[Explorateur d'API](/guides/manage-and-operate/api/first-steps), qui permet d'explorer, d'apprendre et d'interagir avec l'API de façon interactive.

Si vous accédez à la section Kubernetes de l'Explorateur d'API, vous verrez les endpoints disponibles, tels que :

<Api version="v1" section="/cloud" method="GET" route={"/cloud/project/{serviceName}/kube"} />

#### Endpoints de l'API

- Obtenir la personnalisation d'un cluster existant :

<Api version="v1" section="/cloud" method="GET" route={"/cloud/project/\{serviceName\}/kube/\{kubeId\}/customization"} />


**Résultat :**
```json
{
    "apiServer": {
        "admissionPlugins": {
            "disabled": [],
            "enabled": ["AlwaysPullImages", "NodeRestriction"]
        }
    }
}
```

- Mettre à jour la personnalisation d'un cluster existant pour désactiver le plugin d'admission « AlwaysPullImages » (par exemple pour éviter que nos agents kubelet n'atteignent la limite de débit de téléchargement de Docker Hub) :

<Api version="v1" section="/cloud" method="PUT" route={"/cloud/project/\{serviceName\}/kube/\{kubeId\}/customization"} />


```json
{
    "apiServer": {
        "admissionPlugins": {
            "enabled": ["NodeRestriction"],
            "disabled": ["AlwaysPullImages"]
        }
    }
}
```

:::info
`kubeProxy` ne peut pas être modifié. Vous pouvez le définir uniquement à l'étape de création du cluster.
:::


- Créer un cluster Kubernetes dans la région GRA5 en désactivant le plugin d'admission « AlwaysPullImages » :

<Api version="v1" section="/cloud" method="POST" route={"/cloud/project/\{serviceName\}/kube"} />


```json
{
    "region": "GRA5",
    "name": "my-super-cluster",
    "customization": {
        "apiServer": {
            "admissionPlugins": {
                "enabled": ["NodeRestriction"],
                "disabled": ["AlwaysPullImages"]
            }
        }
    }
}
```

- Réinitialiser un cluster existant en désactivant le plugin d'admission « AlwaysPullImages » :

<Api version="v1" section="/cloud" method="POST" route={"/cloud/project/\{serviceName\}/kube/\{kubeId\}/reset"} />


```json
{
    "customization": {
        "apiServer": {
            "admissionPlugins": {
                "enabled": ["NodeRestriction"],
                "disabled": ["AlwaysPullImages"]
            }
        }
    }
}
```

### Configurer les plugins d'admission de l'API server via Terraform

Depuis la version 0.21 et supérieures de notre [provider Terraform OVH](https://registry.terraform.io/providers/ovh/ovh/latest/docs), vous pouvez configurer votre cluster Kubernetes (flags de l'API server, CoreDNS, IPVS...) via Terraform.

#### Récupérer les informations de votre cluster et de vos tokens API

Le « provider OVH » doit être configuré avec un ensemble d'identifiants :

* une `application_key`
* un `application_secret`
* une `consumer_key`

**Pourquoi ?**

Parce que, en arrière-plan, le « provider Terraform OVH » effectue des requêtes vers les API OVHcloud.

Pour récupérer ces informations nécessaires, suivez notre tutoriel [Premiers pas avec les API OVHcloud](/guides/manage-and-operate/api/first-steps).

Plus précisément, vous devez générer ces identifiants via la <CreateToken rights="GET=/*&POST=/*&PUT=/*&DELETE=/*">page de génération de tokens OVHcloud</CreateToken> avec les droits suivants : **GET**, **POST**, **PUT** et **DELETE** sur `/*`.

Lorsque vous avez généré vos tokens OVHcloud avec succès, veillez à les enregistrer, car vous devrez les utiliser très prochainement.

La dernière information nécessaire est le `service_name` : il s'agit de l'identifiant de votre projet Public Cloud.

**Comment l'obtenir ?**

Dans la section Public Cloud, vous pouvez récupérer l'identifiant de votre service grâce au bouton <code className="action">Copier dans le presse-papier</code>.

<img className="thumbnail" alt="Copier-coller le nom du service" src="/images/public-cloud/containers-orchestration/managed-kubernetes/apiserver-flags-configuration/get-service-name.png" loading="lazy" />

Vous utiliserez également cette information dans les fichiers de définition des ressources Terraform.

#### Instructions Terraform

Commencez par créer un fichier `provider.tf` avec la version minimale, l'endpoint européen (« ovh-eu ») et les clés précédemment récupérées dans ce guide.

Terraform 0.13 et versions ultérieures :

```bash
terraform {
  required_providers {
    ovh = {
      source  = "ovh/ovh"
    }
  }
}

provider "ovh" {
  endpoint           = "ovh-eu"
  application_key    = "<your_access_key>"
  application_secret = "<your_application_secret>"
  consumer_key       = "<your_consumer_key>"
}
```

Terraform 0.12 et versions antérieures :

```bash
# Configure the OVHcloud Provider
provider "ovh" {
  endpoint           = "ovh-eu"
  application_key    = "<your_access_key>"
  application_secret = "<your_application_secret>"
  consumer_key       = "<your_consumer_key>"
}
```

Les clés secrètes peuvent également être récupérées depuis votre environnement.

- `OVH_ENDPOINT`
- `OVH_APPLICATION_KEY`
- `OVH_APPLICATION_SECRET`
- `OVH_CONSUMER_KEY`

Cette dernière méthode (ou une alternative similaire) est recommandée pour éviter de stocker des données secrètes dans un dépôt source.

Nous avons ici défini l'endpoint `ovh-eu`, car nous souhaitons appeler l'API OVHcloud Europe, mais d'autres endpoints existent selon vos besoins :

* `ovh-eu` pour l'API OVHcloud Europe
* `ovh-us` pour l'API OVHcloud US
* `ovh-ca` pour l'API OVHcloud Amérique du Nord

Ensuite, créez un fichier `variables.tf` avec service_name :

```bash
variable service_name {
  type        = string
  default     = "`<your_service_name>`"
}
```

Définissez les ressources que vous souhaitez créer dans un nouveau fichier nommé `ovh_kube_cluster.tf` :

```bash
resource "ovh_cloud_project_kube" "cluster" {
  service_name = var.service_name
  name         = "my-super-cluster"
  region       = "GRA5"
  version      = "1.31"

  customization {
    apiserver {
      admissionplugins{
        enabled = ["NodeRestriction"]
        disabled = ["AlwaysPullImages"]
      }
    }
  }
}
```

Dans cette configuration de ressources, nous demandons à Terraform de créer un cluster Kubernetes, dans la région GRA5, avec la version Kubernetes 1.31, tout en désactivant le plugin d'admission « AlwaysPullImages » (par exemple pour éviter que nos agents kubelet n'atteignent la limite de débit de téléchargement de Docker Hub).

- Télécharger et installer les providers/plugins Terraform
