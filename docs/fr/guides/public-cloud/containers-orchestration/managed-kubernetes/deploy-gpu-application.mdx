## Objectif

Dans ce tutoriel, nous allons vous montrer comment déployer une application GPU sur un cluster OVHcloud Managed Kubernetes.

Les GPU fournissent la puissance de calcul nécessaire aux tâches d'IA/ML et de Deep Learning impliquant des calculs intensifs, comme la reconnaissance d'image, le traitement du langage naturel (NLP), ainsi que d'autres tâches gourmandes en calcul comme le transcodage vidéo et le traitement d'image.

L'utilisation de GPU avec Kubernetes vous permet d'étendre la scalabilité de Kubernetes aux applications d'IA/ML.

## Avant de commencer

Ce tutoriel suppose que vous disposez déjà d'un cluster OVHcloud Managed Kubernetes fonctionnel, ainsi que de connaissances de base sur son utilisation. Pour en savoir plus sur ces sujets, consultez le [guide de démarrage rapide d'OVHcloud Managed Kubernetes Service](/guides/public-cloud/containers-orchestration/managed-kubernetes/deploy-hello-world).

Vous devez également avoir [Helm](https://docs.helm.sh/) installé sur votre poste de travail et sur votre cluster. Consultez le tutoriel [comment installer Helm sur OVHcloud Managed Kubernetes Service](/guides/public-cloud/containers-orchestration/managed-kubernetes/install-helm).

## Prérequis

Pour tirer le meilleur parti des GPU sur OVHcloud Managed Kubernetes, de la manière la plus économique possible, et pour profiter de l'autoscaling du cluster, nous recommandons de créer des pools de nœuds GPU distincts dans vos clusters Kubernetes.

Les pools de nœuds GPU regroupent des nœuds de même flavor GPU et peuvent être configurés avec l'autoscaling pour gérer efficacement des charges de travail variables.

L'opérateur GPU que vous allez installer doit s'exécuter sur des nœuds Kubernetes équipés de GPU.

Créez un pool de nœuds qui utilise un flavor GPU. La liste des [flavors de worker nodes](/guides/public-cloud/containers-orchestration/managed-kubernetes/datacenters-nodes-storage-flavors#flavors-de-worker-node-disponibles) indique les flavors GPU et leurs régions, et la page des [tarifs Public Cloud](/links/public-cloud/prices) indique le modèle de GPU de chaque flavor. Le pilote installé plus loin dépend de l'architecture :

- Architectures actuelles : `A100-180`, `H100-*`, `L4-*`, `L40S-*` et `RTX5000-*` (Ampere, Hopper, Ada et Turing).
- Tesla V100 et V100S : `T1-*` et `T2-*` (Volta).

Si vous disposez déjà d'un cluster OVHcloud Kubernetes avec un pool de nœuds GPU, vous pouvez ignorer l'étape suivante « Création d'un pool de nœuds GPU avec autoscaling ».

:::warning
Les machines virtuelles GPU sont extrêmement puissantes et significativement plus coûteuses que les nœuds standards. Si vous utilisez généralement OVHcloud Public Cloud à petite échelle et/ou si vous êtes un nouvel utilisateur, vous devrez peut-être [augmenter votre quota Public Cloud](/guides/public-cloud/cross-functional/increasing-public-cloud-quota) pour accéder à ce type de machines pour votre projet. Notez également que ces machines ne sont disponibles que dans certaines de nos régions Public Cloud.

Notez aussi que si les worker nodes (qu'ils soient ajoutés manuellement ou via l'autoscaler du cluster) sont créés en quelques minutes, le passage au statut prêt de nos worker nodes GPU peut prendre un peu plus d'une heure.
:::

## En pratique

### Création d'un pool de nœuds GPU avec autoscaling

Cliquez sur votre cluster, puis sur l'onglet <code className="action">Pools de nœuds</code>.

Vous allez créer votre pool de nœuds GPU spécial.
Cliquez sur <code className="action">Ajouter un pool de nœuds</code>.

Dans le formulaire de création du pool de nœuds, saisissez un nom pour votre pool de nœuds GPU (par exemple, `gpu-node-pool`).

À l'étape de sélection du flavor, cliquez sur l'onglet <code className="action">GPU</code>. Pour un GPU actuel, choisissez un flavor tel que `H100`, `L4`, `L40S`, `A100-180` ou `RTX5000`. Pour une Tesla V100 ou V100S, choisissez un flavor `T1` ou `T2`, par exemple `T1-45`.

Définissez le nombre de nœuds et, si vous le souhaitez, activez **Autoscaling**, puis définissez la taille minimale et maximale du pool (par exemple, 3 au minimum et 10 au maximum).

Sélectionnez **Horaire** comme mode de facturation pour ce pool de nœuds GPU.

La création du pool de nœuds est maintenant en cours. Elle devrait être disponible en quelques minutes dans votre espace client OVHcloud.

```bash
kubectl get node --show-labels | grep "node.k8s.ovh/type=gpu"
```

Une fois que le statut du pool de nœuds affiche `OK` dans l'espace client OVHcloud, vous pouvez vérifier que les nœuds GPU sont correctement étiquetés à l'aide de la commande ci-dessus.

### NVIDIA GPU Operator

Le [NVIDIA GPU Operator](https://github.com/NVIDIA/gpu-operator) utilise l'[Operator Framework](https://github.com/operator-framework/getting-started) au sein de Kubernetes pour automatiser la gestion de tous les composants logiciels NVIDIA nécessaires au provisionnement des GPU. Ces composants incluent les pilotes NVIDIA (pour activer CUDA), le device plugin Kubernetes pour les GPU, le NVIDIA Container Runtime, l'étiquetage automatique des nœuds, la supervision basée sur DCGM, et d'autres.

![NVIDIA GPU Kubernetes Operator](/images/public-cloud/containers-orchestration/managed-kubernetes/deploying-gpu-application/nvidia-gpu-operator.jpeg)

Si cet opérateur vous intéresse, n'hésitez pas à consulter la [documentation officielle du NVIDIA GPU operator](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/overview.html).

### Installer le chart Helm du NVIDIA GPU Operator

Pour ce tutoriel, nous utilisons le [chart Helm NVIDIA GPU Operator](https://github.com/NVIDIA/gpu-operator/tree/main/deployments/gpu-operator) disponible sur le [dépôt NVIDIA](https://github.com/nvidia/). Le chart est [entièrement configurable](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/getting-started.html). Les commandes ci-dessous ne définissent que les options de pilote requises par l'architecture GPU de votre pool de nœuds.

Ajoutez le dépôt Helm NVIDIA :

:::info
Le chart Helm Nvidia a changé d'emplacement. Si vous avez déjà ajouté un dépôt nommé `nvidia`, vous pouvez le supprimer : `helm repo remove nvidia`.

:::


```bash
helm repo add nvidia https://helm.ngc.nvidia.com/nvidia
helm repo update
```

Cela ajoutera le dépôt NVIDIA et mettra à jour tous vos dépôts : 

```console
$ helm repo add nvidia https://helm.ngc.nvidia.com/nvidia
helm repo update
"nvidia" has been added to your repositories
Hang tight while we grab the latest from your chart repositories...
...Successfully got an update from the "nvidia" chart repository
[...]
Update Complete. ⎈Happy Helming!⎈
```

Installez le GPU Operator dans le namespace `gpu-operator`. Choisissez l'onglet qui correspond au flavor GPU du pool de nœuds. Chaque commande compile les modules du pilote pour le noyau du nœud.

<Tabs>
<Tab label="L4, L40S, H100, A100">

Dans le [catalogue de pilotes NGC](https://catalog.ngc.nvidia.com/orgs/nvidia/-/containers/driver/-/tags), sélectionnez le dernier tag Ubuntu 22.04 de la forme `<version>-ubuntu22.04`. Passez cette version à `driver.version` (par exemple `595.91.07`).

```bash
helm install gpu-operator nvidia/gpu-operator \
  -n gpu-operator --create-namespace \
  --set driver.version=<version> \
  --set driver.usePrecompiled=false
```

</Tab>
<Tab label="RTX 5000">

Dans le [catalogue de pilotes NGC](https://catalog.ngc.nvidia.com/orgs/nvidia/-/containers/driver/-/tags), sélectionnez le dernier tag Ubuntu 22.04 de la forme `<version>-ubuntu22.04`. Passez cette version à `driver.version` (par exemple `595.91.07`).

La Quadro RTX 5000 ne s'initialise pas lorsque le firmware GPU est activé. Créez une ConfigMap qui le désactive :

```bash
kubectl create namespace gpu-operator
kubectl create configmap kernel-module-params -n gpu-operator \
  --from-literal=nvidia.conf=NVreg_EnableGpuFirmware=0
```

Les modules noyau open source utilisent toujours le firmware GPU : installez donc les modules propriétaires avec cette ConfigMap :

```bash
helm install gpu-operator nvidia/gpu-operator \
  -n gpu-operator --create-namespace \
  --set driver.version=<version> \
  --set driver.kernelModuleType=proprietary \
  --set driver.kernelModuleConfig.name=kernel-module-params \
  --set driver.usePrecompiled=false
```

</Tab>
<Tab label="Tesla V100 et V100S (T1, T2)">

Ces cartes utilisent l'architecture Volta, que la dernière branche de pilotes ne prend pas en charge. Dans la [matrice des pilotes et architectures NVIDIA](https://docs.nvidia.com/datacenter/tesla/drivers/latest/cuda-toolkit-driver-and-architecture-matrix.html), repérez la dernière branche de pilotes qui prend encore en charge Volta. Dans le [catalogue de pilotes NGC](https://catalog.ngc.nvidia.com/orgs/nvidia/-/containers/driver/-/tags), sélectionnez le dernier tag Ubuntu 22.04 de cette branche, de la forme `<version>-ubuntu22.04`. Passez cette version à `driver.version` (par exemple `580.178.04`).

```bash
helm install gpu-operator nvidia/gpu-operator \
  -n gpu-operator --create-namespace \
  --set driver.version=<version> \
  --set driver.usePrecompiled=false
```

Les modules noyau open source ne prennent pas en charge Volta : l'opérateur compile donc les modules propriétaires.

</Tab>
</Tabs>

:::info
Si le cluster mélange des nœuds Tesla V100 et d'autres flavors GPU, utilisez la commande Tesla V100 : cette branche de pilotes prend aussi en charge les architectures actuelles. Si l'un des flavors est une RTX 5000, créez également la ConfigMap et ajoutez les options `driver.kernelModuleType` et `driver.kernelModuleConfig.name` de l'onglet RTX 5000.
:::

La compilation des modules prend quelques minutes. Le pod `nvidia-driver-daemonset` reste non prêt jusqu'à la fin de la compilation.

#### Utiliser un pilote précompilé (facultatif)

Sur les nœuds L4, L40S, H100 et A100, une image de [pilote précompilé](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/precompiled-drivers.html) évite la compilation. NVIDIA ne publie ces images que pour certains noyaux Ubuntu 22.04. Relevez le noyau du nœud :

```bash
kubectl get nodes -o jsonpath='{.items[0].status.nodeInfo.kernelVersion}'
```

Dans le [catalogue de pilotes NGC](https://catalog.ngc.nvidia.com/orgs/nvidia/-/containers/driver/-/tags), cherchez un tag Ubuntu 22.04 générique qui contient ce noyau, et passez-le à `driver.image` (par exemple `driver:580-5.15.0-187-generic-ubuntu22.04`). Si aucun tag ne contient le noyau du nœud, gardez la commande de l'onglet L4, L40S, H100, A100.

```bash
helm install gpu-operator nvidia/gpu-operator \
  -n gpu-operator --create-namespace \
  --set driver.image=driver:<tag>
```

### Vérifier l'installation du GPU Operator

Lorsque le GPU operator est actif et en cours d'exécution, il ajoute des labels `nvidia.com/gpu` sur les nœuds GPU.

Vous pouvez vérifier les nouveaux labels avec la commande :

```bash
kubectl get nodes --show-labels | grep "nvidia.com/gpu"
```

Les nouveaux labels ne devraient apparaître que sur vos nœuds GPU :

![Labels NVIDIA des nœuds GPU](/images/public-cloud/containers-orchestration/managed-kubernetes/deploying-gpu-application/gpu-nodes-labels.png)

### Exécuter des applications GPU d'exemple

Vous pouvez maintenant exécuter une application/workload GPU sur votre cluster.

Pour configurer les Pods afin qu'ils consomment des GPU, vous devez utiliser une limite de ressource dans votre fichier manifeste YAML. Vous devez spécifier une limite de ressource dans une spécification de Pod à l'aide de la paire clé-valeur suivante :

```bash
Key: nvidia.com/gpu
Value: Number of GPUs to consume
```

Créez un fichier manifeste YAML `vector.yaml` avec le contenu suivant :

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: cuda-vectoradd
spec:
  restartPolicy: OnFailure
  containers:
  - name: cuda-vectoradd
    image: "nvcr.io/nvidia/k8s/cuda-sample:vectoradd-cuda11.7.1"
    resources:
      limits:
         nvidia.com/gpu: 1
```

Appliquez-le :

```bash
kubectl apply -f vector.yaml -n default
```

Puis observez le démarrage du Pod :

```bash
kubectl get pod -n default -w
```

Vous devriez obtenir un résultat comme celui-ci :

```console
$ kubectl apply -f vector.yaml -n default
pod/cuda-vectoradd created

$ kubectl get pod -n default -w
NAME             READY   STATUS              RESTARTS   AGE
cuda-vectoradd   0/1     ContainerCreating   0          4s
cuda-vectoradd   0/1     Completed   0          35s
```

Une fois que `cuda-vectoradd` a démarré, exécuté et terminé sa tâche, consultez les logs avec la commande suivante :

```bash
kubectl logs cuda-vectoradd -n default
```

```console
$ kubectl logs cuda-vectoradd -n default
[Vector addition of 50000 elements]
Copy input data from the host memory to the CUDA device
CUDA kernel launch with 196 blocks of 256 threads
Copy output data from the CUDA device to the host memory
Test PASSED
Done
```

Notre premier workload GPU vient de démarrer et a terminé sa tâche dans notre cluster OVHcloud Managed Kubernetes.

### Dépannage

Si le pod `nvidia-driver-daemonset` reste non prêt après la compilation, exécutez `nvidia-smi` dans ce pod :

```bash
kubectl exec -n gpu-operator ds/nvidia-driver-daemonset -c nvidia-driver-ctr -- nvidia-smi
```

S'il renvoie `No devices were found`, consultez le journal du noyau :

```bash
kubectl exec -n gpu-operator ds/nvidia-driver-daemonset -c nvidia-driver-ctr -- sh -c 'dmesg | grep NVRM | tail -n 20'
```

Des lignes telles que `Cannot initialize GSP firmware RM`, `kgspWaitForGfwBootOk` ou `RmInitAdapter failed` indiquent que le firmware GPU n'a pas démarré. Cela se produit sur les nœuds RTX 5000. Désinstallez l'opérateur, puis réinstallez-le avec la commande de l'onglet RTX 5000.
