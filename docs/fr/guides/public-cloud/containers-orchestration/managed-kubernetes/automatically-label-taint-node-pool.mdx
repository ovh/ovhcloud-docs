## Objectif

Ce guide vous montre comment gérer l'ordonnancement sur votre OVHcloud Managed Kubernetes Service :

- propager des *labels*, des *annotations* et des *taints* aux nœuds grâce au template d'un pool de nœuds (recommandé avec l'autoscaling, lorsque les nœuds sont créés et supprimés automatiquement)
- cibler tous les nœuds d'un pool de nœuds avec `kubectl` grâce au label `nodepool` propagé

Cela permet plusieurs scénarios d'ordonnancement, comme l'optimisation du coût d'un cluster en répartissant les pods entre deux pools de nœuds dotés de labels, ou la réservation d'un pool de nœuds à des charges de travail spécifiques.

## Prérequis

- un [projet Public Cloud](/links/public-cloud/public-cloud) au sein de votre compte OVHcloud
- [kubectl](https://kubernetes.io/fr/docs/tasks/tools/) configuré pour accéder à votre cluster
- [Terraform](https://developer.hashicorp.com/terraform/install), si vous créez le pool de nœuds avec Terraform

## En pratique

### Créer un cluster Kubernetes

Vous pouvez suivre le guide étape par étape de création d'un cluster Kubernetes si vous souhaitez le créer via la [console OVHcloud](/guides/public-cloud/containers-orchestration/managed-kubernetes/label-nodeaffinity-node-pools#création-du-cluster) ou via [Terraform](/guides/public-cloud/containers-orchestration/managed-kubernetes/create-cluster).

### Gérer les pools de nœuds via l'API

Vous pouvez créer un template de pool de nœuds via l'API, par exemple avec l'[Explorateur d'API](/guides/manage-and-operate/api/first-steps).

Pour créer un pool de nœuds avec un template (labels, annotations, taints, etc.), vous devez effectuer un appel sur :

<Api version="v1" section="/cloud" method="POST" route={"/cloud/project/\{serviceName\}/kube/\{kubeId\}/nodepool"} />


avec le corps de requête suivant :

```json
{
  "name": "my-system-node-pool",
  "flavorName": "b3-8",
  "desiredNodes": 1,
  "minNodes": 0,
  "maxNodes": 1,
  "template": {
    "metadata": {
      "annotations": {
        "my-annotation": "my-value"
      },
      "labels": {
        "app": "my-app"
      }
    },
    "spec": {
      "unschedulable": false,
      "taints": [
        {
          "effect": "NoSchedule",
          "key": "CriticalAddonsOnly",
          "value": "true"
        }
      ]
    }
  }
}
```

Dans le chemin de l'endpoint, remplacez `serviceName` et `kubeId` par l'identifiant de votre projet Public Cloud et celui de votre cluster.

`effect` accepte `NoSchedule` (les pods sans tolérance correspondante ne peuvent pas être ordonnancés), `PreferNoSchedule` (Kubernetes évite de les ordonnancer) ou `NoExecute` (ils sont évincés). `key` et `value` peuvent prendre toute valeur propre à vos charges de travail ; `CriticalAddonsOnly=true` est la paire tolérée par les composants système OVHcloud. Les tolérances doivent correspondre à la clé et à la valeur, ainsi qu'à l'effet lorsqu'il est précisé.

Le taint `CriticalAddonsOnly` réserve le pool de nœuds aux charges de travail système d'OVHcloud (CoreDNS, metrics-server, etc.), qui le tolèrent. Avec l'effet `NoSchedule`, les charges de travail qui ne tolèrent pas ce taint ne peuvent pas être ordonnancées sur ce pool de nœuds.

:::warning
Un cluster MKS a besoin d'au moins un nœud sur lequel ses composants système peuvent être déployés. Il peut s'agir :

- d'un nœud sans aucun taint ;
- d'un nœud dont le seul taint est `CriticalAddonsOnly`.

Si tous les nœuds portent des taints qui empêchent le déploiement de ces composants, le cluster ne sera pas opérationnel.

:::

:::tip
Nous recommandons au moins deux nœuds dans un pool de nœuds dédié aux charges de travail système. Un nœud est le minimum pour que le cluster soit opérationnel, mais deux nœuds offrent une meilleure disponibilité et facilitent les mises à niveau.

:::

Pour évincer les pods qui ne tolèrent pas le taint, au lieu de seulement empêcher tout nouvel ordonnancement, utilisez l'effet `NoExecute`. Les pods qui doivent rester sur le nœud ont besoin d'une tolérance avec l'effet `NoExecute`.

#### Supprimer le pool de nœuds via l'API

Pour supprimer un pool de nœuds avec l'API, utilisez l'appel suivant :

<Api version="v1" section="/cloud" method="DELETE" route={"/cloud/project/\{serviceName\}/kube/\{kubeId\}/nodepool/\{nodePoolId\}"} />


avec les informations suivantes :

- `serviceName` : l'identifiant de votre projet Public Cloud
- `kubeId` : l'identifiant de votre cluster
- `nodePoolId` : l'identifiant du pool de nœuds à supprimer

### Créer un template de pool de nœuds avec Terraform

Consultez le [provider Terraform OVHcloud](https://registry.terraform.io/providers/ovh/ovh/latest/docs/resources/cloud_project_kube_nodepool) pour la documentation complète.

#### Récupérer les informations de votre cluster et de vos tokens API

Le « provider OVH » doit être configuré avec un ensemble d'identifiants :

* une `application_key`
* un `application_secret`
* une `consumer_key`

**Pourquoi ?**

Parce que, en arrière-plan, le « provider Terraform OVH » effectue des requêtes vers les API OVHcloud.

Pour récupérer ces informations nécessaires, suivez notre tutoriel « [Premiers pas avec les API OVHcloud](/guides/manage-and-operate/api/first-steps) ».

Plus précisément, vous devez générer ces identifiants via la <CreateToken rights="GET=/*&POST=/*&PUT=/*&DELETE=/*">page de génération de tokens OVHcloud</CreateToken> avec les droits suivants : **GET**, **POST**, **PUT** et **DELETE** sur `/*`.

Lorsque vous avez généré vos tokens OVHcloud avec succès, veillez à les enregistrer, car vous devrez les utiliser très prochainement.

La dernière information nécessaire est le `service_name` : il s'agit de l'identifiant de votre projet Public Cloud.

**Comment l'obtenir ?**

Pour récupérer l'identifiant de votre projet Public Cloud, cliquez sur le sélecteur de projet en haut du menu de gauche de votre projet Public Cloud, puis sur l'icône de copie située sur la ligne de votre projet (elle apparaît au survol de la ligne).

Vous utiliserez également cette information dans les fichiers de définition des ressources Terraform.

#### Instructions Terraform

Commencez par créer un fichier `provider.tf` avec l'endpoint européen (`ovh-eu`) et les clés précédemment récupérées dans ce guide.

```terraform
terraform {
  required_providers {
    ovh = {
      source = "ovh/ovh"
    }
  }
}

provider "ovh" {
  endpoint           = "ovh-eu"
  application_key    = "<your_access_key>"
  application_secret = "<your_application_secret>"
  consumer_key       = "<your_consumer_key>"
}
```

Les clés secrètes peuvent également être récupérées depuis votre environnement.

- `OVH_ENDPOINT`
- `OVH_APPLICATION_KEY`
- `OVH_APPLICATION_SECRET`
- `OVH_CONSUMER_KEY`

Cette dernière méthode (ou une alternative similaire) est recommandée pour éviter de stocker des données secrètes dans un dépôt source.

Nous avons ici défini l'endpoint `ovh-eu`, car nous souhaitons appeler l'API OVHcloud Europe, mais d'autres endpoints existent selon vos besoins :

* `ovh-eu` pour l'API OVHcloud Europe
* `ovh-us` pour l'API OVHcloud US
* `ovh-ca` pour l'API OVHcloud Amérique du Nord

Ensuite, définissez les ressources que vous souhaitez créer dans un nouveau fichier nommé `ovh_kube_cluster_nodepool.tf` :

```terraform
resource "ovh_cloud_project_kube_nodepool" "pool" {
    service_name  = "<service_name>"
    kube_id       = "<cluster_id>"
    name          = "my-system-node-pool"
    flavor_name   = "b3-8"
    desired_nodes = 1
    min_nodes     = 0
    max_nodes     = 1
    template {
        metadata {
            annotations = {
                my-annotation = "my-value"
            }
            labels = {
                app = "my-app"
            }
        }
        spec {
            unschedulable = false
            taints = [
                {
                    effect = "NoSchedule" // NoSchedule, PreferNoSchedule ou NoExecute
                    key    = "CriticalAddonsOnly" // Ou une clé propre à vos charges de travail
                    value  = "true" // Ou une valeur propre à vos charges de travail
                }
            ]
        }
    }
}
```

:::info
N'oubliez pas de remplacer `<service_name>` et `<cluster_id>` par vos valeurs.

:::


Dans cette configuration de ressources, nous demandons à Terraform d'ajouter un pool de nœuds avec un template à votre cluster Kubernetes. Les valeurs de `effect` et l'avertissement sur les composants système de la section « [Gérer les pools de nœuds via l'API](#gérer-les-pools-de-nœuds-via-lapi) » s'appliquent également ici.

:::info
Consultez la documentation du **provider Terraform ovh** pour voir la [définition de la ressource ovh_cloud_project_kube_nodepool](https://registry.terraform.io/providers/ovh/ovh/latest/docs/resources/cloud_project_kube_nodepool).
:::

### Vérifier que tout est correctement configuré

Pour effectuer certaines opérations sur vos nœuds via la CLI `kubectl`, nous vous invitons à suivre notre guide pour [configurer les paramètres par défaut](/guides/public-cloud/containers-orchestration/managed-kubernetes/configure-kubectl).

Une fois que vous pouvez accéder au cluster via la commande `kubectl`, affichons notre pool de nœuds :

```bash
$ kubectl get nodepool
NAME           FLAVOR   AUTOSCALED   MONTHLYBILLED   ANTIAFFINITY   DESIRED   CURRENT   UP-TO-DATE   AVAILABLE   MIN   MAX   AGE
my-system-node-pool   b3-8     false        false           false          1         1         1            1           0     1     8m13s
```

Notre pool de nœuds existe et nous pouvons voir sa configuration.

Examinons maintenant le template du pool de nœuds :

```bash
$ kubectl describe nodepool my-system-node-pool
Name:         my-system-node-pool
Namespace:
Labels:       id=xxxxxxxx-xxxxx-xxxx-xxxx-xxxxxxxxxxx
Annotations:  <none>
API Version:  kube.cloud.ovh.com/v1alpha1

...
Spec:
  Anti Affinity:  false
  Autoscale:      false
  ...
  Template:
    Metadata:
      Annotations:
        my-annotation:  my-value
      Finalizers:
      Labels:
        App:  my-app

        Effect:       NoSchedule

        Value:        true
```

Le template que vous avez défini demandera à Kubernetes de propager cette configuration à tous les nœuds de ce pool de nœuds.

Affichons notre nœud. Nous devrions avoir 1 nœud en cours d'exécution :

```bash
$ kubectl get nodes

```

Vérifiez que le label, l'annotation et le taint que vous avez définis sont bien propagés au nœud :

```bash
$ kubectl describe node my-system-node-pool-node-5781fa
```

Et si vous modifiez la configuration du pool de nœuds pour activer l'autoscaling et augmenter sa taille maximale, toutes les informations que vous avez définies seront propagées aux nouveaux nœuds.

### Agir sur les nœuds existants avec kubectl

Un taint, un cordon ou un drain appliqué avec `kubectl` n'affecte que les nœuds qui existent à ce moment-là. Lorsque l'autoscaling crée de nouveaux nœuds, ceux-ci n'héritent pas de ces modifications faites avec `kubectl` : utilisez le template du pool de nœuds décrit ci-dessus pour une configuration durable.

Grâce au label `nodepool` propagé à chaque nœud, vous pouvez cibler tous les nœuds d'un pool de nœuds donné en ajoutant `-l "nodepool=<node_pool_name>"` à des commandes comme `kubectl cordon`, `kubectl drain` ou `kubectl taint node`. Pour les opérations elles-mêmes et leurs effets, consultez la documentation Kubernetes sur les [taints et tolérances](https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/) et sur le [drain sécurisé d'un nœud](https://kubernetes.io/docs/tasks/administer-cluster/safely-drain-node/).

### Supprimer le pool de nœuds avec Terraform

Pour supprimer le pool de nœuds, retirez son bloc de ressource `ovh_cloud_project_kube_nodepool` du fichier `ovh_kube_cluster_nodepool.tf`, puis vérifiez et appliquez le plan obtenu :

```bash
$ terraform plan

Plan: 0 to add, 0 to change, 1 to destroy.

$ terraform apply

Apply complete! Resources: 0 added, 0 changed, 1 destroyed.
```

Seule la ressource que vous avez retirée de la configuration est détruite.
