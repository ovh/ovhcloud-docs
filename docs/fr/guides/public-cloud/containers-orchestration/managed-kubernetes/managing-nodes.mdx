## Objectif

Le service OVHcloud Managed Kubernetes met à votre disposition des clusters Kubernetes prêts pour la production, sans les contraintes liées à leur installation ou à leur exploitation.

Ce guide traite l'une des premières étapes suivant la commande d'un cluster : la gestion des nœuds et des pools de nœuds.

Selon la méthode que vous préférez, vous pouvez les gérer via :

- L'<ManagerLink to="/">espace client OVHcloud</ManagerLink>.
- L'<ApiLink>API OVHcloud</ApiLink>.
- La Custom Resource Definition (CRD) `NodePools`, via `kubectl`.

Chacune de ces méthodes est détaillée ci-dessous afin de vous aider à dimensionner et à gérer efficacement votre infrastructure Kubernetes.

## Prérequis

- Disposer d'un cluster OVHcloud Managed Kubernetes.
- Si vous prévoyez de gérer vos pools de nœuds à l'aide de la CRD `NodePools`, assurez-vous d'avoir installé l'outil en ligne de commande [kubectl](https://kubernetes.io/docs/reference/kubectl/overview/). Vous trouverez des [instructions d'installation détaillées](https://kubernetes.io/docs/tasks/tools/install-kubectl/) sur le site officiel de Kubernetes.

### À propos des nœuds et des pools de nœuds

<Tabs>
  <Tab label="Via l'espace client OVHcloud">
    Dans votre cluster OVHcloud Managed Kubernetes, les nœuds sont regroupés en pools de nœuds (des groupes de nœuds partageant la même configuration).
    
    Lorsque vous commandez un nouveau cluster, celui-ci est créé avec un pool de nœuds par défaut. Consultez notre guide « [Créer un cluster](/guides/public-cloud/containers-orchestration/managed-kubernetes/create-cluster) » pour plus d'informations.
    
    Ce guide explique comment effectuer quelques opérations de base sur les nœuds et les pools de nœuds depuis la section Public Cloud de votre <ManagerLink to="/">espace client OVHcloud</ManagerLink>.
  </Tab>
  <Tab label="Via l'API OVHcloud">
    Dans votre cluster OVHcloud Managed Kubernetes, les nœuds sont regroupés en pools de nœuds (des groupes de nœuds partageant la même configuration).
    
    Dans l'appel de création du cluster, vous pouvez spécifier les caractéristiques d'un premier pool de nœuds qui sera créé avec celui-ci. Vous pouvez ensuite modifier ce pool de nœuds, ou ajouter d'autres pools de nœuds de tailles et de types différents.
    
    À sa création, un pool de nœuds est défini par son nom (`name`), le type d'instance choisi dans notre catalogue (`flavorName`), le nombre de nœuds identiques que vous souhaitez y placer (`desiredNodes`) et, éventuellement, des bornes que vous définissez pour encadrer la valeur de `desiredNodes` (`minNodes` et `maxNodes`).
    
    Vous pouvez également activer la fonctionnalité `autoscale` : la valeur `desiredNodes` sera alors mise à jour automatiquement pendant l'exécution, dans les limites de `minNodes` et `maxNodes`, en fonction des réservations de ressources de votre workload (consultez le guide « [Utiliser le cluster autoscaler](/guides/public-cloud/containers-orchestration/managed-kubernetes/using-cluster-autoscaler) »).
    
    Le booléen `antiAffinity` garantit que les nœuds de ce pool de nœuds seront créés sur des hyperviseurs (machines physiques) différents, assurant ainsi la meilleure disponibilité possible pour votre workload. Le nombre maximal de nœuds est fixé à 5 lorsque cette fonctionnalité est activée sur un pool de nœuds (vous pouvez bien entendu créer plusieurs pools de nœuds comportant chacun 5 nœuds en anti-affinité au maximum).
    
    La propriété `template` vous permet de définir certaines caractéristiques (annotations, finalizers, labels, taints, ordonnançabilité) qui seront appliquées à chaque nœud de ce pool de nœuds.
    
    Si votre cluster a été créé dans une région 3AZ, vous devez également spécifier une AZ à l'aide du paramètre `availabilityZones`.
    
    Vous pouvez activer la création de Floating IP avec le paramètre `attachFloatingIps`. Si le booléen `enabled` est défini sur `true`, une Floating IP sera attachée à chaque nœud.
    
    Enfin, le booléen `monthlyBilled` garantit que tous les nœuds d'un pool de nœuds seront créés en mode de facturation mensuelle et bénéficieront donc de la remise mensuelle.
    
    Après la création, les propriétés `desiredNodes`, `minNodes`, `maxNodes`, `autoscale` et `template` peuvent également être modifiées à tout moment.
    
    Ce guide explique comment effectuer quelques opérations de base sur les nœuds et les pools de nœuds via l'<ManagerLink to="/">API OVHcloud</ManagerLink> : ajouter des nœuds à un pool de nœuds existant, créer un nouveau pool de nœuds, etc.
  </Tab>
  <Tab label="Via la CRD NodePools">
    Dans votre cluster OVHcloud Managed Kubernetes, les nœuds sont regroupés en pools de nœuds (des groupes de nœuds partageant la même configuration).
    
    Lorsque vous créez votre cluster, celui-ci est créé avec un pool de nœuds par défaut. Vous pouvez ensuite modifier la taille de ce pool de nœuds, ou ajouter d'autres pools de nœuds de tailles et de types différents.
    
    Ce guide explique comment effectuer quelques opérations de base sur les nœuds et les pools de nœuds à l'aide de la CRD `NodePools` : ajouter des nœuds à un pool de nœuds existant, créer un nouveau pool de nœuds, etc.
  </Tab>
</Tabs>

  <Tab label="Via la CRD NodePools">
    Les [Custom Resources](https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/) Kubernetes sont des extensions de l'API Kubernetes. Comme les ressources Kubernetes par défaut, les Custom Resources sont des endpoints de l'API Kubernetes qui stockent des collections d'objets d'API d'un type donné. Les Custom Resources permettent d'étendre facilement Kubernetes en y ajoutant de nouvelles fonctionnalités et de nouveaux comportements.
    
    La manière la plus simple d'ajouter une Custom Resource à Kubernetes consiste à définir une [`CustomResourceDefinition` (CRD)](https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/#customresourcedefinitions) accompagnée du schéma de la ressource.
    
    L'un de nos objectifs lors du développement des pools de nœuds pour OVHcloud Managed Kubernetes était de permettre à nos utilisateurs de gérer intégralement leurs pools de nœuds (et par extension les nœuds eux-mêmes) depuis Kubernetes. La solution logique consistait donc à les proposer sous forme de Custom Resources dans votre cluster Kubernetes, en développant la CRD `NodePools`.
    
    Pour vérifier que la CRD `NodePools` est disponible dans votre cluster, exécutez :
    
    ```bash
    kubectl get crd
    ```

    Vous pouvez obtenir le détail de la CRD `NodePools` en exécutant :
    
    ```bash
    kubectl describe crd nodepools.kube.cloud.ovh.com
    ```
    
    La partie la plus intéressante est la spécification de la CRD, qui décrit l'objet `NodePool` et ses propriétés :
    
    ```yaml
    spec:
      description: NodePoolSpec defines the desired state of NodePool
      properties:
        antiAffinity:
          description: Represents whether the pool should deploy instances exclusively on different hypervisors.
          nullable: true
          type: boolean
        attachFloatingIPs:
          description: AttachFloatingIPs describe network exposition of all nodes in the pool.
          nullable: true
          properties:
            enabled:
              description: Enabled describe the node network exposition. If True, a FloatingIP will be assigned to each node.
              type: boolean
          type: object
        autoscale:
          description: Represents whether the pool should be autoscaled.
          nullable: true
          type: boolean
        autoscaling:
          description: Represents the autoscaling customization of a node pool.
          nullable: true
          properties:
            scaleDownUnneededTimeSeconds:
              description: Represents how long a node should be unneeded before it is eligible for scale down.
              format: int32
              minimum: 0
              nullable: true
              type: integer
            scaleDownUnreadyTimeSeconds:
              description: Represents how long an unready node should be unneeded before it is eligible for scale down.
              format: int32
              minimum: 0
              nullable: true
              type: integer
            scaleDownUtilizationThreshold:
              description: Represents the ratio of used resources (CPU & RAM)
                over allocatable resources below which a node is eligible for
                scale down Kubebuilder does not handle float, this must be a
                string.
              nullable: true
              type: string
          type: object
        availabilityZones:
          description: Represents the availability zones of the node pool.
          items:
            type: string
          nullable: true
          type: array
        desiredNodes:
          description: Represents the number of nodes wanted in the pool.
          format: int32
          maximum: 999
          minimum: 0
          type: integer
        flavor:
          description: Represents the node flavors wanted in the pool.
          type: string
        maxNodes:
          description: Represents the maximum number of nodes which should be
            present in the pool.
          format: int32
          maximum: 999
          minimum: 0
          nullable: true
          type: integer
        minNodes:
          description: Represents the minimum number of nodes which should be
            present in the pool.
          format: int32
          maximum: 100
          minimum: 0
          nullable: true
          type: integer
        monthlyBilled:
          description: Represents the billing type of the pool. False means that the pool is hourly-billed.
          nullable: true
          type: boolean
        template:
          description: Template describes the configuration of the nodes in the pool. On change, it will be applied to existing and future nodes.
          nullable: true
          properties:
            metadata:
              description: Standard object's metadata.
              properties:
                annotations:
                  additionalProperties:
                    type: string
                  description: 'Annotations is an unstructured key value map
                    stored with a resource that may be set by external tools
                    to store and retrieve arbitrary metadata. They are not queryable
                    and should be preserved when modifying objects. More info:
                    http://kubernetes.io/docs/user-guide/annotations'
                  type: object
                finalizers:
                  description: Must be empty before the object is deleted from
                    the registry. Each entry is an identifier for the responsible
                    component that will remove the entry from the list. If the
                    deletionTimestamp of the object is non-nil, entries in this
                    list can only be removed.
                  items:
                    type: string
                  type: array
                labels:
                  additionalProperties:
                    type: string
                  description: 'Map of string keys and values that can be used
                    to organize and categorize (scope and select) objects. May
                    match selectors of replication controllers and services.
                    More info: http://kubernetes.io/docs/user-guide/labels'
                  type: object
              required:
              - annotations
              - finalizers
              - labels
              type: object
            spec:
              description: Specification of the desired behavior of the node.
              properties:
                taints:
                  description: If specified, the node's taints.
                  items:
                    description: The node this Taint is attached to has the "effect" on any pod that does not tolerate the Taint.
                    properties:
                      effect:
                        description: Required. The effect of the taint on pods
                          that do not tolerate the taint. Valid effects are
                          NoSchedule, PreferNoSchedule and NoExecute.
                        type: string
                      key:
                        description: Required. The taint key to be applied to a node.
                        type: string
                      timeAdded:
                        description: TimeAdded represents the time at which the taint was added. It is only written for NoExecute taints.
                        format: date-time
                        type: string
                      value:
                        description: The taint value corresponding to the taint
                          key.
                        type: string
                    required:
                    - effect
                    - key
                    type: object
                  type: array
                unschedulable:
                  description: 'Unschedulable controls node schedulability of
                    new pods. By default, node is schedulable. More info: https://kubernetes.io/docs/concepts/nodes/node/#manual-node-administration'
                  type: boolean
              required:
              - taints
              - unschedulable
              type: object
          required:
          - metadata
          - spec
          type: object
      required:
      - flavor
     type: object
    ```
    
    Après la création :
    
    - La valeur `desiredNodes` peut être modifiée : le pool de nœuds sera automatiquement redimensionné pour s'adapter à cette nouvelle valeur.
    - `minNodes`, `maxNodes`, `autoscale` et `autoscaling` peuvent également être modifiés à tout moment.
    - /!\ `flavor`, `name` et `antiAffinity` ne sont pas modifiables.
    
    Notez que `maxNodes` est fixé par défaut à 5 lorsque `antiAffinity` est activé.
    
    Pour configurer l'autoscaling du cluster à partir des pools de nœuds, suivez les guides « [Configurer le cluster autoscaler](/guides/public-cloud/containers-orchestration/managed-kubernetes/configure-cluster-autoscaler) » et « [Exemple de cluster autoscaler](/guides/public-cloud/containers-orchestration/managed-kubernetes/cluster-autoscaler-example) ».  
    Si vous développez vos propres scripts d'autoscaling, nous vous recommandons vivement de définir `minNodes` et `maxNodes`.

### Créer un pool de nœuds

<Tabs>
  <Tab label="Via l'espace client OVHcloud">
    Dans l'onglet *Pools de nœuds*, cliquez sur le bouton <code className="action">Ajouter un pool de nœuds</code>.
    
    <img className="thumbnail" alt="Créer un pool de nœuds" src="/images/public-cloud/containers-orchestration/managed-kubernetes/managing-nodes/managing_nodes-06.png" loading="lazy" />

Remplissez les champs afin de créer un nouveau pool de nœuds.
    
    :::warning
    Le **nom du pool de nœuds** doit être en minuscules. Les caractères « _ » et « . » ne sont pas autorisés. Le nom d'un pool de nœuds ne peut pas commencer par un chiffre.

    :::

    
    Les étapes suivantes de configuration du pool de nœuds sont décrites dans le guide « [Créer un cluster](/guides/public-cloud/containers-orchestration/managed-kubernetes/create-cluster) ».
    
    :::info
    Pour en savoir plus sur les flavors de la gamme OVHcloud actuelle, [consultez cette page](/links/public-cloud/public-cloud).

    :::

  </Tab>
  <Tab label="Via l'API OVHcloud">
    Utilisez l'endpoint d'API `POST /cloud/project/{serviceName}/kube/{kubeId}/nodepool` pour créer un nouveau pool de nœuds :
    
    <Api version="v1" section="/cloud" method="POST" route={"/cloud/project/\\{serviceName\\}/kube/\\{kubeId\\}/nodepool"} />

**Requête :**
    
    ```json 
    {
      "antiAffinity": false,
      "autoscale": false,
      "desiredNodes": 1,
      "flavorName": "b2-7",
      "monthlyBilled": false,
      "name": "my-node-pool"
    }
    ```
    
    Vous devrez lui fournir un paramètre `flavorName`, correspondant à la flavor de l'instance que vous souhaitez créer. Pour ce tutoriel, choisissez un nœud à usage générique, comme la flavor `b2-7`.
    
    Si vous souhaitez que votre pool de nœuds comporte au moins un nœud, définissez `desiredNodes` sur une valeur supérieure à 0.
    
    Dans une région 3AZ, le paramètre `availabilityZones` est également obligatoire.
    Pour connaître les `availabilityZones` disponibles dans une région, vous pouvez utiliser l'endpoint d'API `GET /cloud/project/{serviceName}/capabilities/productAvailability `.
  </Tab>
</Tabs>

Via la CRD NodePools
Pour créer un nouveau pool de nœuds, il vous suffit de créer un nouveau manifeste de pool de nœuds.

Copiez le manifeste YAML suivant dans un fichier `new-nodepool.yaml` :

```yaml
apiVersion: kube.cloud.ovh.com/v1alpha1
kind: NodePool
metadata:
  name: my-new-node-pool
spec:
  antiAffinity: false
  autoscale: false
  autoscaling:
    scaleDownUnneededTimeSeconds: 600
    scaleDownUnreadyTimeSeconds: 1200
    scaleDownUtilizationThreshold: "0.5"
  desiredNodes: 3
  flavor: b2-7
  maxNodes: 100
  minNodes: 0
  monthlyBilled: false
```

 :::info
 :::

Les champs `antiAffinity`, `flavor` et `name` ne seront pas modifiables après la création.  
Vous ne pouvez pas faire passer le champ `monthlyBilled` de `true` à `false`.

Appliquez-le ensuite à votre cluster :

```bash
kubectl apply -f new-nodepool.yaml
```

Votre nouveau pool de nœuds sera créé :

```console
$ kubectl apply -f new-nodepool.yaml
nodepool.kube.cloud.ovh.com/my-new-node-pool created

$ kubectl get nodepools

nodepool-b2-7      b2-7     false        true             true           2         2         2            2           0     5     14d
```

Au départ, le nouveau pool de nœuds est vide, mais si vous patientez quelques secondes, vous verrez les nœuds être créés et rendus disponibles progressivement, les uns après les autres.


    Après l'exécution de cette commande, Kubernetes fera passer l'état des nœuds à `Ready,SchedulingDisabled`. Au bout d'un moment, les nœuds seront supprimés.
