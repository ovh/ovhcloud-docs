## Objectif

OVHcloud Managed Kubernetes Service vous fournit des clusters Kubernetes sans que vous ayez à vous soucier de leur installation ou de leur exploitation.

Par défaut, les nœuds de vos clusters du plan Free disposent d'IP publiques. Pour certains cas d'usage, ou pour des raisons de sécurité, vous pouvez préférer que votre cluster Kubernetes se trouve dans un réseau privé.

Le [vRack](/links/network/vrack) OVHcloud est une solution de réseau privé qui permet à nos clients d'acheminer le trafic entre des serveurs dédiés OVHcloud, ainsi qu'avec d'autres services OVHcloud.

**Ce guide traite de l'intégration des clusters OVHcloud Managed Kubernetes dans des réseaux privés vRack.**

## Prérequis

- Disposer d'un projet Public Cloud dans votre compte OVHcloud

## En pratique

Vous devez tout d'abord configurer un réseau privé vRack pour votre Public Cloud. Pour cela, suivez le guide « [Configuration du vRack Public Cloud](/guides/public-cloud/network-services/vrack) ». Une fois que vous avez créé un vRack et l'avez ajouté à un réseau privé, vous pouvez continuer.

L'intégration d'un cluster dans un réseau privé vRack doit se faire lors de la création du cluster, dans la section **Paramètres réseau** de la page **Créer un cluster Kubernetes**, où vous pouvez choisir un réseau privé et un sous-réseau existants pour le cluster.

Votre nouveau cluster sera créé au sein du réseau privé vRack que vous avez choisi.

Une fois le cluster créé, cliquez sur son nom dans la liste <code className="action">Managed Kubernetes Service</code> et ouvrez son onglet <code className="action">Réseau</code> : il affiche le réseau privé choisi.

## Routeur client et exposition publique des nœuds et des workloads désactivée (plan Standard)

Avec le plan Standard, les nœuds n'ont pas d'IP publique par défaut : ils accèdent à Internet via une passerelle managée OVHcloud, ou via des Floating IP définies au niveau du pool de nœuds. Sur les clusters Standard créés depuis le 13 octobre 2026, vous pouvez aller plus loin à la création du cluster, depuis l'API OVHcloud (prise en charge dans la console OVHcloud, la CLI et Terraform en cours) :

- désactiver l'exposition publique des nœuds et des workloads (`disablePublicNetworking`) : ni Floating IP sur les nœuds ou les load balancers, ni Load Balancer public. Cette option sert de garde-fou (rien ne peut être exposé sur Internet par erreur) et peut s'utiliser seule, avec la passerelle managée OVHcloud pour le trafic sortant ;
- utiliser votre propre routeur ou pare-feu comme passerelle par défaut des nœuds (`useUserGateway`, qui exige `disablePublicNetworking`), sans passerelle managée OVHcloud : votre routeur est la passerelle du sous-réseau des nœuds.

Sur tout nouveau cluster Standard, le trafic entre les nœuds et le control plane Kubernetes passe par un chemin privé opéré par OVHcloud.

La configuration et ses limites sont détaillées dans le guide « [Utiliser une passerelle personnalisée sur un cluster OVHcloud Managed Kubernetes](/guides/public-cloud/containers-orchestration/managed-kubernetes/vrack-custom-gateway#utiliser-votre-propre-routeur-ou-pare-feu-plan-standard) ».

## Limites connues

- Tous les nœuds d'un cluster Kubernetes avec un réseau privé vRack activé sont disponibles au sein de ce seul réseau privé. (Pas de mélange public/privé, un seul réseau privé disponible.)
- Pour exposer certains workloads sur Internet, vous pouvez utiliser les Load Balancers externes, désormais compatibles avec les nœuds en vRack. Ce n'est pas possible sur un cluster créé avec `disablePublicNetworking` : aucun Load Balancer public ne peut y être créé.
- L'OVHcloud Public Cloud ne prend pas en charge les groupes de sécurité sur le vRack.
- Sur les clusters du plan Free, vous verrez toujours une adresse IPv4 publique sur vos worker nodes. Cette IP n'est pas accessible depuis Internet et est utilisée exclusivement pour l'administration de vos nœuds et leur lien avec le control plane Kubernetes. Sur les clusters du plan Standard, les nœuds n'ont pas d'IP publique par défaut (voir ci-dessus).
- Comme expliqué dans le guide « [Limites connues](/guides/public-cloud/containers-orchestration/managed-kubernetes/known-limits) », les sous-réseaux suivants ne sont pas compatibles avec la fonctionnalité `vRack` et peuvent générer des comportements incohérents avec nos réseaux overlay :

```bash
10.2.0.0/16 # Subnet used by pods
10.3.0.0/16 # Subnet used by services
172.17.0.0/16 # Subnet used by the Docker daemon
```
