## Objectif

OVHcloud Managed Kubernetes Service vous fournit des clusters Kubernetes sans que vous ayez à vous soucier de leur installation ou de leur exploitation.

Au fil de la vie de votre cluster, vous pouvez vouloir ajuster dynamiquement sa taille pour l'adapter à vos workloads. L'autoscaler de cluster simplifie cette tâche en augmentant ou en réduisant la taille de votre cluster OVHcloud Managed Kubernetes pour répondre à la demande de vos workloads.

Ce guide fait suite au guide [Utiliser l'autoscaler de cluster](/guides/public-cloud/containers-orchestration/managed-kubernetes/using-cluster-autoscaler) et présente en détail la configuration de l'autoscaler de cluster.

## Prérequis

- Un cluster OVHcloud Managed Kubernetes
- Une compréhension de base du [fonctionnement de l'autoscaler de cluster et de son activation](/guides/public-cloud/containers-orchestration/managed-kubernetes/using-cluster-autoscaler)

## En pratique

### Configuration de l'autoscaler

Lorsque l'autoscaler est activé sur un pool de nœuds, il utilise une configuration par défaut.

Voici une description des paramètres utilisés dans la configuration de l'autoscaler et de leur valeur par défaut :

| Paramètre | Description | Valeur par défaut |
| ------- | ----------- | ------- |
| `scan-interval` | Fréquence à laquelle le cluster est réévalué pour une montée ou une descente en charge | 10 secondes |
| `scale-down-delay-after-add` | Délai après une montée en charge avant la reprise de l'évaluation de la descente en charge | 10 minutes |
| `scale-down-delay-after-delete` | Délai après la suppression d'un nœud avant la reprise de l'évaluation de la descente en charge | `scan-interval` |
| `scale-down-delay-after-failure` | Délai après un échec de descente en charge avant la reprise de l'évaluation de la descente en charge | 3 minutes |
| `scale-down-unneeded-time` | Durée pendant laquelle un nœud doit être inutile avant d'être éligible à la descente en charge | 10 minutes |
| `scale-down-unready-time` | Durée pendant laquelle un nœud non prêt doit être inutile avant d'être éligible à la descente en charge | 20 minutes |
| `scale-down-utilization-threshold` | Taux d'utilisation (ressources demandées / capacité) en dessous duquel un nœud est considéré pour la descente en charge | 0.5 |
| `max-graceful-termination-sec` | Délai maximal, en secondes, d'attente de la terminaison des pods lors de la réduction d'un nœud | 600 secondes |
| `balance-similar-node-groups` | Équilibre le nombre de nœuds entre les pools partageant le même type d'instance et les mêmes labels | false |
| `expander` | Stratégie de sélection du pool de nœuds pour la montée en charge : `most-pods`, `random`, `least-waste`, `priority` | `random` |
| `skip-nodes-with-local-storage` | Ne jamais supprimer les nœuds dont les pods utilisent du stockage local (EmptyDir ou HostPath) | false |
| `skip-nodes-with-system-pods` | Ne jamais supprimer les nœuds avec des pods kube-system (sauf DaemonSets et pods miroirs) | false |
| `max-empty-bulk-delete` | Nombre maximal de nœuds vides pouvant être supprimés simultanément | 10 nœuds |
| `new-pod-scale-up-delay` | Âge minimal d'un pod non planifié avant que l'autoscaler n'agisse sur celui-ci | 0 seconde |
| `max-total-unready-percentage` | Pourcentage maximal de nœuds non prêts ; l'autoscaler s'arrête si ce seuil est dépassé | 45% |
| `max-node-provision-time` | Délai maximal d'attente de l'autoscaler pour le provisionnement d'un nœud | 15 minutes |
| `ok-total-unready-count` | Nombre de nœuds non prêts autorisés, indépendamment du seuil en pourcentage | 3 nœuds |

Vous pouvez obtenir plus d'informations sur ces paramètres dans la [documentation de l'autoscaler Kubernetes](https://github.com/kubernetes/autoscaler/blob/master/cluster-autoscaler/FAQ.md).

Si vous pensez que nous devrions réévaluer la valeur par défaut et/ou prioriser la possible personnalisation d'un de ces paramètres, n'hésitez pas à créer un ticket sur notre [roadmap publique](https://github.com/orgs/ovh/projects/16/).

### Configurer l'autoscaler

La façon la plus simple d'activer l'autoscaler consiste à utiliser l'API Kubernetes, par exemple via `kubectl`.

#### Utiliser l'API Kubernetes

Lorsque l'autoscaler est activé sur un pool de nœuds, il utilise une [configuration par défaut](/guides/public-cloud/containers-orchestration/managed-kubernetes/configure-cluster-autoscaler#configuration-de-lautoscaler).

Pour lister les pools de nœuds, vous pouvez utiliser :

```bash
kubectl get nodepools
```

Vous pouvez modifier plusieurs valeurs de paramètres via la commande kubectl :

```bash
kubectl patch nodepool <your_nodepool_name> --type="merge" --patch='{"spec": {"autoscaling": {"scaleDownUnneededTimeSeconds": <a_value>, "scaleDownUnreadyTimeSeconds": <another_value>, "scaleDownUtilizationThreshold": "<and_another_one>"}}}'
```

Dans mon exemple de cluster :
```console
$ kubectl get nodepool nodepool-b2-7 -o json | jq .spec
{
  "antiAffinity": false,
  "autoscale": true,
  "autoscaling": {
    "scaleDownUnneededTimeSeconds": 600,
    "scaleDownUnreadyTimeSeconds": 1200,
    "scaleDownUtilizationThreshold": "0.5"
  },
  "desiredNodes": 3,
  "flavor": "b2-7",
  "maxNodes": 100,
  "minNodes": 0,
  "monthlyBilled": false
}
```

```console
$ kubectl patch nodepool nodepool-b2-7 --type="merge" --patch='{"spec": {"autoscaling": {"scaleDownUnneededTimeSeconds": 900, "scaleDownUnreadyTimeSeconds": 1500, "scaleDownUtilizationThreshold": "0.7"}}}'
nodepool.kube.cloud.ovh.com/nodepool-b2-7 patched
```

```console
$ kubectl get nodepool nodepool-b2-7 -o json | jq .spec
{
  "antiAffinity": false,
  "autoscale": true,
  "autoscaling": {
    "scaleDownUnneededTimeSeconds": 900,
    "scaleDownUnreadyTimeSeconds": 1500,
    "scaleDownUtilizationThreshold": "0.7"
  },
  "desiredNodes": 3,
  "flavor": "b2-7",
  "maxNodes": 100,
  "minNodes": 0,
  "monthlyBilled": false
}
```

Pour le moment, seuls les paramètres suivants sont modifiables :

- autoscale
- autoscaling
- desiredNodes
- minNodes
- maxNodes

Si vous pensez que nous devrions prioriser la possible personnalisation d'autres paramètres d'autoscaling, n'hésitez pas à créer un ticket sur notre [roadmap publique](https://github.com/orgs/ovh/projects/16/).
