## Objectif

Ce guide décrit le processus de migration de votre cluster OVHcloud Managed Kubernetes Service (MKS) du plan Free vers le plan Standard. Il fournit une procédure étape par étape pour garantir une transition sécurisée et efficace tout en minimisant les interruptions de service.

Nous allons aborder les phases essentielles de la migration, notamment :

- **Comparaison des plans** : comprendre les différences entre les plans Free et Standard.
- **Sauvegarde et restauration** : utiliser Trilio, CloudCasa ou Velero pour migrer vos données et workloads en toute sécurité.
- **Migration du cluster** : déplacer l'intégralité de votre cluster ou des namespaces spécifiques vers le plan Standard.
- **Validation post-migration** : vérifier que vos applications sont pleinement fonctionnelles et optimisées sur le plan Standard.

Ce guide est conçu pour vous fournir les connaissances et les bonnes pratiques nécessaires à une migration de plan MKS réussie et sans accroc.

## Prérequis

Pour mettre à jour avec succès le plan de votre cluster Kubernetes au sein d'OVHcloud, assurez-vous de disposer des prérequis suivants :

- Un [projet Public Cloud](/guides/public-cloud/cross-functional/create-a-public-cloud-project) au sein de votre compte OVHcloud.
- **kubectl** : vous devez avoir installé l'outil de ligne de commande kubectl pour interagir avec vos clusters Kubernetes. Consultez la [documentation officielle de Kubernetes](https://kubernetes.io/docs/tasks/tools/) pour les instructions d'installation.

## Comparaison des plans MKS Free et Standard

Bien que ce guide se concentre sur votre plan actuel, il peut être utile de comprendre les différences entre les plans Free et Standard. Le plan Standard propose des fonctionnalités supplémentaires telles que la résilience cross-AZ, un SLA de disponibilité plus élevé, un etcd dédié et une taille de cluster maximale plus importante.

Pour un aperçu complet, incluant un tableau comparatif détaillé entre Free et Standard, reportez-vous à la partie **Comparaison Free vs Standard** de notre guide [Choisir le bon plan OVHcloud Managed Kubernetes : Free ou Standard](/guides/public-cloud/containers-orchestration/managed-kubernetes/mks-plans). Le tableau de ce guide propose une comparaison claire, côte à côte, des fonctionnalités clés.

## En pratique

:::warning
Pour le moment, **les Floating IP ne peuvent pas être attachées aux nœuds MKS**.

Cette fonctionnalité sera disponible dans les semaines à venir.

Dans l'intervalle, planifiez votre migration en conséquence et envisagez des alternatives telles que la reconfiguration des enregistrements DNS ou l'utilisation de services de load balancer.
:::

### 1. Installer, configurer l'outil de sauvegarde et sauvegarder votre cluster

Avant de migrer votre cluster, assurez-vous qu'une solution de sauvegarde est installée et configurée. Vous pouvez utiliser Trilio, CloudCasa ou Velero selon vos préférences.

Choisissez votre outil de sauvegarde :

- Velero : solution open source, s'intègre au stockage compatible S3<sup>1</sup> d'OVHcloud.
- Trilio : solution prête pour l'entreprise, optimisée pour Kubernetes.
- CloudCasa : service de sauvegarde managé, configuration simple pour les clusters.

**Installez l'outil choisi** sur votre cluster Free en suivant la documentation officielle, puis **sauvegardez votre cluster** :

- Pour Velero, suivez notre guide [ici](/guides/public-cloud/containers-orchestration/managed-kubernetes/backing-up-cluster-velero).
- Pour Trilio, suivez notre guide [ici](/guides/public-cloud/containers-orchestration/managed-kubernetes/backup-restore-cluster-trilio).
- Pour CloudCasa, suivez notre guide [ici](/guides/public-cloud/containers-orchestration/managed-kubernetes/backup-restore-cluster-cloudcasa).

### 2. Créer votre cluster Kubernetes cible sur OVHcloud

Connectez-vous à l'<ManagerLink to="/">espace client OVHcloud</ManagerLink>, accédez à la section `Public Cloud` et sélectionnez le projet Public Cloud concerné.

Accédez à l'interface d'administration de vos clusters OVHcloud Managed Kubernetes en cliquant sur `Managed Kubernetes Service` dans le menu de gauche, puis cliquez sur `Create a cluster`.

![Créer un cluster](/images/guides/public-cloud/containers-orchestration/managed-kubernetes/migration-from-free-to-standard/creating-a-cluster1.png)

### 3. Choisir une flavor et un pool de nœuds pour votre nouveau cluster OVHcloud

- **Dimensionnez vos worker nodes** : évaluez soigneusement les besoins en CPU et RAM de votre architecture existante, puis sélectionnez des flavors de nœud OVHcloud correspondant à ces spécifications.
- **Reproduisez la configuration réseau** : assurez-vous que la configuration réseau de votre nouveau cluster reflète celle de votre cluster d'origine (par exemple, nœuds privés sur un sous-réseau privé, gateway de sortie dédiée).
- **Choisissez le mode de déploiement** : sélectionnez un mode de déploiement (par exemple 1AZ ou 3AZ) en fonction de vos besoins de tolérance aux pannes et de haute disponibilité.

:::info
Le plan Standard n'est actuellement disponible que dans les régions 3AZ. Assurez-vous que votre migration cible une région compatible afin d'éviter tout problème de déploiement.
:::

### 4. Restaurer vos sauvegardes sur le nouveau cluster

Avant de migrer vos workloads, vous devez déployer l'outil de sauvegarde choisi sur le nouveau cluster Standard. Cela garantit que vos sauvegardes sont correctement restaurées et que le processus de migration peut se dérouler sans accroc.

Choisissez la documentation correspondant à l'outil que vous utilisez :

<Tabs>
<Tab label="Via Velero">

1\. **Déployer Velero sur le nouveau cluster**

Installez le chart Helm Velero sur votre cluster OVHcloud Kubernetes nouvellement créé en suivant la partie **Installer Velero** de [ce guide](/guides/public-cloud/containers-orchestration/managed-kubernetes/backing-up-cluster-velero).

2\. **Configurer l'accès à vos sauvegardes**

Assurez-vous que Velero, sur le nouveau cluster, pointe vers le même bucket Object Storage compatible S3<sup>1</sup> d'OVHcloud que celui utilisé pour vos sauvegardes. Cela rendra automatiquement les métadonnées de vos sauvegardes existantes visibles pour le nouveau cluster.

Exemple de vérification des sauvegardes disponibles :

```sh
velero backup get <backupName>
```

Remplacez `<backupName>` par le nom de votre sauvegarde.

3\. **Restaurer votre sauvegarde**

Utilisez la CLI Velero pour restaurer des ressources à partir d'une sauvegarde :

```sh
velero restore create --from-backup <backupName>
```

Remplacez `<backupName>` par le nom de la sauvegarde que vous souhaitez restaurer.

Vous pouvez ajouter des options telles que --include-namespaces ou --exclude-resources pour affiner ce qui est restauré.

4\. **Valider la restauration**

Une fois la restauration terminée, vérifiez que vos workloads, services et configurations fonctionnent correctement :

```sh
# Lister les restaurations
velero restore get

# Vérifier le statut global de la restauration
velero restore describe YOUR_RESTORE_NAME

# Vérifier les workloads directement dans le cluster
kubectl get pods --all-namespaces
```

Surveillez les événements et les logs si certains workloads ne démarrent pas comme prévu.

### 5. Valider la migration

Après avoir restauré vos workloads, vérifiez que le cluster est pleinement fonctionnel :

- Vérifiez les déploiements, les services et les contrôleurs d'ingress.
- Testez les endpoints de vos applications pour confirmer leur disponibilité.
- Vérifiez les logs et les événements à la recherche d'erreurs ou de mauvaises configurations.
- Exécutez tous les tests d'intégration de votre application sur le nouveau cluster cible.

### 6. Ajuster les ressources du cluster

Certains workloads peuvent nécessiter des ajustements après la migration :

- Recréez les Load Balancers ou reconfigurez les Ingress si les IP publiques ont changé.
- Assurez-vous que les CRD, Secrets et ConfigMaps sont correctement restaurés.

### 7. Nettoyer les anciennes ressources

Une fois que vous avez validé que tout fonctionne correctement sur le cluster Standard :

- Vous pouvez réaffecter le cluster source (plan Free) à des environnements de test ou de préproduction.
- Vous pouvez également le désaffecter s'il n'est plus nécessaire.

### 8. Configurer des Saving Plans (si nécessaire)

Explorez l'option des [OVHcloud Saving Plans](/guides/public-cloud/cross-functional/savings-plans) pour optimiser vos coûts cloud. Découvrez les Saving Plans disponibles afin de déterminer s'ils correspondent à votre stratégie financière.

### 9. Bonnes pratiques post-migration

- Mettez en place une supervision et des alertes pour suivre l'état de santé du nouveau cluster.
- Planifiez des sauvegardes régulières avec Velero, Trilio ou CloudCasa.
- Documentez tout changement de configuration pour référence future.

## Astuces et bonnes pratiques

- Bonnes pratiques opérationnelles :
    - **Testez régulièrement les restaurations** : ne vous contentez pas de configurer les sauvegardes, effectuez des tests de restauration périodiques pour valider les procédures de reprise.
    - **Utilisez des environnements de préproduction** : exécutez d'abord votre migration sur un cluster non-productif afin de détecter d'éventuels problèmes avant de déplacer les workloads de production.
    - **Vérifiez les quotas et limites** : assurez-vous que votre projet Public Cloud dispose de quotas suffisants pour les nœuds, le stockage et les load balancers.
- Sécurité et conformité :
    - **Revalidez les politiques RBAC** : assurez-vous que les utilisateurs et les comptes de service disposent uniquement des permissions dont ils ont besoin dans le nouveau cluster.
    - **Faites tourner les secrets et identifiants** : après la migration, renouvelez les clés API, jetons et mots de passe de base de données pour réduire les risques.
    - **Auditez les exigences de conformité** : vérifiez que la nouvelle configuration respecte toujours les exigences réglementaires ou de sécurité de votre organisation (par exemple RGPD, ISO).
- Performance et coûts :
    - **Activez l'autoscaling** : configurez le cluster autoscaler et le HPA (Horizontal Pod Autoscaler) pour optimiser l'utilisation des ressources.
    - **Ajustez la taille de vos nœuds** : passez en revue les workloads et ajustez les flavors des pools de nœuds pour équilibrer performance et coût.
    - **Surveillez l'utilisation du stockage** : surveillez la consommation des PVC et ajustez les storage classes si nécessaire.
- Fiabilité :
    - **Utilisez le mode 3AZ pour la production** : garantissez une haute disponibilité en exécutant les workloads sur un cluster 3AZ.
    - **Mettez en place des alertes** : intégrez des outils comme Prometheus, Grafana, etc.
    - **Documentez une stratégie de rollback** : définissez comment revenir au cluster Free ou à une sauvegarde en cas de problème pendant la migration.
