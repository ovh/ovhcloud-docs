## Objectif

Le service OVHcloud Managed Kubernetes vous fournit des clusters Kubernetes sans les contraintes liées à leur installation ou à leur exploitation. Chez OVHcloud, nous souhaitons vous proposer les meilleurs produits et services. Pour nous, la sécurité est essentielle, c'est pourquoi nous appliquons par défaut les mises à jour de sécurité sur vos clusters Kubernetes. <br/>
**Vous pouvez néanmoins modifier la configuration de la politique de mise à jour de sécurité de votre cluster. Découvrez comment procéder dans ce guide.**

## Prérequis

- Un cluster OVHcloud Managed Kubernetes

## En pratique

### Configurer la politique de mise à jour de sécurité via l'espace client OVHcloud

Accédez à l'interface d'administration de vos clusters OVHcloud Managed Kubernetes en cliquant sur <code className="action">Managed Kubernetes Service</code> dans le menu de gauche.

<img className="thumbnail" alt="Accès à l'interface d'administration" src="/images/public-cloud/containers-orchestration/managed-kubernetes/change-security-update/upgrading-kubernetes-version-000.png" loading="lazy" />

Cliquez sur le bouton <code className="action">...</code> à droite de votre cluster Kubernetes et choisissez <code className="action">Gérer le cluster</code>.

<img className="thumbnail" alt="Cliquez sur le bouton à l'extrémité droite et choisissez Gérer le cluster" src="/images/public-cloud/containers-orchestration/managed-kubernetes/change-security-update/upgrading-kubernetes-version-001.png" loading="lazy" />

Dans la section *Management*, cliquez sur <code className="action">Changer la politique de sécurité</code>.

<img className="thumbnail" alt="Cliquez sur Changer la politique de sécurité" src="/images/public-cloud/containers-orchestration/managed-kubernetes/change-security-update/change-security-update-002.png" loading="lazy" />

Une fenêtre pop-up affiche toutes les options disponibles :

- **Ne pas mettre à jour** (NEVER_UPDATE). Nous ne recommandons pas ce choix. OVHcloud se réserve le droit de mettre à jour les composants Kubernetes ou vos nœuds à titre exceptionnel, dans des cas critiques qui limitent la sécurité de notre infrastructure.

- **Indisponibilité minimale** (MINIMAL_DOWNTIME). Applique les mises à jour de sécurité (« patch version ») à votre service Kubernetes, afin de garantir la sécurité et la stabilité du service. Si nous ne pouvons pas éviter une interruption de service lors d'une mise à jour progressive (rolling update) de vos nœuds, nous vous en informerons. Nous vous conseillons de dimensionner votre cluster afin qu'il puisse être mis à jour à tout moment.

- **Sécurité maximale** (ALWAYS_UPDATE). Applique les mises à jour de sécurité (« patch version ») à votre service Kubernetes, afin de garantir la sécurité et la stabilité du service. La mise à jour peut entraîner l'indisponibilité de vos nœuds pendant quelques minutes, le temps d'effectuer la mise à jour progressive (rolling update).

La politique de sécurité **Sécurité maximale** est configurée par défaut. Même si nous recommandons la sécurité maximale, vous pouvez choisir la politique de sécurité qui vous convient.

Choisissez une option et cliquez sur <code className="action">Confirmer</code>.

<img className="thumbnail" alt="Cliquez sur Confirmer" src="/images/public-cloud/containers-orchestration/managed-kubernetes/change-security-update/change-security-update-004.png" loading="lazy" />

### Configurer la politique de mise à jour de sécurité via Terraform

Depuis la version 0.20 et supérieures de notre [provider Terraform OVH](https://registry.terraform.io/providers/ovh/ovh/latest/docs), vous pouvez configurer la politique de mise à jour de sécurité à la création du cluster, ainsi qu'à sa mise à jour, également via Terraform.

#### Récupérer les informations de votre cluster et de vos tokens API

Le « provider OVH » doit être configuré avec un ensemble d'identifiants :

* une `application_key`
* un `application_secret`
* une `consumer_key`

**Pourquoi ?**

Parce que, en arrière-plan, le « provider Terraform OVH » effectue des requêtes vers les API OVHcloud.

Pour récupérer ces informations nécessaires, suivez notre tutoriel [Premiers pas avec les API OVHcloud](/guides/manage-and-operate/api/first-steps).

Plus précisément, vous devez générer ces identifiants via la <CreateToken rights="GET=/*&POST=/*&PUT=/*&DELETE=/*">page de génération de tokens OVHcloud</CreateToken> avec les droits suivants : **GET**, **POST**, **PUT** et **DELETE** sur `/*`.

Lorsque vous avez généré vos tokens OVHcloud avec succès, veillez à les enregistrer, car vous devrez les utiliser très prochainement.

La dernière information nécessaire est le `service_name` : il s'agit de l'identifiant de votre projet Public Cloud.

**Comment l'obtenir ?**

Dans la section Public Cloud, vous pouvez récupérer l'identifiant de votre service grâce au bouton <code className="action">Copier dans le presse-papier</code>.

<img className="thumbnail" alt="Copier-coller le nom du service" src="/images/public-cloud/containers-orchestration/managed-kubernetes/change-security-update/get-service-name.png" loading="lazy" />

Vous utiliserez également cette information dans les fichiers de définition des ressources Terraform.

#### Instructions Terraform

Commencez par créer un fichier `provider.tf` avec la version minimale, l'endpoint européen (« ovh-eu ») et les clés précédemment récupérées dans ce guide.

Terraform 0.13 et versions ultérieures :

```bash
terraform {
  required_providers {
    ovh = {
      source  = "ovh/ovh"
    }
  }
}

provider "ovh" {
  endpoint           = "ovh-eu"
  application_key    = "<your_access_key>"
  application_secret = "<your_application_secret>"
  consumer_key       = "<your_consumer_key>"
}
```

Terraform 0.12 et versions antérieures :

```bash
# Configure the OVHcloud Provider
provider "ovh" {
  endpoint           = "ovh-eu"
  application_key    = "<your_access_key>"
  application_secret = "<your_application_secret>"
  consumer_key       = "<your_consumer_key>"
}
```

Les clés secrètes peuvent également être récupérées depuis votre environnement.

- `OVH_ENDPOINT`
- `OVH_APPLICATION_KEY`
- `OVH_APPLICATION_SECRET`
- `OVH_CONSUMER_KEY`

Cette dernière méthode (ou une alternative similaire) est recommandée pour éviter de stocker des données secrètes dans un dépôt source.

Nous avons ici défini l'endpoint `ovh-eu`, car nous souhaitons appeler l'API OVHcloud Europe, mais d'autres endpoints existent selon vos besoins :

* `ovh-eu` pour l'API OVHcloud Europe
* `ovh-us` pour l'API OVHcloud US
* `ovh-ca` pour l'API OVHcloud Amérique du Nord

Ensuite, créez un fichier `variables.tf` avec service_name :

```bash
variable service_name {
  type        = string
  default     = "<your_service_name>"
}
```

Définissez les ressources que vous souhaitez créer dans un nouveau fichier nommé `ovh_kube_cluster.tf` :

```bash
resource "ovh_cloud_project_kube" "cluster" {
  service_name = var.service_name
  name         = "my-super-cluster"
  region       = "GRA5"
  version      = "1.31"

  update_policy = "NEVER_UPDATE" # "ALWAYS_UPDATE" by default but you can choose also "MINIMAL_DOWNTIME" or "NEVER_UPDATE"
}
```

Dans cette configuration de ressources, nous demandons à Terraform de créer un cluster Kubernetes, dans la région GRA5, avec la version Kubernetes 1.31 (la dernière version recommandée au moment de la rédaction de ce tutoriel), avec une politique de mise à jour de sécurité équivalente à « Ne pas mettre à jour ».

#### Mise à jour

Parce que la sécurité est importante, si vous souhaitez mettre à jour la politique de sécurité, vous pouvez également le faire via Terraform. Modifiez le fichier `ovh_kube_cluster.tf` avec ce contenu :

```bash
resource "ovh_cloud_project_kube" "cluster" {
  service_name = var.service_name
  name         = "my-super-cluster"
  region       = "GRA5"
  version      = "1.31"

  update_policy = "ALWAYS_UPDATE" # "ALWAYS_UPDATE" by default but you can choose also "MINIMAL_DOWNTIME" or "NEVER_UPDATE"
}
```
