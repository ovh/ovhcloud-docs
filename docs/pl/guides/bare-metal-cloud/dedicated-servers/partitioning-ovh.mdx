## Wprowadzenie

:::warning
Ten artykuł jest przeznaczony dla doświadczonych użytkowników posiadających podstawową wiedzę o systemie Linux, a przede wszystkim pogłębioną wiedzę techniczną z zakresu przestrzeni dyskowej, w szczególności sprzętowego i programowego RAID oraz zarządzania woluminami logicznymi (LVM).

:::

W [serwerach dedykowanych OVHcloud](/links/bare-metal/bare-metal) możesz skonfigurować dyski, [sprzętowy RAID](/guides/bare-metal-cloud/dedicated-servers/raid-hard), partycje, [programowy RAID](/guides/bare-metal-cloud/dedicated-servers/raid-soft), LVM, ZFS itp. podczas [reinstalacji systemu operacyjnego](/guides/bare-metal-cloud/dedicated-servers/getting-started-with-dedicated-server) za pomocą <ApiLink>API OVHcloud</ApiLink>, a także w <ManagerLink to="/">konsoli OVHcloud</ManagerLink>. W tym artykule skupimy się na <ApiLink>API OVHcloud</ApiLink>. Dzięki temu poznasz więcej szczegółów dotyczących mechanizmu działającego w tle, który na podstawie danych wejściowych przekazanych do API OVHcloud tworzy spersonalizowaną konfigurację przestrzeni dyskowej na serwerze dedykowanym.

Szczegółowe informacje o konfiguracji przestrzeni dyskowej mogą pomóc klientom zrozumieć, dlaczego:

- ich spersonalizowana konfiguracja przestrzeni dyskowej nie mogła zostać zastosowana na serwerze dedykowanym.
- rzeczywista konfiguracja przestrzeni dyskowej na serwerze dedykowanym nieznacznie różni się od tej, o którą prosił klient.

## Wymagania początkowe

* Posiadanie [serwera dedykowanego](/links/bare-metal/bare-metal) **gotowego do instalacji/reinstalacji** na koncie OVHcloud.
* Dostęp do <ApiLink>API OVHcloud</ApiLink>.

:::warning
Reinstalacja serwera dedykowanego powoduje usunięcie wszystkich zapisanych na nim danych.

:::

## W praktyce

Podczas domyślnej instalacji systemu operacyjnego instalator (dostarczony przez wydawcę oprogramowania) interaktywnie prosi użytkownika o wskazanie dysków, na których zostanie zainstalowany system operacyjny, schematu partycjonowania itp. Po zainstalowaniu systemu operacyjnego można zmienić schemat partycjonowania, ale może to być bardzo trudne i ryzykowne, zwłaszcza w przypadku partycji, które są aktualnie używane przez system. Z tego względu przestrzeń dyskowa jest bardzo ważnym zagadnieniem, które należy przemyśleć **przed** instalacją systemu operacyjnego.

Oprócz prostoty, jaką oferuje API, główną zaletą jest możliwość pełnej personalizacji dysków i partycji, na których zostanie zainstalowany system operacyjny.

Na tej stronie skupiamy się wyłącznie na podsekcji (sub-hash) `storage` wywołania API służącego do reinstalacji systemu operacyjnego na serwerze dedykowanym. Więcej informacji o innych personalizacjach, niezwiązanych z przestrzenią dyskową, znajdziesz w przewodniku [API OVHcloud i instalacja systemu operacyjnego](/guides/bare-metal-cloud/dedicated-servers/api-os-installation).

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "diskGroupId": 1,
            "erase": true
        },
        {
            "diskGroupId": 2,
            "erase": true,
            "hardwareRaid": [
                {
                    "raidLevel": null,
                    "disks": 2
                }
            ],
            "partitioning": {
                "disks": 2,
                "layout": [
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/boot",
                        "size": 1000,
                        "raidLevel": 1
                    },
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/",
                        "size": 0
                    }
                ]
            }
        }
    ]
}
```

### Grupy dysków <a name="disk-group"></a>

Niektóre [serwery dedykowane](/links/bare-metal/bare-metal) mają kilka grup dysków, na przykład jedną grupę z dyskami SATA i drugą grupę z dyskami SSD. Takie serwery są czasem nazywane również **serwerami hybrydowymi**.

Aby wyświetlić listę grup dysków i ich dysków, możesz użyć następującego wywołania API. Pozwoli to wskazać grupę dysków, na której ma zostać ponownie zainstalowany system operacyjny:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/specifications/hardware"} />

Przykładowa odpowiedź:

```json
{
    "bootMode": "uefi",
    "coresPerProcessor": 64,
    "defaultDiskGroupId": 1,
    "defaultHardwareRaidSize": null,
    "defaultHardwareRaidType": null,
    "description": "SCALE-7 - AMD Epyc 7763",
    "diskGroups": [
        {
            "defaultHardwareRaidSize": null,
            "defaultHardwareRaidType": null,
            "description": "2 X Disk SSD 480 GB, JBOD",
            "diskGroupId": 1,
            "diskSize": {
                "unit": "GB",
                "value": 480
            },
            "diskType": "SSD",
            "numberOfDisks": 2,
            "raidController": null
        },
        {
            "defaultHardwareRaidSize": null,
            "defaultHardwareRaidType": null,
            "description": "2 X Disk NVME 1920 GB, JBOD",
            "diskGroupId": 2,
            "diskSize": {
                "unit": "GB",
                "value": 1920
            },
            "diskType": "NVME",
            "numberOfDisks": 2,
            "raidController": null
        }
    ],
    "expansionCards": null,
    "formFactor": "1u",
    "memorySize": {
        "unit": "MB",
        "value": 524288
    },
    "motherboard": "S8036-M",
    "numberOfProcessors": 1,
    "processorArchitecture": "x86_64",
    "processorName": "Epyc7763",
    "threadsPerProcessor": 128,
    "usbKeys": null
}
```

W tym przykładzie istnieją 2 grupy dysków:

- pierwsza (diskGroupId=1) zawiera 2 dyski o pojemności 480 GB. Jest to domyślna wartość diskGroupId.
- druga (diskGroupId=2) zawiera 2 dyski o pojemności 1,9 TB.

Przykład instalacji systemu Debian 13 (Trixie) na grupie dysków diskGroup 2:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "diskGroupId": 2
        }
    ]
}
```

:::info
Domyślnie, jeśli wartość diskGroupId nie zostanie określona lub zostanie ustawiona na 0, system operacyjny zostanie zainstalowany na domyślnej grupie diskGroupId 1.

:::

<br />

:::warning
Obecnie API obsługuje instalację systemu operacyjnego i personalizację przestrzeni dyskowej tylko na 1 grupie dysków. W personalizacji przestrzeni dyskowej może uczestniczyć od 1 do wszystkich dysków wybranej grupy dysków. Pozostałe dyski tej grupy zostaną jednak wyczyszczone. Dyski należące do innych grup dysków również są domyślnie czyszczone, ale ich dane można zachować: zob. [Usuwanie danych](#data-erasure). W każdym przypadku wszystkie te dyski będą nadal widoczne w nowo zainstalowanym systemie operacyjnym i będzie można je później wykorzystać/skonfigurować do przechowywania danych.

:::

### Sprzętowy RAID <a name="hard-raid"></a>

Ta sekcja dotyczy wyłącznie serwerów, które mają co najmniej jeden kontroler sprzętowego RAID w jednej ze swoich [grup dysków](#disk-group).

#### Kompatybilność serwera ze sprzętowym RAID

Informację tę możesz uzyskać za pomocą następującego wywołania API:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/install/hardwareRaidProfile"} />

Jeśli serwer nie ma żadnego kontrolera sprzętowego RAID, zostanie zwrócony błąd HTTP 403 (Forbidden) z następującym komunikatem:

```json
{
  "message": "Hardware RAID is not supported by this server"
}
```

Przykładowa odpowiedź dla serwera z kontrolerem sprzętowego RAID:

```json
{
  "controllers": [
    {
      "type": "mega",
      "disks": [
        {
          "names": [
            "c0:d0",
            "c0:d1",
            "c0:d2"
          ],
          "type": "SSD",
          "capacity": {
            "unit": "GB",
            "value": 960
          },
          "speed": {
            "value": "6g",
            "unit": "GB/s"
          }
        }
      ],
      "model": "9361-8i-2G"
    }
  ]
}
```

:::info
Informację tę możesz również uzyskać, sprawdzając wartość atrybutu `raidController` w wywołaniu API opisanym w sekcji [Grupy dysków](#disk-group).

:::

#### API i sprzętowy RAID

:::warning
Obecnie API obsługuje personalizację sprzętowego RAID tylko dla 1 kontrolera sprzętowego RAID. Jeśli serwer ma kilka kontrolerów sprzętowego RAID, których konfigurację chcesz spersonalizować, możesz skonfigurować kontrolery inne niż ten, który obsługuje grupę dysków wybraną do reinstalacji systemu operacyjnego, **przed** reinstalacją systemu (możesz to również zrobić po zakończeniu reinstalacji, ale zalecamy zrobić to **wcześniej**, aby uniknąć ryzyka przypadkowej utraty danych).

:::

Przykład instalacji systemu operacyjnego ze sprzętowym RAID 1 między 2 pierwszymi dyskami grupy dysków:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "hardwareRaid": [
                {
                    "raidLevel": 1,
                    "disks": 2
                }
            ]
        }
    ]
}
```

:::info
Pominięcie wartości `disks` spowoduje skonfigurowanie sprzętowego RAID na **wszystkich** dyskach grupy dysków.

:::

Załóżmy teraz, że masz serwer dedykowany z 1 grupą dysków podłączoną do kontrolera RAID i 12 dyskami w tej grupie. Przykład ze sprzętowym RAID 10:

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "hardwareRaid": [
                {
                    "raidLevel": 10,
                    "arrays": 4
                }
            ]
        }
    ]
}
```

W tym przykładzie wszystkie 12 dysków zostanie objętych sprzętowym RAID poziomu 10. Powstaną 4 grupy po 3 dyski, czyli 4 macierze RAID 1 na 3 dyskach, a 4 grupy będą połączone w RAID 0.

:::info
Sprzętowy RAID działa na warstwie niewidocznej dla systemu operacyjnego. Wszystkie systemy operacyjne są "kompatybilne" ze sprzętowym RAID.

:::

Wszystkie dyski objęte konfiguracją sprzętowego RAID będą widoczne dla systemu operacyjnego jako 1 dysk wirtualny.

Oznacza to, że jeśli wszystkie dyski docelowej grupy dysków zostały objęte konfiguracją sprzętowego RAID, skonfigurowanie na nim programowego RAID nie jest możliwe, ponieważ system operacyjny będzie widział tylko jeden dysk wirtualny.

### Partycjonowanie <a name="partitioning"></a>

Schemat partycjonowania określa, w jaki sposób dane będą zorganizowane i widziane przez system operacyjny, czyli wszystko, co znajduje się powyżej dysków fizycznych (lub dysku wirtualnego, jeśli skonfigurowano sprzętowy RAID), aż po zamontowany system plików, od najniższej do najwyższej warstwy:

- dysk (dysk fizyczny/wirtualny, PD),
- partycja (partycja fizyczna, PP),
- ZFS: vdev (zgroup, ZG), zpool (ZP), zbiór danych ZFS (ZD), wolumin ZFS (ZV),
- [programowy RAID](/guides/bare-metal-cloud/dedicated-servers/raid-soft) (SR),
- LVM: wolumin fizyczny (PV), grupa woluminów (VG), wolumin logiczny (LV),
- system plików z punktem montowania (FS)

Poniższa tabela przedstawia przegląd różnych komponentów partycjonowania oraz sposób, w jaki te warstwy ze sobą współdziałają:

<img className="thumbnail" alt="Tabela warstw partycjonowania" src="/images/bare-metal-cloud/dedicated-servers/partitioning-ovh/partitioning-layers-table.png" loading="lazy" />

:::info
W powyższej tabeli `/dev/zd1` oznacza wolumin ZFS (zwany również `zvol`). Jest to dysk wirtualny działający na zbiorze danych ZFS (ZD) i zpoolu (ZP), który system operacyjny widzi jako zwykły dysk fizyczny (PD). Ta funkcja nie jest dostępna w API OVHcloud i nie planujemy jej wdrożenia.

:::

#### Kompatybilność systemu operacyjnego z partycjonowaniem <a name="os-partitioning-compatibility"></a>

Ponieważ konfiguracja partycjonowania będzie widoczna dla systemu operacyjnego, system wybrany do reinstalacji wpływa na możliwości personalizacji partycjonowania.

W sekcji <code className="action">/dedicated/installationTemplate</code> możesz wyświetlić szczegóły dotyczące przestrzeni dyskowej, takie jak kompatybilność z LVM i dostępne systemy plików dla danego systemu operacyjnego:

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}"} />

Przykład:

```json
{
    "templateName": "debian13_64",
    "filesystems": [
        "btrfs",
        "ext4",
        "swap",
        "xfs",
        "zfs"
    ],
    ...
    "lvmReady": true,
    "noPartitioning": false,
    "softRaidOnlyMirroring": false
}
```

|Atrybut|Opis|
|---|---|
|filesystems|Typy systemów plików kompatybilne z tym systemem operacyjnym|
|lvmReady|Określa, czy ten system operacyjny jest kompatybilny z LVM|
|noPartitioning|Jeśli ma wartość true, system operacyjny nie obsługuje niestandardowego partycjonowania|
|softRaidOnlyMirroring|Jeśli ma wartość true, system operacyjny obsługuje niestandardowe partycjonowanie tylko częściowo (można skonfigurować jedynie programowy RAID poziomu 0 i 1 i przypisać go do 2 pierwszych dysków grupy dysków)|

Poniższe wywołanie API pozwala wyświetlić listę nazw schematów partycjonowania poszczególnych systemów operacyjnych. Większość systemów operacyjnych obsługuje niestandardową konfigurację partycjonowania i dlatego ma tylko jeden schemat o nazwie `default`. Jedynie niektóre systemy, które nie obsługują niestandardowego partycjonowania (`noPartitioning` ustawione na `true`), **mogą** mieć kilka schematów.

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}/partitionScheme"} />

Poniższe wywołania API pozwalają sprawdzić, jakie partycjonowanie zostanie zastosowane domyślnie, jeśli nie zostanie spersonalizowane lub jeśli system operacyjny nie pozwala na jego personalizację.

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}/partitionScheme/\{schemeName\}/partition"} />

<br />

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}/partitionScheme/\{schemeName\}/partition/\{mountpoint\}"} />

#### Kompatybilność LVM, poziomów RAID i systemów plików <a name="lvm-raid-levels-filesystems-compatibility"></a>

Poniższa tabela przedstawia przegląd kompatybilności systemów plików z poziomami RAID oraz z LVM w środowisku OVHcloud:

|System plików|LVM|RAID 0|RAID 1|RAID 5|RAID 6|RAID 7|RAID 10|
|---|---|---|---|---|---|---|---|
|Btrfs, ext4, XFS|✅|✅|✅|✅|✅|❌|✅|
|ZFS¹|❌|✅|✅|✅|✅|✅|❌|
|swap|❌|⚠️²|❌|❌|❌|❌|❌|
|NTFS|❌|❌|✅³|❌|❌|❌|❌|
|UFS, VMFS5, VMFS6, VMFS-L⁴|❌|❌|❌|❌|❌|❌|❌|

¹ Więcej informacji znajdziesz w tabeli [vdev ZFS a standardowy RAID](#raidz2RAID).<br />
² Poziom RAID dla swap można w <ApiLink>API OVHcloud</ApiLink> ustawić wyłącznie na 1. W rzeczywistości partycje swap nie będą korzystać z RAID. Gdy na serwerze z `n` dyskami zostanie zdefiniowana partycja swap o rozmiarze `s`, na każdym dysku zostanie utworzonych `n` partycji o rozmiarze `s` bez żadnego urządzenia programowego RAID pod spodem.<br />
³ Natywny RAID systemu Windows (konfigurowany przez instalator OVHcloud) obsługuje RAID 1, ale tylko między dwoma dyskami, podczas gdy inne implementacje pozwalają na użycie więcej niż dwóch dysków.<br />
⁴ Instalator ESXi nie obsługuje niestandardowych schematów partycjonowania. Partycjonowanie jest definiowane przez wydawcę oprogramowania. <ApiLink>API OVHcloud</ApiLink> może jednak dać Ci wyobrażenie o tym, jak wygląda partycjonowanie: więcej informacji znajdziesz w sekcji [Kompatybilność systemu operacyjnego z partycjonowaniem](#os-partitioning-compatibility).<br />

:::warning
Ta tabela ma wyłącznie charakter informacyjny. Pamiętaj, że kompatybilność z LVM, a zwłaszcza z systemami plików, zależy również od instalowanego systemu operacyjnego (szablonu OVHcloud). Więcej informacji znajdziesz w sekcji [Kompatybilność systemu operacyjnego z partycjonowaniem](#os-partitioning-compatibility).

:::

#### vdev ZFS a standardowy RAID <a name="raidz2RAID"></a>

ZFS nie obsługuje standardowych poziomów RAID. Do opisu odporności na awarie w obrębie grupy urządzeń wykorzystuje urządzenia wirtualne (vdev). Więcej informacji o vdev znajdziesz w [oficjalnej dokumentacji OpenZFS](https://openzfs.github.io/openzfs-docs/man/7/zpoolconcepts.7.html).

Aby API OVHcloud było jak najprostsze, klienci muszą w API zdefiniować standardowy RAID dla systemów plików ZFS. Standardowy poziom RAID zostanie następnie przełożony na równoważną definicję vdev. Poniższa tabela przedstawia, jak przekładane są poszczególne poziomy RAID oferowane przez API OVHcloud, i przypomina ich charakterystykę.

|Standardowy RAID|Równoważny typ vdev|Minimalna liczba dysków danych|Liczba dysków parzystości|Łączna minimalna wymagana liczba dysków|
|---|---|---|---|---|
|RAID 0|striped vdev|1|0|1|
|RAID 1|mirror|2|0|2|
|RAID 5|raidz1|2|1|3|
|RAID 6|raidz2|3|2|5|
|RAID 7|raidz3|4|3|7|
|RAID 10|❌|4|0|4|

#### API i partycjonowanie

:::warning
Niestandardowy schemat partycjonowania, mimo że jest poprawny i akceptowany przez <ApiLink>API OVHcloud</ApiLink>, może uniemożliwić prawidłowe uruchomienie serwera (na przykład w przypadku nietypowego połączenia systemu plików i programu rozruchowego lub problemu ze złożeniem RAID/LVM/ZFS specyficznego dla Twojego schematu). W takiej sytuacji interwencja wsparcia nie zostanie automatycznie utworzona na serwerze: po ostatnim restarcie wyświetli się jednoznaczny komunikat dla klienta. Więcej informacji znajdziesz w sekcji [Częste błędy klientów](#errors).

:::

Przykład instalacji systemu operacyjnego z niestandardowym schematem partycjonowania:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "partitioning": {
                "disks": 2,
                "layout": [
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/boot",
                        "size": 1000,
                        "raidLevel": 0
                    },
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/",
                        "size": 0
                    }
                ]
            }
        }
    ]
}
```

Wartość `size` 0 oznacza, że partycja zajmie całą pozostałą przestrzeń na wykorzystywanych dyskach.

:::info
Tylko 1 partycja może zostać skonfigurowana tak, aby zajmowała pozostałą przestrzeń (rozmiar 0).

:::

<br />

:::info
Jeśli wartość `raidLevel` nie zostanie określona, zostanie ustawiona na 1.

:::

W tym przykładzie w partycjonowaniu (czyli w programowym RAID) uczestniczą tylko 2 pierwsze dyski grupy dysków.

:::info
Parametr `disks` można pominąć, jeśli chcesz objąć programowym RAID wszystkie dyski grupy dysków.

:::

Jak widać, schemat partycjonowania jest listą partycji. Oto przykład struktury partycji:

```json
{
    "mountPoint": "/var/lib/vz",
    "fileSystem": "ext4",
    "size": 0,
    "raidLevel": "1",
    "extras": {
        "lv": {
            "name": "data"
        }
    }
}
```

Podsekcja `extras` jest opcjonalna. Można jej użyć, aby określić, że partycja będzie woluminem logicznym (oraz nadać mu nazwę). Można jej także użyć dla ZFS:

```json
{
    "mountPoint": "/",
    "fileSystem": "zfs",
    "size": 0,
    "raidLevel": "5",
    "extras": {
        "zp": {
            "name": "poule"
        }
    }
}
```

W tym przykładzie punkt montowania `/` będzie wskazywał na zbiór danych ZFS w zpoolu o nazwie "poule" typu raidz1. Odpowiedniki raidz i standardowych poziomów RAID znajdziesz w tabeli [vdev ZFS a standardowy RAID](#raidz2RAID).

:::info
Jeśli nazwa zpoola nie zostanie określona, zostanie wygenerowana automatycznie. Domyślnie algorytm próbuje grupować różne zbiory danych w tym samym zpoolu, z wyjątkiem zbiorów danych zawierających `/` lub `/boot`, które są umieszczane w osobnych zpoolach. Dzięki temu na pozostałych zpoolach można włączyć zaawansowane funkcje ZFS niekompatybilne z programem rozruchowym.

:::

<br />

:::info
Niestandardowa nazwa zpoola pozwala:

- grupować zbiory danych o tych samych poziomach RAID: użyj tej samej nazwy zpoola,
- wymusić umieszczenie zbiorów danych o tych samych poziomach RAID w osobnych zpoolach: użyj różnych nazw zpooli.

:::

### Usuwanie danych <a name="data-erasure"></a>

Domyślnie podczas instalacji systemu operacyjnego czyszczone są dyski wszystkich grup dysków serwera, niezależnie od tego, czy ich grupa dysków została zadeklarowana w żądaniu `storage`. Ustawienie `erase` na `false` dla grupy dysków to jedyny sposób na zachowanie jej danych.

Grupy dysków inne niż ta, na której instalowany jest system operacyjny, również mogą zostać zadeklarowane, ale wyłącznie w celu określenia, czy ich dane mają zostać usunięte (`erase: true`), czy zachowane (`erase: false`).

System operacyjny jest instalowany na grupie dysków zawierającej atrybuty instalacji (`partitioning`, `hardwareRaid`). Pozostałe zadeklarowane grupy dysków zawierają tylko atrybut `erase`. Jeśli żadna z nich nie zawiera atrybutu instalacji, system operacyjny zostanie zainstalowany na domyślnej grupie dysków, zgodnie z opisem w sekcji [Grupy dysków](#disk-group).

Przykład dla serwera z 2 grupami dysków: prosta instalacja systemu operacyjnego na grupie `diskGroupId` 1 (niejawnie czyszczonej) oraz grupa `diskGroupId` 2 zadeklarowana wyłącznie w celu zachowania jej istniejących danych:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "diskGroupId": 1,
            "partitioning": {
                "schemeName": "default"
            }
        },
        {
            "diskGroupId": 2,
            "erase": false
        }
    ]
}
```

:::warning
W tablicy `storage` obowiązują następujące ograniczenia:

- Nie można ustawić `erase: false` dla grupy dysków, na której instalowany jest system operacyjny.
- Nie można zadeklarować tej samej wartości `diskGroupId` więcej niż raz.
- Nie można zadeklarować więcej niż jednej grupy dysków, na której ma zostać zainstalowany system operacyjny. Dla każdej dodatkowej grupy dysków można ustawić tylko atrybut `erase` — bez instalacji systemu operacyjnego, partycjonowania ani konfiguracji sprzętowego RAID.

:::

:::warning
Ustawienie `erase` na `false` zachowuje wszystkie dane na tej grupie dysków, ale OVHcloud nie może zagwarantować powodzenia instalacji systemu operacyjnego: pozostałości metadanych rozruchowych, superbloki `mdadm`, sygnatury LVM lub etykiety ZFS z poprzedniej instalacji na tej grupie dysków (tj. na dowolnym z jej dysków) mogą powodować konflikty z nową instalacją.

Jeśli instalacja nie powiedzie się z jednego z tych powodów, zgłoszenie do wsparcia nie zostanie utworzone automatycznie. Zamiast tego klientowi zostanie wyświetlony jednoznaczny komunikat podczas partycjonowania lub przy pierwszym uruchomieniu zainstalowanego systemu operacyjnego. Więcej informacji znajdziesz w sekcji [Częste błędy klientów](#errors).

:::

### Obsługa błędów

Podstawowe błędy w danych wejściowych klienta są obsługiwane bezpośrednio przez API OVHcloud. Jest to najczęstsza i najprostsza sytuacja, ponieważ klienci widzą błąd synchronicznie i mogą natychmiast ponowić próbę.

Dane wejściowe klienta dotyczące partycjonowania mogą być zbyt specyficzne, aby API OVHcloud mogło je sprawdzić, i dlatego wymagają czasu na wstępne przetworzenie. Wadą tego rozwiązania jest to, że klienci są powiadamiani później, w trakcie procesu reinstalacji systemu operacyjnego.

W <ManagerLink to="/#/dedicated-servers/server">konsoli OVHcloud</ManagerLink> jest to widoczne na pasku postępu.
W <ApiLink>API OVHcloud</ApiLink> status ten można uzyskać za pomocą następującego wywołania API:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/install/status"} />

Istnieją 2 rodzaje błędów:

- **błędy ovh**: klient nie jest odpowiedzialny za błąd; może przeprowadzić reinstalację z innym schematem partycjonowania, ale OVHcloud musi usunąć usterkę.
- **błędy klienta**: klient zażądał schematu partycjonowania, którego nie można zrealizować lub który uniemożliwiłby prawidłowe uruchomienie serwera.

W następnej sekcji skupimy się wyłącznie na **błędach klienta** związanych z partycjonowaniem, ponieważ tylko te informacje są przydatne dla klienta.

#### Automatyczna korekta danych wejściowych klienta

Aby poprawić komfort klientów, zmniejszyć obciążenie wsparcia OVHcloud i uniknąć wprowadzania zmian powodujących niezgodności dla klientów, niektóre dane wejściowe klienta są automatycznie korygowane lub zmieniane przez backend. Poniższa tabela przedstawia przegląd tego, co jest obecnie automatycznie korygowane/zmieniane:

|Temat|Opis|
|---|---|
|Grupowanie ZP|Wszystkie partycje ZFS o tym samym poziomie RAID zostaną zgrupowane w tym samym zpoolu (ZP), jeśli jest to możliwe w zależności od rozmiaru dysków i jeśli podano tę samą nazwę zpoola lub nie podano żadnej nazwy zpoola|
|Grupowanie LV|Wszystkie partycje typu `lv` o tym samym poziomie RAID zostaną zgrupowane w tej samej VG (jeśli jest to możliwe w zależności od rozmiaru dysków)|
|Rozszerzanie VG|W przypadku partycji LV z poziomem RAID 0 grupa VG obejmie kilka PP (a więc PD) i nie zostanie utworzone żadne urządzenie SR|
|Wypełnianie dysku przez VG|Pozostała przestrzeń dyskowa zostanie wypełniona przez VG (jeśli istnieje jakikolwiek LV). Nie ma to wpływu na rozmiar LV przypisanych do VG.|
|Obniżanie poziomu RAID|Jeśli klient wybierze partycję z poziomem RAID wymagającym większej liczby dysków, niż ma serwer, poziom RAID zostanie automatycznie obniżony w następującej kolejności: 6, 10, 5, 1, 0 (lub raidz3, raidz2, raidz, mirror, striped vdev w przypadku ZFS)|
|Zmniejszanie rozmiaru PP|Jeśli klient wybrał PP wymagającą więcej przestrzeni, niż ma serwer, rozmiar tej PP zostanie zmniejszony tak, aby zmieściła się na dysku. Pamiętaj, że jeśli kilka PP wymaga więcej przestrzeni, niż ma system, skrypt zadziała tylko na pierwszą partycję, a dla drugiej, zbyt dużej partycji zgłosi błąd na dalszym etapie. Pamiętaj również, że błąd zostanie zgłoszony, jeśli klient ustawił w API OVHcloud inną partycję tak, aby zajmowała cały dysk|
