## Objetivo

:::warning
Este artículo está dirigido a usuarios experimentados que tengan como mínimo conocimientos básicos de Linux y, sobre todo, conocimientos más avanzados sobre el almacenamiento, en particular sobre el RAID por software, el RAID por hardware y la gestión lógica de volúmenes (LVM).

:::


Los [servidores dedicados](/links/bare-metal/bare-metal) de OVHcloud le permiten configurar los discos, el [RAID por hardware](/guides/bare-metal-cloud/dedicated-servers/raid-hard), el [RAID por software](/guides/bare-metal-cloud/dedicated-servers/raid-soft), LVM, ZFS, etc. durante [la reinstalación](/guides/bare-metal-cloud/dedicated-servers/getting-started-with-dedicated-server) de su sistema operativo desde la <ApiLink>API de OVHcloud</ApiLink> o desde la <ManagerLink to="/">consola de OVHcloud</ManagerLink>. En este artículo nos centraremos en la <ApiLink>API de OVHcloud</ApiLink>.<br/>
Esto le ofrecerá más detalles sobre el motor que se ejecuta en segundo plano para crear la personalización del almacenamiento en el servidor dedicado a partir de los datos de entrada transmitidos a la API de OVHcloud.

Disponer de información detallada sobre la configuración del almacenamiento puede ayudarle a entender por qué:

- su personalización del almacenamiento no ha podido aplicarse en su servidor dedicado.
- la personalización del almacenamiento real en su servidor dedicado es ligeramente diferente de la que había solicitado.

## Requisitos

* Disponer de un [servidor dedicado](/links/bare-metal/bare-metal) **listo para instalarse/reinstalarse** en su cuenta de OVHcloud.
* Tener acceso a la <ApiLink>API de OVHcloud</ApiLink>.

:::warning
La reinstalación de un servidor dedicado elimina todos los datos almacenados en él.

:::


## Procedimiento

Durante la instalación del sistema operativo por defecto, el instalador del sistema operativo (proporcionado por el editor del software) solicita al usuario que especifique los discos en los que se instalará el sistema operativo, la configuración del particionamiento, etc. Una vez instalado el SO, es posible modificar la distribución del particionamiento, pero puede resultar muy delicado y arriesgado, especialmente en el caso de las particiones que el sistema está utilizando. Por este motivo, la configuración del almacenamiento es un aspecto muy importante que debe tenerse en cuenta **antes** de instalar un sistema operativo.

Además de la sencillez de la API, la principal ventaja es la posibilidad de personalizar por completo los discos y las particiones en los que se instalará el SO.

En esta página nos centraremos únicamente en el subhash `storage` de la llamada a la API utilizada para reinstalar un SO en un servidor dedicado. Para las personalizaciones de la reinstalación del SO no relacionadas con el almacenamiento, consulte la guía [API de OVHcloud e instalación de un SO](/guides/bare-metal-cloud/dedicated-servers/api-os-installation) para más información.

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "diskGroupId": 1,
            "erase": true
        },
        {
            "diskGroupId": 2,
            "erase": true,
            "hardwareRaid": [
                {
                    "raidLevel": null,
                    "disks": 2
                }
            ],
            "partitioning": {
                "disks": 2,
                "layout": [
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/boot",
                        "size": 1000,
                        "raidLevel": 1
                    },
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/",
                        "size": 0
                    }
                ]
            }
        }
    ]
}
```

### Grupos de discos <a name="disk-group"></a>

Algunos [servidores dedicados](/links/bare-metal/bare-metal) tienen varios grupos de discos. Por ejemplo, un grupo con discos SATA y otro grupo con discos SSD. Este tipo de servidores se denominan **servidores híbridos**.

Para listar los grupos y sus discos, puede utilizar la siguiente llamada a fin de determinar el grupo de discos en el que desea realizar la reinstalación del SO:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/specifications/hardware"} />

Ejemplo de respuesta:

```json
{
    "bootMode": "uefi",
    "coresPerProcessor": 64,
    "defaultDiskGroupId": 1,
    "defaultHardwareRaidSize": null,
    "defaultHardwareRaidType": null,
    "description": "SCALE-7 - AMD Epyc 7763",
    "diskGroups": [
        {
            "defaultHardwareRaidSize": null,
            "defaultHardwareRaidType": null,
            "description": "2 X Disk SSD 480 GB, JBOD",
            "diskGroupId": 1,
            "diskSize": {
                "unit": "GB",
                "value": 480
            },
            "diskType": "SSD",
            "numberOfDisks": 2,
            "raidController": null
        },
        {
            "defaultHardwareRaidSize": null,
            "defaultHardwareRaidType": null,
            "description": "2 X Disk NVME 1920 GB, JBOD",
            "diskGroupId": 2,
            "diskSize": {
                "unit": "GB",
                "value": 1920
            },
            "diskType": "NVME",
            "numberOfDisks": 2,
            "raidController": null
        }
    ],
    "expansionCards": null,
    "formFactor": "1u",
    "memorySize": {
        "unit": "MB",
        "value": 524288
    },
    "motherboard": "S8036-M",
    "numberOfProcessors": 1,
    "processorArchitecture": "x86_64",
    "processorName": "Epyc7763",
    "threadsPerProcessor": 128,
    "usbKeys": null
}
```

En este ejemplo, hay 2 grupos de discos:

- el primero (diskGroupId=1) contiene 2 discos de 480 GB cada uno. Es el diskGroupId por defecto.
- el segundo (diskGroupId=2) contiene 2 discos de 1,9 TB cada uno.

Ejemplo de instalación de Debian 13 (Trixie) en el diskGroupId 2:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "diskGroupId": 2
        }
    ]
}
```

:::info
Por defecto, si no se especifica ningún diskGroupId o si se establece en 0, el sistema operativo se instala en el diskGroupId 1 por defecto.

:::


<br />

:::warning
Por el momento, la API solo admite la instalación del SO y la personalización del almacenamiento en 1 único grupo de discos. Puede incluir desde 1 hasta todos los discos del grupo elegido en la personalización del almacenamiento. Sin embargo, los discos restantes de ese grupo se borrarán. Los discos que pertenecen a los demás grupos también se borran por defecto, pero sus datos pueden conservarse: consulte la sección [Borrado de los datos](#data-erasure). En cualquier caso, estos discos seguirán siendo visibles para el SO instalado y podrán utilizarse/configurarse posteriormente para almacenar datos.

:::


### RAID por hardware <a name="hard-raid"></a>

Esta sección solo se aplica a los servidores que tienen al menos un controlador RAID por hardware en uno de sus [grupos de discos](#disk-group).

#### Servidor y compatibilidad del RAID por hardware

Puede utilizar la siguiente llamada a la API para saber si su servidor dedicado es compatible:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/install/hardwareRaidProfile"} />

Si su servidor dedicado no tiene controlador RAID por hardware, la llamada devuelve un error HTTP 403 (Forbidden) con el siguiente mensaje:

```json
{
  "message": "Hardware RAID is not supported by this server"
}
```

Ejemplo de respuesta para un servidor que tiene RAID por hardware:

```json
{
  "controllers": [
    {
      "type": "mega",
      "disks": [
        {
          "names": [
            "c0:d0",
            "c0:d1",
            "c0:d2"
          ],
          "type": "SSD",
          "capacity": {
            "unit": "GB",
            "value": 960
          },
          "speed": {
            "value": "6g",
            "unit": "GB/s"
          }
        }
      ],
      "model": "9361-8i-2G"
    }
  ]
}
```

:::info
También puede obtener esta información a partir del valor del atributo `raidController` de la llamada a la API descrita en la sección [Grupos de discos](#disk-group).

:::


#### API y RAID por hardware

:::warning
Por el momento, la API solo admite la personalización del RAID por hardware para 1 único controlador RAID por hardware. Si su servidor tiene varios controladores RAID por hardware cuya configuración desea personalizar, puede configurar los controladores distintos del que corresponde al grupo de discos elegido para la reinstalación del SO **antes** de la reinstalación del SO (también puede hacerlo una vez finalizada la reinstalación del SO, pero le recomendamos hacerlo **antes** para evitar cualquier riesgo de error de manipulación que pudiera provocar una pérdida de datos).

:::


Ejemplo de una instalación del SO con un RAID 1 por hardware entre los 2 primeros discos del grupo de discos:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "hardwareRaid": [
                {
                    "raidLevel": 1,
                    "disks": 2
                }
            ]
        }
    ]
}
```

:::info
Si no se especifica `disks`, **todos** los discos del grupo de discos formarán parte del RAID por hardware.

:::


Supongamos ahora que tiene un servidor dedicado con 1 grupo de discos conectado al controlador RAID por hardware y 12 discos en ese grupo. Ejemplo con un RAID 10 por hardware:

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "hardwareRaid": [
                {
                    "raidLevel": 10,
                    "arrays": 4
                }
            ]
        }
    ]
}
```

En este ejemplo, los 12 discos formarán parte del RAID por hardware de nivel 10. Habrá 4 grupos de 3 discos, lo que significa 4 RAID 1 entre 3 discos, y los 4 grupos estarán en RAID 0.

:::info
El RAID por hardware se encuentra en una capa que no es visible para el SO. Por lo tanto, todos los SO son "compatibles" con el RAID por hardware.

:::


Todos los discos que formen parte de la configuración del RAID por hardware serán vistos por el SO como 1 único disco virtual.

Por lo tanto, si ha incluido todos los discos del grupo de discos de destino en una configuración de RAID por hardware, no será posible configurar un RAID por software encima, ya que el SO solo ve 1 único disco virtual.

### Particionamiento <a name="partitioning"></a>

Cuando hablamos de esquema de particionamiento, nos referimos a la organización de sus datos en los discos, es decir, a todo lo que se encuentra sobre su disco físico (o disco virtual, si ha configurado un RAID por hardware), hasta el sistema de archivos montado y visible en el SO, de las capas más bajas a las más altas:

- Disco (disco físico/virtual, PD)
- Partición (partición física, PP)
- ZFS: vdev (zgroup, ZG), zpool (ZP), dataset ZFS (ZD), volumen ZFS (ZV)
- [RAID por software](/guides/bare-metal-cloud/dedicated-servers/raid-soft) (SR)
- LVM: volumen físico (VP), grupo de volúmenes (VG), volumen lógico (LV)
- Sistema de archivos con punto de montaje (FS)

La siguiente tabla ofrece una visión general de los diferentes componentes del particionamiento y de la forma en que interactúan estas capas:

<img className="thumbnail" alt="Tabla que representa las diferentes capas del particionamiento" src="/images/bare-metal-cloud/dedicated-servers/partitioning-ovh/partitioning-layers-table.png" loading="lazy" />

:::info
En la tabla anterior, `/dev/zd1` representa un volumen ZFS (también llamado `zvol`). Se trata de un disco virtual situado por encima de un conjunto de datos ZFS (ZD) y de un zpool (ZP), que el sistema operativo considera un disco físico normal (PD). Esta funcionalidad no está disponible en la API de OVHcloud y no tenemos previsto implementarla.

:::


#### SO y compatibilidad del particionamiento <a name="os-partitioning-compatibility"></a>

Como la configuración del particionamiento será visible para el SO, el SO elegido para la reinstalación influye en las posibilidades de personalización del particionamiento.

En la sección <code className="action">/dedicated/installationTemplate</code>, puede obtener detalles como la compatibilidad con LVM o la disponibilidad de los sistemas de archivos para un SO concreto:

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}"} />

Por ejemplo:

```json
{
    "templateName": "debian13_64",
    "filesystems": [
        "btrfs",
        "ext4",
        "swap",
        "xfs",
        "zfs"
    ],
    ...
    "lvmReady": true,
    "noPartitioning": false,
    "softRaidOnlyMirroring": false
}
```

|Atributo|Descripción|
|---|---|
|filesystems|Sistemas de archivos compatibles con este sistema operativo|
|lvmReady|Indica si este sistema operativo es compatible con LVM o no|
|noPartitioning|Si es verdadero, este sistema operativo no admite la personalización del particionamiento|
|softRaidOnlyMirroring|Si es verdadero, este sistema operativo solo admite parcialmente la personalización del particionamiento (solo pueden configurarse los RAID por software de niveles 0 y 1 y asignarse a los 2 primeros discos del grupo de discos)|

La siguiente llamada a la API puede utilizarse para listar los diferentes esquemas de particionamiento de un sistema operativo concreto. La mayoría de los sistemas operativos admiten la personalización del particionamiento y, por lo tanto, tienen un único esquema llamado "default". Solo algunos de ellos no admiten la personalización del particionamiento (`noPartitioning` vale `true`) y, por lo tanto, **pueden** tener varios esquemas de particionamiento.

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}/partitionScheme"} />

Las siguientes llamadas a la API pueden utilizarse para saber qué particionamiento se aplicará por defecto si no se especifica ninguna personalización del particionamiento o si el SO no la admite.

<Api version="v1" section="/dedicated/installationTemplate" method="GET" route={"/dedicated/installationTemplate/\{templateName\}/partitionScheme/\{schemeName\}/partition"} />

#### LVM, niveles de RAID y compatibilidad de los sistemas de archivos <a name="lvm-raid-levels-filesystems-compatibility"></a>

La siguiente tabla ofrece una visión general de la compatibilidad de los sistemas de archivos con los niveles de RAID y LVM en el contexto de OVHcloud:

|Sistema de archivos|LVM|RAID 0|RAID 1|RAID 5|RAID 6|RAID 7|RAID 10|
|---|---|---|---|---|---|---|---|
|Btrfs, ext4, XFS|✅|✅|✅|✅|✅|❌|✅|
|ZFS¹|❌|✅|✅|✅|✅|✅|❌|
|swap|❌|⚠️²|❌|❌|❌|❌|❌|
|NTFS|❌|❌|✅³|❌|❌|❌|❌|
|UFS, VMFS5, VMFS6, VMFS-L⁴|❌|❌|❌|❌|❌|❌|❌|

¹ Para más información, consulte la tabla [Vdevs ZFS frente a RAID estándar](#raidz2RAID).<br />
² El nivel de RAID para swap solo puede ser igual a 1 en la <ApiLink>API de OVHcloud</ApiLink>. En realidad, las particiones swap no utilizarán RAID. Cuando se define una partición swap de tamaño `s` en un servidor con un número `n` de discos, se crearán `n` particiones de tamaño `s` en cada disco sin ningún dispositivo RAID por software debajo.<br />
³ El RAID nativo de Windows (el configurado por el instalador de OVHcloud) admite RAID 1, pero solo entre dos discos, mientras que otras implementaciones permiten más de dos.<br />
⁴ El instalador de ESXi no admite esquemas de particionamiento personalizados. El particionamiento lo define el editor del software. No obstante, la <ApiLink>API de OVHcloud</ApiLink> puede darle una idea del aspecto del particionamiento: para más información, consulte [SO y compatibilidad del particionamiento](#os-partitioning-compatibility).<br />

:::warning
Esta tabla se ofrece únicamente a título informativo. Tenga en cuenta que la compatibilidad con LVM y, sobre todo, con los sistemas de archivos también depende del SO (plantilla de OVHcloud) instalado. Consulte la sección [SO y compatibilidad del particionamiento](#os-partitioning-compatibility) para más información.

#### Vdevs ZFS frente a RAID estándar <a name="raidz2RAID"></a>

ZFS no admite los niveles de RAID estándar. Utiliza dispositivos virtuales (vdevs) para describir la tolerancia a fallos dentro de un grupo de dispositivos. Consulte la [documentación oficial de OpenZFS](https://openzfs.github.io/openzfs-docs/man/7/zpoolconcepts.7.html) (en inglés) para más información sobre los vdevs.

Para que la API de OVHcloud sea lo más sencilla posible, es necesario que defina un RAID estándar en la API para los sistemas de archivos ZFS. El nivel de RAID estándar se traducirá entonces en una definición de vdev equivalente. La siguiente tabla ilustra la traducción de los diferentes niveles de RAID que ofrece la API de OVHcloud, así como un recordatorio de sus respectivas características.

|RAID estándar|Tipo de vdev equivalente|Número mínimo de discos de datos|Número de discos de paridad|Número mínimo total de discos necesarios|
|---|---|---|---|---|
|RAID 0|striped vdev|1|0|1|
|RAID 1|mirror|2|0|2|
|RAID 5|raidz1|2|1|3|
|RAID 6|raidz2|3|2|5|
|RAID 7|raidz3|4|3|7|
|RAID 10|❌|4|0|4|

#### API y particionamiento

:::warning
Un particionamiento personalizado, aunque sea válido y la <ApiLink>API de OVHcloud</ApiLink> lo acepte, puede impedir que el servidor arranque correctamente (por ejemplo, una combinación poco habitual de sistema de archivos y gestor de arranque, o un problema de ensamblaje RAID/LVM/ZFS propio de su configuración). En ese caso, no se creará automáticamente ninguna intervención del soporte en el servidor: se mostrará al cliente un mensaje explícito tras el último reinicio. Consulte la sección [Errores frecuentes de los clientes](#errors) para más información.

:::

Ejemplo de instalación del SO con un particionamiento personalizado:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "partitioning": {
                "disks": 2,
                "layout": [
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/boot",
                        "size": 1000,
                        "raidLevel": 0
                    },
                    {
                        "fileSystem": "ext4",
                        "mountPoint": "/",
                        "size": 0
                    }
                ]
            }
        }
    ]
}
```

`size` 0 significa que la partición ocupará todo el espacio restante en los discos afectados.

:::info
Como máximo, 1 partición puede configurarse para ocupar el espacio restante (tamaño 0).

:::


<br />

:::info
Si no se especifica, `raidLevel` tendrá el valor 1.

:::


En este ejemplo, solo los 2 primeros discos del grupo forman parte del particionamiento (es decir, del RAID por software).

:::info
El parámetro `disks` puede omitirse si desea incluir todos los discos del grupo de discos en el RAID por software.

:::


Como puede ver, un esquema de particionamiento es una lista de particiones. Este es un ejemplo de estructura de una partición:

```json
{
    "mountPoint": "/var/lib/vz",
    "fileSystem": "ext4",
    "size": 0,
    "raidLevel": "1",
    "extras": {
        "lv": {
            "name": "data"
        }
    }
}
```

El subhash `extras` es opcional. Por el momento, puede utilizarse para especificar que la partición será un volumen lógico (LVM) e indicar el nombre de ese volumen lógico. El subhash también puede utilizarse para ZFS:

```json
{
    "mountPoint": "/",
    "fileSystem": "zfs",
    "size": 0,
    "raidLevel": "5",
    "extras": {
        "zp": {
            "name": "poule"
        }
    }
}
```

En este ejemplo, el punto de montaje `/` corresponde a un dataset ZFS en un zpool llamado "poule" de tipo raidz1. Consulte la tabla [Vdevs ZFS frente a RAID estándar](#raidz2RAID) para obtener la correspondencia entre los raidz y los niveles de RAID estándar.

:::info
Si no se especifica ningún nombre de zpool, este se generará automáticamente. Por defecto, el algoritmo intenta agrupar los diferentes datasets en un mismo zpool, excepto los datasets que contienen `/` o `/boot`, que se colocan en zpools separados. Esto permite activar en los demás zpools funcionalidades avanzadas de ZFS incompatibles con el gestor de arranque.

:::


<br />

:::info
Utilizar un nombre de zpool personalizado puede resultar útil en los siguientes casos:

- agrupar datasets con los mismos niveles de RAID: utilice el mismo nombre de zpool,
- forzar que datasets con los mismos niveles de RAID estén en zpools distintos: utilice nombres diferentes.

:::

### Borrado de los datos <a name="data-erasure"></a>

Por defecto, los discos de todos los grupos de discos del servidor se borran durante la instalación del SO, tanto si su grupo se declara en la petición `storage` como si no. Establecer `erase` en `false` en un grupo de discos es la única forma de conservar sus datos.

Los grupos de discos distintos de aquel en el que se instala el SO también pueden declararse, pero únicamente para controlar si sus datos se borran (`erase: true`) o se conservan (`erase: false`).

El SO se instala en el grupo de discos que contiene los atributos de instalación (`partitioning`, `hardwareRaid`); los demás grupos declarados solo contienen el atributo `erase`. Si ninguno de ellos contiene un atributo de instalación, el SO se instala en el grupo de discos por defecto, tal y como se describe en la sección [Grupos de discos](#disk-group).

Ejemplo con un servidor que dispone de 2 grupos de discos: una instalación simple del SO en el `diskGroupId` 1 (cuyos discos se borran implícitamente) y el `diskGroupId` 2 declarado únicamente para conservar sus datos existentes:

<Api version="v1" section="/dedicated/server" method="POST" route={"/dedicated/server/\{serviceName\}/reinstall"} />

```json
{
    "operatingSystem": "debian13_64",
    "storage": [
        {
            "diskGroupId": 1,
            "partitioning": {
                "schemeName": "default"
            }
        },
        {
            "diskGroupId": 2,
            "erase": false
        }
    ]
}
```

:::warning
Se aplican las siguientes restricciones a la lista `storage`:

- No puede establecer `erase: false` para el grupo de discos en el que se instala el SO.
- No puede declarar varias veces el mismo `diskGroupId`.
- No puede declarar más de un grupo de discos en el que instalar el SO. Para cualquier grupo de discos adicional, solo puede definirse el atributo `erase`, sin instalación del SO, particionamiento ni configuración de RAID por hardware.

:::

:::warning
Establecer `erase` en `false` conserva todos los datos de ese grupo de discos, pero OVHcloud no puede garantizar que la instalación del SO se realice correctamente: metadatos de arranque residuales, superbloques `mdadm`, firmas LVM o etiquetas ZFS procedentes de una instalación anterior en ese grupo de discos (en cualquiera de sus discos) pueden entrar en conflicto con la nueva instalación.

Si la instalación falla por uno de estos motivos, no se crea automáticamente ningún ticket de soporte. En su lugar, se muestra al cliente un mensaje explícito, ya sea durante el particionamiento o en el primer arranque del SO instalado. Consulte la sección [Errores frecuentes de los clientes](#errors) para más información.

:::

### Gestión de los errores

Los errores básicos en los datos de entrada del cliente los gestiona directamente la API de OVHcloud. Se trata de la situación más habitual y más sencilla, ya que los clientes pueden ver el error de forma síncrona y volver a intentarlo inmediatamente.

Los datos de entrada del cliente relacionados con el particionamiento pueden ser demasiado específicos para que la API de OVHcloud los verifique y, por lo tanto, requerir un tiempo de procesamiento. El inconveniente es que los clientes reciben la notificación más tarde, durante el proceso de reinstalación del sistema operativo.

Este estado puede consultarse en la barra de progreso de <ManagerLink to="/#/dedicated-servers/server">la consola de OVHcloud</ManagerLink>.
Desde la <ApiLink>API de OVHcloud</ApiLink>, este estado puede obtenerse con la siguiente llamada a la API:

<Api version="v1" section="/dedicated/server" method="GET" route={"/dedicated/server/\{serviceName\}/install/status"} />

Existen 2 tipos de errores:

- **errores ovh**: usted no es responsable del error; puede reinstalar con otra distribución del particionamiento, pero OVHcloud deberá corregir el fallo.
- **errores de cliente**: ha solicitado un esquema de particionamiento que no puede realizarse o que impediría que el servidor arrancara correctamente.

En la siguiente sección, nos centraremos únicamente en los tipos de **errores de cliente** en la etapa del particionamiento, ya que solo son útiles para los clientes.

#### Errores frecuentes de los clientes <a name="errors"></a>

La siguiente tabla ofrece una visión general de los errores de cliente más conocidos y de la forma de corregirlos.

|---|---|---|

No lo permitimos para evitar crear particiones `swap` innecesariamente grandes.|- Defina un tamaño fijo para la partición `swap`.|
|`message`. Please adjust partitions so that the `p` partition fits on `n` disk(s)|Ha elegido una partición con un RAID que requiere un número de discos que su servidor puede proporcionar, pero algunos discos ya están llenos debido a otras particiones y/o a esta partición.|- Si no lo ha hecho ya en otra partición, defina el tamaño de la partición para que ocupe el disco (o partición de tamaño cero si se define a través de la <ApiLink>API de OVHcloud</ApiLink>).<br />- Reduzca el tamaño de esta partición para que quepa en los discos.<br />- Reduzca el tamaño de las demás particiones para que esta partición quepa en los discos.|

#### Autocorrección de los datos de entrada del cliente

Con el fin de mejorar la experiencia del cliente, reducir la carga de trabajo del soporte de OVHcloud y evitar cambios bruscos que pudieran afectar al cliente, algunos datos introducidos por el cliente se corrigen o modifican automáticamente en el backend. La siguiente tabla ofrece una visión general de lo que actualmente se autocorrige o modifica:

|Asunto|Descripción|
|---|---|
|Agrupación ZP|Todas las particiones ZFS del mismo nivel de RAID se agruparán en un mismo zpool (ZP), si es posible en función del tamaño de los discos y si no se especifica ningún nombre de zpool o se especifica el mismo nombre de zpool para todas esas particiones.|
|Agrupación LV|Todas las particiones de tipo `lv` con el mismo nivel de RAID se agruparán en un mismo VG (si es posible en función del tamaño de los discos).|
|Expansión VG|En el caso de particiones lv de nivel de RAID 0, el VG se extenderá por varios PP (y, por lo tanto, PD) y no se creará ningún dispositivo SR.|
|VG Relleno de disco|El espacio en disco restante lo ocupará un VG (si existe un LV). El tamaño de los LV contenidos en ese VG no se ve afectado.|
|Reducción del nivel de RAID|Si elige una partición con un nivel de RAID que requiere más discos de los que tiene el servidor, el nivel de RAID se reducirá automáticamente en el siguiente orden: 6, 10, 5, 1, 0 (o raidz3, raidz2, raidz, mirror, striped vdev para ZFS).|
|Reducción del tamaño del PP|Si ha elegido un PP que requiere más espacio del que tiene el servidor, el tamaño de ese PP se reducirá para que quepa en el disco. Tenga en cuenta que, si varios PP requieren más espacio del que dispone el sistema, el script solo actuará sobre la primera partición y devolverá un error más adelante en el script para la segunda partición sobredimensionada. Tenga en cuenta también que se generará un error si ha configurado otra partición para que ocupe el disco a través de la API de OVHcloud.|
