# Public Cloud Network Services - FAQ

**Here are the most frequently asked questions about Public Cloud Network Services.**

:::tip

Click each question to expand the answer.

:::

 

## Load Balancer

<details>
<summary>The Load Balancer offer is priced according to the bandwidth capacity. How can this be set/changed?</summary>

Load Balancer is offered in different sizes (S/M/L/XL) to best fit our customers' needs. These different sizes are defined via flavors. As of today, to change the size of your Load Balancer, you will need to spawn a new one, configure it the same way (with the same backends as the old one), and reconnect the Floating IP to the new one. Then the old Load Balancer can be deleted.

</details>

<details>
<summary>Can I use my Load Balancer with bare metal servers as backends? Can I use my Load Balancer with backends in different Public Cloud regions?</summary>

Yes, provided you configure the network connectivity between the Load Balancer and your bare metal server (either through the private network (vRack) or through a public IP). If your network is configured correctly, a Load Balancer can redirect traffic to members in different Public Cloud regions.

</details>

<details>
<summary>Can I connect my Load Balancer to my Managed Kubernetes Service (MKS)?</summary>

Octavia Load Balancer is not currently supported with MKS. This is currently on the roadmap.

</details>

<details>
<summary>I want to monitor Octavia Load Balancer. Is it possible to enable metrics automatically on the Load Balancer?</summary>

Yes, this feature has been available since we rolled out the Zed version in June 2023. You can find [more information here](https://support.us.ovhcloud.com/hc/en-us/articles/26358387002515).

</details>

<details>
<summary>How is the redundancy implemented for each type of service plan? Are the Amphoras configured in an ACT/STBY mode?</summary>

Yes, we offer Active/Standby mode for all plans S/M/L/XL.

</details>

<details>
<summary>Can the Load Balancer be used with Additional IPs (IP Failover)?</summary>

No. A new type of IP has been introduced for this purpose, Floating IP. It's more flexible and works on a pay-as-you-go model for automation purposes. With Floating IP, you can use a single Floating IP per Load Balancer service.

</details>

<details>
<summary>Can I use multiple protocols (UDP, TCP, HTTP) on one Load Balancer?</summary>

Yes, multiple listeners (frontends) and backends can be configured. There is a limitation of using a single Floating IP per Load Balancer.

</details>

<details>
<summary>What happens if our Octavia Load Balancer receives more requests than indicated? Will the price increase? Will I be notified?</summary>

First of all, the values shown are only a rough estimate of the Load Balancer's capabilities. The price will not increase. Pricing is linked to the flavors (S/M/L/XL), and we cannot change the flavor at this time. This is up to the customers' orchestration services.

It is up to the customer to monitor the load balancer using the metrics feature and to change the flavor accordingly.

</details>

<details>
<summary>In a Public to Public architecture, which component should be sized for the outbound traffic?</summary>

In a Public to Public architecture, the outbound traffic is managed by the Gateway component. If you use that architecture, you should size the Gateway accordingly.

</details>

 

## Gateway

<details>
<summary>What is Gateway? How does it fit into the OpenStack ecosystem?</summary>

Gateway is the product name for the Distributed Virtual Router (DvR) component in OpenStack. It is offered with High Availability and a Service Level Agreement.

</details>

<details>
<summary>The Gateway solution is priced according to the bandwidth capacity. How can this be set/changed?</summary>

Gateway is offered in different sizes (S/M/L) to best fit our customers' needs. These different sizes are defined via QoS policies. As of today, to change the size of Gateway, a change of QoS policy between S/M/L can be done.

</details>

<details>
<summary>Can the Gateway be used with instances of Load Balancer in other regions?</summary>

No, a Gateway can only be used in one region.

If you have a private network that spreads over multiple regions (thanks to the same VLAN ID), you need to spawn a Gateway in each region.

For example, the following architecture can be used:

| Region     | Private Network VLAN ID | Subnet CIDR | DHCP | Gateway IP | Subnet DHCP Allocation Pool |
| ---------- | ----------------------- | ----------- | ---- | ---------- | --------------------------- |
| US-EAST-VA | 42                      | 10.0.0.0/8  | true | 10.0.0.1   | 10.0.0.2-10.0.0.254         |
| US-WEST-OR | 42                      | 10.0.0.0/8  | true | 10.0.1.1   | 10.0.1.2-10.0.1.254         |

</details>

<details>
<summary>Can the L3 virtual router (Gateway) help me if I would like to have a gateway to access the Internet for all my VMs in my vRack?</summary>

Yes, that's exactly the use case for Gateway (L3 router with SNAT option). Currently, only instances in **private mode** of networking that are connected to a single-region private network are supported. For more information, please refer to our [Concepts - Public Cloud Networking](https://support.us.ovhcloud.com/hc/en-us/articles/19580166719763) guide.

</details>

<details>
<summary>Can I use an L3 router to route traffic between different subnets inside a Public Cloud region?</summary>

Yes, you can use an L3 router without the SNAT option through the OpenStack GUI / CLI / Terraform. In that case, the bandwidth limits are driven by the quality of service on the instance's private bandwidth. Hence, choosing an `S` flavor would not impact the performance.

</details>

<details>
<summary>Can I use an L3 router to route traffic between different subnets in multiple Public Cloud regions?</summary>

No, inter-region routing is not supported.

</details>

<details>
<summary>Will a Gateway be provided with a public IP and port?</summary>

It depends on the usage:

- For outbound use cases, we offer a public IP, which is included in the Gateway price. This IP is associated with the instantiated Gateway and **cannot be moved from one gateway to another**. In other words, the IP used for outbound traffic is not a 'Floating IP'. The only use case where this IP is kept is when the gateway size is changed (e.g., from `S` to `M`). If this is creating friction for your use case, please upvote for this [roadmap item](https://github.com/ovh/public-cloud-roadmap/issues/448).
- For inbound use cases (to expose a service running on a private instance to the Internet), you need to have a Floating IP to attach via Gateway to your instance or network service.

</details>

<details>
<summary>How can I spawn a private instance to be used with Gateway and SNAT options?</summary>

You can create a private network in a selected region and attach a Gateway to it. Then, while creating an instance, select "Attach to private network" and confirm it using the button "Yes, I want my instance to be fully private".

</details>

<details>
<summary>Is the Gateway outbound public IP protected against DDoS attacks?</summary>

Yes, the [OHVcloud Anti-DDoS infrastructure](https://us.ovhcloud.com/security/anti-ddos/) is activated on all those IPs. You can view that information in the `Bare Metal Cloud > Network > IP` section of the Control Panel.

</details>

<details>
<summary>I created an instance in private mode (it only has private ports). How can I connect to it?</summary>

Two options can be used:

- Using a "jump host" (SSH proxy): You need to use another instance that has a Floating IP (allowing for external access) and a private port in the same private network that your new instance is in. Log on to it and connect via SSH to the private IP of your new instance.
- Attaching a Floating IP address (at least for the time of maintenance) to your newly created instance and connecting to it using that Floating IP.

</details>

<details>
<summary>What happens if I associate a Gateway with a private network where instances are currently in public mode?</summary>

In this scenario, associating a Gateway with the private network will make those instances unreachable via their public IP. Before proceeding, review and adjust your instance network settings to ensure they will remain accessible.

</details>

 

## Floating IPs

<details>
<summary>When I try to associate the Floating IP to the port on the Ext-Net network, I get the following error: "External network ... is not reachable from subnet .... Therefore, cannot associate Port ... with a Floating IP."</summary>

A Floating IP is a flexible public IP address that can be associated with a private port only (port on a private network in vRack). You will also need a Gateway for it to work.

</details>

<details>
<summary>I have VMs communicating in a private network, and I want to associate a Floating IP with one of these VMs. What is the pool to choose for the Floating IP?</summary>

The pool for a Floating IP must be "Ext-Net", and you can associate it with a port on the private network.

</details>

<details>
<summary>Are the Floating IPs protected against DDoS attacks?</summary>

Yes, the [OHVcloud Anti-DDoS infrastructure](https://us.ovhcloud.com/security/anti-ddos/) is activated on all the Floating IPs. You can view that information in the `Bare Metal Cloud > Network > IP` section of the Control Panel.

</details>
